## 2. Findings that matter for CR-010

**F1 — N0's tau is ambiguous in the repository.** DECISIONS freezes "tau 0.1", but the dev run that produced the reported dev number (`dev1/FINAL.json`, exact micro F1 0.505, 0 items pruned) recorded `tau 0.0` (the CLI did not pass the flag); the test run (`test1/TEST_V4.json`, 0.501, 96 pruned) used `tau 0.1`. A replay at tau 0.1 on the live baseline gave 0.510 (vs 0.507). P&D production runs (`slice3_c1/c2`) used tau 0, and `c2` also used **strict G-links**, which the IIR runs never had (the flag did not exist). So "the final selected CR-009 pipeline" has three real variants.
**Proposed resolution (implementation only, needs owner OK):** define **N0 = G1, depth 1, M4/M5 off, P1 pruner tau 0.1, no strict G-links** (the configuration DECISIONS froze and the test split actually ran); re-run N0 on dev once live (about $0.07) so dev and test baselines are the same configuration; reuse the frozen test run unchanged. `configs/concept_gvp.yaml` still holds the CR-009 *draft* (form G2, iterations 3, tau null): I propose to update it to the frozen values as the first commit on this branch, so N0 is read from config and not reconstructed.

**F2 — Node gold exists only for IIR.** Exact micro F1 needs FACE gold, which exists for IIR dev (13 sections) and IIR test (70 sections) only; P&D has no concept gold. Node arms are therefore measured on IIR; on P&D only counts and an owner sample are possible.

**F3 — The IIR test split was already used once for CR-009 final reporting.** It stays held-out for CR-010 only if the N-arms are tuned on dev alone and evaluated on test once (the CR's rule); I will note this explicitly in the report.

**F4 — The package mapping table lists relations that are not active** (`identifies`, `encapsulates`, `trades_off_with`, `instantiates`, `equivalent_to`, `conflated_with`). It stays a hypothesis aid (NOT GOLD); REL-MAP-180 will be drawn only from the 17 active relations.

**F5 — REL-MAP-180 is feasible from the CR-009 run `slice3_c2`** (current architecture = registry v1.3, relation prompts family v3 / choice v4 / qualifiers v4): 529 accepted selected edges (120 needed), 260 `no_relation` (30 needed), 214 `other` + 99 rejected (30 needed) across 24 evidence sections, so a section-grouped 60 / 120 split is possible.

## 3. Items that need a Research decision (they are not implementation choices)

1. **Pair-recall denominator.** The CR defines recall over "validated true edges", but no validated edge set exists beyond the owner-marked samples. Alternatives: (a) union of REL-MAP-180 accepted edges and owner-validated edges from P0–P3 pools; (b) a stratified random sample of the 8,604 candidate pairs classified and owner-validated (cost: owner time, about 60–100 extra items); (c) the CR-007 style estimate from classified unselected samples. Consequence: the denominator choice changes the pair-recall figure and the owner burden.
2. **Scope of the "experimental eRST graph" for P3 and `dual`.** Full corpus (about 74,000 words, about 43 units, thousands of discourse units) vs only the evidence spans of the evaluated pairs. Consequence: API cost differs by roughly 5-10x and `dual` can only be called an eRST-compatible graph either way.
3. **Second annotator.** At least 60 double annotations and κ are required but no second annotator is named; annotation time is the largest cost (§5).
4. **N0 definition (F1)** and the unusual fact that the IIR test split has been used once already (F3): confirm the proposal above.
