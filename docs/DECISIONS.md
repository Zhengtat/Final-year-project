- **2026-09-28 · M1: textbook parser is heading-regex, not docutils** (BUILD_PLAN said "try docutils first"). Reason: the book uses many Sphinx-only directives (`figure`, `numref`, `table`, custom roles); registering pass-throughs for all of them in docutils was more machinery than a direct text extractor for this use case. Chosen granularity: **one Section per toctree-leaf `.rst` file**, not per in-file heading depth — the book's own nesting (root `index.rst` → chapter file → chapter's own toctree of section files) already gives exactly the "lowest-level heading" granularity BUILD_PLAN asks for (e.g. `congestion/tcpcc.rst` → section_id "6.3"). Deeper in-file subheadings (e.g. "6.3.1 ...") are kept as inline paragraph text, not split into separate Sections. Verified on the real 6th-edition source: 64 sections, all 9 numbered chapters + 3 front-matter files, 0 sections under 20 words, `order_index` strictly increasing, 0 residual RST markup found in a full-book scan (one "false positive" was an ellipsis `...` in ordinary prose).
- **2026-09-28 · M1 finding: SAF `score` is not a global 0–1 fraction** — it is an absolute point value whose maximum varies per question (1.0 to 3.5 across the 26 seen questions), confirmed by `verification_feedback == "Correct"` always landing at that question's own max. M4 must normalise `score / per_question_max_score` before using it as a proposition-weight hint; using raw `score` directly would be wrong. Logged in `reports/m1_eda_saf.md` §2.
- **2026-09-28 · M1 finding: 26 "seen" questions (train/validation/test_unseen_answers, identical set) + 5 disjoint "unseen" questions (test_unseen_questions) = 31 distinct question texts total.** No question overlap between seen and unseen splits (confirms the unseen-questions split is genuinely novel-topic, not just reworded). Two of the 26 seen questions are cosmetic rewordings of the same TCP-congestion-control question (differ only in a trailing "total." vs "."), which likely explains the paper's count of 22 vs the dataset card's 26.

- **2026-09-28 · M2 schema/registry implementation notes.** (1) `cumap gold validate` dispatches by path convention under `data/gold/` (`expert_pilot/*.yaml` -> `list[ExpertEdge]`, `student_pilot/*.yaml` -> `list[StudentEdge]`, `propositions.jsonl` -> `Proposition` per line, `verified_labels.jsonl` -> `SilverAnswerLabel` per line, `misconceptions*.yaml` -> `list[Misconception]`); anything else is **skipped, not failed**, since this is a human-owned directory that may hold files with no pydantic schema yet (e.g. `question_section_map.csv`). (2) `Evidence` requires exactly one of `section_id`/`answer_id` (a model validator) so quote verification always has an unambiguous source to check against. (3) `RelationRegistry.is_reversal` relies on `normalise()` already canonicalising symmetric-relation endpoint order, so a symmetric relation's "reversed" pair normalises to the identical edge and is correctly reported as *not* a reversal, without a separate special case. (4) `check_types`/evidence-substring checks only flag *known* concepts/sections as wrong — missing lookups (concept not yet in the KG, unknown section) are reported as their own distinct issue, never silently treated as a type violation.
- **2026-09-28 · Residual limitation: coverage-guess quality is capped by embedding top-3 retrieval, not just the truncation bug.** For "transparent bridges" and "piggybacking", the section that actually covers the topic (3.2 Switched Ethernet §3.2.1 "Learning Bridges"; 2.5 Reliable Transmission) ranked outside the embedding top-3 (ranks 4-5), so the LLM correctly judged "none"/"partial" *given what it was shown*, disagreeing with direct manual verification against the book text. This is the project's own stated principle in action ("embeddings only propose candidates; the verdict comes from checked evidence") — treat the automated `coverage` column as a first pass, not a substitute for checking the actual top-5 list (or the book) before ruling a question out. Same caution applies going into M5's concept/relation retrieval.
