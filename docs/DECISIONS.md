# Decisions log

Format: date · decision · reason · alternatives considered.

- **2026-09-28 · Domain = university-level CS (computer networking).** Reason: the project is meant to use university-level content. Alternatives: Beetle/SciEntsBank (school science; they have gold incomplete-vs-contradictory labels) — kept only as an optional sanity check.
- **2026-09-28 · Primary dataset = SAF Communication Networks (English).** Reason: university course; explanatory answers (~82 tokens on average); human-written feedback on what is wrong or missing; CC BY 4.0; unseen-question split. Limitations: no incomplete/contradictory label (derive silver labels, M4); no student IDs.
- **2026-09-28 · Expert source = Peterson & Davie, *Computer Networks: A Systems Approach* 6e.** Reason: open (CC BY 4.0), structured reStructuredText source, covers most SAF topics. Check coverage per question in M1 (DQDB, queueing, frame bursting may be thin).
- **2026-09-28 · Second domain (stretch) = Mohler data structures + *Open Data Structures*.** Reason: allows comparison with MitiGaTe (RMSE 0.762); strong published misconception research for data structures and hashing.
- **2026-09-28 · LLM provider = OpenAI (Responses API + Structured Outputs).** Strong tier `gpt-6-astra`, bulk tier `gpt-6-luna`; both configurable. Reason: user choice. All calls are cached and version-logged.
- **2026-09-28 · Graph store = NetworkX + JSONL during the MVP; Neo4j export optional.** Reason: simplicity and reproducibility; Neo4j only for visualisation/queries later.
- **2026-09-28 · Relation registry v0 = 14 relations** (see `configs/relations_v0.yaml`) — awaiting human approval in M2.
- **2026-09-28 · Evaluation priority:** the human-verified label subset (M4) is the primary test set; silver labels are secondary. Reason: the silver labeller is an LLM, so evaluating only against it would be circular.
- **2026-09-28 · M0: verified `openai` SDK (installed version 3.19.2) against CLAUDE.md's description of the Responses API — no deviations found.** `Responses.parse(model=, input=, text_format=, reasoning=, ...)` exists as described; `response.output_parsed` is a computed property on `ParsedResponse`; `response.usage.input_tokens` / `.output_tokens` exist on `ResponseUsage`. `reasoning` is a TypedDict with an `effort` field whose literal values include `none, minimal, low, medium, high, xhigh, max` — the installed SDK's type does allow `effort="none"` (unlike the informal claim that "none" is unsupported generally); CLAUDE.md's rule is scoped to the specific model `gpt-6-astra` not accepting it, so `LLMClient` always passes `reasoning={"effort": ...}` and only coerces `none → low` when the target model is `gpt-6-astra`. No `configs/default.yaml` changes were needed.
- **2026-09-28 · `data/gold/` and `data/interim/` are committed (not gitignored); only `data/raw/`, `data/processed/`, `data/cache/`, `data/logs/` and `.env` are ignored**, per BUILD_PLAN M0 task 8's explicit list. `.gitkeep` placeholders added so the empty `data/gold/` and `data/interim/suggestions/` directories exist in a fresh clone.
- **2026-09-28 · M1: textbook parser is heading-regex, not docutils** (BUILD_PLAN said "try docutils first"). Reason: the book uses many Sphinx-only directives (`figure`, `numref`, `table`, custom roles); registering pass-throughs for all of them in docutils was more machinery than a direct text extractor for this use case. Chosen granularity: **one Section per toctree-leaf `.rst` file**, not per in-file heading depth — the book's own nesting (root `index.rst` → chapter file → chapter's own toctree of section files) already gives exactly the "lowest-level heading" granularity BUILD_PLAN asks for (e.g. `congestion/tcpcc.rst` → section_id "6.3"). Deeper in-file subheadings (e.g. "6.3.1 ...") are kept as inline paragraph text, not split into separate Sections. Verified on the real 6th-edition source: 64 sections, all 9 numbered chapters + 3 front-matter files, 0 sections under 20 words, `order_index` strictly increasing, 0 residual RST markup found in a full-book scan (one "false positive" was an ellipsis `...` in ordinary prose).
- **2026-09-28 · M1 finding: SAF `score` is not a global 0–1 fraction** — it is an absolute point value whose maximum varies per question (1.0 to 3.5 across the 26 seen questions), confirmed by `verification_feedback == "Correct"` always landing at that question's own max. M4 must normalise `score / per_question_max_score` before using it as a proposition-weight hint; using raw `score` directly would be wrong. Logged in `reports/m1_eda_saf.md` §2.
- **2026-09-28 · M1 finding: 26 "seen" questions (train/validation/test_unseen_answers, identical set) + 5 disjoint "unseen" questions (test_unseen_questions) = 31 distinct question texts total.** No question overlap between seen and unseen splits (confirms the unseen-questions split is genuinely novel-topic, not just reworded). Two of the 26 seen questions are cosmetic rewordings of the same TCP-congestion-control question (differ only in a trailing "total." vs "."), which likely explains the paper's count of 22 vs the dataset card's 26.
- **2026-09-28 · M1 coverage-guess LLM pricing is a placeholder** (`configs/default.yaml`: `assumed_usd_per_1k_*_tokens`). `gpt-6-astra`/`gpt-6-luna` have no published per-token price found; the `--dry-run` cost estimate uses an assumed rate pending confirmation, and is order-of-magnitude only.
