=== SECTION 5.2: End-to-End Protocols > Reliable Byte Stream (TCP) ===
[5.2_s0000] In contrast to a simple demultiplexing protocol like UDP, a more sophisticated transport protocol is one that offers a reliable, connection-oriented, byte-stream service.
[5.2_s0001] Such a service has proven useful to a wide assortment of applications because it frees the application from having to worry about missing or reordered data.
[5.2_s0002] The Internet’s Transmission Control Protocol is probably the most widely used protocol of this type; it is also the most carefully tuned.
[5.2_s0003] It is for these two reasons that this section studies TCP in detail, although we identify and discuss alternative design choices at the end of the section.
[5.2_s0004] In terms of the properties of transport protocols given in the problem statement at the start of this chapter, TCP guarantees the reliable, in-order delivery of a stream of bytes.
[5.2_s0005] It is a full-duplex protocol, meaning that each TCP connection supports a pair of byte streams, one flowing in each direction.
[5.2_s0006] It also includes a flow-control mechanism for each of these byte streams that allows the receiver to limit how much data the sender can transmit at a given time.
[5.2_s0007] Finally, like UDP, TCP supports a demultiplexing mechanism that allows multiple application programs on any given host to simultaneously carry on a conversation with their peers.
[5.2_s0008] In addition to the above features, TCP also implements a highly tuned congestion-control mechanism.
[5.2_s0009] The idea of this mechanism is to throttle how fast TCP sends data, not for the sake of keeping the sender from over-running the receiver, but so as to keep the sender from overloading the network.
[5.2_s0010] A description of TCP’s congestion-control mechanism is postponed until the next chapter, where we discuss it in the larger context of how network resources are fairly allocated.
[5.2_s0011] Since many people confuse congestion control and flow control, we restate the difference.
[5.2_s0012] Flow control involves preventing senders from over-running the capacity of receivers.
[5.2_s0013] Congestion control involves preventing too much data from being injected into the network, thereby causing switches or links to become overloaded.
[5.2_s0014] Thus, flow control is an end-to-end issue, while congestion control is concerned with how hosts and networks interact.
[5.2_s0015] 5.2.1 End-to-End Issues  At the heart of TCP is the sliding window algorithm.
[5.2_s0016] Even though this is the same basic algorithm as is often used at the link level, because TCP runs over the Internet rather than a physical point-to-point link, there are many important differences.
[5.2_s0017] This subsection identifies these differences and explains how they complicate TCP.
[5.2_s0018] The following subsections then describe how TCP addresses these and other complications.
[5.2_s0019] First, whereas the link-level sliding window algorithm presented runs over a single physical link that always connects the same two computers, TCP supports logical connections between processes that are running on any two computers in the Internet.
[5.2_s0020] This means that TCP needs an explicit connection establishment phase during which the two sides of the connection agree to exchange data with each other.
[5.2_s0021] This difference is analogous to having to dial up the other party, rather than having a dedicated phone line.
[5.2_s0022] TCP also has an explicit connection teardown phase.
[5.2_s0023] One of the things that happens during connection establishment is that the two parties establish some shared state to enable the sliding window algorithm to begin.
[5.2_s0024] Connection teardown is needed so each host knows it is OK to free this state.
[5.2_s0025] Second, whereas a single physical link that always connects the same two computers has a fixed round-trip time (RTT), TCP connections are likely to have widely different round-trip times.
[5.2_s0026] For example, a TCP connection between a host in San Francisco and a host in Boston, which are separated by several thousand kilometers, might have an RTT of 100 ms, while a TCP connection between two hosts in the same room, only a few meters apart, might have an RTT of only 1 ms.
[5.2_s0027] The same TCP protocol must be able to support both of these connections.
[5.2_s0028] To make matters worse, the TCP connection between hosts in San Francisco and Boston might have an RTT of 100 ms at 3 a.m., but an RTT of 500 ms at 3 p.m. Variations in the RTT are even possible during a single TCP connection that lasts only a few minutes.
[5.2_s0029] What this means to the sliding window algorithm is that the timeout mechanism that triggers retransmissions must be adaptive.
[5.2_s0030] (Certainly, the timeout for a point-to-point link must be a settable parameter, but it is not necessary to adapt this timer for a particular pair of nodes.)
[5.2_s0031] A third difference is that packets may be reordered as they cross the Internet, but this is not possible on a point-to-point link where the first packet put into one end of the link must be the first to appear at the other end.
[5.2_s0032] Packets that are slightly out of order do not cause a problem since the sliding window algorithm can reorder packets correctly using the sequence number.
[5.2_s0033] The real issue is how far out of order packets can get or, said another way, how late a packet can arrive at the destination.
[5.2_s0034] In the worst case, a packet can be delayed in the Internet until the IP time to live (TTL) field expires, at which time the packet is discarded (and hence there is no danger of it arriving late).
[5.2_s0035] Knowing that IP throws packets away after their TTL expires, TCP assumes that each packet has a maximum lifetime.
[5.2_s0036] The exact lifetime, known as the maximum segment lifetime (MSL), is an engineering choice.
[5.2_s0037] The current recommended setting is 120 seconds.
[5.2_s0038] Keep in mind that IP does not directly enforce this 120-second value; it is simply a conservative estimate that TCP makes of how long a packet might live in the Internet.
[5.2_s0039] The implication is significant—TCP has to be prepared for very old packets to suddenly show up at the receiver, potentially confusing the sliding window algorithm.
[5.2_s0040] Fourth, the computers connected to a point-to-point link are generally engineered to support the link.
[5.2_s0041] For example, if a link’s delay × bandwidth product is computed to be 8 KB—meaning that a window size is selected to allow up to 8 KB of data to be unacknowledged at a given time—then it is likely that the computers at either end of the link have the ability to buffer up to 8 KB of data.
[5.2_s0042] Designing the system otherwise would be silly.
[5.2_s0043] On the other hand, almost any kind of computer can be connected to the Internet, making the amount of resources dedicated to any one TCP connection highly variable, especially considering that any one host can potentially support hundreds of TCP connections at the same time.
[5.2_s0044] This means that TCP must include a mechanism that each side uses to “learn” what resources (e.g., how much buffer space) the other side is able to apply to the connection.
[5.2_s0045] This is the flow control issue.
[5.2_s0046] Fifth, because the transmitting side of a directly connected link cannot send any faster than the bandwidth of the link allows, and only one host is pumping data into the link, it is not possible to unknowingly congest the link.
[5.2_s0047] Said another way, the load on the link is visible in the form of a queue of packets at the sender.
[5.2_s0048] In contrast, the sending side of a TCP connection has no idea what links will be traversed to reach the destination.
[5.2_s0049] For example, the sending machine might be directly connected to a relatively fast Ethernet—and capable of sending data at a rate of 10 Gbps—but somewhere out in the middle of the network, a 1.5-Mbps link must be traversed.
[5.2_s0050] And, to make matters worse, data being generated by many different sources might be trying to traverse this same slow link.
[5.2_s0051] This leads to the problem of network congestion.
[5.2_s0052] Discussion of this topic is delayed until the next chapter.
[5.2_s0053] We conclude this discussion of end-to-end issues by comparing TCP’s approach to providing a reliable/ordered delivery service with the approach used by virtual-circuit-based networks like the historically important X.25 network.
[5.2_s0054] In TCP, the underlying IP network is assumed to be unreliable and to deliver messages out of order; TCP uses the sliding window algorithm on an end-to-end basis to provide reliable/ordered delivery.
[5.2_s0055] In contrast, X.25 networks use the sliding window protocol within the network, on a hop-by-hop basis.
[5.2_s0056] The assumption behind this approach is that if messages are delivered reliably and in order between each pair of nodes along the path between the source host and the destination host, then the end-to-end service also guarantees reliable/ordered delivery.
[5.2_s0057] The problem with this latter approach is that a sequence of hop-by-hop guarantees does not necessarily add up to an end-to-end guarantee.
[5.2_s0058] First, if a heterogeneous link (say, an Ethernet) is added to one end of the path, then there is no guarantee that this hop will preserve the same service as the other hops.
[5.2_s0059] Second, just because the sliding window protocol guarantees that messages are delivered correctly from node A to node B, and then from node B to node C, it does not guarantee that node B behaves perfectly.
[5.2_s0060] For example, network nodes have been known to introduce errors into messages while transferring them from an input buffer to an output buffer.
[5.2_s0061] They have also been known to accidentally reorder messages.
[5.2_s0062] As a consequence of these small windows of vulnerability, it is still necessary to provide true end-to-end checks to guarantee reliable/ordered service, even though the lower levels of the system also implement that functionality.
[5.2_s0063] 5.2.2 Segment Format  TCP is a byte-oriented protocol, which means that the sender writes bytes into a TCP connection and the receiver reads bytes out of the TCP connection.
[5.2_s0064] Although “byte stream” describes the service TCP offers to application processes, TCP does not, itself, transmit individual bytes over the Internet.
[5.2_s0065] Instead, TCP on the source host buffers enough bytes from the sending process to fill a reasonably sized packet and then sends this packet to its peer on the destination host.
[5.2_s0066] TCP on the destination host then empties the contents of the packet into a receive buffer, and the receiving process reads from this buffer at its leisure.
[5.2_s0067] This situation is illustrated in Figure, which, for simplicity, shows data flowing in only one direction.
[5.2_s0068] Remember that, in general, a single TCP connection supports byte streams flowing in both directions.
[5.2_s0069] The packets exchanged between TCP peers in Figure are called segments, since each one carries a segment of the byte stream.
[5.2_s0070] Each TCP segment contains the header schematically depicted in Figure.
[5.2_s0071] The relevance of most of these fields will become apparent throughout this section.
[5.2_s0072] For now, we simply introduce them.
[5.2_s0073] The SrcPort and DstPort fields identify the source and destination ports, respectively, just as in UDP.
[5.2_s0074] These two fields, plus the source and destination IP addresses, combine to uniquely identify each TCP connection.
[5.2_s0075] That is, TCP’s demux key is given by the 4-tuple  Note that because TCP connections come and go, it is possible for a connection between a particular pair of ports to be established, used to send and receive data, and closed, and then at a later time for the same pair of ports to be involved in a second connection.
[5.2_s0076] We sometimes refer to this situation as two different incarnations of the same connection.
[5.2_s0077] The Acknowledgement, SequenceNum, and AdvertisedWindow fields are all involved in TCP’s sliding window algorithm.
[5.2_s0078] Because TCP is a byte-oriented protocol, each byte of data has a sequence number.
[5.2_s0079] The SequenceNum field contains the sequence number for the first byte of data carried in that segment, and the Acknowledgement and AdvertisedWindow fields carry information about the flow of data going in the other direction.
[5.2_s0080] To simplify our discussion, we ignore the fact that data can flow in both directions, and we concentrate on data that has a particular SequenceNum flowing in one direction and Acknowledgement and AdvertisedWindow values flowing in the opposite direction, as illustrated in Figure.
[5.2_s0081] The use of these three fields is described more fully later in this chapter.
[5.2_s0082] The 6-bit Flags field is used to relay control information between TCP peers.
[5.2_s0083] The possible flags include SYN, FIN, RESET, PUSH, URG, and ACK.
[5.2_s0084] The SYN and FIN flags are used when establishing and terminating a TCP connection, respectively.
[5.2_s0085] Their use is described in a later section.
[5.2_s0086] The ACK flag is set any time the Acknowledgement field is valid, implying that the receiver should pay attention to it.
[5.2_s0087] The URG flag signifies that this segment contains urgent data.
[5.2_s0088] When this flag is set, the UrgPtr field indicates where the nonurgent data contained in this segment begins.
[5.2_s0089] The urgent data is contained at the front of the segment body, up to and including a value of UrgPtr bytes into the segment.
[5.2_s0090] The PUSH flag signifies that the sender invoked the push operation, which indicates to the receiving side of TCP that it should notify the receiving process of this fact.
[5.2_s0091] We discuss these last two features more in a later section.
[5.2_s0092] Finally, the RESET flag signifies that the receiver has become confused—for example, because it received a segment it did not expect to receive—and so wants to abort the connection.
[5.2_s0093] Finally, the Checksum field is used in exactly the same way as for UDP—it is computed over the TCP header, the TCP data, and the pseudoheader, which is made up of the source address, destination address, and length fields from the IP header.
[5.2_s0094] The checksum is required for TCP in both IPv4 and IPv6.
[5.2_s0095] Also, since the TCP header is of variable length (options can be attached after the mandatory fields), a HdrLen field is included that gives the length of the header in 32-bit words.
[5.2_s0096] This field is also known as the Offset field, since it measures the offset from the start of the packet to the start of the data.
[5.2_s0097] 5.2.3 Connection Establishment and Termination  A TCP connection begins with a client (caller) doing an active open to a server (callee).
[5.2_s0098] Assuming that the server had earlier done a passive open, the two sides engage in an exchange of messages to establish the connection.
[5.2_s0099] (Recall from Chapter 1 that a party wanting to initiate a connection performs an active open, while a party willing to accept a connection does a passive open.\ [#]_)
[5.2_s0100] Only after this connection establishment phase is over do the two sides begin sending data.
[5.2_s0101] Likewise, as soon as a participant is done sending data, it closes one direction of the connection, which causes TCP to initiate a round of connection termination messages.
[5.2_s0102] Notice that, while connection setup is an asymmetric activity (one side does a passive open and the other side does an active open), connection teardown is symmetric (each side has to close the connection independently).
[5.2_s0103] Therefore, it is possible for one side to have done a close, meaning that it can no longer send data, but for the other side to keep the other half of the bidirectional connection open and to continue sending data.
[5.2_s0104] Three-Way Handshake  The algorithm used by TCP to establish and terminate a connection is called a three-way handshake.
[5.2_s0105] We first describe the basic algorithm and then show how it is used by TCP.
[5.2_s0106] The three-way handshake involves the exchange of three messages between the client and the server, as illustrated by the timeline given in Figure.
[5.2_s0107] The idea is that two parties want to agree on a set of parameters, which, in the case of opening a TCP connection, are the starting sequence numbers the two sides plan to use for their respective byte streams.
[5.2_s0108] In general, the parameters might be any facts that each side wants the other to know about.
[5.2_s0109] First, the client (the active participant) sends a segment to the server (the passive participant) stating the initial sequence number it plans to use (Flags = SYN, SequenceNum = x).
[5.2_s0110] The server then responds with a single segment that both acknowledges the client’s sequence number (Flags = ACK, Ack = x + 1) and states its own beginning sequence number (Flags = SYN, SequenceNum = y).
[5.2_s0111] That is, both the SYN and ACK bits are set in the Flags field of this second message.
[5.2_s0112] Finally, the client responds with a third segment that acknowledges the server’s sequence number (Flags = ACK, Ack = y + 1).
[5.2_s0113] The reason why each side acknowledges a sequence number that is one larger than the one sent is that the Acknowledgement field actually identifies the “next sequence number expected,” thereby implicitly acknowledging all earlier sequence numbers.
[5.2_s0114] Although not shown in this timeline, a timer is scheduled for each of the first two segments, and if the expected response is not received the segment is retransmitted.
[5.2_s0115] You may be asking yourself why the client and server have to exchange starting sequence numbers with each other at connection setup time.
[5.2_s0116] It would be simpler if each side simply started at some “well-known” sequence number, such as 0.
[5.2_s0117] In fact, the TCP specification requires that each side of a connection select an initial starting sequence number at random.
[5.2_s0118] The reason for this is to protect against two incarnations of the same connection reusing the same sequence numbers too soon—that is, while there is still a chance that a segment from an earlier incarnation of a connection might interfere with a later incarnation of the connection.
[5.2_s0119] State-Transition Diagram  TCP is complex enough that its specification includes a state-transition diagram.
[5.2_s0120] A copy of this diagram is given in Figure.
[5.2_s0121] This diagram shows only the states involved in opening a connection (everything above ESTABLISHED) and in closing a connection (everything below ESTABLISHED).
[5.2_s0122] Everything that goes on while a connection is open—that is, the operation of the sliding window algorithm—is hidden in the ESTABLISHED state.
[5.2_s0123] TCP’s state-transition diagram is fairly easy to understand.
[5.2_s0124] Each box denotes a state that one end of a TCP connection can find itself in.
[5.2_s0125] All connections start in the CLOSED state.
[5.2_s0126] As the connection progresses, the connection moves from state to state according to the arcs.
[5.2_s0127] Each arc is labeled with a tag of the form event/action.
[5.2_s0128] Thus, if a connection is in the LISTEN state and a SYN segment arrives (i.e., a segment with the SYN flag set), the connection makes a transition to the SYN_RCVD state and takes the action of replying with an ACK+SYN segment.
[5.2_s0129] Notice that two kinds of events trigger a state transition: (1) a segment arrives from the peer (e.g., the event on the arc from LISTEN to SYN_RCVD), or (2) the local application process invokes an operation on TCP (e.g., the active open event on the arc from CLOSED to SYN_SENT).
[5.2_s0130] In other words, TCP’s state-transition diagram effectively defines the semantics of both its peer-to-peer interface and its service interface.
[5.2_s0131] The syntax of these two interfaces is given by the segment format (as illustrated in Figure) and by some application programming interface, such as the socket API, respectively.
[5.2_s0132] Now let’s trace the typical transitions taken through the diagram in Figure.
[5.2_s0133] Keep in mind that at each end of the connection, TCP makes different transitions from state to state.
[5.2_s0134] When opening a connection, the server first invokes a passive open operation on TCP, which causes TCP to move to the LISTEN state.
[5.2_s0135] At some later time, the client does an active open, which causes its end of the connection to send a SYN segment to the server and to move to the SYN_SENT state.
[5.2_s0136] When the SYN segment arrives at the server, it moves to the SYN_RCVD state and responds with a SYN+ACK segment.
[5.2_s0137] The arrival of this segment causes the client to move to the ESTABLISHED state and to send an ACK back to the server.
[5.2_s0138] When this ACK arrives, the server finally moves to the ESTABLISHED state.
[5.2_s0139] In other words, we have just traced the three-way handshake.
[5.2_s0140] There are three things to notice about the connection establishment half of the state-transition diagram.
[5.2_s0141] First, if the client’s ACK to the server is lost, corresponding to the third leg of the three-way handshake, then the connection still functions correctly.
[5.2_s0142] This is because the client side is already in the ESTABLISHED state, so the local application process can start sending data to the other end.
[5.2_s0143] Each of these data segments will have the ACK flag set, and the correct value in the Acknowledgement field, so the server will move to the ESTABLISHED state when the first data segment arrives.
[5.2_s0144] This is actually an important point about TCP—every segment reports what sequence number the sender is expecting to see next, even if this repeats the same sequence number contained in one or more previous segments.
[5.2_s0145] The second thing to notice about the state-transition diagram is that there is a funny transition out of the LISTEN state whenever the local process invokes a send operation on TCP.
[5.2_s0146] That is, it is possible for a passive participant to identify both ends of the connection (i.e., itself and the remote participant that it is willing to have connect to it), and then for it to change its mind about waiting for the other side and instead actively establish the connection.
[5.2_s0147] To the best of our knowledge, this is a feature of TCP that no application process actually takes advantage of.
[5.2_s0148] The final thing to notice about the diagram is the arcs that are not shown.
[5.2_s0149] Specifically, most of the states that involve sending a segment to the other side also schedule a timeout that eventually causes the segment to be resent if the expected response does not happen.
[5.2_s0150] These retransmissions are not depicted in the state-transition diagram.
[5.2_s0151] If after several tries the expected response does not arrive, TCP gives up and returns to the CLOSED state.
[5.2_s0152] Turning our attention now to the process of terminating a connection, the important thing to keep in mind is that the application process on both sides of the connection must independently close its half of the connection.
[5.2_s0153] If only one side closes the connection, then this means it has no more data to send, but it is still available to receive data from the other side.
[5.2_s0154] This complicates the state-transition diagram because it must account for the possibility that the two sides invoke the close operator at the same time, as well as the possibility that first one side invokes close and then, at some later time, the other side invokes close.
[5.2_s0155] Thus, on any one side there are three combinations of transitions that get a connection from the ESTABLISHED state to the CLOSED state:  -  This side closes first: ESTABLISHED \rightarrow FIN_WAIT_1 \rightarrow FIN_WAIT_2 \rightarrow TIME_WAIT \rightarrow CLOSED.  -  The other side closes first: ESTABLISHED \rightarrow CLOSE_WAIT \rightarrow LAST_ACK \rightarrow CLOSED.  -  Both sides close at the same time: ESTABLISHED \rightarrow FIN_WAIT_1 \rightarrow CLOSING \rightarrow TIME_WAIT \rightarrow CLOSED.
[5.2_s0156] There is actually a fourth, although rare, sequence of transitions that leads to the CLOSED state; it follows the arc from FIN_WAIT_1 to TIME_WAIT.
[5.2_s0157] We leave it as an exercise for you to figure out what combination of circumstances leads to this fourth possibility.
[5.2_s0158] The main thing to recognize about connection teardown is that a connection in the TIME_WAIT state cannot move to the CLOSED state until it has waited for two times the maximum amount of time an IP datagram might live in the Internet (i.e., 120 seconds).
[5.2_s0159] The reason for this is that, while the local side of the connection has sent an ACK in response to the other side’s FIN segment, it does not know that the ACK was successfully delivered.
[5.2_s0160] As a consequence, the other side might retransmit its FIN segment, and this second FIN segment might be delayed in the network.
[5.2_s0161] If the connection were allowed to move directly to the CLOSED state, then another pair of application processes might come along and open the same connection (i.e., use the same pair of port numbers), and the delayed FIN segment from the earlier incarnation of the connection would immediately initiate the termination of the later incarnation of that connection.
[5.2_s0162] 5.2.4 Sliding Window
[5.2_s0163] Revisited  We are now ready to discuss TCP’s variant of the sliding window algorithm, which serves several purposes: (1) it guarantees the reliable delivery of data, (2) it ensures that data is delivered in order, and (3) it enforces flow control between the sender and the receiver.
[5.2_s0164] TCP’s use of the sliding window algorithm is the same as at the link level in the case of the first two of these three functions.
[5.2_s0165] Where TCP differs from the link-level algorithm is that it folds the flow-control function in as well.
[5.2_s0166] In particular, rather than having a fixed-size sliding window, the receiver advertises a window size to the sender.
[5.2_s0167] This is done using the AdvertisedWindow field in the TCP header.
[5.2_s0168] The sender is then limited to having no more than a value of AdvertisedWindow bytes of unacknowledged data at any given time.
[5.2_s0169] The receiver selects a suitable value for AdvertisedWindow based on the amount of memory allocated to the connection for the purpose of buffering data.
[5.2_s0170] The idea is to keep the sender from over-running the receiver’s buffer.
[5.2_s0171] We discuss this at greater length below.
[5.2_s0172] Reliable and Ordered Delivery  To see how the sending and receiving sides of TCP interact with each other to implement reliable and ordered delivery, consider the situation illustrated in Figure.
[5.2_s0173] TCP on the sending side maintains a send buffer.
[5.2_s0174] This buffer is used to store data that has been sent but not yet acknowledged, as well as data that has been written by the sending application but not transmitted.
[5.2_s0175] On the receiving side, TCP maintains a receive buffer.
[5.2_s0176] This buffer holds data that arrives out of order, as well as data that is in the correct order (i.e., there are no missing bytes earlier in the stream) but that the application process has not yet had the chance to read.
[5.2_s0177] To make the following discussion simpler to follow, we initially ignore the fact that both the buffers and the sequence numbers are of some finite size and hence will eventually wrap around.
[5.2_s0178] Also, we do not distinguish between a pointer into a buffer where a particular byte of data is stored and the sequence number for that byte.
[5.2_s0179] Looking first at the sending side, three pointers are maintained into the send buffer, each with an obvious meaning: LastByteAcked, LastByteSent, and LastByteWritten.
[5.2_s0180] Clearly,  since the receiver cannot have acknowledged a byte that has not yet been sent, and  since TCP cannot send a byte that the application process has not yet written.
[5.2_s0181] Also note that none of the bytes to the left of LastByteAcked need to be saved in the buffer because they have already been acknowledged, and none of the bytes to the right of LastByteWritten need to be buffered because they have not yet been generated.
[5.2_s0182] A similar set of pointers (sequence numbers) are maintained on the receiving side: LastByteRead, NextByteExpected, and LastByteRcvd.
[5.2_s0183] The inequalities are a little less intuitive, however, because of the problem of out-of-order delivery.
[5.2_s0184] The first relationship  is true because a byte cannot be read by the application until it is received and all preceding bytes have also been received.
[5.2_s0185] NextByteExpected points to the byte immediately after the latest byte to meet this criterion.
[5.2_s0186] Second,  since, if data has arrived in order, NextByteExpected points to the byte after LastByteRcvd, whereas if data has arrived out of order, then NextByteExpected points to the start of the first gap in the data, as in Figure.
[5.2_s0187] Note that bytes to the left of LastByteRead need not be buffered because they have already been read by the local application process, and bytes to the right of LastByteRcvd need not be buffered because they have not yet arrived.
[5.2_s0188] Flow Control  Most of the above discussion is similar to that found in the standard sliding window algorithm; the only real difference is that this time we elaborated on the fact that the sending and receiving application processes are filling and emptying their local buffer, respectively.
[5.2_s0189] (The earlier discussion glossed over the fact that data arriving from an upstream node was filling the send buffer and data being transmitted to a downstream node was emptying the receive buffer.)
[5.2_s0190] You should make sure you understand this much before proceeding because now comes the point where the two algorithms differ more significantly.
[5.2_s0191] In what follows, we reintroduce the fact that both buffers are of some finite size, denoted MaxSendBuffer and MaxRcvBuffer, although we don’t worry about the details of how they are implemented.
[5.2_s0192] In other words, we are only interested in the number of bytes being buffered, not in where those bytes are actually stored.
[5.2_s0193] Recall that in a sliding window protocol, the size of the window sets the amount of data that can be sent without waiting for acknowledgment from the receiver.
[5.2_s0194] Thus, the receiver throttles the sender by advertising a window that is no larger than the amount of data that it can buffer.
[5.2_s0195] Observe that TCP on the receive side must keep  to avoid overflowing its buffer.
[5.2_s0196] It therefore advertises a window size of  which represents the amount of free space remaining in its buffer.
[5.2_s0197] As data arrives, the receiver acknowledges it as long as all the preceding bytes have also arrived.
[5.2_s0198] In addition, LastByteRcvd moves to the right (is incremented), meaning that the advertised window potentially shrinks.
[5.2_s0199] Whether or not it shrinks depends on how fast the local application process is consuming data.
[5.2_s0200] If the local process is reading data just as fast as it arrives (causing LastByteRead to be incremented at the same rate as LastByteRcvd), then the advertised window stays open (i.e., AdvertisedWindow = MaxRcvBuffer).
[5.2_s0201] If, however, the receiving process falls behind, perhaps because it performs a very expensive operation on each byte of data that it reads, then the advertised window grows smaller with every segment that arrives, until it eventually goes to 0.
[5.2_s0202] TCP on the send side must then adhere to the advertised window it gets from the receiver.
[5.2_s0203] This means that at any given time, it must ensure that  Said another way, the sender computes an effective window that limits how much data it can send:
[5.2_s0204] Clearly, EffectiveWindow must be greater than 0 before the source can send more data.
[5.2_s0205] It is possible, therefore, that a segment arrives acknowledging x bytes, thereby allowing the sender to increment LastByteAcked by x, but because the receiving process was not reading any data, the advertised window is now x bytes smaller than the time before.
[5.2_s0206] In such a situation, the sender would be able to free buffer space, but not to send any more data.
[5.2_s0207] All the while this is going on, the send side must also make sure that the local application process does not overflow the send buffer—that is,  If the sending process tries to write y bytes to TCP, but  then TCP blocks the sending process and does not allow it to generate more data.
[5.2_s0208] It is now possible to understand how a slow receiving process ultimately stops a fast sending process.
[5.2_s0209] First, the receive buffer fills up, which means the advertised window shrinks to 0.
[5.2_s0210] An advertised window of 0 means that the sending side cannot transmit any data, even though data it has previously sent has been successfully acknowledged.
[5.2_s0211] Finally, not being able to transmit any data means that the send buffer fills up, which ultimately causes TCP to block the sending process.
[5.2_s0212] As soon as the receiving process starts to read data again, the receive-side TCP is able to open its window back up, which allows the send-side TCP to transmit data out of its buffer.
[5.2_s0213] When this data is eventually acknowledged, LastByteAcked is incremented, the buffer space holding this acknowledged data becomes free, and the sending process is unblocked and allowed to proceed.
[5.2_s0214] There is only one remaining detail that must be resolved—how does the sending side know that the advertised window is no longer 0?
[5.2_s0215] As mentioned above, TCP always sends a segment in response to a received data segment, and this response contains the latest values for the Acknowledge and AdvertisedWindow fields, even if these values have not changed since the last time they were sent.
[5.2_s0216] The problem is this.
[5.2_s0217] Once the receive side has advertised a window size of 0, the sender is not permitted to send any more data, which means it has no way to discover that the advertised window is no longer 0 at some time in the future.
[5.2_s0218] TCP on the receive side does not spontaneously send nondata segments; it only sends them in response to an arriving data segment.
[5.2_s0219] TCP deals with this situation as follows.
[5.2_s0220] Whenever the other side advertises a window size of 0, the sending side persists in sending a segment with 1 byte of data every so often.
[5.2_s0221] It knows that this data will probably not be accepted, but it tries anyway, because each of these 1-byte segments triggers a response that contains the current advertised window.
[5.2_s0222] Eventually, one of these 1-byte probes triggers a response that reports a nonzero advertised window.
[5.2_s0223] Note that these 1-byte messages are called Zero Window Probes and in practice they are sent every 5 to 60 seconds.
[5.2_s0224] As for what single byte of data to send in the probe: it’s the next byte of actual data just outside the window.
[5.2_s0225] (It has to be real data in case it’s accepted by the receiver.)
[5.2_s0226] Protecting Against Wraparound  This subsection and the next consider the size of the SequenceNum and AdvertisedWindow fields and the implications of their sizes on TCP’s correctness and performance.
[5.2_s0227] TCP’s SequenceNum field is 32 bits long, and its AdvertisedWindow field is 16 bits long, meaning that TCP has easily satisfied the requirement of the sliding window algorithm that the sequence number space be twice as big as the window size: 2\ 32 >> 2 × 2\ 16.
[5.2_s0228] However, this requirement is not the interesting thing about these two fields.
[5.2_s0229] Consider each field in turn.
[5.2_s0230] The relevance of the 32-bit sequence number space is that the sequence number used on a given connection might wrap around—a byte with sequence number S could be sent at one time, and then at a later time a second byte with the same sequence number S might be sent.
[5.2_s0231] Once again, we assume that packets cannot survive in the Internet for longer than the recommended MSL.
[5.2_s0232] Thus, we currently need to make sure that the sequence number does not wrap around within a 120-second period of time.
[5.2_s0233] Whether or not this happens depends on how fast data can be transmitted over the Internet—that is, how fast the 32-bit sequence number space can be consumed.
[5.2_s0234] (This discussion assumes that we are trying to consume the sequence number space as fast as possible, but of course we will be if we are doing our job of keeping the pipe full.)
[5.2_s0235] Table shows how long it takes for the sequence number to wrap around on networks with various bandwidths.
[5.2_s0236] As you can see, the 32-bit sequence number space is adequate at modest bandwidths, but given that OC-192 links are now common in the Internet backbone, and that most servers now come with 10Gig Ethernet (or 10 Gbps) interfaces, we’re now well-past the point where 32 bits is too small.
[5.2_s0237] Fortunately, the IETF has worked out an extension to TCP that effectively extends the sequence number space to protect against the sequence number wrapping around.
[5.2_s0238] This and related extensions are described in a later section.
[5.2_s0239] Keeping the Pipe Full  The relevance of the 16-bit AdvertisedWindow field is that it must be big enough to allow the sender to keep the pipe full.
[5.2_s0240] Clearly, the receiver is free to not open the window as large as the AdvertisedWindow field allows; we are interested in the situation in which the receiver has enough buffer space to handle as much data as the largest possible AdvertisedWindow allows.
[5.2_s0241] In this case, it is not just the network bandwidth but the delay x bandwidth product that dictates how big the AdvertisedWindow field needs to be—the window needs to be opened far enough to allow a full delay × bandwidth product’s worth of data to be transmitted.
[5.2_s0242] Assuming an RTT of 100 ms (a typical number for a cross-country connection in the United States), Table gives the delay × bandwidth product for several network technologies.
[5.2_s0243] As you can see, TCP’s AdvertisedWindow field is in even worse shape than its SequenceNum field—it is not big enough to handle even a T3 connection across the continental United States, since a 16-bit field allows us to advertise a window of only 64 KB.
[5.2_s0244] The very same TCP extension mentioned above provides a mechanism for effectively increasing the size of the advertised window.
[5.2_s0245] 5.2.5 Triggering Transmission  We next consider a surprisingly subtle issue: how TCP decides to transmit a segment.
[5.2_s0246] As described earlier, TCP supports a byte-stream abstraction; that is, application programs write bytes into the stream, and it is up to TCP to decide that it has enough bytes to send a segment.
[5.2_s0247] What factors govern this decision?
[5.2_s0248] If we ignore the possibility of flow control—that is, we assume the window is wide open, as would be the case when a connection first starts—then TCP has three mechanisms to trigger the transmission of a segment.
[5.2_s0249] First, TCP maintains a variable, typically called the maximum segment size (MSS), and it sends a segment as soon as it has collected MSS bytes from the sending process.
[5.2_s0250] MSS is usually set to the size of the largest segment TCP can send without causing the local IP to fragment.
[5.2_s0251] That is, MSS is set to the maximum transmission unit (MTU) of the directly connected network, minus the size of the TCP and IP headers.
[5.2_s0252] The second thing that triggers TCP to transmit a segment is that the sending process has explicitly asked it to do so.
[5.2_s0253] Specifically, TCP supports a push operation, and the sending process invokes this operation to effectively flush the buffer of unsent bytes.
[5.2_s0254] The final trigger for transmitting a segment is that a timer fires; the resulting segment contains as many bytes as are currently buffered for transmission.
[5.2_s0255] However, as we will soon see, this “timer” isn’t exactly what you expect.
[5.2_s0256] Silly Window Syndrome  Of course, we can’t just ignore flow control, which plays an obvious role in throttling the sender.
[5.2_s0257] If the sender has MSS bytes of data to send and the window is open at least that much, then the sender transmits a full segment.
[5.2_s0258] Suppose, however, that the sender is accumulating bytes to send, but the window is currently closed.
[5.2_s0259] Now suppose an ACK arrives that effectively opens the window enough for the sender to transmit, say, MSS/2 bytes.
[5.2_s0260] Should the sender transmit a half-full segment or wait for the window to open to a full MSS?
[5.2_s0261] The original specification was silent on this point, and early implementations of TCP decided to go ahead and transmit a half-full segment.
[5.2_s0262] After all, there is no telling how long it will be before the window opens further.
[5.2_s0263] It turns out that the strategy of aggressively taking advantage of any available window leads to a situation now known as the silly window syndrome.
[5.2_s0264] Figure helps visualize what happens.
[5.2_s0265] If you think of a TCP stream as a conveyor belt with “full” containers (data segments) going in one direction and empty containers (ACKs) going in the reverse direction, then MSS-sized segments correspond to large containers and 1-byte segments correspond to very small containers.
[5.2_s0266] As long as the sender is sending MSS-sized segments and the receiver ACKs at least one MSS of data at a time, everything is good (Figure (a)).
[5.2_s0267] But, what if the receiver has to reduce the window, so that at some time the sender can’t send a full MSS of data?
[5.2_s0268] If the sender aggressively fills a smaller-than-\ MSS empty container as soon as it arrives, then the receiver will ACK that smaller number of bytes, and hence the small container introduced into the system remains in the system indefinitely.
[5.2_s0269] That is, it is immediately filled and emptied at each end and is never coalesced with adjacent containers to create larger containers, as in Figure (b).
[5.2_s0270] This scenario was discovered when early implementations of TCP regularly found themselves filling the network with tiny segments.
[5.2_s0271] Note that the silly window syndrome is only a problem when either the sender transmits a small segment or the receiver opens the window a small amount.
[5.2_s0272] If neither of these happens, then the small container is never introduced into the stream.
[5.2_s0273] It’s not possible to outlaw sending small segments; for example, the application might do a push after sending a single byte.
[5.2_s0274] It is possible, however, to keep the receiver from introducing a small container (i.e., a small open window).
[5.2_s0275] The rule is that after advertising a zero window the receiver must wait for space equal to an MSS before it advertises an open window.
[5.2_s0276] Since we can’t eliminate the possibility of a small container being introduced into the stream, we also need mechanisms to coalesce them.
[5.2_s0277] The receiver can do this by delaying ACKs—sending one combined ACK rather than multiple smaller ones—but this is only a partial solution because the receiver has no way of knowing how long it is safe to delay waiting either for another segment to arrive or for the application to read more data (thus opening the window).
[5.2_s0278] The ultimate solution falls to the sender, which brings us back to our original issue: When does the TCP sender decide to transmit a segment?
[5.2_s0279] Nagle’s Algorithm  Returning to the TCP sender, if there is data to send but the window is open less than MSS, then we may want to wait some amount of time before sending the available data, but the question is how long?
[5.2_s0280] If we wait too long, then we hurt interactive applications like Telnet.
[5.2_s0281] If we don’t wait long enough, then we risk sending a bunch of tiny packets and falling into the silly window syndrome.
[5.2_s0282] The answer is to introduce a timer and to transmit when the timer expires.
[5.2_s0283] While we could use a clock-based timer—for example, one that fires every 100 ms—Nagle introduced an elegant self-clocking solution.
[5.2_s0284] The idea is that as long as TCP has any data in flight, the sender will eventually receive an ACK.
[5.2_s0285] This ACK can be treated like a timer firing, triggering the transmission of more data.
[5.2_s0286] Nagle’s algorithm provides a simple, unified rule for deciding when to transmit:
[5.2_s0287] In other words, it’s always OK to send a full segment if the window allows.
[5.2_s0288] It’s also all right to immediately send a small amount of data if there are currently no segments in transit, but if there is anything in flight the sender must wait for an ACK before transmitting the next segment.
[5.2_s0289] Thus, an interactive application like Telnet that continually writes one byte at a time will send data at a rate of one segment per RTT.
[5.2_s0290] Some segments will contain a single byte, while others will contain as many bytes as the user was able to type in one round-trip time.
[5.2_s0291] Because some applications cannot afford such a delay for each write it does to a TCP connection, the socket interface allows the application to turn off Nagle’s algorithm by setting the TCP_NODELAY option.
[5.2_s0292] Setting this option means that data is transmitted as soon as possible.
[5.2_s0293] 5.2.6 Adaptive Retransmission  Because TCP guarantees the reliable delivery of data, it retransmits each segment if an ACK is not received in a certain period of time.
[5.2_s0294] TCP sets this timeout as a function of the RTT it expects between the two ends of the connection.
[5.2_s0295] Unfortunately, given the range of possible RTTs between any pair of hosts in the Internet, as well as the variation in RTT between the same two hosts over time, choosing an appropriate timeout value is not that easy.
[5.2_s0296] To address this problem, TCP uses an adaptive retransmission mechanism.
[5.2_s0297] We now describe this mechanism and how it has evolved over time as the Internet community has gained more experience using TCP.
[5.2_s0298] Original Algorithm  We begin with a simple algorithm for computing a timeout value between a pair of hosts.
[5.2_s0299] This is the algorithm that was originally described in the TCP specification—and the following description presents it in those terms—but it could be used by any end-to-end protocol.
[5.2_s0300] The idea is to keep a running average of the RTT and then to compute the timeout as a function of this RTT.
[5.2_s0301] Specifically, every time TCP sends a data segment, it records the time.
[5.2_s0302] When an ACK for that segment arrives, TCP reads the time again, and then takes the difference between these two times as a SampleRTT.
[5.2_s0303] TCP then computes an EstimatedRTT as a weighted average between the previous estimate and this new sample.

[5.2_s0305] A small alpha tracks changes in the RTT but is perhaps too heavily influenced by temporary fluctuations.
[5.2_s0306] On the other hand, a large alpha is more stable but perhaps not quick enough to adapt to real changes.
[5.2_s0307] The original TCP specification recommended a setting of alpha between 0.8 and 0.9.
[5.2_s0308] TCP then uses EstimatedRTT to compute the timeout in a rather conservative way:  Karn/Partridge Algorithm
[5.2_s0309] After several years of use on the Internet, a rather obvious flaw was discovered in this simple algorithm.
[5.2_s0310] The problem was that an ACK does not really acknowledge a transmission; it actually acknowledges the receipt of data.
[5.2_s0311] In other words, whenever a segment is retransmitted and then an ACK arrives at the sender, it is impossible to determine if this ACK should be associated with the first or the second transmission of the segment for the purpose of measuring the sample RTT.
[5.2_s0312] It is necessary to know which transmission to associate it with so as to compute an accurate SampleRTT.
[5.2_s0313] As illustrated in Figure, if you assume that the ACK is for the original transmission but it was really for the second, then the SampleRTT is too large (a); if you assume that the ACK is for the second transmission but it was actually for the first, then the SampleRTT is too small (b).
[5.2_s0314] The solution, which was proposed in 1987, is surprisingly simple.
[5.2_s0315] Whenever TCP retransmits a segment, it stops taking samples of the RTT; it only measures SampleRTT for segments that have been sent only once.
[5.2_s0316] This solution is known as the Karn/Partridge algorithm, after its inventors.
[5.2_s0317] Their proposed fix also includes a second small change to TCP’s timeout mechanism.
[5.2_s0318] Each time TCP retransmits, it sets the next timeout to be twice the last timeout, rather than basing it on the last EstimatedRTT.
[5.2_s0319] That is, Karn and Partridge proposed that TCP use exponential backoff, similar to what the Ethernet does.
[5.2_s0320] The motivation for using exponential backoff is simple: Congestion is the most likely cause of lost segments, meaning that the TCP source should not react too aggressively to a timeout.
[5.2_s0321] In fact, the more times the connection times out, the more cautious the source should become.
[5.2_s0322] We will see this idea again, embodied in a much more sophisticated mechanism, in the next chapter.
[5.2_s0323] Jacobson/Karels Algorithm  The Karn/Partridge algorithm was introduced at a time when the Internet was suffering from high levels of network congestion.
[5.2_s0324] Their approach was designed to fix some of the causes of that congestion, but, although it was an improvement, the congestion was not eliminated.
[5.2_s0325] The following year (1988), two other researchers—Jacobson and Karels—proposed a more drastic change to TCP to battle congestion.
[5.2_s0326] The bulk of that proposed change is described in the next chapter.
[5.2_s0327] Here, we focus on the aspect of that proposal that is related to deciding when to time out and retransmit a segment.
[5.2_s0328] As an aside, it should be clear how the timeout mechanism is related to congestion—if you time out too soon, you may unnecessarily retransmit a segment, which only adds to the load on the network.
[5.2_s0329] The other reason for needing an accurate timeout value is that a timeout is taken to imply congestion, which triggers a congestion-control mechanism.
[5.2_s0330] Finally, note that there is nothing about the Jacobson/Karels timeout computation that is specific to TCP.
[5.2_s0331] It could be used by any end-to-end protocol.

[5.2_s0357] 5.2.7 Record Boundaries
[5.2_s0358] Since TCP is a byte-stream protocol, the number of bytes written by the sender are not necessarily the same as the number of bytes read by the receiver.
[5.2_s0359] For example, the application might write 8 bytes, then 2 bytes, then 20 bytes to a TCP connection, while on the receiving side the application reads 5 bytes at a time inside a loop that iterates 6 times.
[5.2_s0360] TCP does not interject record boundaries between the 8th and 9th bytes, nor between the 10th and 11th bytes.
[5.2_s0361] This is in contrast to a message-oriented protocol, such as UDP, in which the message that is sent is exactly the same length as the message that is received.
[5.2_s0362] Even though TCP is a byte-stream protocol, it has two different features that can be used by the sender to insert record boundaries into this byte stream, thereby informing the receiver how to break the stream of bytes into records.
[5.2_s0363] (Being able to mark record boundaries is useful, for example, in many database applications.)
[5.2_s0364] Both of these features were originally included in TCP for completely different reasons; they have only come to be used for this purpose over time.
[5.2_s0365] The first mechanism is the urgent data feature, as implemented by the URG flag and the UrgPtr field in the TCP header.
[5.2_s0366] Originally, the urgent data mechanism was designed to allow the sending application to send out-of-band data to its peer.
[5.2_s0367] By “out of band” we mean data that is separate from the normal flow of data (e.g., a command to interrupt an operation already under way).
[5.2_s0368] This out-of-band data was identified in the segment using the UrgPtr field and was to be delivered to the receiving process as soon as it arrived, even if that meant delivering it before data with an earlier sequence number.
[5.2_s0369] Over time, however, this feature has not been used, so instead of signifying “urgent” data, it has come to be used to signify “special” data, such as a record marker.
[5.2_s0370] This use has developed because, as with the push operation, TCP on the receiving side must inform the application that urgent data has arrived.
[5.2_s0371] That is, the urgent data in itself is not important.
[5.2_s0372] It is the fact that the sending process can effectively send a signal to the receiver that is important.
[5.2_s0373] The second mechanism for inserting end-of-record markers into a byte is the push operation.
[5.2_s0374] Originally, this mechanism was designed to allow the sending process to tell TCP that it should send (flush) whatever bytes it had collected to its peer.
[5.2_s0375] The push operation can be used to implement record boundaries because the specification says that TCP must send whatever data it has buffered at the source when the application says push, and, optionally, TCP at the destination notifies the application whenever an incoming segment has the PUSH flag set.
[5.2_s0376] If the receiving side supports this option (the socket interface does not), then the push operation can be used to break the TCP stream into records.
[5.2_s0377] Of course, the application program is always free to insert record boundaries without any assistance from TCP.
[5.2_s0378] For example, it can send a field that indicates the length of a record that is to follow, or it can insert its own record boundary markers into the data stream.
[5.2_s0379] 5.2.8 TCP Extensions  We have mentioned at four different points in this section that there are now extensions to TCP that help to mitigate some problem that TCP faced as the underlying network got faster.
[5.2_s0380] These extensions are designed to have as small an impact on TCP as possible.
[5.2_s0381] In particular, they are realized as options that can be added to the TCP header.
[5.2_s0382] (We glossed over this point earlier, but the reason why the TCP header has a HdrLen field is that the header can be of variable length; the variable part of the TCP header contains the options that have been added.)
[5.2_s0383] The significance of adding these extensions as options rather than changing the core of the TCP header is that hosts can still communicate using TCP even if they do not implement the options.
[5.2_s0384] Hosts that do implement the optional extensions, however, can take advantage of them.
[5.2_s0385] The two sides agree that they will use the options during TCP’s connection establishment phase.
[5.2_s0386] The first extension helps to improve TCP’s timeout mechanism.
[5.2_s0387] Instead of measuring the RTT using a coarse-grained event, TCP can read the actual system clock when it is about to send a segment, and put this time—think of it as a 32-bit timestamp\ —in the segment’s header.
[5.2_s0388] The receiver then echoes this timestamp back to the sender in its acknowledgment, and the sender subtracts this timestamp from the current time to measure the RTT.
[5.2_s0389] In essence, the timestamp option provides a convenient place for TCP to store the record of when a segment was transmitted; it stores the time in the segment itself.
[5.2_s0390] Note that the endpoints in the connection do not need synchronized clocks, since the timestamp is written and read at the same end of the connection.
[5.2_s0391] The second extension addresses the problem of TCP’s 32-bit SequenceNum field wrapping around too soon on a high-speed network.
[5.2_s0392] Rather than define a new 64-bit sequence number field, TCP uses the 32-bit timestamp just described to effectively extend the sequence number space.
[5.2_s0393] In other words, TCP decides whether to accept or reject a segment based on a 64-bit identifier that has the SequenceNum field in the low-order 32 bits and the timestamp in the high-order 32 bits.
[5.2_s0394] Since the timestamp is always increasing, it serves to distinguish between two different incarnations of the same sequence number.
[5.2_s0395] Note that the timestamp is being used in this setting only to protect against wraparound; it is not treated as part of the sequence number for the purpose of ordering or acknowledging data.
[5.2_s0396] The third extension allows TCP to advertise a larger window, thereby allowing it to fill larger delay × bandwidth pipes that are made possible by high-speed networks.
[5.2_s0397] This extension involves an option that defines a scaling factor for the advertised window.
[5.2_s0398] That is, rather than interpreting the number that appears in the AdvertisedWindow field as indicating how many bytes the sender is allowed to have unacknowledged, this option allows the two sides of TCP to agree that the AdvertisedWindow field counts larger chunks (e.g., how many 16-byte units of data the sender can have unacknowledged).
[5.2_s0399] In other words, the window scaling option specifies how many bits each side should left-shift the AdvertisedWindow field before using its contents to compute an effective window.
[5.2_s0400] The fourth extension allows TCP to augment its cumulative acknowledgment with selective acknowledgments of any additional segments that have been received but aren’t contiguous with all previously received segments.
[5.2_s0401] This is the selective acknowledgment, or SACK, option.
[5.2_s0402] When the SACK option is used, the receiver continues to acknowledge segments normally—the meaning of the Acknowledge field does not change—but it also uses optional fields in the header to acknowledge any additional blocks of received data.
[5.2_s0403] This allows the sender to retransmit just the segments that are missing according to the selective acknowledgment.
[5.2_s0404] Without SACK, there are only two reasonable strategies for a sender.
[5.2_s0405] The pessimistic strategy responds to a timeout by retransmitting not just the segment that timed out, but any segments transmitted subsequently.
[5.2_s0406] In effect, the pessimistic strategy assumes the worst: that all those segments were lost.
[5.2_s0407] The disadvantage of the pessimistic strategy is that it may unnecessarily retransmit segments that were successfully received the first time.
[5.2_s0408] The other strategy is the optimistic strategy, which responds to a timeout by retransmitting only the segment that timed out.
[5.2_s0409] In effect, the optimistic approach assumes the rosiest scenario: that only the one segment has been lost.
[5.2_s0410] The disadvantage of the optimistic strategy is that it is very slow, unnecessarily, when a series of consecutive segments has been lost, as might happen when there is congestion.
[5.2_s0411] It is slow because each segment’s loss is not discovered until the sender receives an ACK for its retransmission of the previous segment.
[5.2_s0412] So it consumes one RTT per segment until it has retransmitted all the segments in the lost series.
[5.2_s0413] With the SACK option, a better strategy is available to the sender: retransmit just the segments that fill the gaps between the segments that have been selectively acknowledged.
[5.2_s0414] These extensions, by the way, are not the full story.
[5.2_s0415] We’ll see some more extensions in the next chapter when we look at how TCP handles congestion.
[5.2_s0416] The Internet Assigned Numbers Authority (IANA) keeps track of all the options that are defined for TCP (and for many other Internet protocols).
[5.2_s0417] See the references at the end of the chapter for a link to IANA’s protocol number registry.

[5.2_s0419] Performance  Recall that Chapter 1 introduced the two quantitative metrics by which network performance is evaluated: latency and throughput.
[5.2_s0420] As mentioned in that discussion, these metrics are influenced not only by the underlying hardware (e.g., propagation delay and link bandwidth) but also by software overheads.
[5.2_s0421] Now that we have a complete software-based protocol graph available to us that includes alternative transport protocols, we can discuss how to meaningfully measure its performance.
[5.2_s0422] The importance of such measurements is that they represent the performance seen by application programs.

[5.2_s0426] The Ethernet spans a single machine room so propagation is not an issue, making this a measure of processor/software overheads.
[5.2_s0427] A test program running on top of the socket interface simply tries to transfer data as quickly as possible from one machine to the other.

[5.2_s0430] The point of this section is not to show how fast a particular protocol can run, but to illustrate the general methodology for measuring and reporting protocol performance.
[5.2_s0431] The throughput test is performed for a variety of message sizes using a standard benchmarking tool called TTCP.

[5.2_s0438] For example, looking at CPU load might give an indication of whether the CPU is the bottleneck or whether memory bandwidth, adaptor performance, or some other issue is to blame.
[5.2_s0439] We also note that the network in this test is basically “perfect.”
[5.2_s0440] It has almost no delay or loss, so the only factors affecting performance are the TCP implementation and the workstation hardware and software.
[5.2_s0441] By contrast, most of the time we deal with networks that are far from perfect, notably our bandwidth-constrained, last-mile links and loss-prone wireless links.
[5.2_s0442] Before we can fully appreciate how these links affect TCP performance, we need to understand how TCP deals with congestion, which is the topic of the next chapter.
[5.2_s0443] At various times in the history of networking, the steadily increasing speed of network links has threatened to run ahead of what could be delivered to applications.
[5.2_s0444] For example, a large research effort was begun in the United States in 1989 to build “gigabit networks,” where the goal was not only to build links and switches that could run at 1Gbps or higher but also to deliver that throughput all the way to a single application process.
[5.2_s0445] There were some real problems (e.g., network adaptors, workstation architectures, and operating systems all had to be designed with network-to-application throughput in mind) and also some perceived problems that turned out to be not so serious.
[5.2_s0446] High on the list of such problems was the concern that existing transport protocols, TCP in particular, might not be up to the challenge of gigabit operation.
[5.2_s0447] As it turns out, TCP has done well keeping up with the increasing demands of high-speed networks and applications.
[5.2_s0448] One of the most important factors was the introduction of window scaling to deal with larger bandwidth-delay products.
[5.2_s0449] However, there is often a big difference between the theoretical performance of TCP and what is achieved in practice.
[5.2_s0450] Relatively simple problems like copying the data more times than necessary as it passes from network adaptor to application can drive down performance, as can insufficient buffer memory when the bandwidth-delay product is large.
[5.2_s0451] And the dynamics of TCP are complex enough (as will become even more apparent in the next chapter) that subtle interactions among network behavior, application behavior, and the TCP protocol itself can dramatically alter performance.
[5.2_s0452] For our purposes, it’s worth noting that TCP continues to perform very well as network speeds increase, and when it runs up against some limit (normally related to congestion, increasing bandwidth-delay products, or both), researchers rush in to find solutions.
[5.2_s0453] We’ve seen some of those in this chapter, and we’ll see some more in the next.
[5.2_s0454] 5.2.10 Alternative Design Choices (SCTP, QUIC)
[5.2_s0455] Although TCP has proven to be a robust protocol that satisfies the needs of a wide range of applications, the design space for transport protocols is quite large.
[5.2_s0456] TCP is by no means the only valid point in that design space.
[5.2_s0457] We conclude our discussion of TCP by considering alternative design choices.
[5.2_s0458] While we offer an explanation for why TCP’s designers made the choices they did, we observe that other protocols exist that have made other choices, and more such protocols may appear in the future.
[5.2_s0459] First, we have suggested from the very first chapter of this book that there are at least two interesting classes of transport protocols: stream-oriented protocols like TCP and request/reply protocols like RPC.
[5.2_s0460] In other words, we have implicitly divided the design space in half and placed TCP squarely in the stream-oriented half of the world.
[5.2_s0461] We could further divide the stream-oriented protocols into two groups—reliable and unreliable—with the former containing TCP and the latter being more suitable for interactive video applications that would rather drop a frame than incur the delay associated with a retransmission.
[5.2_s0462] This exercise in building a transport protocol taxonomy is interesting and could be continued in greater and greater detail, but the world isn’t as black and white as we might like.
[5.2_s0463] Consider the suitability of TCP as a transport protocol for request/reply applications, for example.
[5.2_s0464] TCP is a full-duplex protocol, so it would be easy to open a TCP connection between the client and server, send the request message in one direction, and send the reply message in the other direction.
[5.2_s0465] There are two complications, however.
[5.2_s0466] The first is that TCP is a byte-oriented protocol rather than a message-oriented protocol, and request/reply applications always deal with messages.
[5.2_s0467] (We explore the issue of bytes versus messages in greater detail in a moment.)
[5.2_s0468] The second complication is that in those situations where both the request message and the reply message fit in a single network packet, a well-designed request/reply protocol needs only two packets to implement the exchange, whereas TCP would need at least nine: three to establish the connection, two for the message exchange, and four to tear down the connection.
[5.2_s0469] Of course, if the request or reply messages are large enough to require multiple network packets (e.g., it might take 100 packets to send a 100,000-byte reply message), then the overhead of setting up and tearing down the connection is inconsequential.
[5.2_s0470] In other words, it isn’t always the case that a particular protocol cannot support a certain functionality; it’s sometimes the case that one design is more efficient than another under particular circumstances.
[5.2_s0471] Second, as just suggested, you might question why TCP chose to provide a reliable byte-stream service rather than a reliable message-stream service; messages would be the natural choice for a database application that wants to exchange records.
[5.2_s0472] There are two answers to this question.
[5.2_s0473] The first is that a message-oriented protocol must, by definition, establish an upper bound on message sizes.
[5.2_s0474] After all, an infinitely long message is a byte stream.
[5.2_s0475] For any message size that a protocol selects, there will be applications that want to send larger messages, rendering the transport protocol useless and forcing the application to implement its own transport-like services.
[5.2_s0476] The second reason is that, while message-oriented protocols are definitely more appropriate for applications that want to send records to each other, you can easily insert record boundaries into a byte stream to implement this functionality.
[5.2_s0477] A third decision made in the design of TCP is that it delivers bytes in order to the application.
[5.2_s0478] This means that it may hold onto bytes that were received out of order from the network, awaiting some missing bytes to fill a hole.
[5.2_s0479] This is enormously helpful for many applications but turns out to be quite unhelpful if the application is capable of processing data out of order.
[5.2_s0480] As a simple example, a Web page containing multiple embedded objects doesn’t need all the objects to be delivered in order before starting to display the page.
[5.2_s0481] In fact, there is a class of applications that would prefer to handle out-of-order data at the application layer, in return for getting data sooner when packets are dropped or misordered within the network.
[5.2_s0482] The desire to support such applications led to the creation of not one but two IETF standard transport protocols.
[5.2_s0483] The first of these was SCTP, the Stream Control Transmission Protocol.
[5.2_s0484] SCTP provides a partially ordered delivery service, rather than the strictly ordered service of TCP.  (SCTP also makes some other design decisions that differ from TCP, including message orientation and support of multiple IP addresses for a single session.)
[5.2_s0485] More recently, the IETF has been standardizing a protocol optimized for Web traffic, known as QUIC.
[5.2_s0486] More on QUIC in a moment.
[5.2_s0487] Fourth, TCP chose to implement explicit setup/teardown phases, but this is not required.
[5.2_s0488] In the case of connection setup, it would be possible to send all necessary connection parameters along with the first data message.
[5.2_s0489] TCP elected to take a more conservative approach that gives the receiver the opportunity to reject the connection before any data arrives.
[5.2_s0490] In the case of teardown, we could quietly close a connection that has been inactive for a long period of time, but this would complicate applications like remote login that want to keep a connection alive for weeks at a time; such applications would be forced to send out-of-band “keep alive” messages to keep the connection state at the other end from disappearing.
[5.2_s0491] Finally, TCP is a window-based protocol, but this is not the only possibility.
[5.2_s0492] The alternative is a rate-based design, in which the receiver tells the sender the rate—expressed in either bytes or packets per second—at which it is willing to accept incoming data.
[5.2_s0493] For example, the receiver might inform the sender that it can accommodate 100 packets a second.
[5.2_s0494] There is an interesting duality between windows and rate, since the number of packets (bytes) in the window, divided by the RTT, is exactly the rate.
[5.2_s0495] For example, a window size of 10 packets and a 100-ms RTT implies that the sender is allowed to transmit at a rate of 100 packets a second.
[5.2_s0496] It is by increasing or decreasing the advertised window size that the receiver is effectively raising or lowering the rate at which the sender can transmit.
[5.2_s0497] In TCP, this information is fed back to the sender in the AdvertisedWindow field of the ACK for every segment.
[5.2_s0498] One of the key issues in a rate-based protocol is how often the desired rate—which may change over time—is relayed back to the source: Is it for every packet, once per RTT, or only when the rate changes?
[5.2_s0499] While we have just now considered window versus rate in the context of flow control, it is an even more hotly contested issue in the context of congestion control, which we will discuss in the next chapter.
[5.2_s0500] QUIC  QUIC originated at Google in 2012 and was subsequently developed as a proposed standard at the IETF.
[5.2_s0501] Unlike many other efforts to add to the set of transport protocols in the Internet, QUIC has achieved widespread deployment.
[5.2_s0502] As discussed further in Chapter 9, QUIC was motivated in large part by the challenges of matching the request/response semantics of HTTP to the stream-oriented nature of TCP.
[5.2_s0503] These issues have become more noticeable over time, due to factors such as the rise of high-latency wireless networks, the availability of multiple networks for a single device (e.g., Wi-Fi and cellular), and the increasing use of encrypted, authenticated connections on the Web (as discussed in Chapter 8).
[5.2_s0504] While a full description of QUIC is beyond our scope, some of the key design decisions are worth discussing.
[5.2_s0505] If network latency is high—say 100 milliseconds or more—then a few RTTs can quickly add up to a visible annoyance for an end user.
[5.2_s0506] Establishing an HTTP session over TCP with Transport Layer Security (Section 8.5) would typically take at least three round trips (one for TCP session establishment and two for setting up the encryption parameters) before the first HTTP message could be sent.
[5.2_s0507] The designers of QUIC recognized that this delay—the direct result of a layered approach to protocol design—could be dramatically reduced if connection setup and the required security handshakes were combined and optimized for minimal round trips.
[5.2_s0508] Note also how the presence of multiple network interfaces might affect the design.
[5.2_s0509] If your mobile phone loses its Wi-Fi connection and needs to switch to a cellular connection, that would typically require both a TCP timeout on one connection and a new series of handshakes on the other.
[5.2_s0510] Making the connection something that can persist over different network layer connections was another design goal for QUIC.
[5.2_s0511] Finally, as noted above, the reliable byte stream model for TCP is a poor match to a Web page request, when many objects need to be fetched and page rendering could begin before they have all arrived.
[5.2_s0512] While one workaround for this would be to open multiple TCP connections in parallel, this approach (which was used in the early days of the Web) has its own set of drawbacks, notably on congestion control (see Chapter 6).
[5.2_s0513] Specifically, each connection runs its own congestion control loop, so the experience of congestion on one connection is not apparent to the other connections, and each connection tries to figure out the appropriate amount of bandwidth to consume on its own.
[5.2_s0514] QUIC introduced the idea of streams within a connection, so that objects could be delivered out-of-order while maintaining a holistic view of congestion across all the streams.
[5.2_s0515] Interestingly, by the time QUIC emerged, many design decisions had been made that presented challenges for the deployment of a new transport protocol.
[5.2_s0516] Notably, many "middleboxes'' such as NATs and firewalls (see Section 8.5) have enough understanding of the existing widespread transport protocols (TCP and UDP) that they can't be relied upon to pass a new transport protocol.
[5.2_s0517] As a result, QUIC actually rides on top of UDP.
[5.2_s0518] In other words, it is a transport protocol running on top of a transport protocol.
[5.2_s0519] This is not as uncommon as our focus on layering might suggest, as the next two subsections also illustrate.
[5.2_s0520] This choice was made in the interests of making QUIC deployable on the Internet as it exists, and has been quite successful.
[5.2_s0521] QUIC implements fast connection establishment with encryption and authentication in the first RTT.
[5.2_s0522] It provides a connection identifier that persists across changes in the underlying network.
[5.2_s0523] It supports the multiplexing of several streams onto a single transport connection, to avoid the head-of-line blocking that may arise when a single packet is dropped while other useful data continues to arrive.
[5.2_s0524] And it preserves (and in some ways improves on) the congestion avoidance properties of TCP, an important aspect of transport protocols that we return to in Chapter 6.  HTTP went through a number of versions (1.0, 1.1, 2.0, discussed in Section 9.1) in an effort to map its requirements more cleanly onto the capabilities of TCP.
[5.2_s0525] With the arrival of QUIC, HTTP/3 is now able to leverage a transport layer that was explicitly designed to meet the application requirements of the Web.
[5.2_s0526] QUIC is a most interesting development in the world of transport protocols.
[5.2_s0527] Many of the limitations of TCP have been known for decades, but QUIC represents one of the most successful efforts to date to stake out a different point in the design space.
[5.2_s0528] Because QUIC was inspired by experience with HTTP and the Web—which arose long after TCP was well established in the Internet—it presents a fascinating case study in the unforeseen consequences of layered designs and in the evolution of the Internet.
=== SECTION 6.5: Congestion Control > Quality of Service ===
[6.5_s0000] The promise of general-purpose packet-switched networks is that they support all kinds of applications and data, including multimedia applications that transmit digitized audio and video streams.
[6.5_s0001] In the early days, one obstacle to the fulfillment of this promise was the need for higher-bandwidth links.
[6.5_s0002] That is no longer an issue, but there is more to transmitting audio and video over a network than just providing sufficient bandwidth.
[6.5_s0003] Participants in a telephone conversation, for example, expect to be able to converse in such a way that one person can respond to something said by the other and be heard almost immediately.
[6.5_s0004] Thus, the timeliness of delivery can be very important.
[6.5_s0005] We refer to applications that are sensitive to the timeliness of data as real-time applications.
[6.5_s0006] Voice and video applications tend to be the canonical examples, but there are others such as industrial control—you would like a command sent to a robot arm to reach it before the arm crashes into something.
[6.5_s0007] Even file transfer applications can have timeliness constraints, such as a requirement that a database update complete overnight before the business that needs the data resumes on the next day.
[6.5_s0008] The distinguishing characteristic of real-time applications is that they need some sort of assurance from the network that data is likely to arrive on time (for some definition of “on time”).
[6.5_s0009] Whereas a non-real-time application can use an end-to-end retransmission strategy to make sure that data arrives correctly, such a strategy cannot provide timeliness: Retransmission only adds to total latency if data arrives late.
[6.5_s0010] Timely arrival must be provided by the network itself (the routers), not just at the network edges (the hosts).
[6.5_s0011] We therefore conclude that the best-effort model, in which the network tries to deliver your data but makes no promises and leaves the cleanup operation to the edges, is not sufficient for real-time applications.
[6.5_s0012] What we need is a new service model, in which applications that need higher assurances can ask the network for them.
[6.5_s0013] The network may then respond by providing an assurance that it will do better or perhaps by saying that it cannot promise anything better at the moment.
[6.5_s0014] Note that such a service model is a superset of the original model: Applications that are happy with best-effort service should be able to use the new service model; their requirements are just less stringent.
[6.5_s0015] This implies that the network will treat some packets differently from others—something that is not done in the best-effort model.
[6.5_s0016] A network that can provide these different levels of service is often said to support quality of service (QoS).
[6.5_s0017] 6.5.1 Application Requirements  Before looking at the various protocols and mechanisms that may be used to provide quality of service to applications, we should try to understand what the needs of those applications are.
[6.5_s0018] To begin, we can divide applications into two types: real-time and non-real-time.
[6.5_s0019] The latter are sometimes called traditional data applications, since they have traditionally been the major applications found on data networks.
[6.5_s0020] They include most popular applications like SSH, file transfer, email, web browsing, and so on.
[6.5_s0021] All of these applications can work without guarantees of timely delivery of data.
[6.5_s0022] Another term for this non-real-time class of applications is elastic, since they are able to stretch gracefully in the face of increased delay.
[6.5_s0023] Note that these applications can benefit from shorter-length delays, but they do not become unusable as delays increase.
[6.5_s0024] Also note that their delay requirements vary from the interactive applications like SSH to more asynchronous ones like email, with interactive bulk transfers like file transfer in the middle.
[6.5_s0025] Real-Time Audio Example  As a concrete example of a real-time application, consider an audio application similar to the one illustrated in Figure.
[6.5_s0026] Data is generated by collecting samples from a microphone and digitizing them using an analog-to-digital (A-to-D) converter.
[6.5_s0027] The digital samples are placed in packets, which are transmitted across the network and received at the other end.
[6.5_s0028] At the receiving host, the data must be played back at some appropriate rate.
[6.5_s0029] For example, if the voice samples were collected at a rate of one per 125 μs, they should be played back at the same rate.
[6.5_s0030] Thus, we can think of each sample as having a particular playback time: the point in time at which it is needed in the receiving host.
[6.5_s0031] In the voice example, each sample has a playback time that is 125 μs later than the preceding sample.
[6.5_s0032] If data arrives after its appropriate playback time, either because it was delayed in the network or because it was dropped and subsequently retransmitted, it is essentially useless.
[6.5_s0033] It is the complete worthlessness of late data that characterizes real-time applications.
[6.5_s0034] In elastic applications, it might be nice if data turns up on time, but we can still use it when it does not.
[6.5_s0035] One way to make our voice application work would be to make sure all samples take exactly the same amount of time to traverse the network.
[6.5_s0036] Then, since samples are injected at a rate of one per 125 μs, they will appear at the receiver at the same rate, ready to be played back.
[6.5_s0037] However, it is generally difficult to guarantee that all data traversing a packet-switched network will experience exactly the same delay.
[6.5_s0038] Packets encounter queues in switches or routers, and the lengths of these queues vary with time, meaning that the delays tend to vary with time and, as a consequence, are potentially different for each packet in the audio stream.
[6.5_s0039] The way to deal with this at the receiver end is to buffer up some amount of data in reserve, thereby always providing a store of packets waiting to be played back at the right time.
[6.5_s0040] If a packet is delayed a short time, it goes in the buffer until its playback time arrives.
[6.5_s0041] If it gets delayed a long time, then it will not need to be stored for very long in the receiver’s buffer before being played back.
[6.5_s0042] Thus, we have effectively added a constant offset to the playback time of all packets as a form of insurance.
[6.5_s0043] We call this offset the playback point.
[6.5_s0044] The only time we run into trouble is if packets get delayed in the network for such a long time that they arrive after their playback time, causing the playback buffer to be drained.
[6.5_s0045] The operation of a playback buffer is illustrated in Figure.
[6.5_s0046] The left-hand diagonal line shows packets being generated at a steady rate.
[6.5_s0047] The wavy line shows when the packets arrive, some variable amount of time after they were sent, depending on what they encountered in the network.
[6.5_s0048] The right-hand diagonal line shows the packets being played back at a steady rate, after sitting in the playback buffer for some period of time.
[6.5_s0049] As long as the playback line is far enough to the right in time, the variation in network delay is never noticed by the application.
[6.5_s0050] However, if we move the playback line a little to the left, then some packets will begin to arrive too late to be useful.
[6.5_s0051] For our audio application, there are limits to how far we can delay playing back data.
[6.5_s0052] It is hard to carry on a conversation if the time between when you speak and when your listener hears you is more than 300 ms.
[6.5_s0053] Thus, what we want from the network in this case is a guarantee that all our data will arrive within 300 ms.
[6.5_s0054] If data arrives early, we buffer it until its correct playback time.
[6.5_s0055] If it arrives late, we have no use for it and must discard it.
[6.5_s0056] To get a better appreciation of how variable network delay can be, Figure shows the one-way delay measured over a certain path across the Internet over the course of one particular day.
[6.5_s0057] While the exact numbers would vary depending on the path and the date, the key factor here is the variability of the delay, which is consistently found on almost any path at any time.
[6.5_s0058] As denoted by the cumulative percentages given across the top of the graph, 97% of the packets in this case had a latency of 100 ms or less.
[6.5_s0059] This means that if our example audio application were to set the playback point at 100 ms, then, on average, 3 out of every 100 packets would arrive too late to be of any use.
[6.5_s0060] One important thing to notice about this graph is that the tail of the curve—how far it extends to the right—is very long.
[6.5_s0061] We would have to set the playback point at over 200 ms to ensure that all packets arrived in time.
[6.5_s0062] Taxonomy of Real-Time Applications  Now that we have a concrete idea of how real-time applications work, we can look at some different classes of applications that serve to motivate our service model.
[6.5_s0063] The following taxonomy owes much to the work of Clark, Braden, Shenker, and Zhang, whose papers on this subject can be found in the Further Reading section for this chapter.
[6.5_s0064] The taxonomy of applications is summarized in Figure.
[6.5_s0065] The first characteristic by which we can categorize applications is their tolerance of loss of data, where “loss” might occur because a packet arrived too late to be played back as well as arising from the usual causes in the network.
[6.5_s0066] On the one hand, one lost audio sample can be interpolated from the surrounding samples with relatively little effect on the perceived audio quality.
[6.5_s0067] It is only as more and more samples are lost that quality declines to the point that the speech becomes incomprehensible.
[6.5_s0068] On the other hand, a robot control program is likely to be an example of a real-time application that cannot tolerate loss—losing the packet that contains the command instructing the robot arm to stop is unacceptable.
[6.5_s0069] Thus, we can categorize real-time applications as tolerant or intolerant depending on whether they can tolerate occasional loss.
[6.5_s0070] (As an aside, note that many real-time applications are more tolerant of occasional loss than non-real-time applications; for example, compare our audio application to file transfer, where the uncorrected loss of one bit might render a file completely useless.)
[6.5_s0071] A second way to characterize real-time applications is by their adaptability.
[6.5_s0072] For example, an audio application might be able to adapt to the amount of delay that packets experience as they traverse the network.
[6.5_s0073] If we notice that packets are almost always arriving within 300 ms of being sent, then we can set our playback point accordingly, buffering any packets that arrive in less than 300 ms.
[6.5_s0074] Suppose that we subsequently observe that all packets are arriving within 100 ms of being sent.
[6.5_s0075] If we moved up our playback point to 100 ms, then the users of the application would probably perceive an improvement.
[6.5_s0076] The process of shifting the playback point would actually require us to play out samples at an increased rate for some period of time.
[6.5_s0077] With a voice application, this can be done in a way that is barely perceptible, simply by shortening the silences between words.
[6.5_s0078] Thus, playback point adjustment is fairly easy in this case, and it has been effectively implemented for several voice applications such as the audio teleconferencing program known as vat.
[6.5_s0079] Note that playback point adjustment can happen in either direction, but that doing so actually involves distorting the played-back signal during the period of adjustment, and that the effects of this distortion will very much depend on how the end user uses the data.
[6.5_s0080] Observe that if we set our playback point on the assumption that all packets will arrive within 100 ms and then find that some packets are arriving slightly late, we will have to drop them, whereas we would not have had to drop them if we had left the playback point at 300 ms.
[6.5_s0081] Thus, we should advance the playback point only when it provides a perceptible advantage and only when we have some evidence that the number of late packets will be acceptably small.
[6.5_s0082] We may do this because of observed recent history or because of some assurance from the network.
[6.5_s0083] We call applications that can adjust their playback point delay-adaptive applications.
[6.5_s0084] Another class of adaptive applications is rate adaptive.
[6.5_s0085] For example, many video coding algorithms can trade off bit rate versus quality.
[6.5_s0086] Thus, if we find that the network can support a certain bandwidth, we can set our coding parameters accordingly.
[6.5_s0087] If more bandwidth becomes available later, we can change parameters to increase the quality.
[6.5_s0088] Approaches to QoS Support  Considering this rich space of application requirements, what we need is a richer service model that meets the needs of any application.
[6.5_s0089] This leads us to a service model with not just one class (best effort), but with several classes, each available to meet the needs of some set of applications.
[6.5_s0090] Towards this end, we are now ready to look at some of the approaches that have been developed to provide a range of qualities of service.
[6.5_s0091] These can be divided into two broad categories:  -  Fine-grained approaches, which provide QoS to individual applications or flows  -  Coarse-grained approaches, which provide QoS to large classes of data or aggregated traffic  In the first category, we find Integrated Services, a QoS architecture developed in the IETF and often associated with the Resource Reservation Protocol (RSVP).
[6.5_s0092] In the second category lies Differentiated Services, which is probably the most widely deployed QoS mechanism today.
[6.5_s0093] We discuss these in turn in the next two subsections.
[6.5_s0094] Finally, as we suggested at the start of this section, adding QoS support to the network isn’t necessarily the entire story about supporting real-time applications.
[6.5_s0095] We conclude our discussion by revisiting what the end-host might do to better support real-time streams, independent of how widely deployed QoS mechanisms like Integrated or Differentiated Services become.
[6.5_s0096] 6.5.2 Integrated Services (RSVP)
[6.5_s0097] The term Integrated Services (often called IntServ for short) refers to a body of work that was produced by the IETF around 1995-97.
[6.5_s0098] The IntServ working group developed specifications of a number of service classes designed to meet the needs of some of the application types described above.
[6.5_s0099] It also defined how RSVP could be used to make reservations using these service classes.
[6.5_s0100] The following paragraphs provide an overview of these specifications and the mechanisms that are used to implement them.
[6.5_s0101] Service Classes  One of the service classes is designed for intolerant applications.
[6.5_s0102] These applications require that a packet never arrive late.
[6.5_s0103] The network should guarantee that the maximum delay that any packet will experience has some specified value; the application can then set its playback point so that no packet will ever arrive after its playback time.
[6.5_s0104] We assume that early arrival of packets can always be handled by buffering.
[6.5_s0105] This service is referred to as the guaranteed service.
[6.5_s0106] In addition to the guaranteed service, the IETF considered several other services, but eventually settled on one to meet the needs of tolerant, adaptive applications.
[6.5_s0107] The service is known as controlled load and was motivated by the observation that existing applications of this type run quite well on networks that are not heavily loaded.
[6.5_s0108] Audio applications, for example, adjust their playback point as network delay varies and produces reasonable audio quality as long as loss rates remain on the order of 10% or less.
[6.5_s0109] The aim of the controlled load service is to emulate a lightly loaded network for those applications that request the service, even though the network as a whole may in fact be heavily loaded.
[6.5_s0110] The trick to this is to use a queuing mechanism such as WFQ to isolate the controlled load traffic from the other traffic and some form of admission control to limit the total amount of controlled load traffic on a link such that the load is kept reasonably low.
[6.5_s0111] We discuss admission control in more detail below.
[6.5_s0112] Clearly, these two service classes are a subset of all the classes that might be provided.
[6.5_s0113] In fact, other services were specified but never standardized as part of the IETF’s work.
[6.5_s0114] So far, the two services described above (along with traditional best effort) have proven flexible enough to meet the needs of a wide range of applications.
[6.5_s0115] Overview of Mechanisms  Now that we have augmented our best-effort service model with some new service classes, the next question is how we implement a network that provides these services to applications.
[6.5_s0116] This section outlines the key mechanisms.
[6.5_s0117] Keep in mind while reading this section that the mechanisms being described are still being hammered out by the Internet design community.
[6.5_s0118] The main thing to take away from the discussion is a general understanding of the pieces involved in supporting the service model outlined above.
[6.5_s0119] First, whereas with a best-effort service we can just tell the network where we want our packets to go and leave it at that, a real-time service involves telling the network something more about the type of service we require.
[6.5_s0120] We may give it qualitative information such as “use a controlled load service” or quantitative information such as “I need a maximum delay of 100 ms.”
[6.5_s0121] In addition to describing what we want, we need to tell the network something about what we are going to inject into it, since a low-bandwidth application is going to require fewer network resources than a high-bandwidth application.
[6.5_s0122] The set of information that we provide to the network is referred to as a flowspec.
[6.5_s0123] This name comes from the idea that a set of packets associated with a single application and that share common requirements is called a flow, consistent with our use of the term in the earlier section outlining the relevant issues.
[6.5_s0124] Second, when we ask the network to provide us with a particular service, the network needs to decide if it can in fact provide that service.
[6.5_s0125] For example, if 10 users ask for a service in which each will consistently use 2 Mbps of link capacity, and they all share a link with 10-Mbps capacity, the network will have to say no to some of them.
[6.5_s0126] The process of deciding when to say no is called admission control.
[6.5_s0127] Third, we need a mechanism by which the users of the network and the components of the network itself exchange information such as requests for service, flowspecs, and admission control decisions.
[6.5_s0128] This is sometimes called signalling, but since that word has several meanings, we refer to this process as resource reservation, and it is achieved using a resource reservation protocol.
[6.5_s0129] Finally, when flows and their requirements have been described, and admission control decisions have been made, the network switches and routers need to meet the requirements of the flows.
[6.5_s0130] A key part of meeting these requirements is managing the way packets are queued and scheduled for transmission in the switches and routers.
[6.5_s0131] This last mechanism is packet scheduling.
[6.5_s0132] Flowspecs  There are two separable parts to the flowspec: the part that describes the flow’s traffic characteristics (called the TSpec) and the part that describes the service requested from the network (the RSpec).
[6.5_s0133] The RSpec is very service specific and relatively easy to describe.
[6.5_s0134] For example, with a controlled load service, the RSpec is trivial: The application just requests controlled load service with no additional parameters.
[6.5_s0135] With a guaranteed service, you could specify a delay target or bound.
[6.5_s0136] (In the IETF’s guaranteed service specification, you specify not a delay but another quantity from which delay can be calculated.)
[6.5_s0137] The TSpec is a little more complicated.
[6.5_s0138] As our example above showed, we need to give the network enough information about the bandwidth used by the flow to allow intelligent admission control decisions to be made.
[6.5_s0139] For most applications, however, the bandwidth is not a single number; it is something that varies constantly.
[6.5_s0140] A video application, for example, will generally generate more bits per second when the scene is changing rapidly than when it is still.
[6.5_s0141] Just knowing the long-term average bandwidth is not enough, as the following example illustrates.
[6.5_s0142] Suppose that we have 10 flows that arrive at a switch on separate input ports and that all leave on the same 10-Mbps link.
[6.5_s0143] Assume that over some suitably long interval each flow can be expected to send no more than 1 Mbps.
[6.5_s0144] You might think that this presents no problem.
[6.5_s0145] However, if these are variable bit rate applications, such as compressed video, then they will occasionally send more than their average rates.
[6.5_s0146] If enough sources send at above their average rates, then the total rate at which data arrives at the switch will be greater than 10 Mbps.
[6.5_s0147] This excess data will be queued before it can be sent on the link.
[6.5_s0148] The longer this condition persists, the longer the queue will get.
[6.5_s0149] Packets might have to be dropped and, even if it doesn’t come to that, data sitting in the queue is being delayed.
[6.5_s0150] If packets are delayed long enough, the service that was requested will not be provided.
[6.5_s0151] Exactly how we manage our queues to control delay and avoid dropping packets is something we discuss below.
[6.5_s0152] However, note here that we need to know something about how the bandwidth of our sources varies with time.
[6.5_s0153] One way to describe the bandwidth characteristics of sources is called a token bucket filter.
[6.5_s0154] Such a filter is described by two parameters: a token rate r, and a bucket depth B.
[6.5_s0155] It works as follows.
[6.5_s0156] To be able to send a byte, I must have a token.
[6.5_s0157] To send a packet of length n, I need n tokens.
[6.5_s0158] I start with no tokens and I accumulate them at a rate of r per second.
[6.5_s0159] I can accumulate no more than B tokens.
[6.5_s0160] What this means is that I can send a burst of as many as B bytes into the network as fast as I want, but over a sufficiently long interval I can’t send more than r bytes per second.
[6.5_s0161] It turns out that this information is very helpful to the admission control algorithm when it tries to figure out whether it can accommodate a new request for service.
[6.5_s0162] Figure illustrates how a token bucket can be used to characterize a flow’s bandwidth requirements.
[6.5_s0163] For simplicity, assume that each flow can send data as individual bytes rather than as packets.
[6.5_s0164] Flow A generates data at a steady rate of 1 MBps, so it can be described by a token bucket filter with a rate r = 1 MBps and a bucket depth of 1 byte.
[6.5_s0165] This means that it receives tokens at a rate of 1 MBps but that it cannot store more than 1 token—it spends them immediately.
[6.5_s0166] Flow B also sends at a rate that averages out to 1 MBps over the long term, but does so by sending at 0.5 MBps for 2 seconds and then at 2 MBps for 1 second.
[6.5_s0167] Since the token bucket rate r is, in a sense, a long-term average rate, flow B can be described by a token bucket with a rate of 1 MBps.
[6.5_s0168] Unlike flow A, however, flow B needs a bucket depth B of at least 1 MB, so that it can store up tokens while it sends at less than 1 MBps to be used when it sends at 2 MBps.
[6.5_s0169] For the first 2 seconds in this example, it receives tokens at a rate of 1 MBps but spends them at only 0.5 MBps, so it can save up 2 × 0.5 = 1 MB of tokens, which it then spends in the third second (along with the new tokens that continue to accrue in that second) to send data at 2 MBps.
[6.5_s0170] At the end of the third second, having spent the excess tokens, it starts to save them up again by sending at 0.5 MBps again.
[6.5_s0171] It is interesting to note that a single flow can be described by many different token buckets.
[6.5_s0172] As a trivial example, flow A could be described by the same token bucket as flow B, with a rate of 1 MBps and a bucket depth of 1 MB.
[6.5_s0173] The fact that it never actually needs to accumulate tokens does not make that an inaccurate description, but it does mean that we have failed to convey some useful information to the network—the fact that flow A is actually very consistent in its bandwidth needs.
[6.5_s0174] In general, it is good to be as explicit about the bandwidth needs of an application as possible to avoid over-allocation of resources in the network.
[6.5_s0175] Admission Control
[6.5_s0176] The idea behind admission control is simple: When some new flow wants to receive a particular level of service, admission control looks at the TSpec and RSpec of the flow and tries to decide if the desired service can be provided to that amount of traffic, given the currently available resources, without causing any previously admitted flow to receive worse service than it had requested.
[6.5_s0177] If it can provide the service, the flow is admitted; if not, then it is denied.
[6.5_s0178] The hard part is figuring out when to say yes and when to say no.
[6.5_s0179] Admission control is very dependent on the type of requested service and on the queuing discipline employed in the routers; we discuss the latter topic later in this section.
[6.5_s0180] For a guaranteed service, you need to have a good algorithm to make a definitive yes/no decision.
[6.5_s0181] The decision is fairly straightforward if weighted fair queuing is used at each router.
[6.5_s0182] For a controlled load service, the decision may be based on heuristics, such as “The last time I allowed a flow with this TSpec into this class, the delays for the class exceeded the acceptable bound, so I’d better say no” or “My current delays are so far inside the bounds that I should be able to admit another flow without difficulty.”
[6.5_s0183] Admission control should not be confused with policing.
[6.5_s0184] The former is a per-flow decision to admit a new flow or not.
[6.5_s0185] The latter is a function applied on a per-packet basis to make sure that a flow conforms to the TSpec that was used to make the reservation.
[6.5_s0186] If a flow does not conform to its TSpec—for example, because it is sending twice as many bytes per second as it said it would—then it is likely to interfere with the service provided to other flows, and some corrective action must be taken.
[6.5_s0187] There are several options, the obvious one being to drop offending packets.
[6.5_s0188] However, another option would be to check if the packets really are interfering with the service of other flows.
[6.5_s0189] If they are not interfering, the packets could be sent on after being marked with a tag that says, in effect, “This is a nonconforming packet.
[6.5_s0190] Drop it first if you need to drop any packets.”
[6.5_s0191] Admission control is closely related to the important issue of policy.
[6.5_s0192] For example, a network administrator might wish to allow reservations made by his company’s CEO to be admitted while rejecting reservations made by more lowly employees.
[6.5_s0193] Of course, the CEO’s reservation request might still fail if the requested resources aren’t available, so we see that issues of policy and resource availability may both be addressed when admission control decisions are made.
[6.5_s0194] The application of policy to networking is an area receiving much attention at the time of writing.
[6.5_s0195] Reservation Protocol  While connection-oriented networks have always needed some sort of setup protocol to establish the necessary virtual circuit state in the switches, connectionless networks like the Internet have had no such protocols.
[6.5_s0196] As this section has indicated, however, we need to provide a lot more information to our network when we want a real-time service from it.
[6.5_s0197] While there have been a number of setup protocols proposed for the Internet, the one on which most current attention is focused is the RSVP.
[6.5_s0198] It is particularly interesting because it differs so substantially from conventional signalling protocols for connection-oriented networks.
[6.5_s0199] One of the key assumptions underlying RSVP is that it should not detract from the robustness that we find in today’s connectionless networks.
[6.5_s0200] Because connectionless networks rely on little or no state being stored in the network itself, it is possible for routers to crash and reboot and for links to go up and down while end-to-end connectivity is still maintained.
[6.5_s0201] RSVP tries to maintain this robustness by using the idea of soft state in the routers.
[6.5_s0202] Soft state—in contrast to the hard state found in connection-oriented networks—does not need to be explicitly deleted when it is no longer needed.
[6.5_s0203] Instead, it times out after some fairly short period (say, a minute) if it is not periodically refreshed.
[6.5_s0204] We will see later how this helps robustness.
[6.5_s0205] Another important characteristic of RSVP is that it aims to support multicast flows just as effectively as unicast flows.
[6.5_s0206] This is not surprising, since many of the first applications that could benefit from improved quality of service were also multicast applications—video conferencing tools, for example.
[6.5_s0207] One of the insights of RSVP’s designers is that most multicast applications have many more receivers than senders, as typified by the large audience and one speaker for a lecture.
[6.5_s0208] Also, receivers may have different requirements.
[6.5_s0209] For example, one receiver might want to receive data from only one sender, while others might wish to receive data from all senders.
[6.5_s0210] Rather than having the senders keep track of a potentially large number of receivers, it makes more sense to let the receivers keep track of their own needs.
[6.5_s0211] This suggests the receiver-oriented approach adopted by RSVP.
[6.5_s0212] In contrast, connection-oriented networks usually leave resource reservation to the sender, just as it is normally the originator of a phone call who causes resources to be allocated in the phone network.
[6.5_s0213] The soft state and receiver-oriented nature of RSVP give it a number of good properties.
[6.5_s0214] One such property is that it is very straightforward to increase or decrease the level of resource allocation provided to a receiver.
[6.5_s0215] Since each receiver periodically sends refresh messages to keep the soft state in place, it is easy to send a new reservation that asks for a new level of resources.
[6.5_s0216] Further, soft state deals gracefully with the possibility of network or node failures.
[6.5_s0217] In the event of a host crash, resources allocated by that host to a flow will naturally time out and be released.
[6.5_s0218] To see what happens in the event of a router or link failure, we need to look a little more closely at the mechanics of making a reservation.
[6.5_s0219] Initially, consider the case of one sender and one receiver trying to get a reservation for traffic flowing between them.
[6.5_s0220] There are two things that need to happen before a receiver can make the reservation.
[6.5_s0221] First, the receiver needs to know what traffic the sender is likely to send so that it can make an appropriate reservation.
[6.5_s0222] That is, it needs to know the sender’s TSpec.
[6.5_s0223] Second, it needs to know what path the packets will follow from sender to receiver, so that it can establish a resource reservation at each router on the path.
[6.5_s0224] Both of these requirements can be met by sending a message from the sender to the receiver that contains the TSpec.
[6.5_s0225] Obviously, this gets the TSpec to the receiver.
[6.5_s0226] The other thing that happens is that each router looks at this message (called a PATH message) as it goes past, and it figures out the reverse path that will be used to send reservations from the receiver back to the sender in an effort to get the reservation to each router on the path.
[6.5_s0227] Building the multicast tree in the first place is done by mechanisms such as those described in another chapter.
[6.5_s0228] Having received a PATH message, the receiver sends a reservation back up the multicast tree in a RESV message.
[6.5_s0229] This message contains the sender’s TSpec and an RSpec describing the requirements of this receiver.
[6.5_s0230] Each router on the path looks at the reservation request and tries to allocate the necessary resources to satisfy it.
[6.5_s0231] If the reservation can be made, the RESV request is passed on to the next router.
[6.5_s0232] If not, an error message is returned to the receiver who made the request.
[6.5_s0233] If all goes well, the correct reservation is installed at every router between the sender and the receiver.
[6.5_s0234] As long as the receiver wants to retain the reservation, it sends the same RESV message about once every 30 seconds.
[6.5_s0235] Now we can see what happens when a router or link fails.
[6.5_s0236] Routing protocols will adapt to the failure and create a new path from sender to receiver.
[6.5_s0237] PATH messages are sent about every 30 seconds, and may be sent sooner if a router detects a change in its forwarding table, so the first one after the new route stabilizes will reach the receiver over the new path.
[6.5_s0238] The receiver’s next RESV message will follow the new path and, if all goes well, establish a new reservation on the new path.
[6.5_s0239] Meanwhile, the routers that are no longer on the path will stop getting RESV messages, and these reservations will time out and be released.
[6.5_s0240] Thus, RSVP deals quite well with changes in topology, as long as routing changes are not excessively frequent.
[6.5_s0241] The next thing we need to consider is how to cope with multicast, where there may be multiple senders to a group and multiple receivers.
[6.5_s0242] This situation is illustrated in Figure.
[6.5_s0243] First, let’s deal with multiple receivers for a single sender.
[6.5_s0244] As a RESV message travels up the multicast tree, it is likely to hit a piece of the tree where some other receiver’s reservation has already been established.
[6.5_s0245] It may be the case that the resources reserved upstream of this point are adequate to serve both receivers.
[6.5_s0246] For example, if receiver A has already made a reservation that provides for a guaranteed delay of less than 100 ms, and the new request from receiver B is for a delay of less than 200 ms, then no new reservation is required.
[6.5_s0247] On the other hand, if the new request were for a delay of less than 50 ms, then the router would first need to see if it could accept the request; if so, it would send the request on upstream.
[6.5_s0248] The next time receiver A asked for a minimum of a 100-ms delay, the router would not need to pass this request on.
[6.5_s0249] In general, reservations can be merged in this way to meet the needs of all receivers downstream of the merge point.
[6.5_s0250] If there are also multiple senders in the tree, receivers need to collect the TSpecs from all senders and make a reservation that is large enough to accommodate the traffic from all senders.
[6.5_s0251] However, this may not mean that the TSpecs need to be added up.
[6.5_s0252] For example, in an audioconference with 10 speakers, there is not much point in allocating enough resources to carry 10 audio streams, since the result of 10 people speaking at once would be incomprehensible.
[6.5_s0253] Thus, we could imagine a reservation that is large enough to accommodate two speakers and no more.
[6.5_s0254] Calculating the correct overall TSpec from all of the sender TSpecs is clearly application specific.
[6.5_s0255] Also, we may only be interested in hearing from a subset of all possible speakers; RSVP has different reservation styles to deal with such options as “Reserve resources for all speakers,” “Reserve resources for any n speakers,” and “Reserve resources for speakers A and B only.”
[6.5_s0256] Packet Classifying and Scheduling  Once we have described our traffic and our desired network service and have installed a suitable reservation at all the routers on the path, the only thing that remains is for the routers to actually deliver the requested service to the data packets.
[6.5_s0257] There are two things that need to be done:  -  Associate each packet with the appropriate reservation so that it can be handled correctly, a process known as classifying packets.
[6.5_s0258] -  Manage the packets in the queues so that they receive the service that has been requested, a process known as packet scheduling.
[6.5_s0259] The first part is done by examining up to five fields in the packet: the source address, destination address, protocol number, source port, and destination port.
[6.5_s0260] (In IPv6, it is possible that the FlowLabel field in the header could be used to enable the lookup to be done based on a single, shorter key.)
[6.5_s0261] Based on this information, the packet can be placed in the appropriate class.
[6.5_s0262] For example, it may be classified into the controlled load classes, or it may be part of a guaranteed flow that needs to be handled separately from all other guaranteed flows.
[6.5_s0263] In short, there is a mapping from the flow-specific information in the packet header to a single class identifier that determines how the packet is handled in the queue.
[6.5_s0264] For guaranteed flows this might be a one-to-one mapping, while for other services it might be many to one.
[6.5_s0265] The details of classification are closely related to the details of queue management.
[6.5_s0266] It should be clear that something as simple as a FIFO queue in a router will be inadequate to provide many different services and to provide different levels of delay within each service.
[6.5_s0267] Several more sophisticated queue management disciplines were discussed in an earlier section, and some combination of these is likely to be used in a router.
[6.5_s0268] The details of packet scheduling ideally should not be specified in the service model.
[6.5_s0269] Instead, this is an area where implementors can try to do creative things to realize the service model efficiently.
[6.5_s0270] In the case of guaranteed service, it has been established that a weighted fair queuing discipline, in which each flow gets its own individual queue with a certain share of the link, will provide a guaranteed end-to-end delay bound that can readily be calculated.
[6.5_s0271] For controlled load, simpler schemes may be used.
[6.5_s0272] One possibility includes treating all the controlled load traffic as a single, aggregated flow (as far as the scheduling mechanism is concerned), with the weight for that flow being set based on the total amount of traffic admitted in the controlled load class.
[6.5_s0273] The problem is made harder when you consider that, in a single router, many different services are likely to be provided concurrently and that each of these services may require a different scheduling algorithm.
[6.5_s0274] Thus, some overall queue management algorithm is needed to manage the resources between the different services.
[6.5_s0275] Scalability Issues
[6.5_s0276] Although the Integrated Services architecture and RSVP represented a significant enhancement of the best-effort service model of IP, many Internet service providers felt that it was not the right model for them to deploy.
[6.5_s0277] The reason for this reticence relates to one of the fundamental design goals of IP: scalability.
[6.5_s0278] In the best-effort service model, routers in the Internet store little or no state about the individual flows passing through them.
[6.5_s0279] Thus, as the Internet grows, the only thing routers have to do to keep up with that growth is to move more bits per second and to deal with larger routing tables, but RSVP raises the possibility that every flow passing through a router might have a corresponding reservation.
[6.5_s0280] To understand the severity of this problem, suppose that every flow on an OC-48 (2.5-Gbps) link represents a 64-kbps audio stream.
[6.5_s0281] The number of such flows is  Each of those reservations needs some amount of state that needs to be stored in memory and refreshed periodically.
[6.5_s0282] The router needs to classify, police, and queue each of those flows.
[6.5_s0283] Admission control decisions need to be made every time such a flow requests a reservation, and some mechanism is needed to “push back” on users (e.g., charge their credit cards) so that they don’t make arbitrarily large reservations for long periods of time.
[6.5_s0284] These scalability concerns have limited widespread deployment of IntServ.
[6.5_s0285] Because of these concerns, other approaches that do not require so much “per-flow” state have been developed.
[6.5_s0286] The next section discusses a number of such approaches.
[6.5_s0287] 6.5.3 Differentiated Services (EF, AF)
[6.5_s0288] Whereas the Integrated Services architecture allocates resources to individual flows, the Differentiated Services model (often called DiffServ for short) allocates resources to a small number of classes of traffic.
[6.5_s0289] In fact, some proposed approaches to DiffServ simply divide traffic into two classes.
[6.5_s0290] This is an eminently sensible approach to take: If you consider the difficulty that network operators experience just trying to keep a best-effort internet running smoothly, it makes sense to add to the service model in small increments.
[6.5_s0291] Suppose that we have decided to enhance the best-effort service model by adding just one new class, which we’ll call “premium.”
[6.5_s0292] Clearly, we will need some way to figure out which packets are premium and which are regular old best effort.
[6.5_s0293] Rather than using a protocol like RSVP to tell all the routers that some flow is sending premium packets, it would be much easier if the packets could just identify themselves to the router when they arrive.
[6.5_s0294] This could obviously be done by using a bit in the packet header—if that bit is a 1, the packet is a premium packet; if it’s a 0, the packet is best effort.
[6.5_s0295] With this in mind, there are two questions we need to address:  -  Who sets the premium bit and under what circumstances?  -  What does a router do differently when it sees a packet with the bit set?
[6.5_s0296] There are many possible answers to the first question, but a common approach is to set the bit at an administrative boundary.
[6.5_s0297] For example, the router at the edge of an Internet service provider’s network might set the bit for packets arriving on an interface that connects to a particular company’s network.
[6.5_s0298] The Internet service provider might do this because that company has paid for a higher level of service than best effort.
[6.5_s0299] It is also possible that not all packets would be marked as premium; for example, the router might be configured to mark packets as premium up to some maximum rate and to leave all excess packets as best effort.
[6.5_s0300] Assuming that packets have been marked in some way, what do the routers that encounter marked packets do with them?
[6.5_s0301] Here again there are many answers.
[6.5_s0302] In fact, the IETF standardized a set of router behaviors to be applied to marked packets.
[6.5_s0303] These are called per-hop behaviors (PHBs), a term that indicates that they define the behavior of individual routers rather than end-to-end services.
[6.5_s0304] Because there is more than one new behavior, there is also a need for more than 1 bit in the packet header to tell the routers which behavior to apply.
[6.5_s0305] The IETF decided to take the old TOS byte from the IP header, which had not been widely used, and redefine it.
[6.5_s0306] Six bits of this byte have been allocated for DiffServ code points (DSCPs), where each DSCP is a 6-bit value that identifies a particular PHB to be applied to a packet.
[6.5_s0307] (The remaining two bits are used by ECN.)
[6.5_s0308] The Expedited Forwarding (EF) PHB  One of the simplest PHBs to explain is known as expedited forwarding (EF).
[6.5_s0309] Packets marked for EF treatment should be forwarded by the router with minimal delay and loss.
[6.5_s0310] The only way that a router can guarantee this to all EF packets is if the arrival rate of EF packets at the router is strictly limited to be less than the rate at which the router can forward EF packets.
[6.5_s0311] For example, a router with a 100-Mbps interface needs to be sure that the arrival rate of EF packets destined for that interface never exceeds 100 Mbps.
[6.5_s0312] It might also want to be sure that the rate will be somewhat below 100 Mbps, so that it occasionally has time to send other packets such as routing updates.
[6.5_s0313] The rate limiting of EF packets is achieved by configuring the routers at the edge of an administrative domain to allow a certain maximum rate of EF packet arrivals into the domain.
[6.5_s0314] A simple, albeit conservative, approach would be to ensure that the sum of the rates of all EF packets entering the domain is less than the bandwidth of the slowest link in the domain.
[6.5_s0315] This would ensure that, even in the worst case where all EF packets converge on the slowest link, it is not overloaded and can provide the correct behavior.
[6.5_s0316] There are several possible implementation strategies for the EF behavior.
[6.5_s0317] One is to give EF packets strict priority over all other packets.
[6.5_s0318] Another is to perform weighted fair queuing between EF packets and other packets, with the weight of EF set sufficiently high that all EF packets can be delivered quickly.
[6.5_s0319] This has an advantage over strict priority: The non-EF packets can be assured of getting some access to the link, even if the amount of EF traffic is excessive.
[6.5_s0320] This might mean that the EF packets fail to get exactly the specified behavior, but it could also prevent essential routing traffic from being locked out of the network in the event of an excessive load of EF traffic.
[6.5_s0321] The Assured Forwarding (AF) PHB  The assured forwarding (AF) PHB has its roots in an approach known as RED with In and Out (RIO) or Weighted RED, both of which are enhancements to the basic RED algorithm described in an earlier section.
[6.5_s0322] Figure shows how RIO works; as with RED, we see drop probability on the y\ -axis increasing as average queue length increases along the x\ -axis.
[6.5_s0323] But now, for our two classes of traffic, we have two separate drop probability curves.
[6.5_s0324] RIO calls the two classes “in” and “out” for reasons that will become clear shortly.
[6.5_s0325] Because the “out” curve has a lower MinThreshold than the “in” curve, it is clear that, under low levels of congestion, only packets marked “out” will be discarded by the RED algorithm.
[6.5_s0326] If the congestion becomes more serious, a higher percentage of “out” packets are dropped, and then if the average queue length exceeds Min\ in, RED starts to drop “in” packets as well.
[6.5_s0327] The reason for calling the two classes of packets “in” and “out” stems from the way the packets are marked.
[6.5_s0328] We already noted that packet marking can be performed by a router at the edge of an administrative domain.
[6.5_s0329] We can think of this router as being at the boundary between a network service provider and some customer of that network.
[6.5_s0330] The customer might be any other network—for example, the network of a corporation or of another network service provider.
[6.5_s0331] The customer and the network service provider agree on some sort of profile for the assured service (and perhaps the customer pays the network service provider for this profile).
[6.5_s0332] The profile might be something like “Customer X is allowed to send up to y Mbps of assured traffic,” or it could be significantly more complex.
[6.5_s0333] Whatever the profile is, the edge router can clearly mark the packets that arrive from this customer as being either in or out of profile.
[6.5_s0334] In the example just mentioned, as long as the customer sends less than y Mbps, all his packets will be marked “in,” but once he exceeds that rate the excess packets will be marked “out.”
[6.5_s0335] The combination of a profile meter at the edge and RIO in all the routers of the service provider’s network should provide the customer with a high assurance (but not a guarantee) that packets within his profile can be delivered.
[6.5_s0336] In particular, if the majority of packets, including those sent by customers who have not paid extra to establish a profile, are “out” packets, then it should usually be the case that the RIO mechanism will act to keep congestion low enough that “in” packets are rarely dropped.
[6.5_s0337] Clearly, there must be enough bandwidth in the network so that the “in” packets alone are rarely able to congest a link to the point where RIO starts dropping “in” packets.
[6.5_s0338] Just like RED, the effectiveness of a mechanism like RIO depends to some extent on correct parameter choices, and there are considerably more parameters to set for RIO.
[6.5_s0339] Exactly how well the scheme will work in production networks is not known at the time of writing.
[6.5_s0340] One interesting property of RIO is that it does not change the order of “in” and “out” packets.
[6.5_s0341] For example, if a TCP connection is sending packets through a profile meter, and some packets are being marked “in” while others are marked “out,” those packets will receive different drop probabilities in the router queues, but they will be delivered to the receiver in the same order in which they were sent.
[6.5_s0342] This is important for most TCP implementations, which perform much better when packets arrive in order, even if they are designed to cope with misordering.
[6.5_s0343] Note also that mechanisms such as fast retransmit can be falsely triggered when misordering happens.
[6.5_s0344] The idea of RIO can be generalized to provide more than two drop probability curves, and this is the idea behind the approach known as weighted RED (WRED).
[6.5_s0345] In this case, the value of the DSCP field is used to pick one of several drop probability curves, so that several different classes of service can be provided.
[6.5_s0346] A third way to provide Differentiated Services is to use the DSCP value to determine which queue to put a packet into in a weighted fair queuing scheduler.
[6.5_s0347] As a very simple case, we might use one code point to indicate the best-effort queue and a second code point to select the premium queue.
[6.5_s0348] We then need to choose a weight for the premium queue that makes the premium packets get better service than the best-effort packets.
[6.5_s0349] This depends on the offered load of premium packets.
[6.5_s0350] For example, if we give the premium queue a weight of 1 and the best-effort queue a weight of 4, that ensures that the bandwidth available to premium packets is  That is, we have effectively reserved 20% of the link for premium packets, so if the offered load of premium traffic is only 10% of the link on average, then the premium traffic will behave as if it is running on a very underloaded network and the service will be very good.
[6.5_s0351] In particular, the delay experienced by the premium class can be kept low, since WFQ will try to transmit premium packets as soon as they arrive in this scenario.
[6.5_s0352] On the other hand, if the premium traffic load were 30%, it would behave like a highly loaded network, and delay could be very high for the premium packets—even worse than for the so-called best-effort packets.
[6.5_s0353] Thus, knowledge of the offered load and careful setting of weights is important for this type of service.
[6.5_s0354] However, note that the safe approach is to be very conservative in setting the weight for the premium queue.
[6.5_s0355] If this weight is made very high relative to the expected load, it provides a margin of error and yet does not prevent the best-effort traffic from using any bandwidth that has been reserved for premium but is not used by premium packets.
[6.5_s0356] Just as in WRED, we can generalize this WFQ-based approach to allow more than two classes represented by different code points.
[6.5_s0357] Furthermore, we can combine the idea of a queue selector with a drop preference.
[6.5_s0358] For example, with 12 code points we can have four queues with different weights, each of which has three drop preferences.
[6.5_s0359] This is exactly what the IETF has done in the definition of “assured service.”  6.5.4 Equation-Based Congestion Control
[6.5_s0360] We conclude our discussion of QoS by returning full circle to TCP congestion control, but this time in the context of real-time applications.
[6.5_s0361] Recall that TCP adjusts the sender’s congestion window (and, hence, the rate at which it can transmit) in response to ACK and timeout events.
[6.5_s0362] One of the strengths of this approach is that it does not require cooperation from the network’s routers; it is a purely host-based strategy.
[6.5_s0363] Such a strategy complements the QoS mechanisms we’ve been considering, because (1) applications can use host-based solutions without depending on router support, and (2) even with DiffServ fully deployed, it is still possible for a router queue to be oversubscribed, and we would like real-time applications to react in a reasonable way should this happen.
[6.5_s0364] While we would like to take advantage of TCP’s congestion control algorithm, TCP itself is not appropriate for real-time applications.
[6.5_s0365] One reason is that TCP is a reliable protocol, and real-time applications often cannot afford the delays introduced by retransmission.
[6.5_s0366] However, what if we were to decouple TCP from its congestion control mechanism, to add TCP-like congestion control to an unreliable protocol like UDP?
[6.5_s0367] Could real-time applications make use of such a protocol?
[6.5_s0368] On the one hand, this is an appealing idea because it would cause real-time streams to compete fairly with TCP streams.
[6.5_s0369] The alternative (which happens today) is that video applications use UDP without any form of congestion control and, as a consequence, steal bandwidth away from TCP flows that back off in the presence of congestion.
[6.5_s0370] On the other hand, the sawtooth behavior of TCP’s congestion-control algorithm is not appropriate for real-time applications; it means that the rate at which the application transmits is constantly going up and down.
[6.5_s0371] In contrast, real-time applications work best when they are able to sustain a smooth transmission rate over a relatively long period of time.
[6.5_s0372] Is it possible to achieve the best of both worlds: compatibility with TCP congestion control for the sake of fairness, while sustaining a smooth transmission rate for the sake of the application?
[6.5_s0373] Recent work suggests that the answer is yes.
[6.5_s0374] Specifically, several so called TCP-friendly congestion-control algorithms have been proposed.
[6.5_s0375] These algorithms have two main goals.
[6.5_s0376] One is to slowly adapt the congestion window.
[6.5_s0377] This is done by adapting over relatively longer time periods (e.g., an RTT) rather than on a per-packet basis.
[6.5_s0378] This smooths out the transmission rate.
[6.5_s0379] The second is to be TCP friendly in the sense of being fair to competing TCP flows.
[6.5_s0380] This property is often enforced by ensuring that the flow’s behavior adheres to an equation that models TCP’s behavior.
[6.5_s0381] Hence, this approach is sometimes called equation-based congestion control.
[6.5_s0382] We saw a simplified form of the TCP rate equation in an earlier section.
[6.5_s0383] For our purposes, it is sufficient to note that the equation takes this general form:  which says that to be TCP-friendly, the transmission rate must be inversely proportional to the round-trip time (RTT) and the square root of the loss rate (\rho).
[6.5_s0384] In other words, to build a congestion control mechanism out of this relationship, the receiver must periodically report the loss rate it is experiencing back to the sender (e.g., it might report that it failed to receive 10% of the last 100 packets), and the sender then adjusts its sending rate up or down, such that this relationship continues to hold.
[6.5_s0385] Of course, it is still up to the application to adapt to these changes in the available rate, but as we will see in the next chapter, many real-time applications are quite adaptable.
=== SECTION 9.1: Applications > Traditional Applications ===
[9.1_s0000] We begin our discussion of applications by focusing on two of the most popular—the World Wide Web and email.
[9.1_s0001] Broadly speaking, both of these applications use the request/reply paradigm—users send requests to servers, which then respond accordingly.
[9.1_s0002] We refer to these as “traditional” applications because they typify the sort of applications that have existed since the early days of computer networks (although the Web is a lot newer than email but has its roots in file transfers that predated it).
[9.1_s0003] By contrast, later sections will look at a class of applications that have become popular more recently: streaming applications (e.g., multimedia applications like video and audio) and various overlay-based applications.
[9.1_s0004] (Note that there is a bit of a blurring between these classes, as we increasingly access streaming multimedia data over the Web, but for now we’ll focus on the general usage of the Web to request pages, images, etc.)  Before taking a close look at each of these applications, there are three general points that we need to make.
[9.1_s0005] The first is that it is important to distinguish between application programs and application protocols.
[9.1_s0006] For example, the HyperText Transport Protocol (HTTP) is an application protocol that is used to retrieve Web pages from remote servers.
[9.1_s0007] Many different application programs—that is, web clients like Internet Explorer, Chrome, Firefox, and Safari—provide users with a different look and feel, but all of them use the same HTTP protocol to communicate with web servers over the Internet.
[9.1_s0008] Indeed, it is the fact that the protocol is published and standardized that enables application programs developed by many different companies and individuals to interoperate.
[9.1_s0009] That is how so many browsers are able to interoperate with all the web servers (of which there are also many varieties).
[9.1_s0010] This section looks at two very widely used, standardized application protocols:  -  Simple Mail Transfer Protocol (SMTP) is used to exchange electronic mail.  -  HyperText Transport Protocol (HTTP) is used to communicate between web browsers and web servers.
[9.1_s0011] Second, we observe that many application layer protocols, including HTTP and SMTP, have a companion protocol that specifies the format of the data that can be exchanged.
[9.1_s0012] This is one reason WHY these protocols are relatively simple: much of the complexity is managed in this companion standard.
[9.1_s0013] For example, SMTP is a protocol for exchanging electronic mail messages, but RFC 822 and Multipurpose Internet Mail Extensions (MIME) define the format of email messages.
[9.1_s0014] Similarly, HTTP is a protocol for fetching Web pages, but HyperText Markup Language (HTML) is a companion specification that defines the basic form of those pages.
[9.1_s0015] Finally, since the application protocols described in this section follow the same request/reply communication pattern, you might expect that they would be built on top of a Remote Procedure Call (RPC) transport protocol.
[9.1_s0016] This is not the case, however, as they are instead implemented on top of TCP [#]_.
[9.1_s0017] In effect, each protocol reinvents a simple RPC-like mechanism on top of a reliable transport protocol (TCP).
[9.1_s0018] We say “simple” because each protocol is not designed to support arbitrary remote procedure calls of the sort discussed in an earlier chapter, but is instead designed to send and respond to a specific set of request messages.
[9.1_s0019] Interestingly, the approach taken by HTTP has proven quite powerful, which has led to it being adopted widely by the Web Services architecture, with general RPC mechanisms built on top of HTTP rather than the other way around.
[9.1_s0020] More on this topic at the end of this section.
[9.1_s0021] 9.1.1 Electronic Mail (SMTP, MIME, IMAP)
[9.1_s0022] Email is one of the oldest network applications.
[9.1_s0023] After all, what could be more natural than wanting to send a message to the user at the other end of a cross-country link you just managed to get running?
[9.1_s0024] It’s the 20th century’s version of “Mr. Watson, come here… I want to see you.”
[9.1_s0025] Surprisingly, the pioneers of the ARPANET had not really envisioned email as a key application when the network was created—remote access to computing resources was the main design goal—but it turned out to be the Internet’s original killer app.
[9.1_s0026] As noted above, it is important (1) to distinguish the user interface (i.e., your mail reader) from the underlying message transfer protocols (such as SMTP or IMAP), and (2) to distinguish between this transfer protocol and a companion standard (RFC 822 and MIME) that defines the format of the messages being exchanged.
[9.1_s0027] We start by looking at the message format.
[9.1_s0028] Message Format  RFC 822 defines messages to have two parts: a header and a body.
[9.1_s0029] Both parts are represented in ASCII text.
[9.1_s0030] Originally, the body was assumed to be simple text.
[9.1_s0031] This is still the case, although RFC 822 has been augmented by MIME to allow the message body to carry all sorts of data.
[9.1_s0032] This data is still represented as ASCII text, but because it may be an encoded version of, say, a JPEG image, it’s not necessarily readable by human users.
[9.1_s0033] More on MIME in a moment.
[9.1_s0034] The message header is a series of <CRLF>-terminated lines.
[9.1_s0035] (<CRLF> stands for carriage-return plus line-feed, which are a pair of ASCII control characters often used to indicate the end of a line of text.)
[9.1_s0036] The header is separated from the message body by a blank line.
[9.1_s0037] Each header line contains a type and value separated by a colon.
[9.1_s0038] Many of these header lines are familiar to users, since they are asked to fill them out when they compose an email message; for example, the To: header identifies the message recipient, and the Subject: header says something about the purpose of the message.
[9.1_s0039] Other headers are filled in by the underlying mail delivery system.
[9.1_s0040] Examples include Date: (when the message was transmitted), From: (what user sent the message), and Received: (each mail server that handled this message).
[9.1_s0041] There are, of course, many other header lines; the interested reader is referred to RFC 822.
[9.1_s0042] RFC 822 was extended in 1993 (and updated quite a few times since then) to allow email messages to carry many different types of data: audio, video, images, PDF documents, and so on.
[9.1_s0043] MIME consists of three basic pieces.
[9.1_s0044] The first piece is a collection of header lines that augment the original set defined by RFC 822.
[9.1_s0045] These header lines describe, in various ways, the data being carried in the message body.
[9.1_s0046] They include MIME-Version: (the version of MIME being used), Content-Description: (a human-readable description of what’s in the message, analogous to the Subject: line), Content-Type: (the type of data contained in the message), and Content-Transfer-Encoding: (how the data in the message body is encoded).
[9.1_s0047] The second piece is definitions for a set of content types (and subtypes).
[9.1_s0048] For example, MIME defines several different image types, including image/gif and image/jpeg, each with the obvious meaning.
[9.1_s0049] As another example, text/plain refers to simple text you might find in a vanilla 822-style message, while text/richtext denotes a message that contains “marked up” text (text using special fonts, italics, etc.).
[9.1_s0050] As a third example, MIME defines an application type, where the subtypes correspond to the output of different application programs (e.g., application/postscript and application/msword).
[9.1_s0051] MIME also defines a multipart type that says how a message carrying more than one data type is structured.
[9.1_s0052] This is like a programming language that defines both base types (e.g., integers and floats) and compound types (e.g., structures and arrays).
[9.1_s0053] One possible multipart subtype is mixed, which says that the message contains a set of independent data pieces in a specified order.
[9.1_s0054] Each piece then has its own header line that describes the type of that piece.
[9.1_s0055] The third piece is a way to encode the various data types so they can be shipped in an ASCII email message.
[9.1_s0056] The problem is that, for some data types (a JPEG image, for example), any given 8-bit byte in the image might contain one of 256 different values.
[9.1_s0057] Only a subset of these values are valid ASCII characters.
[9.1_s0058] It is important that email messages contain only ASCII, because they might pass through a number of intermediate systems (gateways, as described below) that assume all email is ASCII and would corrupt the message if it contained non-ASCII characters.
[9.1_s0059] To address this issue, MIME uses a straightforward encoding of binary data into the ASCII character set.
[9.1_s0060] The encoding is called base64.
[9.1_s0061] The idea is to map every three bytes of the original binary data into four ASCII characters.
[9.1_s0062] This is done by grouping the binary data into 24-bit units and breaking each such unit into four 6-bit pieces.
[9.1_s0063] Each 6-bit piece maps onto one of 64 valid ASCII characters; for example, 0 maps onto A, 1 maps onto B, and so on.
[9.1_s0064] If you look at a message that has been encoded using the base64 encoding scheme, you’ll notice only the 52 upper- and lowercase letters, the 10 digits 0 through 9, and the special characters + and /.
[9.1_s0065] These are the first 64 values in the ASCII character set.
[9.1_s0066] As one aside, so as to make reading mail as painless as possible for those who still insist on using text-only mail readers, a MIME message that consists of regular text only can be encoded using 7-bit ASCII.
[9.1_s0067] There’s also a readable encoding for mostly ASCII data.
[9.1_s0068] Putting this all together, a message that contains some plain text, a JPEG image, and a PostScript file would look something like this:  In this example, the line in the message header says that this message contains various pieces, each denoted by a character string that does not appear in the data itself.
[9.1_s0069] Each piece then has its own Content-Type and Content-Transfer-Encoding lines.
[9.1_s0070] Message Transfer  For many years, the majority of email was moved from host to host using only SMTP.
[9.1_s0071] While SMTP continues to play a central role, it is now just one email protocol of several, Internet Message Access Protocol (IMAP) and Post Office Protocol (POP) being two other important protocols for retrieving mail messages.
[9.1_s0072] We’ll begin our discussion by looking at SMTP, and move on to IMAP below.
[9.1_s0073] To place SMTP in the right context, we need to identify the key players.
[9.1_s0074] First, users interact with a mail reader when they compose, file, search, and read their email.
[9.1_s0075] Countless mail readers are available, just like there are many web browsers to choose from.
[9.1_s0076] In the early days of the Internet, users typically logged into the machine on which their mailbox resided, and the mail reader they invoked was a local application program that extracted messages from the file system.
[9.1_s0077] Today, of course, users remotely access their mailbox from their laptop or smartphone; they do not first log into the host that stores their mail (a mail server).
[9.1_s0078] A second mail transfer protocol, such as POP or IMAP, is used to remotely download email from a mail server to the user’s device.
[9.1_s0079] Second, there is a mail daemon (or process) running on each host that holds a mailbox.
[9.1_s0080] You can think of this process, also called a message transfer agent (MTA), as playing the role of a post office:
[9.1_s0081] Users (or their mail readers) give the daemon messages they want to send to other users, the daemon uses SMTP running over TCP to transmit the message to a daemon running on another machine, and the daemon puts incoming messages into the user’s mailbox (where that user’s mail reader can later find them).
[9.1_s0082] Since SMTP is a protocol that anyone could implement, in theory there could be many different implementations of the mail daemon.
[9.1_s0083] It turns out, though, that there are only a few popular implementations, with the old sendmail program from Berkeley Unix and postfix being the most widespread.
[9.1_s0084] While it is certainly possible that the MTA on a sender’s machine establishes an SMTP/TCP connection to the MTA on the recipient’s mail server, in many cases the mail traverses one or more mail gateways on its route from the sender’s host to the receiver’s host.
[9.1_s0085] Like the end hosts, these gateways also run a message transfer agent process.
[9.1_s0086] It’s not an accident that these intermediate nodes are called gateways since their job is to store and forward email messages, much like an “IP gateway” (which we have referred to as a router) stores and forwards IP datagrams.
[9.1_s0087] The only difference is that a mail gateway typically buffers messages on disk and is willing to try retransmitting them to the next machine for several days, while an IP router buffers datagrams in memory and is only willing to retry transmitting them for a fraction of a second.
[9.1_s0088] Figure illustrates a two-hop path from the sender to the receiver.
[9.1_s0089] Why, you might ask, are mail gateways necessary?
[9.1_s0090] Why can’t the sender’s host send the message to the receiver’s host?
[9.1_s0091] One reason is that the recipient does not want to include the specific host on which he or she reads email in his or her address.
[9.1_s0092] Another is scale: In large organizations, it’s often the case that a number of different machines hold the mailboxes for the organization.
[9.1_s0093] For example, mail delivered to bob@cs.princeton.edu is first sent to a mail gateway in the CS Department at Princeton (that is, to the host named cs.princeton.edu), and then forwarded—involving a second connection—to the specific machine on which Bob has a mailbox.
[9.1_s0094] The forwarding gateway maintains a database that maps users into the machine on which their mailbox resides; the sender need not be aware of this specific name.
[9.1_s0095] (The list of header lines in the message will help you trace the mail gateways that a given message traversed.)
[9.1_s0096] Yet another reason, particularly true in the early days of email, is that the machine that hosts any given user’s mailbox may not always be up or reachable, in which case the mail gateway holds the message until it can be delivered.
[9.1_s0097] Independent of how many mail gateways are in the path, an independent SMTP connection is used between each host to move the message closer to the recipient.
[9.1_s0098] Each SMTP session involves a dialog between the two mail daemons, with one acting as the client and the other acting as the server.
[9.1_s0099] Multiple messages might be transferred between the two hosts during a single session.
[9.1_s0100] Since RFC 822 defines messages using ASCII as the base representation, it should come as no surprise to learn that SMTP is also ASCII based.
[9.1_s0101] This means it is possible for a human at a keyboard to pretend to be an SMTP client program.
[9.1_s0102] SMTP is best understood by a simple example.
[9.1_s0103] The following is an exchange between sending host cs.princeton.edu and receiving host systemsapproach.org .
[9.1_s0104] In this case, user Bob at Princeton is trying to send mail to users Alice and Tom at Systems Approach.
[9.1_s0105] Extra blank lines have been added to make the dialog more readable.
[9.1_s0106] As you can see, SMTP involves a sequence of exchanges between the client and the server.
[9.1_s0107] In each exchange, the client posts a command (e.g., QUIT) and the server responds with a code (e.g., 250, 550, 354, 221).
[9.1_s0108] The server also returns a human-readable explanation for the code (e.g., No such user here).
[9.1_s0109] In this particular example, the client first identifies itself to the server with the HELO command.
[9.1_s0110] It gives its domain name as an argument.
[9.1_s0111] The server verifies that this name corresponds to the IP address being used by the TCP connection; you’ll notice the server states this IP address back to the client.
[9.1_s0112] The client then asks the server if it is willing to accept mail for two different users; the server responds by saying “yes” to one and “no” to the other.
[9.1_s0113] Then the client sends the message, which is terminated by a line with a single period (“.”) on it.
[9.1_s0114] Finally, the client terminates the connection.
[9.1_s0115] There are, of course, many other commands and return codes.
[9.1_s0116] For example, the server can respond to a client’s RCPT command with a 251 code, which indicates that the user does not have a mailbox on this host, but that the server promises to forward the message onto another mail daemon.
[9.1_s0117] In other words, the host is functioning as a mail gateway.
[9.1_s0118] As another example, the client can issue a VRFY operation to verify a user’s email address, but without actually sending a message to the user.
[9.1_s0119] The only other point of interest is the arguments to the MAIL and RCPT operations; for example, FROM:<Bob@cs.princeton.edu> and TO:<Alice@systemsapproach.org>, respectively.
[9.1_s0120] These look a lot like 822 header fields, and in some sense they are.
[9.1_s0121] What actually happens is that the mail daemon parses the message to extract the information it needs to run SMTP.
[9.1_s0122] The information it extracts is said to form an envelope for the message.
[9.1_s0123] The SMTP client uses this envelope to parameterize its exchange with the SMTP server.
[9.1_s0124] One historical note: The reason sendmail became so popular is that no one wanted to reimplement this message parsing function.
[9.1_s0125] While today’s email addresses look pretty tame (e.g., Bob@cs.princeton.edu), this was not always the case.
[9.1_s0126] In the days before everyone was connected to the Internet, it was not uncommon to see email addresses of the form user%host@site!neighbor.
[9.1_s0127] Mail Reader  The final step is for the user to actually retrieve his or her messages from the mailbox, read them, reply to them, and possibly save a copy for future reference.
[9.1_s0128] The user performs all these actions by interacting with a mail reader.
[9.1_s0129] As pointed out earlier, this reader was originally just a program running on the same machine as the user’s mailbox, in which case it could simply read and write the file that implements the mailbox.
[9.1_s0130] This was the common case in the pre-laptop era.
[9.1_s0131] Today, most often the user accesses his or her mailbox from a remote machine using yet another protocol, such as POP or IMAP.
[9.1_s0132] It is beyond the scope of this book to discuss the user interface aspects of the mail reader, but it is definitely within our scope to talk about the access protocol.
[9.1_s0133] We consider IMAP, in particular.
[9.1_s0134] IMAP is similar to SMTP in many ways.
[9.1_s0135] It is a client/server protocol running over TCP, where the client (running on the user’s desktop machine) issues commands in the form of <CRLF>-terminated ASCII text lines and the mail server (running on the machine that maintains the user’s mailbox) responds in kind.
[9.1_s0136] The exchange begins with the client authenticating him- or herself and identifying the mailbox he or she wants to access.
[9.1_s0137] This can be represented by the simple state transition diagram shown in Figure.
[9.1_s0138] In this diagram, LOGIN and LOGOUT are example commands that the client can issue, while OK is one possible server response.
[9.1_s0139] Other common commands include FETCH and EXPUNGE, with the obvious meanings.
[9.1_s0140] Additional server responses include NO (client does not have permission to perform that operation) and BAD (command is ill formed).
[9.1_s0141] When the user asks to FETCH a message, the server returns it in MIME format and the mail reader decodes it.
[9.1_s0142] In addition to the message itself, IMAP also defines a set of message attributes that are exchanged as part of other commands, independent of transferring the message itself.
[9.1_s0143] Message attributes include information like the size of the message and, more interestingly, various flags associated with the message (e.g., Seen, Answered, Deleted, and Recent).
[9.1_s0144] These flags are used to keep the client and server synchronized; that is, when the user deletes a message in the mail reader, the client needs to report this fact to the mail server.
[9.1_s0145] Later, should the user decide to expunge all deleted messages, the client issues an EXPUNGE command to the server, which knows to actually remove all earlier deleted messages from the mailbox.
[9.1_s0146] Finally, note that when the user replies to a message, or sends a new message, the mail reader does not forward the message from the client to the mail server using IMAP, but it instead uses SMTP.
[9.1_s0147] This means that the user’s mail server is effectively the first mail gateway traversed along the path from the desktop to the recipient’s mailbox.
[9.1_s0148] 9.1.2 World Wide Web (HTTP)  The World Wide Web has been so successful and has made the Internet accessible to so many people that sometimes it seems to be synonymous with the Internet.
[9.1_s0149] In fact, the design of the system that became the Web started around 1989, long after the Internet had become a widely deployed system.
[9.1_s0150] The original goal of the Web was to find a way to organize and retrieve information, drawing on ideas about hypertext—interlinked documents—that had been around since at least the 1960s.\
[9.1_s0151] [#]_
[9.1_s0152] The core idea of hypertext is that one document can link to another document, and the protocol (HTTP) and document language (HTML) were designed to meet that goal.
[9.1_s0153] One helpful way to think of the Web is as a set of cooperating clients and servers, all of whom speak the same language: HTTP.
[9.1_s0154] Most people are exposed to the Web through a graphical client program or web browser such as Safari, Chrome, Firefox, or Internet Explorer.
[9.1_s0155] Figure shows the Safari browser in use, displaying a page of information from Princeton University.
[9.1_s0156] If you want to organize information into a system of linked documents or objects, there needs to be a way to identify documents so you can link to them.
[9.1_s0157] Uniform Resource Locators (URLs) are so familiar to most of us by now that it’s easy to forget that they haven’t been around forever.
[9.1_s0158] They provide information that allows objects on the Web to be located, and they look like the following:  If you opened that particular URL, your web browser would open a TCP connection to the web server at a machine called www.cs.princeton.edu and immediately retrieve and display the file called index.html.
[9.1_s0159] Most files on the Web contain images and text, and many have other objects such as audio and video clips, pieces of code, etc.
[9.1_s0160] They also frequently include URLs that point to other files that may be located on other machines, which is the core of the “hypertext” part of HTTP and HTML.
[9.1_s0161] A web browser has some way in which you can recognize URLs (often by highlighting or underlining some text) and then you can ask the browser to open them.
[9.1_s0162] These embedded URLs are an example of hypertext links.
[9.1_s0163] When you ask your web browser to open one of these embedded URLs (e.g., by pointing and clicking on it with a mouse), it will retrieve and display the named file.
[9.1_s0164] It thus becomes very easy to hop from one machine to another around the network, following links to all sorts of information.
[9.1_s0165] Once you have a means to embed a link in a document and allow a user to follow that link to get another document, you have the basis of a hypertext system.
[9.1_s0166] When you ask your browser to view a page, your browser (the client) fetches the page from the server using HTTP, which traditionally runs over TCP.
[9.1_s0167] Like SMTP, HTTP is a text-oriented protocol.
[9.1_s0168] At its core, HTTP is a request/response protocol, where every message has the general form  where, as before, <CRLF> stands for carriage-return+line-feed.
[9.1_s0169] The first line (START_LINE) indicates whether this is a request message or a response message.
[9.1_s0170] In effect, it identifies the “remote procedure” to be executed (in the case of a request message), or the status of the request (in the case of a response message).
[9.1_s0171] The next set of lines specifies a collection of options and parameters that qualify the request or response.
[9.1_s0172] There are zero or more of these MESSAGE_HEADER lines—the set is terminated by a blank line—each of which looks like a header line in an email message.
[9.1_s0173] HTTP defines many possible header types, some of which pertain to request messages, some to response messages, and some to the data carried in the message body.
[9.1_s0174] Instead of giving the full set of possible header types, though, we just give a handful of representative examples.
[9.1_s0175] Finally, after the blank line comes the contents of the requested message (MESSAGE_BODY); this part of the message is where a server would place the requested page when responding to a request, and it is typically empty for request messages.
[9.1_s0176] Why was HTTP designed to run over TCP?
[9.1_s0177] The designers didn’t have to do it that way, but TCP provides numerous services that HTTP needs: reliable delivery (who wants a Web page with missing data?), flow control, and congestion control.
[9.1_s0178] However, as we’ll see below, there are a few issues that arose from building a request/response protocol on top of TCP, that become more apparent as you consider the details of the interactions between the application and transport layer protocols.
[9.1_s0179] This has led to new versions of HTTP and a new underlying transport, QUIC, discussed below.
[9.1_s0180] Request Messages  The first line of an HTTP request message specifies three things: the operation to be performed, the Web page the operation should be performed on, and the version of HTTP being used.
[9.1_s0181] Although HTTP defines a wide assortment of possible request operations—including write operations that allow a Web page to be posted on a server—the two most common operations are GET (fetch the specified Web page) and HEAD (fetch status information about the specified Web page).
[9.1_s0182] The former is obviously used when your browser wants to retrieve and display a Web page.
[9.1_s0183] The latter is used to test the validity of a hypertext link or to see if a particular page has been modified since the browser last fetched it.

[9.1_s0203] Uniform Resource Identifiers  The URLs that HTTP uses as addresses are one type of Uniform Resource Identifier (URI).
[9.1_s0204] A URI is a character string that identifies a resource, where a resource can be anything that has identity, such as a document, an image, or a service.
[9.1_s0205] The format of URIs allows various more specialized kinds of resource identifiers to be incorporated into the URI space of identifiers.
[9.1_s0206] The first part of a URI is a scheme that names a particular way of identifying a certain kind of resource, such as mailto for email addresses or file for file names.
[9.1_s0207] The second part of a URI, separated from the first part by a colon, is the scheme-specific part.
[9.1_s0208] It is a resource identifier consistent with the scheme in the first part, as in the URIs mailto:santa@northpole.org and file:///C:/foo.html.
[9.1_s0209] A resource doesn’t have to be retrievable or accessible.
[9.1_s0210] We saw an example of this in an earlier chapter—extensible markup language (XML) namespaces are identified by URIs that look an awful lot like URLs, but strictly speaking they are not locators because they don’t tell you how to locate something; they just provide a globally unique identifier for the namespace.
[9.1_s0211] There is no requirement that you can retrieve anything at the URI given as the target namespace of an XML document.
[9.1_s0212] We’ll see another example of a URI that is not a URL in a later section.
[9.1_s0213] TCP Connections  The original version of HTTP (1.0) established a separate TCP connection for each data item retrieved from the server.
[9.1_s0214] It’s not too hard to see how this was a very inefficient mechanism: connection setup and teardown messages had to be exchanged between the client and server even if all the client wanted to do was verify that it had the most recent copy of a page.
[9.1_s0215] Thus, retrieving a page that included some text and a dozen icons or other small graphics would result in 13 separate TCP connections being established and closed.
[9.1_s0216] Figure shows the sequence of events for fetching a page that has just a single embedded object.
[9.1_s0217] Colored lines indicate TCP messages, while black lines indicate the HTTP requests and responses.
[9.1_s0218] (Some of the TCP ACKs are not shown to avoid cluttering the picture.)
[9.1_s0219] You can see two round trip times are spent setting up TCP connections while another two (at least) are spent getting the page and image.
[9.1_s0220] As well as the latency impact, there is also processing cost on the server to handle the extra TCP connection establishment and termination.
[9.1_s0221] To overcome this situation, HTTP version 1.1 introduced persistent connections—the client and server can exchange multiple request/response messages over the same TCP connection.
[9.1_s0222] Persistent connections have many advantages.
[9.1_s0223] First, they eliminate the connection setup overhead, thereby reducing the load on the server, the load on the network caused by the additional TCP packets, and the delay perceived by the user.
[9.1_s0224] Second, because a client can send multiple request messages down a single TCP connection, TCP’s congestion window mechanism is able to operate more efficiently.
[9.1_s0225] This is because it’s not necessary to go through the slow start phase for each page.
[9.1_s0226] Figure shows the transaction from Figure using a persistent connection in the case where the connection is already open (presumably due to some prior access of the same server).
[9.1_s0227] Persistent connections do not come without a price, however.
[9.1_s0228] The problem is that neither the client nor server necessarily knows how long to keep a particular TCP connection open.
[9.1_s0229] This is especially critical on the server, which might be asked to keep connections opened on behalf of thousands of clients.
[9.1_s0230] The solution is that the server must time out and close a connection if it has received no requests on the connection for a period of time.
[9.1_s0231] Also, both the client and server must watch to see if the other side has elected to close the connection, and they must use that information as a signal that they should close their side of the connection as well.
[9.1_s0232] (Recall that both sides must close a TCP connection before it is fully terminated.)
[9.1_s0233] Concerns about this added complexity may be one reason why persistent connections were not used from the outset, but today it is widely accepted that the benefits of persistent connections more than offset the drawbacks.
[9.1_s0234] While 1.1 is still widely supported, version 2.0 was formally approved by the IETF in 2015.
[9.1_s0235] Known as HTTP/2, the new version is backwards compatible with 1.1 (i.e,.
[9.1_s0236] it adopts the same syntax for header fields, status codes, and URIs), but it adds two new features.
[9.1_s0237] The first is to make it easier for web servers to minify the information they send back to web browsers.
[9.1_s0238] If you look closely at the makeup of the HTML in a typical web page, you will find a plethora of references to other bits-and-pieces (e.g., images, scripts, style files) that the browser needs to render the page.
[9.1_s0239] Rather than force the client to request these bits-and-pieces (technically known as resources) in subsequent requests, HTTP/2 provides a means for the server to bundle the required resources and proactively push them to the client without incurring the round-trip delay of forcing the client to request them.
[9.1_s0240] This feature is coupled with a compression mechanism that reduces the number of bytes that need to be pushed.
[9.1_s0241] The whole goal is to minimize the latency an end-user experiences from the moment they click on a hyperlink until the selected page is fully rendered.
[9.1_s0242] The second big advance of HTTP/2 is to multiplex several requests on a single TCP connection.
[9.1_s0243] This goes beyond what version 1.1 supports—allowing a sequence of requests to reuse a TCP connection—by permitting these requests to overlap with each other.
[9.1_s0244] The way HTTP/2 does this should sound familiar: it defines a channel abstraction (technically, the channels are called streams), permits multiple concurrent streams to be active at a given time (each labeled with a unique stream id), and limits each stream to one active request/reply exchange at a time.  HTTP/3 and QUIC
[9.1_s0245] As the preceding discussion illustrates, the history of HTTP has included a series of incremental changes to make better use of TCP as the underlying transport.
[9.1_s0246] But there is a fundamental issue that can't be fully resolved: TCP provides a byte-stream abstraction, while HTTP is a request/response protocol.
[9.1_s0247] The natural solution would be to adopt a more suitable transport, but as we saw in Chapter 5, there is no standard RPC protocol that enjoys the widespread acceptance of TCP.
[9.1_s0248] Ultimately, the solution to this mismatch was to create a new transport protocol in QUIC.
[9.1_s0249] QUIC was explicitly designed to provide a good match to the requirements of HTTP, and HTTP/3 takes advantage of the improved underlying transport.
[9.1_s0250] For example, QUIC explicitly supports stream multiplexing at the transport layer.
[9.1_s0251] Thus, a single packet loss only impacts the delivery of the stream that suffered the loss, rather than causing a stall in the entire TCP connection while waiting for that lost packet to be retransmitted.
[9.1_s0252] At the same time, that lost packet provides a congestion signal that is applied to all streams in the QUIC connection.
[9.1_s0253] We cover QUIC in more detail in Section 5.2.
[9.1_s0254] Another significant advantage of QUIC compared to TCP is the way it handles the steps required to secure an HTTP connection.
[9.1_s0255] Whereas the exchange of certificates and encryption keys follows the establishment of a TCP session, QUIC handles these steps as part of session establishment, leading to a considerable reduction in the number of round-trips needed to establish a secure connection before the first content is delivered.
[9.1_s0256] HTTP/3 is implemented in the majority of browsers and is incrementally being deployed on servers across the Internet.
[9.1_s0257] There remain plenty of servers running HTTP/2 and even some HTTP/1.1 as well, so version negotiation is likely to be part of HTTP implementations for the foreseeable future.
[9.1_s0258] Caching  An important implementation strategy that makes the web more usable is to cache Web pages.
[9.1_s0259] Caching has many benefits.
[9.1_s0260] From the client’s perspective, a page that can be retrieved from a nearby cache can be displayed much more quickly than if it has to be fetched from across the world.
[9.1_s0261] From the server’s perspective, having a cache intercept and satisfy a request reduces the load on the server.
[9.1_s0262] Caching can be implemented in many different places.
[9.1_s0263] For example, a user’s browser can cache recently accessed pages and simply display the cached copy if the user visits the same page again.
[9.1_s0264] As another example, a site can support a single site-wide cache.
[9.1_s0265] This allows users to take advantage of pages previously downloaded by other users.
[9.1_s0266] Closer to the middle of the Internet, Internet Service Providers (ISPs) can cache pages.\
[9.1_s0267] [#]_ Note that, in the second case, the users within the site most likely know what machine is caching pages on behalf of the site, and they configure their browsers to connect directly to the caching host.
[9.1_s0268] This node is sometimes called a proxy.
[9.1_s0269] In contrast, the sites that connect to the ISP are probably not aware that the ISP is caching pages.
[9.1_s0270] It simply happens to be the case that HTTP requests coming out of the various sites pass through a common ISP router.
[9.1_s0271] This router can peek inside the request message and look at the URL for the requested page.
[9.1_s0272] If it has the page in its cache, it returns it.
[9.1_s0273] If not, it forwards the request to the server and watches for the response to fly by in the other direction.
[9.1_s0274] When it does, the router saves a copy in the hope that it can use it to satisfy a future request.
[9.1_s0275] No matter where pages are cached, the ability to cache Web pages is important enough that HTTP has been designed to make the job easier.
[9.1_s0276] The trick is that the cache needs to make sure it is not responding with an out-of-date version of the page.
[9.1_s0277] For example, the server assigns an expiration date (the Expires header field) to each page it sends back to the client (or to a cache between the server and client).
[9.1_s0278] The cache remembers this date and knows that it need not reverify the page each time it is requested until after that expiration date has passed.
[9.1_s0279] After that time (or if that header field is not set) the cache can use the HEAD or conditional GET operation (GET with header line) to verify that it has the most recent copy of the page.
[9.1_s0280] More generally, there are a set of cache directives that must be obeyed by all caching mechanisms along the request/response chain.
[9.1_s0281] These directives specify whether or not a document can be cached, how long it can be cached, how fresh a document must be, and so on.
[9.1_s0282] We’ll look at the related issue of CDNs—which are effectively distributed caches—in a later section.
[9.1_s0283] 9.1.3 Web Services  So far we have focused on interactions between a human and a web server.
[9.1_s0284] For example, a human uses a web browser to interact with a server, and the interaction proceeds in response to input from the user (e.g., by clicking on links).
[9.1_s0285] However, there is increasing demand for direct computer-to-computer interaction.
[9.1_s0286] And, just as the applications described above need protocols, so too do the applications that communicate directly with each other.
[9.1_s0287] We conclude this section by looking at the challenges of building large numbers of application-to-application protocols and some of the proposed solutions.
[9.1_s0288] Much of the motivation for enabling direct application-to-application communication comes from the business world.
[9.1_s0289] Historically, interactions between enterprises—businesses or other organizations—have involved some manual steps such as filling out an order form or making a phone call to determine whether some product is in stock.
[9.1_s0290] Even within a single enterprise it is common to have manual steps between software systems that cannot interact directly because they were developed independently.
[9.1_s0291] Increasingly, such manual interactions are being replaced with direct application-to-application interaction.
[9.1_s0292] An ordering application at enterprise A would send a message to an order fulfillment application at enterprise B, which would respond immediately indicating whether the order can be filled.
[9.1_s0293] Perhaps, if the order cannot be filled by B, the application at A would immediately order from another supplier or solicit bids from a collection of suppliers.
[9.1_s0294] Here is a simple example of what we are talking about.
[9.1_s0295] Suppose you buy a book at an online retailer like Amazon.
[9.1_s0296] Once your book has been shipped, Amazon could send you the tracking number in an email, and then you could head over to the website for the shipping company—\ http://www.fedex.com, perhaps—and track the package.
[9.1_s0297] However, you can also track your package directly from the Amazon.com website.
[9.1_s0298] In order to make this happen, Amazon has to be able to send a query to FedEx, in a format that FedEx understands, interpret the result, and display it in a Web page that perhaps contains other information about your order.
[9.1_s0299] Underlying the user experience of getting all the information about the order served up at once on the Amazon.com Web page is the fact that Amazon and FedEx had to have a protocol for exchanging the information needed to track packages—call it the Package Tracking Protocol.
[9.1_s0300] It should be clear that there are so many potential protocols of this type that we’d better have some tools to simplify the task of specifying them and building them.
[9.1_s0301] Network applications, even those that cross organization boundaries, are not new—email and web browsing cross such boundaries.
[9.1_s0302] What is new about this problem is the scale.
[9.1_s0303] Not scale in the size of the network, but scale in the number of different kinds of network applications.
[9.1_s0304] Both the protocol specifications and the implementations of those protocols for traditional applications like electronic mail and file transfer have typically been developed by a small group of networking experts.
[9.1_s0305] To enable the vast number of potential network applications to be developed quickly, it was necessary to come up with some technologies that simplify and automate the task of application protocol design and implementation.
[9.1_s0306] Two architectures have been advocated as solutions to this problem.
[9.1_s0307] Both architectures are called Web Services, taking their name from the term for the individual applications that offer a remotely accessible service to client applications to form network applications.
[9.1_s0308] The terms used as informal shorthand to distinguish the two Web Services architectures are SOAP and REST.
[9.1_s0309] We will discuss the technical meanings of those terms shortly.
[9.1_s0310] The SOAP architecture’s approach to the problem is to make it feasible, at least in theory, to generate protocols that are customized to each network application.
[9.1_s0311] The key elements of the approach are a framework for protocol specification, software toolkits for automatically generating protocol implementations from the specifications, and modular partial specifications that can be reused across protocols.
[9.1_s0312] The REST architecture’s approach to the problem is to regard individual Web Services as World Wide Web resources—identified by URIs and accessed via HTTP.
[9.1_s0313] Essentially, the REST architecture is just the Web architecture.
[9.1_s0314] The Web architecture’s strengths include stability and a demonstrated scalability (in the network-size sense).
[9.1_s0315] It could be considered a weakness that HTTP is not well suited to the usual procedural or operation-oriented style of invoking a remote service.
[9.1_s0316] REST advocates argue, however, that rich services can nonetheless be exposed using a more data-oriented or document-passing style for which HTTP is well suited.
[9.1_s0317] Custom Application Protocols (WSDL, SOAP)
[9.1_s0318] The architecture informally referred to as SOAP is based on Web Services Description Language (WSDL) and SOAP.\
[9.1_s0319] [#]_ Both of these standards are issued by the World Wide Web Consortium (W3C).
[9.1_s0320] This is the architecture that people usually mean when they use the term Web Services without any preceding qualifier.
[9.1_s0321] As these standards are still evolving, our discussion here is effectively a snapshot.
[9.1_s0322] WSDL and SOAP are frameworks for specifying and implementing application protocols and transport protocols, respectively.
[9.1_s0323] They are generally used together, although that is not strictly required.
[9.1_s0324] WSDL is used to specify application-specific details such as what operations are supported, the formats of the application data to invoke or respond to those operations, and whether an operation involves a response.
[9.1_s0325] SOAP’s role is to make it easy to define a transport protocol with exactly the desired semantics regarding protocol features such as reliability and security.
[9.1_s0326] Both WSDL and SOAP consist primarily of a protocol specification language.
[9.1_s0327] Both languages are based on XML with an eye toward making specifications accessible to software tools such as stub compilers and directory services.
[9.1_s0328] In a world of many custom protocols, support for automating generation of implementations is crucial to avoid the effort of manually implementing each protocol.
[9.1_s0329] Support software generally takes the form of toolkits and application servers developed by third-party vendors, which allows developers of individual Web Services to focus more on the business problem they need to solve (such as tracking the package purchased by a customer).
[9.1_s0330] Defining Application Protocols  WSDL has chosen a procedural operation model of application protocols.
[9.1_s0331] An abstract Web Service interface consists of a set of named operations, each representing a simple interaction between a client and the Web Service.
[9.1_s0332] An operation is analogous to a remotely callable procedure in an RPC system.
[9.1_s0333] An example from W3C’s WSDL Primer is a hotel reservation Web Service with two operations, CheckAvailability and MakeReservation.
[9.1_s0334] Each operation specifies a Message Exchange Pattern (MEP) that gives the sequence in which the messages are to be transmitted, including the fault messages to be sent when an error disrupts the message flow.
[9.1_s0335] Several MEPs are predefined, and new custom MEPs can be defined, but it appears that in practice only two MEPs are being used: In-Only (a single message from client to service) and In-Out (a request from client and a corresponding reply from service).
[9.1_s0336] These patterns should be very familiar, and suggest that the costs of supporting MEP flexibility perhaps outweigh the benefits.
[9.1_s0337] MEPs are templates that have placeholders instead of specific message types or formats, so part of the definition of an operation involves specifying which message formats to map into the placeholders in the pattern.
[9.1_s0338] Message formats are not defined at the bit level that is typical of protocols we have discussed.
[9.1_s0339] They are instead defined as an abstract data model using XML.
[9.1_s0340] XML Schema provides a set of primitive data types and ways to define compound data types.
[9.1_s0341] Data that conforms to an XML Schema-defined format—its abstract data model—can be concretely represented using XML, or it can use another representation, such as the “binary” representation Fast Infoset.
[9.1_s0342] WSDL nicely separates the parts of a protocol that can be specified abstractly—operations, MEPs, abstract message formats—from the parts that must be concrete.
[9.1_s0343] WSDL’s concrete part specifies an underlying protocol, how MEPs are mapped onto it, and what bit-level representation is used for messages on the wire.
[9.1_s0344] This part of a specification is known as a binding, although it is better described as an implementation, or a mapping onto an implementation.
[9.1_s0345] WSDL has predefined bindings for HTTP and SOAP-based protocols, with parameters that allow the protocol designer to fine-tune the mapping onto those protocols.
[9.1_s0346] There is a framework for defining new bindings, but SOAP protocols dominate.
[9.1_s0347] A crucial aspect of how WSDL mitigates the problem of specifying large numbers of protocols is through reuse of what are essentially specification modules.
[9.1_s0348] The WSDL specification of a Web Service may be composed of multiple WSDL documents, and individual WSDL documents may also be used in other Web Service specifications.
[9.1_s0349] This modularity makes it easier to develop a specification and easier to ensure that, if two specifications are supposed to have some elements that are identical (for example, so that they can be supported by the same tool), then those elements are indeed identical.
[9.1_s0350] This modularity, together with WSDL’s defaulting rules, also helps keep specifications from becoming overwhelmingly verbose for human protocol designers.
[9.1_s0351] WSDL modularity should be familiar to anyone who has developed moderately large pieces of software.
[9.1_s0352] A WSDL document need not be a complete specification; it could, for example, define a single message format.
[9.1_s0353] The partial specifications are uniquely identified using XML Namespaces; each WSDL document specifies the URI of a target namespace, and any new definitions in the document are named in the context of that namespace.
[9.1_s0354] One WSDL document can incorporate components of another by including the second document if both share the same target namespace or importing it if the target namespaces differ.
[9.1_s0355] Defining Transport Protocols
[9.1_s0356] Although SOAP is sometimes called a protocol, it is better thought of as a framework for defining protocols.
[9.1_s0357] As the SOAP 1.2 specification explains, “SOAP provides a simple messaging framework whose core functionality is concerned with providing extensibility.”
[9.1_s0358] SOAP uses many of the same strategies as WSDL, including message formats defined using XML Schema, bindings to underlying protocols, Message Exchange Patterns, and reusable specification elements identified using XML namespaces.
[9.1_s0359] SOAP is used to define transport protocols with exactly the features needed to support a particular application protocol.
[9.1_s0360] SOAP aims to make it feasible to define many such protocols by using reusable components.
[9.1_s0361] Each component captures the header information and logic that go into implementing a particular feature.
[9.1_s0362] To define a protocol with a certain set of features, just compose the corresponding components.
[9.1_s0363] Let’s look more closely at this aspect of SOAP.
[9.1_s0364] SOAP 1.2 introduced a feature abstraction, which the specification describes thus:  A SOAP feature is an extension of the SOAP messaging framework.
[9.1_s0365] Although SOAP poses no constraints on the potential scope of such features, example features may include “reliability,” “security,” “correlation,” “routing,” and message exchange patterns (MEPs) such as request/response, one-way, and peer-to-peer conversations.
[9.1_s0366] A SOAP feature specification must include:  -  A URI that identifies the feature  -  The state information and processing, abstractly described, that is required at each SOAP node to implement the feature  -  The information to be relayed to the next node  -  (If the feature is a MEP)
[9.1_s0367] the life cycle and temporal/causal relationships of the messages exchanged—for example, responses follow requests and are sent to the originator of the request  Note that this formalization of the concept of a protocol feature is rather low level; it is almost a design.
[9.1_s0368] Given a set of features, there are two strategies for defining a SOAP protocol that will implement them.
[9.1_s0369] One is by layering: binding SOAP to an underlying protocol in such a way as to derive the features.
[9.1_s0370] For example, we could obtain a request/response protocol by binding SOAP to HTTP, with a SOAP request in an HTTP request and a SOAP reply in an HTTP response.
[9.1_s0371] Because this is such a common example, it happens that SOAP has a predefined binding to HTTP; new bindings may be defined using the SOAP Protocol Binding Framework.
[9.1_s0372] The second and more flexible way to implement features involves header blocks.
[9.1_s0373] A SOAP message consists of an Envelope, which contains a Header that contains header blocks, and a Body, which contains the payload destined for the ultimate receiver.
[9.1_s0374] This message structure is illustrated in Figure.
[9.1_s0375] It should be a familiar notion by now that certain header information corresponds to particular features.
[9.1_s0376] A digital signature is used to implement authentication, a sequence number is used for reliability, and a checksum is used to detect message corruption.
[9.1_s0377] A SOAP header block is intended to encapsulate the header information that corresponds to a particular feature.
[9.1_s0378] The correspondence is not always one-to-one since multiple header blocks could be involved in a single feature, or a single header block could be used in multiple features.
[9.1_s0379] A SOAP module is a specification of the syntax and the semantics of one or more header blocks.
[9.1_s0380] Each module is intended to provide one or more features and must declare the features it implements.
[9.1_s0381] The goal behind SOAP modules is to be able to compose a protocol with a set of features by simply including each of the corresponding module specifications.
[9.1_s0382] If your protocol is required to have at-most-once semantics and authentication, include the corresponding modules in your specification.
[9.1_s0383] This represents a novel approach to modularizing protocol services, an alternative to the protocol layering we have seen throughout this book.
[9.1_s0384] It is a bit like flattening a series of protocol layers into a single protocol, but in a structured way.
[9.1_s0385] It remains to be seen how well SOAP features and modules, introduced in version 1.2 of SOAP, will work in practice.
[9.1_s0386] The main weakness of this scheme is that modules may well interfere with each other.
[9.1_s0387] A module specification is required to specify any known interactions with other SOAP modules, but clearly that doesn’t do much to alleviate the problem.
[9.1_s0388] On the other hand, a core set of features and modules that provides the most important properties may be small enough to be well known and well understood.
[9.1_s0389] Standardizing Web Services Protocols
[9.1_s0390] As we’ve said, WSDL and SOAP aren’t protocols; they are standards for specifying protocols.
[9.1_s0391] For different enterprises to implement Web Services that interoperate with each other, it is not enough to agree to use WSDL and SOAP to define their protocols; they must agree on—standardize—specific protocols.
[9.1_s0392] For example, you could imagine that online retailers and shipping companies might like to standardize a protocol by which they exchange information, along the lines of the simple package tracking example at the start of this section.
[9.1_s0393] This standardization is crucial for tool support as well as interoperability.
[9.1_s0394] And, yet, different network applications in this architecture must necessarily differ in at least the message formats and operations they use.
[9.1_s0395] This tension between standardization and customization is tackled by establishing partial standards called profiles.
[9.1_s0396] A profile is a set of guidelines that narrow or constrain choices available in WSDL, SOAP, and other standards that may be referenced in defining a protocol.
[9.1_s0397] They may at the same time resolve ambiguities or gaps in those standards.
[9.1_s0398] In practice, a profile often formalizes an emerging de facto standard.
[9.1_s0399] The broadest and most widely adopted profile is known as the WS-I Basic Profile.
[9.1_s0400] It was proposed by the Web Services Interoperability Organization (WS-I), an industry consortium, while WSDL and SOAP are specified by the World Wide Web Consortium (W3C).
[9.1_s0401] The Basic Profile resolves some of the most basic choices faced in defining a Web Service.
[9.1_s0402] Most notably it requires that WSDL be bound exclusively to SOAP and SOAP be bound exclusively to HTTP and use the HTTP POST method.
[9.1_s0403] It also specifies which versions of WSDL and SOAP must be used.
[9.1_s0404] The WS-I Basic Security Profile adds security constraints to the Basic Profile by specifying how the SSL/TLS layer is to be used and requiring conformance to WS-Security (Web Services Security).
[9.1_s0405] WS-Security specifies how to use various existing techniques such as X.509 public key certificates and Kerberos to provide security features in SOAP protocols.
[9.1_s0406] WS-Security is just the first of a growing suite of SOAP-level standards established by the industry consortium OASIS (Organization for the Advancement of Structured Information Standards).
[9.1_s0407] The standards known collectively as WS-\ \* include WS-Reliability, WS-ReliableMessaging, WS-Coordination, and WS-AtomicTransaction.
[9.1_s0408] A Generic Application Protocol (REST)  The WSDL/SOAP Web Services architecture is based on the assumption that the best way to integrate applications across networks is via protocols that are customized to each application.
[9.1_s0409] That architecture is designed to make it practical to specify and implement all those protocols.
[9.1_s0410] In contrast, the REST Web Services architecture is based on the assumption that the best way to integrate applications across networks is by re-applying the model underlying the World Wide Web architecture.
[9.1_s0411] This model, articulated by Web architect Roy Fielding, is known as REpresentational State Transfer (REST).
[9.1_s0412] There is no need for a new REST architecture for Web Services—the existing Web architecture is sufficient, although a few extensions are probably necessary.
[9.1_s0413] In the Web architecture, individual Web Services are regarded as resources identified by URIs and accessed via HTTP—a single generic application protocol with a single generic addressing scheme.
[9.1_s0414] Where WSDL has user-defined operations, REST uses the small set of available HTTP methods, such as GET and POST (see Table).
[9.1_s0415] So how can these simple methods provide an interface to a rich Web Service?
[9.1_s0416] By employing the REST model, in which the complexity is shifted from the protocol to the payload.
[9.1_s0417] The payload is a representation of the abstract state of a resource.
[9.1_s0418] For example, a GET could return a representation of the current state of the resource, and a POST could send a representation of a desired state of the resource.
[9.1_s0419] The representation of a resource state is abstract; it need not resemble how the resource is actually implemented by a particular Web Service instance.
[9.1_s0420] It is not necessary to transmit a complete resource state in each message.
[9.1_s0421] The size of messages can be reduced by transmitting just the parts of a state that are of interest (e.g., just the parts that are being modified).
[9.1_s0422] And, because Web Services share a single protocol and address space with other web resources, parts of states can be passed by reference—by URI—even when they are other Web Services.
[9.1_s0423] This approach is best summarized as a data-oriented or document-passing style, as opposed to a procedural style.
[9.1_s0424] Defining an application protocol in this architecture consists of defining the document structure (i.e., the state representation).
[9.1_s0425] XML and the lighter-weight JavaScript Object Notation (JSON) are the most frequently used presentation languages for this state.
[9.1_s0426] Interoperability depends on agreement, between a Web Service and its clients, on the state representation.
[9.1_s0427] Of course, the same is true in the SOAP architecture; a Web Service and its client have to be in agreement on payload format.
[9.1_s0428] The difference is that in the SOAP architecture interoperability additionally depends on agreement on the protocol; in the REST architecture, the protocol is always HTTP, so that source of interoperability problems is eliminated.
[9.1_s0429] One of the selling features of REST is that it leverages the infrastructure that has been deployed to support the Web.
[9.1_s0430] For example, Web proxies can enforce security or cache information.
[9.1_s0431] Existing content distribution networks (CDNs) can be used to support RESTful applications.
[9.1_s0432] In contrast with WSDL/SOAP, the Web has had time for standards to stabilize and to demonstrate that it scales very well.
[9.1_s0433] It also comes with some security in the form of Secure Socket Layer (SSL)/Transport Layer Security (TLS).
[9.1_s0434] The Web and REST may also have an advantage in evolvability.
[9.1_s0435] Although the WSDL and SOAP frameworks are highly flexible with regard to what new features and bindings can go into the definition of a protocol, that flexibility is irrelevant once the protocol is defined.
[9.1_s0436] Standardized protocols such as HTTP are designed with a provision for being extended in a backward-compatible way.
[9.1_s0437] HTTP’s own extensibility takes the form of headers, new methods, and new content types.
[9.1_s0438] Protocol designers using WSDL/SOAP need to design such extensibility into each of their custom protocols.
[9.1_s0439] Of course, the designers of state representations in a REST architecture also have to design for evolvability.
[9.1_s0440] An area where WSDL/SOAP may have an advantage is in adapting or wrapping previously written, “legacy” applications to conform to Web Services.
[9.1_s0441] This is an important point since most Web Services will be based on legacy applications for the near future at least.
[9.1_s0442] These applications usually have a procedural interface that maps more easily into WSDL’s operations than REST states.
[9.1_s0443] The REST versus WSDL/SOAP competition may very well hinge on how easy or difficult it turns out to be to devise REST-style interfaces for individual Web Services.
[9.1_s0444] We may find that some Web Services are better served by WSDL/SOAP and others by REST.
[9.1_s0445] The online retailer Amazon, as it happens, was an early adopter (2002) of Web Services.
[9.1_s0446] Interestingly, Amazon made its systems publicly accessible via both of the Web Services architectures, and according to some reports a substantial majority of developers use the REST interface.
[9.1_s0447] Of course, this is just one data point and may well reflect factors specific to Amazon.
[9.1_s0448] From Web Services to Cloud Services  If Web Services is what we call it when the web server that implements my application sends a request to the web server that implements your application, then what do we call it when we both put our applications in the cloud so that they can support scalable workloads?
[9.1_s0449] We can call both of them Cloud Services if we want to, but is that a distinction without a difference?
[9.1_s0450] It depends.
[9.1_s0451] Moving a server process from a physical machine running in my machine room into a virtual machine running in a cloud provider’s datacenter shifts responsibility for keeping the machine running from my system admin to the cloud provider’s operations team, but the application is still designed according to the Web Services architecture.
[9.1_s0452] On the other hand, if the application is designed from scratch to run on a scalable cloud platform, for example by adhering to the micro-services architecture, then we say the application is cloud native.
[9.1_s0453] So the important distinction is cloud native versus legacy web services deployed in the cloud.
[9.1_s0454] We briefly saw the micro-services architecture in Chapter 5 when describing gRPC, and although it’s difficult to definitively declare micro-services superior to web services, the current trend in industry almost certainly favors the former.
[9.1_s0455] More interesting, perhaps, is the ongoing debate about REST+Json versus gRPC+Protbufs as the preferred RPC mechanism for implementing micro-services.
[9.1_s0456] Keeping in mind that both run on top of HTTP, we leave it as an exercise for the reader to pick a side and defend it.
=== SECTION 9.4: Applications > Overlay Networks ===
[9.4_s0000] From its inception, the Internet has adopted a clean model, in which the routers inside the network are responsible for forwarding packets from source to destination, and application programs run on the hosts connected to the edges of the network.
[9.4_s0001] The client/server paradigm illustrated by the applications discussed in the first two sections of this chapter certainly adhere to this model.
[9.4_s0002] In the last few years, however, the distinction between packet forwarding and application processing has become less clear.
[9.4_s0003] New applications are being distributed across the Internet, and in many cases these applications make their own forwarding decisions.
[9.4_s0004] These new hybrid applications can sometimes be implemented by extending traditional routers and switches to support a modest amount of application-specific processing.
[9.4_s0005] For example, so-called level-7 switches sit in front of server clusters and forward HTTP requests to a specific server based on the requested URL.
[9.4_s0006] However, overlay networks are quickly emerging as the mechanism of choice for introducing new functionality into the Internet.
[9.4_s0007] You can think of an overlay as a logical network implemented on top of some underlying network.
[9.4_s0008] By this definition, the Internet started out as an overlay network on top of the links provided by the old telephone network.
[9.4_s0009] Figure depicts an overlay implemented on top of an underlying network.
[9.4_s0010] Each node in the overlay also exists in the underlying network; it processes and forwards packets in an application-specific way.
[9.4_s0011] The links that connect the overlay nodes are implemented as tunnels through the underlying network.
[9.4_s0012] Multiple overlay networks can exist on top of the same underlying network—each implementing its own application-specific behavior—and overlays can be nested, one on top of another.
[9.4_s0013] For example, all of the example overlay networks discussed in this section treat today’s Internet as the underlying network.
[9.4_s0014] We have already seen examples of tunneling, for example, to implement virtual private networks (VPNs).
[9.4_s0015] As a brief refresher, the nodes on either end of a tunnel treat the multi-hop path between them as a single logical link, the nodes that are tunneled through forward packets based on the outer header, never aware that the end nodes have attached an inner header.
[9.4_s0016] Figure shows three overlay nodes (A, B, and C) connected by a pair of tunnels.
[9.4_s0017] In this example, overlay node B might make a forwarding decision for packets from A to C based on the inner header (IHdr), and then attach an outer header (OHdr) that identifies C as the destination in the underlying network.
[9.4_s0018] Nodes A, B, and C are able to interpret both the inner and outer header, whereas the intermediate routers understand only the outer header.
[9.4_s0019] Similarly, A, B, and C have addresses in both the overlay network and the underlying network, but they are not necessarily the same; for example, their underlying address might be a 32-bit IP address, while their overlay address might be an experimental 128-bit address.
[9.4_s0020] In fact, the overlay need not use conventional addresses at all but may route based on URLs, domain names, an XML query, or even the content of the packet.
[9.4_s0021] 9.4.1 Routing Overlays  The simplest kind of overlay is one that exists purely to support an alternative routing strategy; no additional application-level processing is performed at the overlay nodes.
[9.4_s0022] You can view a virtual private network (VPN) as an example of a routing overlay, but one that doesn’t so much define an alternative strategy or algorithm as it does alternative routing table entries to be processed by the standard IP forwarding algorithm.
[9.4_s0023] In this particular case, the overlay is said to use “IP tunnels,” and the ability to utilize these VPNs is supported in many commercial routers.
[9.4_s0024] Suppose, however, you wanted to use a routing algorithm that commercial router vendors were not willing to include in their products.
[9.4_s0025] How would you go about doing it?
[9.4_s0026] You could simply run your algorithm on a collection of end hosts, and tunnel through the Internet routers.
[9.4_s0027] These hosts would behave like routers in the overlay network: As hosts they are probably connected to the Internet by only one physical link, but as a node in the overlay they would be connected to multiple neighbors via tunnels.
[9.4_s0028] Since overlays, almost by definition, are a way to introduce new technologies independent of the standardization process, there are no standard overlays we can point to as examples.
[9.4_s0029] Instead, we illustrate the general idea of routing overlays by describing several experimental systems that have been built by network researchers.
[9.4_s0030] Experimental Versions of IP  Overlays are ideal for deploying experimental versions of IP that you hope will eventually take over the world.
[9.4_s0031] For example, IP multicast started off as an extension to IP and even today is not enabled in many Internet routers.
[9.4_s0032] The MBone (multicast backbone) was an overlay network that implemented IP multicast on top of the unicast routing provided by the Internet.
[9.4_s0033] A number of multimedia conference tools were developed for and deployed on the Mbone.
[9.4_s0034] For example, IETF meetings—which are a week long and attract thousands of participants—were for many years broadcast over the MBone.
[9.4_s0035] (Today, the wide availability of commercial conferencing tools have replaced the MBone-based approach.)
[9.4_s0036] Like VPNs, the MBone used both IP tunnels and IP addresses, but unlike VPNs, the MBone implemented a different forwarding algorithm—forwarding packets to all downstream neighbors in the shortest path multicast tree.
[9.4_s0037] As an overlay, multicast-aware routers tunnel through legacy routers, with the hope that one day there will be no more legacy routers.
[9.4_s0038] The 6-BONE was a similar overlay that was used to incrementally deploy IPv6.
[9.4_s0039] Like the MBone, the 6-BONE used tunnels to forward packets through IPv4 routers.
[9.4_s0040] Unlike the MBone, however, 6-BONE nodes did not simply provide a new interpretation of IPv4’s 32-bit addresses.
[9.4_s0041] Instead, they forwarded packets based on IPv6’s 128-bit address space.
[9.4_s0042] The 6-BONE also supported IPv6 multicast.
[9.4_s0043] (Today, commercial routers support IPv6, but again, overlays are a valuable approach while a new technology is being evaluated and tuned.)
[9.4_s0044] End System Multicast
[9.4_s0045] Although IP multicast is popular with researchers and certain segments of the networking community, its deployment in the global Internet has been limited at best.
[9.4_s0046] In response, multicast-based applications like videoconferencing have recently turned to an alternative strategy, called end system multicast.
[9.4_s0047] The idea of end system multicast is to accept that IP multicast will never become ubiquitous and to instead let the end hosts that are participating in a particular multicast-based application implement their own multicast trees.
[9.4_s0048] Before describing how end system multicast works, it is important to first understand that, unlike VPNs and the MBone, end system multicast assumes that only Internet hosts (as opposed to Internet routers) participate in the overlay.
[9.4_s0049] Moreover, these hosts typically exchange messages with each other through UDP tunnels rather than IP tunnels, making it easy to implement as regular application programs.
[9.4_s0050] This makes it possible to view the underlying network as a fully connected graph, since every host in the Internet is able to send a message to every other host.
[9.4_s0051] Abstractly, then, end system multicast solves the following problem: Starting with a fully connected graph representing the Internet, the goal is to find the embedded multicast tree that spans all the group members.
[9.4_s0052] Note that there is a simpler version of this problem, enabled by the ready availability of cloud-hosted VMs around the world.
[9.4_s0053] The multicast-aware “end systems” can be VMs running at multiple sites.
[9.4_s0054] As these sites are well-known and relatively fixed, it’s possible to construct a static multicast tree in the cloud, and have the actual end-hosts simply connect to the nearest cloud location.
[9.4_s0055] But for the sake of completeness, the following describes the approach in its full glory.
[9.4_s0056] Since we take the underlying Internet to be fully connected, a naive solution would be to have each source directly connected to each member of the group.
[9.4_s0057] In other words, end system multicast could be implemented by having each node send unicast messages to every group member.
[9.4_s0058] To see the problem in doing this, especially compared to implementing IP multicast in routers, consider the example topology in Figure.
[9.4_s0059] Figure depicts an example physical topology, where R1 and R2 are routers connected by a low-bandwidth transcontinental link; A, B, C, and D are end hosts; and link delays are given as edge weights.
[9.4_s0060] Assuming A wants to send a multicast message to the other three hosts, Figure shows how naive unicast transmission would work.
[9.4_s0061] This is clearly undesirable because the same message must traverse the link A-R1 three times, and two copies of the message traverse R1-R2.
[9.4_s0062] Figure depicts the IP multicast tree constructed by the Distance Vector Multicast Routing Protocol (DVMRP).
[9.4_s0063] Clearly, this approach eliminates the redundant messages.
[9.4_s0064] Without support from the routers, however, the best one can hope for with end system multicast is a tree similar to the one shown in Figure.
[9.4_s0065] End system multicast defines an architecture for constructing this tree.
[9.4_s0066] The general approach is to support multiple levels of overlay networks, each of which extracts a subgraph from the overlay below it, until we have selected the subgraph that the application expects.
[9.4_s0067] For end system multicast, in particular, this happens in two stages:
[9.4_s0068] First we construct a simple mesh overlay on top of the fully connected Internet, and then we select a multicast tree within this mesh.
[9.4_s0069] The idea is illustrated in Figure, again assuming the four end hosts A, B, C, and D.
[9.4_s0070] The first step is the critical one: Once we have selected a suitable mesh overlay, we simply run a standard multicast routing algorithm (e.g., DVMRP) on top of it to build the multicast tree.
[9.4_s0071] We also have the luxury of ignoring the scalability issue that Internet-wide multicast faces since the intermediate mesh can be selected to include only those nodes that want to participate in a particular multicast group.
[9.4_s0072] The key to constructing the intermediate mesh overlay is to select a topology that roughly corresponds to the physical topology of the underlying Internet, but we have to do this without anyone telling us what the underlying Internet actually looks like since we are running only on end hosts and not routers.
[9.4_s0073] The general strategy is for the end hosts to measure the roundtrip latency to other nodes and decide to add links to the mesh only when they like what they see.
[9.4_s0074] This works as follows.
[9.4_s0075] First, assuming a mesh already exists, each node exchanges the list of all other nodes it believes is part of the mesh with its directly connected neighbors.
[9.4_s0076] When a node receives such a membership list from a neighbor, it incorporates that information into its membership list and forwards the resulting list to its neighbors.
[9.4_s0077] This information eventually propagates through the mesh, much as in a distance vector routing protocol.
[9.4_s0078] When a host wants to join the multicast overlay, it must know the IP address of at least one other node already in the overlay.
[9.4_s0079] It then sends a “join mesh” message to this node.
[9.4_s0080] This connects the new node to the mesh by an edge to the known node.
[9.4_s0081] In general, the new node might send a join message to multiple current nodes, thereby joining the mesh by multiple links.
[9.4_s0082] Once a node is connected to the mesh by a set of links, it periodically sends “keepalive” messages to its neighbors, letting them know that it still wants to be part of the group.
[9.4_s0083] When a node leaves the group, it sends a “leave mesh” message to its directly connected neighbors, and this information is propagated to the other nodes in the mesh via the membership list described above.
[9.4_s0084] Alternatively, a node can fail or just silently decide to quit the group, in which case its neighbors detect that it is no longer sending “keep alive” messages.
[9.4_s0085] Some node departures have little effect on the mesh, but should a node detect that the mesh has become partitioned due to a departing node, it creates a new edge to a node in the other partition by sending it a “join mesh” message.
[9.4_s0086] Note that multiple neighbors can simultaneously decide that a partition has occurred in the mesh, leading to multiple cross-partition edges being added to the mesh.
[9.4_s0087] As described so far, we will end up with a mesh that is a subgraph of the original fully connected Internet, but it may have suboptimal performance because (1) initial neighbor selection adds random links to the topology, (2) partition repair might add edges that are essential at the moment but not useful in the long run, (3) group membership may change due to dynamic joins and departures, and (4) underlying network conditions may change.
[9.4_s0088] What needs to happen is that the system must evaluate the value of each edge, resulting in new edges being added to the mesh and existing edges being removed over time.
[9.4_s0089] To add new edges, each node i periodically probes some random member j that it is not currently connected to in the mesh, measures the round-trip latency of edge (i,j), and then evaluates the utility of adding this edge.
[9.4_s0090] If the utility is above a certain threshold, link (i,j) is added to the mesh.
[9.4_s0091] Evaluating the utility of adding edge (i,j) might look something like this:  Deciding to remove an edge is similar, except each node i computes the cost of each link to current neighbor j as follows:  It then picks the neighbor with the lowest cost, and drops it if the cost falls below a certain threshold.
[9.4_s0092] Finally, since the mesh is maintained using what is essentially a distance vector protocol, it is trivial to run DVMRP to find an appropriate multicast tree in the mesh.
[9.4_s0093] Note that, although it is not possible to prove that the protocol just described results in the optimum mesh network, thereby allowing DVMRP to select the best possible multicast tree, both simulation and extensive practical experience suggests that it does a good job.
[9.4_s0094] Resilient Overlay Networks  Another function that can be performed by an overlay is to find alternative routes for traditional unicast applications.
[9.4_s0095] Such overlays exploit the observation that the triangle inequality does not hold in the Internet.
[9.4_s0096] Figure illustrates what we mean by this.
[9.4_s0097] It is not uncommon to find three sites in the Internet—call them A, B, and C—such that the latency between A and B is greater than the sum of the latencies from A to C and from C to B. That is, sometimes you would be better off indirectly sending your packets via some intermediate node than sending them directly to the destination.
[9.4_s0098] How can this be?
[9.4_s0099] Well, the Border Gateway Protocol (BGP) never promised that it would find the shortest route between any two sites; it only tries to find some route.
[9.4_s0100] To make matters more complex, BGP’s routes are heavily influenced by policy issues, such as who is paying whom to carry their traffic.
[9.4_s0101] This often happens, for example, at peering points between major backbone ISPs.
[9.4_s0102] In short, that the triangle inequality does not hold in the Internet should not come as a surprise.
[9.4_s0103] How do we exploit this observation?
[9.4_s0104] The first step is to realize that there is a fundamental tradeoff between the scalability and optimality of a routing algorithm.
[9.4_s0105] On the one hand, BGP scales to very large networks, but often does not select the best possible route and is slow to adapt to network outages.
[9.4_s0106] On the other hand, if you were only worried about finding the best route among a handful of sites, you could do a much better job of monitoring the quality of every path you might use, thereby allowing you to select the best possible route at any moment in time.
[9.4_s0107] An experimental overlay, called the Resilient Overlay Network (RON), did exactly this.
[9.4_s0108] RON scaled to only a few dozen nodes because it used an N ×
[9.4_s0109] N strategy of closely monitoring (via active probes) three aspects of path quality—latency, available bandwidth, and loss probability—between every pair of sites.
[9.4_s0110] It was then able to both select the optimal route between any pair of nodes, and rapidly change routes should network conditions change.
[9.4_s0111] Experience showed that RON was able to deliver modest performance improvements to applications, but more importantly, it recovered from network failures much more quickly.
[9.4_s0112] For example, during one 64-hour period in 2001, an instance of RON running on 12 nodes detected 32 outages lasting over 30 minutes, and it was able to recover from all of them in less than 20 seconds on average.
[9.4_s0113] This experiment also suggested that forwarding data through just one intermediate node is usually sufficient to recover from Internet failures.
[9.4_s0114] Since RON was not designed to be a scalable approach, it is not possible to use RON to help random host A communicate with random host B; A and B have to know ahead of time that they are likely to communicate and then join the same RON.
[9.4_s0115] However, RON seems like a good idea in certain settings, such as when connecting a few dozen corporate sites spread across the Internet or allowing you and 50 of your friends to establish your own private overlay for the sake of running some application.
[9.4_s0116] (Today, this idea is put to practice with the marketing name Software-Defined WAN, or SD-WAN.)
[9.4_s0117] The real question, though, is what happens when everyone starts to run their own RON.
[9.4_s0118] Does the overhead of millions of RONs aggressively probing paths swamp the network, and does anyone see improved behavior when many RONs compete for the same paths?
[9.4_s0119] These questions are still unanswered.
[9.4_s0120] 9.4.2 Peer-to-Peer Networks  Music-sharing applications like Napster and KaZaA introduced the term “peer-to-peer” into the popular vernacular.
[9.4_s0121] But what exactly does it mean for a system to be “peer-to-peer”?
[9.4_s0122] Certainly in the context of sharing MP3 files it means not having to download music from a central site, but instead being able to access music files directly from whoever in the Internet happens to have a copy stored on their computer.
[9.4_s0123] More generally then, we could say that a peer-to-peer network allows a community of users to pool their resources (content, storage, network bandwidth, disk bandwidth, CPU), thereby providing access to a larger archival store, larger video/audio conferences, more complex searches and computations, and so on than any one user could afford individually.
[9.4_s0124] Quite often, attributes like decentralized and self-organizing are mentioned when discussing peer-to-peer networks, meaning that individual nodes organize themselves into a network without any centralized coordination.
[9.4_s0125] If you think about it, terms like these could be used to describe the Internet itself.
[9.4_s0126] Ironically, however, Napster was not a true peer-to-peer system by this definition since it depended on a central registry of known files, and users had to search this directory to find what machine offered a particular file.
[9.4_s0127] It was only the last step—actually downloading the file—that took place between machines that belong to two users, but this is little more than a traditional client/server transaction.
[9.4_s0128] The only difference is that the server is owned by someone just like you rather than a large corporation.
[9.4_s0129] So we are back to the original question: What’s interesting about peer-to-peer networks?
[9.4_s0130] One answer is that both the process of locating an object of interest and the process of downloading that object onto your local machine happen without your having to contact a centralized authority, and at the same time the system is able to scale to millions of nodes.
[9.4_s0131] A peer-to-peer system that can accomplish these two tasks in a decentralized manner turns out to be an overlay network, where the nodes are those hosts that are willing to share objects of interest (e.g., music and other assorted files), and the links (tunnels) connecting these nodes represent the sequence of machines that you have to visit to track down the object you want.
[9.4_s0132] This description will become clearer after we look at two examples.
[9.4_s0133] Gnutella  Gnutella is an early peer-to-peer network that attempted to distinguish between exchanging music (which likely violates somebody’s copyright) and the general sharing of files (which must be good since we’ve been taught to share since the age of two).
[9.4_s0134] What’s interesting about Gnutella is that it was one of the first such systems to not depend on a centralized registry of objects.
[9.4_s0135] Instead, Gnutella participants arrange themselves into an overlay network similar to the one shown in Figure.
[9.4_s0136] That is, each node that runs the Gnutella software (i.e., implements the Gnutella protocol) knows about some set of other machines that also run the Gnutella software.
[9.4_s0137] The relationship “A and B know each other” corresponds to the edges in this graph.
[9.4_s0138] (We’ll talk about how this graph is formed in a moment.)
[9.4_s0139] Whenever the user on a given node wants to find an object, Gnutella sends a QUERY message for the object—for example, specifying the file’s name—to its neighbors in the graph.
[9.4_s0140] If one of the neighbors has the object, it responds to the node that sent it the query with a QUERY RESPONSE message, specifying where the object can be downloaded (e.g., an IP address and TCP port number).
[9.4_s0141] That node can subsequently use GET or PUT messages to access the object.
[9.4_s0142] If the node cannot resolve the query, it forwards the QUERY message to each of its neighbors (except the one that sent it the query), and the process repeats.
[9.4_s0143] In other words, Gnutella floods the overlay to locate the desired object.
[9.4_s0144] Gnutella sets a TTL on each query so this flood does not continue indefinitely.
[9.4_s0145] In addition to the TTL and query string, each QUERY message contains a unique query identifier (QID), but it does not contain the identity of the original message source.
[9.4_s0146] Instead, each node maintains a record of the QUERY messages it has seen recently: both the QID and the neighbor that sent it the QUERY.
[9.4_s0147] It uses this history in two ways.
[9.4_s0148] First, if it ever receives a QUERY with a QID that matches one it has seen recently, the node does not forward the QUERY message.
[9.4_s0149] This serves to cut off forwarding loops more quickly than the TTL might have done.
[9.4_s0150] Second, whenever the node receives a QUERY RESPONSE from a downstream neighbor, it knows to forward the response to the upstream neighbor that originally sent it the QUERY message.
[9.4_s0151] In this way, the response works its way back to the original node without any of the intermediate nodes knowing who wanted to locate this particular object in the first place.
[9.4_s0152] Returning to the question of how the graph evolves, a node certainly has to know about at least one other node when it joins a Gnutella overlay.
[9.4_s0153] The new node is attached to the overlay by at least this one link.
[9.4_s0154] After that, a given node learns about other nodes as the result of QUERY RESPONSE messages, both for objects it requested and for responses that just happen to pass through it.
[9.4_s0155] A node is free to decide which of the nodes it discovers in this way that it wants to keep as a neighbor.
[9.4_s0156] The Gnutella protocol provides PING and PONG messages by which a node probes whether or not a given neighbor still exists and that neighbor’s response, respectively.
[9.4_s0157] It should be clear that Gnutella as described here is not a particularly clever protocol, and subsequent systems have tried to improve upon it.
[9.4_s0158] One dimension along which improvements are possible is in how queries are propagated.
[9.4_s0159] Flooding has the nice property that it is guaranteed to find the desired object in the fewest possible hops, but it does not scale well.
[9.4_s0160] It is possible to forward queries randomly, or according to the probability of success based on past results.
[9.4_s0161] A second dimension is to proactively replicate the objects, since the more copies of a given object there are, the easier it should be to find a copy.
[9.4_s0162] Alternatively, one could develop a completely different strategy, which is the topic we consider next.
[9.4_s0163] Structured Overlays  At the same time file sharing systems started fighting to fill the void left by Napster, the research community began to explore an alternative design for peer-to-peer networks.
[9.4_s0164] We refer to these networks as structured, to contrast them with the essentially random (unstructured) way in which a Gnutella network evolves.
[9.4_s0165] Unstructured overlays like Gnutella employ trivial overlay construction and maintenance algorithms, but the best they can offer is unreliable, random search.
[9.4_s0166] In contrast, structured overlays are designed to conform to a particular graph structure that allows reliable and efficient (probabilistically bounded delay) object location, in return for additional complexity during overlay construction and maintenance.
[9.4_s0167] If you think about what we are trying to do at a high level, there are two questions to consider: (1) How do we map objects onto nodes, and (2) How do we route a request to the node that is responsible for a given object?
[9.4_s0168] We start with the first question, which has a simple statement: How do we map an object with name x into the address of some node n that is able to serve that object?
[9.4_s0169] While traditional peer-to-peer networks have no control over which node hosts object x, if we could control how objects get distributed over the network, we might be able to do a better job of finding those objects at a later time.
[9.4_s0170] A well-known technique for mapping names into an address is to use a hash table, so that  implies object x is first placed on node n, and at a later time a client trying to locate x would only have to perform the hash of x to determine that it is on node n.
[9.4_s0171] A hash-based approach has the nice property that it tends to spread the objects evenly across the set of nodes, but straightforward hashing algorithms suffer from a fatal flaw: How many possible values of n should we allow?
[9.4_s0172] (In hashing terminology, how many buckets should there be?)
[9.4_s0173] Naively, we could decide that there are, say, 101 possible hash values, and we use a modulo hash function; that is,  Unfortunately, if there are more than 101 nodes willing to host objects, then we can’t take advantage of all of them.
[9.4_s0174] On the other hand, if we select a number larger than the largest possible number of nodes, then there will be some values of x that will hash into an address for a node that does not exist.
[9.4_s0175] There is also the not-so-small issue of translating the value returned by the hash function into an actual IP address.
[9.4_s0176] To address these issues, structured peer-to-peer networks use an algorithm known as consistent hashing, which hashes a set of objects x uniformly across a large ID space.
[9.4_s0177] Figure visualizes a 128-bit ID space as a circle, where we use the algorithm to place both objects  and nodes  onto this circle.
[9.4_s0178] Since a 128-bit ID space is enormous, it is unlikely that an object will hash to exactly the same ID as a machine’s IP address hashes to.
[9.4_s0179] To account for this unlikelihood, each object is maintained on the node whose ID is closest, in this 128-bit space, to the object ID.
[9.4_s0180] In other words, the idea is to use a high-quality hash function to map both nodes and objects into the same large, sparse ID space; you then map objects to nodes by numerical proximity of their respective identifiers.
[9.4_s0181] Like ordinary hashing, this distributes objects fairly evenly across nodes, but, unlike ordinary hashing, only a small number of objects have to move when a node (hash bucket) joins or leaves.
[9.4_s0182] We now turn to the second question—how does a user that wants to access object x know which node is closest in x\ ’s ID in this space?
[9.4_s0183] One possible answer is that each node keeps a complete table of node IDs and their associated IP addresses, but this would not be practical for a large network.
[9.4_s0184] The alternative, which is the approach used by structured peer-to-peer networks, is to route a message to this node!
[9.4_s0185] In other words, if we construct the overlay in a clever way—which is the same as saying that we need to choose entries for a node’s routing table in a clever way—then we find a node simply by routing toward it.
[9.4_s0186] Collectively, this approach is sometimes called a distributed hash table (DHT), since conceptually, the hash table is distributed over all the nodes in the network.
[9.4_s0187] Figure illustrates what happens for a simple 28-bit ID space.
[9.4_s0188] To keep the discussion as concrete as possible, we consider the approach used by a particular peer-to-peer network called Pastry.
[9.4_s0189] Other systems work in a similar manner.
[9.4_s0190] Suppose you are at the node with id 65a1fc (hex) and you are trying to locate the object with ID d46a1c.
[9.4_s0191] You realize that your ID shares nothing with the object’s, but you know of a node that shares at least the prefix d.
[9.4_s0192] That node is closer than you in the 128-bit ID space, so you forward the message to it.
[9.4_s0193] (We do not give the format of the message being forwarded, but you can think of it as saying “locate object d46a1c”.)
[9.4_s0194] Assuming node d13da3 knows of another node that shares an even longer prefix with the object, it forwards the message on.
[9.4_s0195] This process of moving closer in ID-space continues until you reach a node that knows of no closer node.
[9.4_s0196] This node is, by definition, the one that hosts the object.
[9.4_s0197] Keep in mind that as we logically move through “ID space” the message is actually being forwarded, node to node, through the underlying Internet.
[9.4_s0198] Each node maintains a both routing table (more below) and the IP addresses of a small set of numerically larger and smaller node IDs.
[9.4_s0199] This is called the node’s leaf set.
[9.4_s0200] The relevance of the leaf set is that, once a message is routed to any node in the same leaf set as the node that hosts the object, that node can directly forward the message to the ultimate destination.
[9.4_s0201] Said another way, the leaf set facilitates correct and efficient delivery of a message to the numerically closest node, even though multiple nodes may exist that share a maximal length prefix with the object ID.
[9.4_s0202] Moreover, the leaf set makes routing more robust because any of the nodes in a leaf set can route a message just as well as any other node in the same set.
[9.4_s0203] Thus, if one node is unable to make progress routing a message, one of its neighbors in the leaf set may be able to.
[9.4_s0204] In summary, the routing procedure is defined as follows:  The routing table, denoted RouteTab, is a two-dimensional array.
[9.4_s0205] It has a row for every hex digit in an ID (there such 32 digits in a 128-bit ID) and a column for every hex value (there are obviously 16 such values).
[9.4_s0206] Every entry in row i shares a prefix of length i with this node, and within this row the entry in column j has the hex value j in the i+1-th position.
[9.4_s0207] Figure shows the first three rows of an example routing table for node 65a1fcx, where x denotes an unspecified suffix.
[9.4_s0208] This figure shows the ID prefix matched by every entry in the table.
[9.4_s0209] It does not show the actual value contained in this entry—the IP address of the next node to route to.
[9.4_s0210] Adding a node to the overlay works much like routing a “locate object message” to an object.
[9.4_s0211] The new node must know of at least one current member.
[9.4_s0212] It asks this member to route an “add node message” to the node numerically closest to the ID of the joining node, as shown in Figure.
[9.4_s0213] It is through this routing process that the new node learns about other nodes with a shared prefix and is able to begin filling out its routing table.
[9.4_s0214] Over time, as additional nodes join the overlay, existing nodes also have the option of including information about the newly joined node in their routing tables.
[9.4_s0215] They do this when the new node adds a longer prefix than they currently have in their table.
[9.4_s0216] Neighbors in the leaf sets also exchange routing tables with each other, which means that over time routing information propagates through the overlay.
[9.4_s0217] The reader may have noticed that although structured overlays provide a probabilistic bound on the number of routing hops required to locate a given object—the number of hops in Pastry is bounded by log_{16}N, where N is the number of nodes in the overlay—each hop may contribute substantial delay.
[9.4_s0218] This is because each intermediate node may be at a random location in the Internet.
[9.4_s0219] (In the worst case, each node is on a different continent!)
[9.4_s0220] In fact, in a world-wide overlay network using the algorithm as described above, the expected delay of each hop is the average delay among all pairs of nodes in the Internet!
[9.4_s0221] Fortunately, one can do much better in practice.
[9.4_s0222] The idea is to choose each routing table entry such that it refers to a nearby node in the underlying physical network, among all nodes with an ID prefix that is appropriate for the entry.
[9.4_s0223] It turns out that doing so achieves end-to-end routing delays that are within a small factor of the delay between source and destination node.
[9.4_s0224] Finally, the discussion up to this point has focused on the general problem of locating objects in a peer-to-peer network.
[9.4_s0225] Given such a routing infrastructure, it is possible to build different services.
[9.4_s0226] For example, a file sharing service would use file names as object names.
[9.4_s0227] To locate a file, you first hash its name into a corresponding object ID and then route a “locate object message” to this ID.
[9.4_s0228] The system might also replicate each file across multiple nodes to improve availability.
[9.4_s0229] Storing multiple copies on the leaf set of the node to which a given file normally routes would be one way of doing this.
[9.4_s0230] Keep in mind that even though these nodes are neighbors in the ID space, they are likely to be physically distributed across the Internet.
[9.4_s0231] Thus, while a power outage in an entire city might take down physically close replicas of a file in a traditional file system, one or more replicas would likely survive such a failure in a peer-to-peer network.
[9.4_s0232] Services other than file sharing can also be built on top of distributed hash tables.
[9.4_s0233] Consider multicast applications, for example.
[9.4_s0234] Instead of constructing a multicast tree from a mesh, one could construct the tree from edges in the structured overlay, thereby amortizing the cost of overlay construction and maintenance across several applications and multicast groups.
[9.4_s0235] BitTorrent  BitTorrent is a peer-to-peer file sharing protocol devised by Bram Cohen.
[9.4_s0236] It is based on replicating the file or, rather, replicating segments of the file, which are called pieces.
[9.4_s0237] Any particular piece can usually be downloaded from multiple peers, even if only one peer has the entire file.
[9.4_s0238] The primary benefit of BitTorrent’s replication is avoiding the bottleneck of having only one source for a file.
[9.4_s0239] This is particularly useful when you consider that any given computer has a limited speed at which it can serve files over its uplink to the Internet, often quite a low limit due to the asymmetric nature of most broadband networks.
[9.4_s0240] The beauty of BitTorrent is that replication is a natural side effect of the downloading process: As soon as a peer downloads a particular piece, it becomes another source for that piece.
[9.4_s0241] The more peers downloading pieces of the file, the more piece replication occurs, distributing the load proportionately, and the more total bandwidth is available to share the file with others.
[9.4_s0242] Pieces are downloaded in random order to avoid a situation where peers find themselves lacking the same set of pieces.
[9.4_s0243] Each file is shared via its own independent BitTorrent network, called a swarm.
[9.4_s0244] (A swarm could potentially share a set of files, but we describe the single file case for simplicity.)
[9.4_s0245] The lifecycle of a typical swarm is as follows.
[9.4_s0246] The swarm starts as a singleton peer with a complete copy of the file.
[9.4_s0247] A node that wants to download the file joins the swarm, becoming its second member, and begins downloading pieces of the file from the original peer.
[9.4_s0248] In doing so, it becomes another source for the pieces it has downloaded, even if it has not yet downloaded the entire file.
[9.4_s0249] (In fact, it is common for peers to leave the swarm once they have completed their downloads, although they are encouraged to stay longer.)
[9.4_s0250] Other nodes join the swarm and begin downloading pieces from multiple peers, not just the original peer.
[9.4_s0251] See Figure.
[9.4_s0252] If the file remains in high demand, with a stream of new peers replacing those who leave the swarm, the swarm could remain active indefinitely; if not, it could shrink back to include only the original peer until new peers join the swarm.
[9.4_s0253] Now that we have an overview of BitTorrent, we can ask how requests are routed to the peers that have a given piece.
[9.4_s0254] To make requests, a would-be downloader must first join the swarm.
[9.4_s0255] It starts by downloading a file containing meta-information about the file and swarm.
[9.4_s0256] The file, which may be easily replicated, is typically downloaded from a web server and discovered by following links from Web pages.
[9.4_s0257] It contains:  -  The target file’s size  -  The piece size  -  SHA-1 hash values precomputed from each piece  -  The URL of the swarm’s tracker  A tracker is a server that tracks a swarm’s current membership.
[9.4_s0258] We’ll see later that BitTorrent can be extended to eliminate this point of centralization, with its attendant potential for bottleneck or failure.
[9.4_s0259] The would-be downloader then joins the swarm, becoming a peer, by sending a message to the tracker giving its network address and a peer ID that it has generated randomly for itself.
[9.4_s0260] The message also carries a SHA-1 hash of the main part of the file, which is used as a swarm ID.
[9.4_s0261] Let’s call the new peer P.
[9.4_s0262] The tracker replies to P with a partial list of peers giving their IDs and network addresses, and P establishes connections, over TCP, with some of these peers.
[9.4_s0263] Note that P is directly connected to just a subset of the swarm, although it may decide to contact additional peers or even request more peers from the tracker.
[9.4_s0264] To establish a BitTorrent connection with a particular peer after their TCP connection has been established, P sends P’s own peer ID and swarm ID, and the peer replies with its peer ID and swarm ID.
[9.4_s0265] If the swarm IDs don’t match, or the reply peer ID is not what P expects, the connection is aborted.
[9.4_s0266] The resulting BitTorrent connection is symmetric: Each end can download from the other.
[9.4_s0267] Each end begins by sending the other a bitmap reporting which pieces it has, so each peer knows the other’s initial state.
[9.4_s0268] Whenever a downloader (D) finishes downloading another piece, it sends a message identifying that piece to each of its directly connected peers, so those peers can update their internal representation of D’s state.
[9.4_s0269] This, finally, is the answer to the question of how a download request for a piece is routed to a peer that has the piece, because it means that each peer knows which directly connected peers have the piece.
[9.4_s0270] If D needs a piece that none of its connections has, it could connect to more or different peers (it can get more from the tracker) or occupy itself with other pieces in hopes that some of its connections will obtain the piece from their connections.
[9.4_s0271] How are objects—in this case, pieces—mapped onto peer nodes?
[9.4_s0272] Of course each peer eventually obtains all the pieces, so the question is really about which pieces a peer has at a given time before it has all the pieces or, equivalently, about the order in which a peer downloads pieces.
[9.4_s0273] The answer is that they download pieces in random order, to keep them from having a strict subset or superset of the pieces of any of their peers.
[9.4_s0274] The BitTorrent described so far utilizes a central tracker that constitutes a single point of failure for the swarm and could potentially be a performance bottleneck.
[9.4_s0275] Also, providing a tracker can be a nuisance for someone who would like to make a file available via BitTorrent.
[9.4_s0276] Newer versions of BitTorrent additionally support “trackerless” swarms that use a DHT-based implementation.
[9.4_s0277] BitTorrent client software that is trackerless capable implements not just a BitTorrent peer but also what we’ll call a peer finder (the BitTorrent terminology is simply node), which the peer uses to find peers.
[9.4_s0278] Peer finders form their own overlay network, using their own protocol over UDP to implement a DHT.
[9.4_s0279] Furthermore, a peer finder network includes peer finders whose associated peers belong to different swarms.
[9.4_s0280] In other words, while each swarm forms a distinct network of BitTorrent peers, a peer finder network instead spans swarms.
[9.4_s0281] Peer finders randomly generate their own finder IDs, which are the same size (160 bits) as swarm IDs.
[9.4_s0282] Each finder maintains a modest table containing primarily finders (and their associated peers) whose IDs are close to its own, plus some finders whose IDs are more distant.
[9.4_s0283] The following algorithm ensures that finders whose IDs are close to a given swarm ID are likely to know of peers from that swarm; the algorithm simultaneously provides a way to look them up.
[9.4_s0284] When a finder F needs to find peers from a particular swarm, it sends a request to the finders in its table whose IDs are close to that swarm’s ID.
[9.4_s0285] If a contacted finder knows of any peers for that swarm, it replies with their contact information.
[9.4_s0286] Otherwise, it replies with the contact information of the finders in its table that are close to the swarm, so that F can iteratively query those finders.
[9.4_s0287] After the search is exhausted, because there are no finders closer to the swarm, F inserts the contact information for itself and its associated peer into the finders closest to the swarm.
[9.4_s0288] The net effect is that peers for a particular swarm get entered in the tables of the finders that are close to that swarm.
[9.4_s0289] The above scheme assumes that F is already part of the finder network, that it already knows how to contact some other finders.
[9.4_s0290] This assumption is true for finder installations that have run previously, because they are supposed to save information about other finders, even across executions.
[9.4_s0291] If a swarm uses a tracker, its peers are able to tell their finders about other finders (in a reversal of the peer and finder roles) because the BitTorrent peer protocol has been extended to exchange finder contact information.
[9.4_s0292] But, how can a newly installed finder discover other finders?
[9.4_s0293] The files for trackerless swarms include contact information for one or a few finders, instead of a tracker URL, for just that situation.
[9.4_s0294] An unusual aspect of BitTorrent is that it deals head-on with the issue of fairness, or good “network citizenship.”
[9.4_s0295] Protocols often depend on the good behavior of individual peers without being able to enforce it.
[9.4_s0296] For example, an unscrupulous Ethernet peer could get better performance by using a backoff algorithm that is more aggressive than exponential backoff, or an unscrupulous TCP peer could get better performance by not cooperating in congestion control.
[9.4_s0297] The good behavior that BitTorrent depends on is peers uploading pieces to other peers.
[9.4_s0298] Since the typical BitTorrent user just wants to download the file as quickly as possible, there is a temptation to implement a peer that tries to download all the pieces while doing as little uploading as possible—this is a bad peer.
[9.4_s0299] To discourage bad behavior, the BitTorrent protocol includes mechanisms that allow peers to reward or punish each other.
[9.4_s0300] If a peer is misbehaving by not nicely uploading to another peer, the second peer can choke the bad peer: It can decide to stop uploading to the bad peer, at least temporarily, and send it a message saying so.
[9.4_s0301] There is also a message type for telling a peer that it has been unchoked.
[9.4_s0302] The choking mechanism is also used by a peer to limit the number of its active BitTorrent connections, to maintain good TCP performance.
[9.4_s0303] There are many possible choking algorithms, and devising a good one is an art.
[9.4_s0304] 9.4.3 Content Distribution Networks  We have already seen how HTTP running over TCP allows web browsers to retrieve pages from web servers.
[9.4_s0305] However, anyone who has waited an eternity for a Web page to return knows that the system is far from perfect.
[9.4_s0306] Considering that the backbone of the Internet is now constructed from 40-Gbps links, it’s not obvious why this should happen.
[9.4_s0307] It is generally agreed that when it comes to downloading Web pages there are four potential bottlenecks in the system:  -  The first mile.
[9.4_s0308] The Internet may have high-capacity links in it, but that doesn’t help you download a Web page any faster when you’re connected by a 1.5Mbps DSL line or a poorly performing wireless link.  -  The last mile.
[9.4_s0309] The link that connects the server to the Internet can be overloaded by too many requests, even if the aggregate bandwidth of that link is quite high.  -
[9.4_s0310] The server itself.
[9.4_s0311] A server has a finite amount of resources (CPU, memory, disk bandwidth, etc.) and can be overloaded by too many concurrent requests.
[9.4_s0312] -  Peering points.
[9.4_s0313] The handful of ISPs that collectively implement the backbone of the Internet may internally have high-bandwidth pipes, but they have little motivation to provide high-capacity connectivity to their peers.
[9.4_s0314] If you are connected to ISP A and the server is connected to ISP B, then the page you request may get dropped at the point where A and B peer with each other.
[9.4_s0315] There’s not a lot anyone except you can do about the first problem, but it is possible to use replication to address the remaining problems.
[9.4_s0316] Systems that do this are often called Content Distribution Networks (CDNs).
[9.4_s0317] Akamai operates what is probably the best-known CDN.
[9.4_s0318] The idea of a CDN is to geographically distribute a collection of server surrogates that cache pages normally maintained in some set of backend servers.
[9.4_s0319] Thus, rather than having millions of users wait forever to contact when a big news story breaks—such a situation is known as a flash crowd—it is possible to spread this load across many servers.
[9.4_s0320] Moreover, rather than having to traverse multiple ISPs to reach www.cnn.com, if these surrogate servers happen to be spread across all the backbone ISPs, then it should be possible to reach one without having to cross a peering point.
[9.4_s0321] Clearly, maintaining thousands of surrogate servers all over the Internet is too expensive for any one site that wants to provide better access to its Web pages.
[9.4_s0322] Commercial CDNs provide this service for many sites, thereby amortizing the cost across many customers.
[9.4_s0323] Although we call them surrogate servers, in fact, they can just as correctly be viewed as caches.
[9.4_s0324] If they don’t have a page that has been requested by a client, they ask the backend server for it.
[9.4_s0325] In practice, however, the backend servers proactively replicate their data across the surrogates rather than wait for surrogates to request it on demand.
[9.4_s0326] It’s also the case that only static pages, as opposed to dynamic content, are distributed across the surrogates.
[9.4_s0327] Clients have to go to the backend server for any content that either changes frequently (e.g., sports scores and stock quotes) or is produced as the result of some computation (e.g., a database query).
[9.4_s0328] Having a large set of geographically distributed servers does not fully solve the problem.
[9.4_s0329] To complete the picture, CDNs also need to provide a set of redirectors that forward client requests to the most appropriate server, as shown in Figure.
[9.4_s0330] The primary objective of the redirectors is to select the server for each request that results in the best response time for the client.
[9.4_s0331] A secondary objective is for the system as a whole to process as many requests per second as the underlying hardware (network links and web servers) is able to support.
[9.4_s0332] The average number of requests that can be satisfied in a given time period—known as the system throughput—is primarily an issue when the system is under heavy load, such as when a flash crowd is accessing a small set of pages or a Distributed Denial of Service (DDoS) attacker is targeting a particular site, as happened to CNN, Yahoo, and several other high-profile sites in February 2000.
[9.4_s0333] CDNs use several factors to decide how to distribute client requests.
[9.4_s0334] For example, to minimize response time, a redirector might select a server based on its network proximity.
[9.4_s0335] In contrast, to improve the overall system throughput, it is desirable to evenly balance the load across a set of servers.
[9.4_s0336] Both throughput and response time are improved if the distribution mechanism takes locality into consideration; that is, it selects a server that is likely to already have the page being requested in its cache.
[9.4_s0337] The exact combination of factors that should be employed by a CDN is open to debate.
[9.4_s0338] This section considers some of the possibilities.
[9.4_s0339] Mechanisms  As described so far, a redirector is just an abstract function, although it sounds like what something a router might be asked to do since it logically forwards a request message much like a router forwards packets.
[9.4_s0340] In fact, there are several mechanisms that can be used to implement redirection.
[9.4_s0341] Note that for the purpose of this discussion we assume that each redirector knows the address of every available server.
[9.4_s0342] (From here on, we drop the “surrogate” qualifier and talk simply in terms of a set of servers.)
[9.4_s0343] In practice, some form of out-of-band communication takes place to keep this information up-to-date as servers come and go.
[9.4_s0344] First, redirection could be implemented by augmenting DNS to return different server addresses to clients.
[9.4_s0345] For example, when a client asks to resolve the name www.cnn.com, the DNS server could return the IP address of a server hosting CNN’s Web pages that is known to have the lightest load.
[9.4_s0346] Alternatively, for a given set of servers, it might just return addresses in a round-robin fashion.
[9.4_s0347] Note that the granularity of DNS-based redirection is usually at the level of a site (e.g., cnn.com) rather than a specific URL (e.g., https://www.cnn.com/2020/11/12/politics/biden-wins-arizona/index.html).
[9.4_s0348] However, when returning an embedded link, the server can rewrite the URL, thereby effectively pointing the client at the most appropriate server for that specific object.
[9.4_s0349] Commercial CDNs essentially use a combination of URL rewriting and DNS-based redirection.
[9.4_s0350] For scalability reasons, the high-level DNS server first points to a regional-level DNS server, which replies with the actual server address.
[9.4_s0351] In order to respond to changes quickly, the DNS servers tweak the TTL of the resource records they return to a very short period, such as 20 seconds.
[9.4_s0352] This is necessary so clients don’t cache results and thus fail to go back to the DNS server for the most recent URL-to-server mapping.
[9.4_s0353] Another possibility is to use the HTTP redirect feature: The client sends a request message to a server, which responds with a new (better) server that the client should contact for the page.
[9.4_s0354] Unfortunately, server-based redirection incurs an additional round-trip time across the Internet, and, even worse, servers can be vulnerable to being overloaded by the redirection task itself.
[9.4_s0355] Instead, if there is a node close to the client (e.g., a local Web proxy) that is aware of the available servers, then it can intercept the request message and instruct the client to instead request the page from an appropriate server.
[9.4_s0356] In this case, either the redirector would need to be on a choke point so that all requests leaving the site pass through it, or the client would have to cooperate by explicitly addressing the proxy (as with a classical, rather than transparent, proxy).
[9.4_s0357] At this point you may be wondering what CDNs have to do with overlay networks, and while viewing a CDN as an overlay is a bit of a stretch, they do share one very important trait in common.
[9.4_s0358] Like an overlay node, a proxy-based redirector makes an application-level routing decision.
[9.4_s0359] Rather than forward a packet based on an address and its knowledge of the network topology, it forwards HTTP requests based on a URL and its knowledge of the location and load of a set of servers.
[9.4_s0360] Today’s Internet architecture does not support redirection directly—where by “directly” we mean the client sends the HTTP request to the redirector, which forwards to the destination—so instead redirection is typically implemented indirectly by having the redirector return the appropriate destination address and the client contacts the server itself.
[9.4_s0361] Policies  We now consider some example policies that redirectors might use to forward requests.
[9.4_s0362] Actually, we have already suggested one simple policy—round-robin.
[9.4_s0363] A similar scheme would be to simply select one of the available servers at random.
[9.4_s0364] Both of these approaches do a good job of spreading the load evenly across the CDN, but they do not do a particularly good job of lowering the client-perceived response time.
[9.4_s0365] It’s obvious that neither of these two schemes takes network proximity into consideration, but, just as importantly, they also ignore locality.
[9.4_s0366] That is, requests for the same URL are forwarded to different servers, making it less likely that the page will be served from the selected server’s in-memory cache.
[9.4_s0367] This forces the server to retrieve the page from its disk, or possibly even from the backend server.
[9.4_s0368] How can a distributed set of redirectors cause requests for the same page to go to the same server (or small set of servers) without global coordination?
[9.4_s0369] The answer is surprisingly simple: All redirectors use some form of hashing to deterministically map URLs into a small range of values.
[9.4_s0370] The primary benefit of this approach is that no inter-redirector communication is required to achieve coordinated operation; no matter which redirector receives a URL, the hashing process produces the same output.
[9.4_s0371] So what makes for a good hashing scheme?
[9.4_s0372] The classic modulo hashing scheme—which hashes each URL modulo the number of servers—is not suitable for this environment.
[9.4_s0373] This is because should the number of servers change, the modulo calculation will result in a diminishing fraction of the pages keeping their same server assignments.
[9.4_s0374] While we do not expect frequent changes in the set of servers, the fact that the addition of new servers into the set will cause massive reassignment is undesirable.
[9.4_s0375] An alternative is to use the same consistent hashing algorithm discussed in the previous section.
[9.4_s0376] Specifically, each redirector first hashes every server into the unit circle.
[9.4_s0377] Then, for each URL that arrives, the redirector also hashes the URL to a value on the unit circle, and the URL is assigned to the server that lies closest on the circle to its hash value.
[9.4_s0378] If a node fails in this scheme, its load shifts to its neighbors (on the unit circle), so the addition or removal of a server only causes local changes in request assignments.
[9.4_s0379] Note that unlike the peer-to-peer case, where a message is routed from one node to another in order to find the server whose ID is closest to the objects, each redirector knows how the set of servers map onto the unit circle, so they can each, independently, select the “nearest” one.
[9.4_s0380] This strategy can easily be extended to take server load into account.
[9.4_s0381] Assume the redirector knows the current load of each of the available servers.
[9.4_s0382] This information may not be perfectly up-to-date, but we can imagine the redirector simply counting how many times it has forwarded a request to each server in the last few seconds and using this count as an estimate of that server’s current load.
[9.4_s0383] Upon receiving a URL, the redirector hashes the URL plus each of the available servers and sorts the resulting values.
[9.4_s0384] This sorted list effectively defines the order in which the redirector will consider the available servers.
[9.4_s0385] The redirector then walks down this list until it finds a server whose load is below some threshold.
[9.4_s0386] The benefit of this approach compared to plain consistent hashing is that server order is different for each URL, so if one server fails, its load is distributed evenly among the other machines.
[9.4_s0387] This approach is the basis for the Cache Array Routing Protocol (CARP) and is shown in pseudocode below.
[9.4_s0388] As the load increases, this scheme changes from using only the first server on the sorted list to spreading requests across several servers.
[9.4_s0389] Some pages normally handled by busy servers will also start being handled by less busy servers.
[9.4_s0390] Since this process is based on aggregate server load rather than the popularity of individual pages, servers hosting some popular pages may find more servers sharing their load than servers hosting collectively unpopular pages.
[9.4_s0391] In the process, some unpopular pages will be replicated in the system simply because they happen to be primarily hosted on busy servers.
[9.4_s0392] At the same time, if some pages become extremely popular, it is conceivable that all of the servers in the system could be responsible for serving them.
[9.4_s0393] Finally, it is possible to introduce network proximity into the equation in at least two different ways.
[9.4_s0394] The first is to blur the distinction between server load and network proximity by monitoring how long a server takes to respond to requests and using this measurement as the “server load” parameter in the preceding algorithm.
[9.4_s0395] This strategy tends to prefer nearby/lightly loaded servers over distant/heavily loaded servers.
[9.4_s0396] A second approach is to factor proximity into the decision at an earlier stage by limiting the candidate set of servers considered by the above algorithms (S) to only those that are nearby.
[9.4_s0397] The harder problem is deciding which of the potentially many servers are suitably close.
[9.4_s0398] One approach would be to select only those servers that are available on the same ISP as the client.
[9.4_s0399] A slightly more sophisticated approach would be to look at the map of autonomous systems produced by BGP and select only those servers within some number of hops from the client as candidate servers.
[9.4_s0400] Finding the right balance between network proximity and server cache locality is a subject of ongoing research.
