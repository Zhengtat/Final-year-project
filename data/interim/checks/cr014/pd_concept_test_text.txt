=== SECTION 4.2: Advanced Internetworking > IP Version 6 ===
[4.2_s0000] The motivation for defining a new version of IP is simple: to deal with exhaustion of the IP address space.
[4.2_s0001] CIDR helped considerably to contain the rate at which the Internet address space was being consumed and also helped to control the growth of routing table information needed in the Internet’s routers.
[4.2_s0002] However, these techniques are no longer adequate.
[4.2_s0003] In particular, it is virtually impossible to achieve 100% address utilization efficiency, so the address space was consumed well before the 4 billionth host was connected to the Internet.
[4.2_s0004] Even if we were able to use all 4 billion addresses, it is now clear that IP addresses need to be assigned to more than traditional computers, including smart phones, televisions, household appliances, and drones.
[4.2_s0005] With the clarity of 20/20 hindsight, a 32-bit address space is quite small.
[4.2_s0006] 4.2.1 Historical Perspective  The IETF began looking at the problem of expanding the IP address space in 1991, and several alternatives were proposed.
[4.2_s0007] Since the IP address is carried in the header of every IP packet, increasing the size of the address dictates a change in the packet header.
[4.2_s0008] This means a new version of the Internet Protocol and, as a consequence, a need for new software for every host and router in the Internet.
[4.2_s0009] This is clearly not a trivial matter—it is a major change that needs to be thought about very carefully.
[4.2_s0010] The effort to define a new version of IP was originally known as IP Next Generation, or IPng.
[4.2_s0011] As the work progressed, an official IP version number was assigned, so IPng became IPv6.
[4.2_s0012] Note that the version of IP discussed so far in this chapter is version 4 (IPv4).
[4.2_s0013] The apparent discontinuity in numbering is the result of version number 5 being used for an experimental protocol many years ago.
[4.2_s0014] The significance of changing to a new version of IP caused a snowball effect.
[4.2_s0015] The general feeling among network designers was that if you are going to make a change of this magnitude you might as well fix as many other things in IP as possible at the same time.
[4.2_s0016] Consequently, the IETF solicited white papers from anyone who cared to write one, asking for input on the features that might be desired in a new version of IP.
[4.2_s0017] In addition to the need to accommodate scalable routing and addressing, some of the other wish list items for IPng included:  -  Support for real-time services  -  Security support  -  Autoconfiguration (i.e., the ability of hosts to automatically configure themselves with such information as their own IP address and domain name)  -  Enhanced routing functionality, including support for mobile hosts  It is interesting to note that, while many of these features were absent from IPv4 at the time IPv6 was being designed, support for all of them has made its way into IPv4 in recent years, often using similar techniques in both protocols.
[4.2_s0018] It can be argued that the freedom to think of IPv6 as a clean slate facilitated the design of new capabilities for IP that were then retrofitted into IPv4.
[4.2_s0019] In addition to the wish list, one absolutely non-negotiable feature for IPv6 was that there must be a transition plan to move from the current version of IP (version 4) to the new version.
[4.2_s0020] With the Internet being so large and having no centralized control, it would be completely impossible to have a “flag day” on which everyone shut down their hosts and routers and installed a new version of IP.
[4.2_s0021] The architects expected a long transition period in which some hosts and routers would run IPv4 only, some will run IPv4 and IPv6, and some will run IPv6 only.
[4.2_s0022] It is doubtful they anticipated that transition period would be approaching its 30th anniversary.
[4.2_s0023] 4.2.2 Addresses and Routing  First and foremost, IPv6 provides a 128-bit address space, as opposed to the 32 bits of version 4.
[4.2_s0024] Thus, while version 4 can potentially address 4 billion nodes if address assignment efficiency reaches 100%, IPv6 can address 3.4 × 10\ 38 nodes, again assuming 100% efficiency.
[4.2_s0025] As we have seen, though, 100% efficiency in address assignment is not likely.
[4.2_s0026] Some analysis of other addressing schemes, such as those of the French and U.S. telephone networks, as well as that of IPv4, have turned up some empirical numbers for address assignment efficiency.
[4.2_s0027] Based on the most pessimistic estimates of efficiency drawn from this study, the IPv6 address space is predicted to provide over 1500 addresses per square foot of the Earth’s surface, which certainly seems like it should serve us well even when toasters on Venus have IP addresses.
[4.2_s0028] Address Space Allocation  Drawing on the effectiveness of CIDR in IPv4, IPv6 addresses are also classless, but the address space is still subdivided in various ways based on the leading bits.
[4.2_s0029] Rather than specifying different address classes, the leading bits specify different uses of the IPv6 address.
[4.2_s0030] The current assignment of prefixes is listed in Table.
[4.2_s0031] This allocation of the address space warrants a little discussion.
[4.2_s0032] First, the entire functionality of IPv4’s three main address classes (A, B, and C) is contained inside the “everything else” range.
[4.2_s0033] Global Unicast Addresses, as we will see shortly, are a lot like classless IPv4 addresses, only much longer.
[4.2_s0034] These are the main ones of interest at this point, with over 99% of the total IPv6 address space available to this important form of address.
[4.2_s0035] (At the time of writing, IPv6 unicast addresses are being allocated from the block that begins 001, with the remaining address space—about 87%—being reserved for future use.)
[4.2_s0036] The multicast address space is (obviously) for multicast, thereby serving the same role as class D addresses in IPv4.
[4.2_s0037] Note that multicast addresses are easy to distinguish—they start with a byte of all 1s.
[4.2_s0038] We will see how these addresses are used in a later section.
[4.2_s0039] The idea behind link-local use addresses is to enable a host to construct an address that will work on the network to which it is connected without being concerned about the global uniqueness of the address.
[4.2_s0040] This may be useful for autoconfiguration, as we will see below.
[4.2_s0041] Similarly, the site-local use addresses are intended to allow valid addresses to be constructed on a site (e.g., a private corporate network) that is not connected to the larger Internet; again, global uniqueness need not be an issue.
[4.2_s0042] Within the global unicast address space are some important special types of addresses.
[4.2_s0043] A node may be assigned an IPv4-compatible IPv6 address by zero-extending a 32-bit IPv4 address to 128 bits.
[4.2_s0044] A node that is only capable of understanding IPv4 can be assigned an IPv4-mapped IPv6 address by prefixing the 32-bit IPv4 address with 2 bytes of all 1s and then zero-extending the result to 128 bits.
[4.2_s0045] These two special address types have uses in the IPv4-to-IPv6 transition (see the sidebar on this topic).

[4.2_s0047] The standard representation is x:x:x:x:x:x:x:x, where each x is a hexadecimal representation of a 16-bit piece of the address.
[4.2_s0048] An example would be  Any IPv6 address can be written using this notation.
[4.2_s0049] Since there are a few special types of IPv6 addresses, there are some special notations that may be helpful in certain circumstances.
[4.2_s0050] For example, an address with a large number of contiguous 0s can be written more compactly by omitting all the 0 fields.
[4.2_s0051] Thus,  could be written  Clearly, this form of shorthand can only be used for one set of contiguous 0s in an address to avoid ambiguity.
[4.2_s0052] The two types of IPv6 addresses that contain an embedded IPv4 address have their own special notation that makes extraction of the IPv4 address easier.
[4.2_s0053] For example, the IPv4-mapped IPv6 address of a host whose IPv4 address was 128.96.33.81 could be written as  That is, the last 32 bits are written in IPv4 notation, rather than as a pair of hexadecimal numbers separated by a colon.
[4.2_s0054] Note that the double colon at the front indicates the leading 0s.
[4.2_s0055] Global Unicast Addresses  By far the most important sort of addressing that IPv6 must provide is plain old unicast addressing.
[4.2_s0056] It must do this in a way that supports the rapid rate of addition of new hosts to the Internet and that allows routing to be done in a scalable way as the number of physical networks in the Internet grows.
[4.2_s0057] Thus, at the heart of IPv6 is the unicast address allocation plan that determines how unicast addresses will be assigned to service providers, autonomous systems, networks, hosts, and routers.
[4.2_s0058] In fact, the address allocation plan that is proposed for IPv6 unicast addresses is extremely similar to that being deployed with CIDR in IPv4.
[4.2_s0059] To understand how it works and how it provides scalability, it is helpful to define some new terms.
[4.2_s0060] We may think of a nontransit AS (i.e., a stub or multihomed AS) as a subscriber, and we may think of a transit AS as a provider.
[4.2_s0061] Furthermore, we may subdivide providers into direct and indirect.
[4.2_s0062] The former are directly connected to subscribers.
[4.2_s0063] The latter primarily connect other providers, are not connected directly to subscribers, and are often known as backbone networks.
[4.2_s0064] With this set of definitions, we can see that the Internet is not just an arbitrarily interconnected set of autonomous systems; it has some intrinsic hierarchy.
[4.2_s0065] The difficulty lies in making use of this hierarchy without inventing mechanisms that fail when the hierarchy is not strictly observed, as happened with EGP.
[4.2_s0066] For example, the distinction between direct and indirect providers becomes blurred when a subscriber connects to a backbone or when a direct provider starts connecting to many other providers.
[4.2_s0067] As with CIDR, the goal of the IPv6 address allocation plan is to provide aggregation of routing information to reduce the burden on intradomain routers.
[4.2_s0068] Again, the key idea is to use an address prefix—a set of contiguous bits at the most significant end of the address—to aggregate reachability information to a large number of networks and even to a large number of autonomous systems.
[4.2_s0069] The main way to achieve this is to assign an address prefix to a direct provider and then for that direct provider to assign longer prefixes that begin with that prefix to its subscribers.
[4.2_s0070] Thus, a provider can advertise a single prefix for all of its subscribers.
[4.2_s0071] Of course, the drawback is that if a site decides to change providers, it will need to obtain a new address prefix and renumber all the nodes in the site.
[4.2_s0072] This could be a colossal undertaking, enough to dissuade most people from ever changing providers.
[4.2_s0073] For this reason, there is ongoing research on other addressing schemes, such as geographic addressing, in which a site’s address is a function of its location rather than the provider to which it attaches.
[4.2_s0074] At present, however, provider-based addressing is necessary to make routing work efficiently.
[4.2_s0075] Note that while IPv6 address assignment is essentially equivalent to the way address assignment has happened in IPv4 since the introduction of CIDR, IPv6 has the significant advantage of not having a large installed base of assigned addresses to fit into its plans.
[4.2_s0076] One question is whether it makes sense for hierarchical aggregation to take place at other levels in the hierarchy.
[4.2_s0077] For example, should all providers obtain their address prefixes from within a prefix allocated to the backbone to which they connect?
[4.2_s0078] Given that most providers connect to multiple backbones, this probably doesn’t make sense.
[4.2_s0079] Also, since the number of providers is much smaller than the number of sites, the benefits of aggregating at this level are much fewer.
[4.2_s0080] One place where aggregation may make sense is at the national or continental level.
[4.2_s0081] Continental boundaries form natural divisions in the Internet topology.
[4.2_s0082] If all addresses in Europe, for example, had a common prefix, then a great deal of aggregation could be done, and most routers in other continents would only need one routing table entry for all networks with the Europe prefix.
[4.2_s0083] Providers in Europe would all select their prefixes such that they began with the European prefix.
[4.2_s0084] Using this scheme, an IPv6 address might look like Figure.
[4.2_s0085] The RegistryID might be an identifier assigned to a European address registry, with different IDs assigned to other continents or countries.
[4.2_s0086] Note that prefixes would be of different lengths under this scenario.
[4.2_s0087] For example, a provider with few customers could have a longer prefix (and thus less total address space available) than one with many customers.
[4.2_s0088] One tricky situation could occur when a subscriber is connected to more than one provider.
[4.2_s0089] Which prefix should the subscriber use for his or her site?
[4.2_s0090] There is no perfect solution to the problem.
[4.2_s0091] For example, suppose a subscriber is connected to two providers, X and Y.
[4.2_s0092] If the subscriber takes his prefix from X, then Y has to advertise a prefix that has no relationship to its other subscribers and that as a consequence cannot be aggregated.
[4.2_s0093] If the subscriber numbers part of his AS with the prefix of X and part with the prefix of Y, he runs the risk of having half his site become unreachable if the connection to one provider goes down.
[4.2_s0094] One solution that works fairly well if X and Y have a lot of subscribers in common is for them to have three prefixes between them: one for subscribers of X only, one for subscribers of Y only, and one for the sites that are subscribers of both X and Y.  4.2.3 Packet Format  Despite the fact that IPv6 extends IPv4 in several ways, its header format is actually simpler.
[4.2_s0095] This simplicity is due to a concerted effort to remove unnecessary functionality from the protocol.
[4.2_s0096] Figure shows the result.
[4.2_s0097] As with many headers, this one starts with a Version field, which is set to 6 for IPv6.
[4.2_s0098] The Version field is in the same place relative to the start of the header as IPv4’s Version field so that header-processing software can immediately decide which header format to look for.
[4.2_s0099] The TrafficClass and FlowLabel fields both relate to quality of service issues.
[4.2_s0100] The PayloadLen field gives the length of the packet, excluding the IPv6 header, measured in bytes.
[4.2_s0101] The NextHeader field cleverly replaces both the IP options and the Protocol field of IPv4.
[4.2_s0102] If options are required, then they are carried in one or more special headers following the IP header, and this is indicated by the value of the NextHeader field.
[4.2_s0103] If there are no special headers, the NextHeader field is the demux key identifying the higher-level protocol running over IP (e.g., TCP or UDP); that is, it serves the same purpose as the IPv4 Protocol field.
[4.2_s0104] Also, fragmentation is now handled as an optional header, which means that the fragmentation-related fields of IPv4 are not included in the IPv6 header.
[4.2_s0105] The HopLimit field is simply the TTL of IPv4, renamed to reflect the way it is actually used.
[4.2_s0106] Finally, the bulk of the header is taken up with the source and destination addresses, each of which is 16 bytes (128 bits) long.
[4.2_s0107] Thus, the IPv6 header is always 40 bytes long.
[4.2_s0108] Considering that IPv6 addresses are four times longer than those of IPv4, this compares quite well with the IPv4 header, which is 20 bytes long in the absence of options.
[4.2_s0109] The way that IPv6 handles options is quite an improvement over IPv4.
[4.2_s0110] In IPv4, if any options were present, every router had to parse the entire options field to see if any of the options were relevant.
[4.2_s0111] This is because the options were all buried at the end of the IP header, as an unordered collection of ‘(type, length, value)’ tuples.
[4.2_s0112] In contrast, IPv6 treats options as extension headers that must, if present, appear in a specific order.
[4.2_s0113] This means that each router can quickly determine if any of the options are relevant to it; in most cases, they will not be.
[4.2_s0114] Usually this can be determined by just looking at the NextHeader field.
[4.2_s0115] The end result is that option processing is much more efficient in IPv6, which is an important factor in router performance.
[4.2_s0116] In addition, the new formatting of options as extension headers means that they can be of arbitrary length, whereas in IPv4 they were limited to 44 bytes at most.
[4.2_s0117] We will see how some of the options are used below.
[4.2_s0118] Each option has its own type of extension header.
[4.2_s0119] The type of each extension header is identified by the value of the NextHeader field in the header that precedes it, and each extension header contains a NextHeader field to identify the header following it.
[4.2_s0120] The last extension header will be followed by a transport-layer header (e.g., TCP) and in this case the value of the NextHeader field is the same as the value of the Protocol field would be in an IPv4 header.
[4.2_s0121] Thus, the NextHeader field does double duty; it may either identify the type of extension header to follow, or, in the last extension header, it serves as a demux key to identify the higher-layer protocol running over IPv6.
[4.2_s0122] Consider the example of the fragmentation header, shown in Figure.
[4.2_s0123] This header provides functionality similar to the fragmentation fields in the IPv4 header, but it is only present if fragmentation is necessary.
[4.2_s0124] Assuming it is the only extension header present, then the NextHeader field of the IPv6 header would contain the value \ 44, which is the value assigned to indicate the fragmentation header.
[4.2_s0125] The NextHeader field of the fragmentation header itself contains a value describing the header that follows it.
[4.2_s0126] Again, assuming no other extension headers are present, then the next header might be the TCP header, which results in NextHeader containing the value \ 6, just as the Protocol field would in IPv4.
[4.2_s0127] If the fragmentation header were followed by, say, an authentication header, then the fragmentation header’s NextHeader field would contain the value \ 51.
[4.2_s0128] 4.2.4 Advanced Capabilities
[4.2_s0129] As mentioned at the beginning of this section, the primary motivation behind the development of IPv6 was to support the continued growth of the Internet.
[4.2_s0130] Once the IP header had to be changed for the sake of the addresses, however, the door was open for a wide variety of other changes, two of which we describe below.
[4.2_s0131] But IPv6 includes several additional features, most of which are covered elsewhere in this book; e.g., mobility, security, quality-of-service.
[4.2_s0132] It is interesting to note that, in most of these areas, the IPv4 and IPv6 capabilities have become virtually indistinguishable, so that the main driver for IPv6 remains the need for larger addresses.
[4.2_s0133] Autoconfiguration  While the Internet’s growth has been impressive, one factor that has inhibited faster acceptance of the technology is the fact that getting connected to the Internet has typically required a fair amount of system administration expertise.
[4.2_s0134] In particular, every host that is connected to the Internet needs to be configured with a certain minimum amount of information, such as a valid IP address, a subnet mask for the link to which it attaches, and the address of a name server.
[4.2_s0135] Thus, it has not been possible to unpack a new computer and connect it to the Internet without some preconfiguration.
[4.2_s0136] One goal of IPv6, therefore, is to provide support for autoconfiguration, sometimes referred to as plug-and-play operation.
[4.2_s0137] As we saw in the previous chapter, autoconfiguration is possible for IPv4, but it depends on the existence of a server that is configured to hand out addresses and other configuration information to Dynamic Host Configuration Protocol (DHCP) clients.
[4.2_s0138] The longer address format in IPv6 helps provide a useful, new form of autoconfiguration called stateless autoconfiguration, which does not require a server.
[4.2_s0139] Recall that IPv6 unicast addresses are hierarchical, and that the least significant portion is the interface ID.
[4.2_s0140] Thus, we can subdivide the autoconfiguration problem into two parts:  1.
[4.2_s0141] Obtain an interface ID that is unique on the link to which the host is attached.
[4.2_s0142] 2.
[4.2_s0143] Obtain the correct address prefix for this subnet.
[4.2_s0144] The first part turns out to be rather easy, since every host on a link must have a unique link-level address.
[4.2_s0145] For example, all hosts on an Ethernet have a unique 48-bit Ethernet address.
[4.2_s0146] This can be turned into a valid link-local use address by adding the appropriate prefix from Table (1111 1110 10) followed by enough 0s to make up 128 bits.
[4.2_s0147] For some devices—for example, printers or hosts on a small routerless network that do not connect to any other networks—this address may be perfectly adequate.
[4.2_s0148] Those devices that need a globally valid address depend on a router on the same link to periodically advertise the appropriate prefix for the link.
[4.2_s0149] Clearly, this requires that the router be configured with the correct address prefix, and that this prefix be chosen in such a way that there is enough space at the end (e.g., 48 bits) to attach an appropriate link-level address.
[4.2_s0150] The ability to embed link-level addresses as long as 48 bits into IPv6 addresses was one of the reasons for choosing such a large address size.
[4.2_s0151] Not only does 128 bits allow the embedding, but it leaves plenty of space for the multilevel hierarchy of addressing that we discussed above.
[4.2_s0152] Source-Directed Routing  Another of IPv6’s extension headers is the routing header.
[4.2_s0153] In the absence of this header, routing for IPv6 differs very little from that of IPv4 under CIDR.
[4.2_s0154] The routing header contains a list of IPv6 addresses that represent nodes or topological areas that the packet should visit en route to its destination.
[4.2_s0155] A topological area may be, for example, a backbone provider’s network.
[4.2_s0156] Specifying that packets must visit this network would be a way of implementing provider selection on a packet-by-packet basis.
[4.2_s0157] Thus, a host could say that it wants some packets to go through a provider that is cheap, others through a provider that provides high reliability, and still others through a provider that the host trusts to provide security.
[4.2_s0158] To provide the ability to specify topological entities rather than individual nodes, IPv6 defines an anycast address.
[4.2_s0159] An anycast address is assigned to a set of interfaces, and packets sent to that address will go to the “nearest” of those interfaces, with nearest being determined by the routing protocols.
[4.2_s0160] For example, all the routers of a backbone provider could be assigned a single anycast address, which would be used in the routing header.
=== SECTION 5.3: End-to-End Protocols > Remote Procedure Call ===
[5.3_s0000] A common pattern of communication used by application programs structured as a client/server pair is the request/reply message transaction:
[5.3_s0001] A client sends a request message to a server, and the server responds with a reply message, with the client blocking (suspending execution) to wait for the reply.
[5.3_s0002] Figure illustrates the basic interaction between the client and server in such an exchange.
[5.3_s0003] A transport protocol that supports the request/reply paradigm is much more than a UDP message going in one direction followed by a UDP message going in the other direction.
[5.3_s0004] It needs to deal with correctly identifying processes on remote hosts and correlating requests with responses.
[5.3_s0005] It may also need to overcome some or all of the limitations of the underlying network outlined in the problem statement at the beginning of this chapter.
[5.3_s0006] While TCP overcomes these limitations by providing a reliable byte-stream service, it doesn’t perfectly match the request/reply paradigm either.
[5.3_s0007] This section describes a third category of transport protocol, called Remote Procedure Call (RPC), that more closely matches the needs of an application involved in a request/reply message exchange.
[5.3_s0008] 5.3.1 RPC Fundamentals  RPC is not technically a protocol—it is better thought of as a general mechanism for structuring distributed systems.
[5.3_s0009] RPC is popular because it is based on the semantics of a local procedure call—the application program makes a call into a procedure without regard for whether it is local or remote and blocks until the call returns.
[5.3_s0010] An application developer can be largely unaware of whether the procedure is local or remote, simplifying his task considerably.
[5.3_s0011] When the procedures being called are actually methods of remote objects in an object-oriented language, RPC is known as remote method invocation (RMI).
[5.3_s0012] While the RPC concept is simple, there are two main problems that make it more complicated than local procedure calls:  -  The network between the calling process and the called process has much more complex properties than the backplane of a computer.
[5.3_s0013] For example, it is likely to limit message sizes and has a tendency to lose and reorder messages.  -
[5.3_s0014] The computers on which the calling and called processes run may have significantly different architectures and data representation formats.
[5.3_s0015] Thus, a complete RPC mechanism actually involves two major components:  1.
[5.3_s0016] A protocol that manages the messages sent between the client and the server processes and that deals with the potentially undesirable properties of the underlying network.
[5.3_s0017] 2.
[5.3_s0018] Programming language and compiler support to package the arguments into a request message on the client machine and then to translate this message back into the arguments on the server machine, and likewise with the return value (this piece of the RPC mechanism is usually called a stub compiler).
[5.3_s0019] Figure schematically depicts what happens when a client invokes a remote procedure.
[5.3_s0020] First, the client calls a local stub for the procedure, passing it the arguments required by the procedure.
[5.3_s0021] This stub hides the fact that the procedure is remote by translating the arguments into a request message and then invoking an RPC protocol to send the request message to the server machine.
[5.3_s0022] At the server, the RPC protocol delivers the request message to the server stub, which translates it into the arguments to the procedure and then calls the local procedure.
[5.3_s0023] After the server procedure completes, it returns in a reply message that it hands off to the RPC protocol for transmission back to the client.
[5.3_s0024] The RPC protocol on the client passes this message up to the client stub, which translates it into a return value that it returns to the client program.
[5.3_s0025] This section considers just the protocol-related aspects of an RPC mechanism.
[5.3_s0026] That is, it ignores the stubs and focuses instead on the RPC protocol, sometimes referred to as a request/reply protocol, that transmits messages between client and server.
[5.3_s0027] The transformation of arguments into messages and vice versa is covered elsewhere.
[5.3_s0028] It is also important to keep in mind that the client and server programs are written in some programming language, meaning that a given RPC mechanism might support Python stubs, Java stubs, GoLang stubs, and so on, each of which includes language-specific idioms for how procedures are invoked.
[5.3_s0029] The term RPC refers to a type of protocol rather than a specific standard like TCP, so specific RPC protocols vary in the functions they perform.
[5.3_s0030] And, unlike TCP, which is the dominant reliable byte-stream protocol, there is no one dominant RPC protocol.
[5.3_s0031] Thus, in this section we will talk more about alternative design choices than previously.
[5.3_s0032] Identifiers in RPC  Two functions that must be performed by any RPC protocol are:  -  Provide a name space for uniquely identifying the procedure to be called.  -  Match each reply message to the corresponding request message.
[5.3_s0033] The first problem has some similarities to the problem of identifying nodes in a network (something IP addresses do, for example).
[5.3_s0034] One of the design choices when identifying things is whether to make this name space flat or hierarchical.
[5.3_s0035] A flat name space would simply assign a unique, unstructured identifier (e.g., an integer) to each procedure, and this number would be carried in a single field in an RPC request message.
[5.3_s0036] This would require some kind of central coordination to avoid assigning the same procedure number to two different procedures.
[5.3_s0037] Alternatively, the protocol could implement a hierarchical name space, analogous to that used for file pathnames, which requires only that a file’s “basename” be unique within its directory.
[5.3_s0038] This approach potentially simplifies the job of ensuring uniqueness of procedure names.
[5.3_s0039] A hierarchical name space for RPC could be implemented by defining a set of fields in the request message format, one for each level of naming in, say, a two- or three-level hierarchical name space.
[5.3_s0040] The key to matching a reply message to the corresponding request is to uniquely identify request-replies pairs using a message ID field.
[5.3_s0041] A reply message had its message ID field set to the same value as the request message.
[5.3_s0042] When the client RPC module receives the reply, it uses the message ID to search for the corresponding outstanding request.
[5.3_s0043] To make the RPC transaction appear like a local procedure call to the caller, the caller is blocked until the reply message is received.
[5.3_s0044] When the reply is received, the blocked caller is identified based on the request number in the reply, the remote procedure’s return value is obtained from the reply, and the caller is unblocked so that it can return with that return value.
[5.3_s0045] One of the recurrent challenges in RPC is dealing with unexpected responses, and we see this with message IDs.
[5.3_s0046] For example, consider the following pathological (but realistic) situation.
[5.3_s0047] A client machine sends a request message with a message ID of 0, then crashes and reboots, and then sends an unrelated request message, also with a message ID of 0.
[5.3_s0048] The server may not have been aware that the client crashed and rebooted and, upon seeing a request message with a message ID of 0, acknowledges it and discards it as a duplicate.
[5.3_s0049] The client never gets a response to the request.
[5.3_s0050] One way to eliminate this problem is to use a boot ID.
[5.3_s0051] A machine’s boot ID is a number that is incremented each time the machine reboots; this number is read from nonvolatile storage (e.g., a disk or flash drive), incremented, and written back to the storage device during the machine’s start-up procedure.
[5.3_s0052] This number is then put in every message sent by that host.
[5.3_s0053] If a message is received with an old message ID but a new boot ID, it is recognized as a new message.
[5.3_s0054] In effect, the message ID and boot ID combine to form a unique ID for each transaction.
[5.3_s0055] Overcoming Network Limitations  RPC protocols often perform additional functions to deal with the fact that networks are not perfect channels.
[5.3_s0056] Two such functions are:  -  Provide reliable message delivery  -  Support large message sizes through fragmentation and reassembly  An RPC protocol might “define this problem away” by choosing to run on top of a reliable protocol like TCP, but in many cases, the RPC protocol implements its own reliable message delivery layer on top of an unreliable substrate (e.g., UDP/IP).
[5.3_s0057] Such an RPC protocol would likely implement reliability using acknowledgments and timeouts, similarly to TCP.
[5.3_s0058] The basic algorithm is straightforward, as illustrated by the timeline given in Figure.
[5.3_s0059] The client sends a request message and the server acknowledges it.
[5.3_s0060] Then, after executing the procedure, the server sends a reply message and the client acknowledges the reply.
[5.3_s0061] Either a message carrying data (a request message or a reply message) or the ACK sent to acknowledge that message may be lost in the network.
[5.3_s0062] To account for this possibility, both client and server save a copy of each message they send until an ACK for it has arrived.
[5.3_s0063] Each side also sets a RETRANSMIT timer and resends the message should this timer expire.
[5.3_s0064] Both sides reset this timer and try again some agreed-upon number of times before giving up and freeing the message.
[5.3_s0065] If an RPC client receives a reply message, clearly the corresponding request message must have been received by the server.
[5.3_s0066] Hence, the reply message itself is an implicit acknowledgment, and any additional acknowledgment from the server is not logically necessary.
[5.3_s0067] Similarly, a request message could implicitly acknowledge the preceding reply message—assuming the protocol makes request-reply transactions sequential, so that one transaction must complete before the next begins.
[5.3_s0068] Unfortunately, this sequentiality would severely limit RPC performance.
[5.3_s0069] A way out of this predicament is for the RPC protocol to implement a channel abstraction.
[5.3_s0070] Within a given channel, request/reply transactions are sequential—there can be only one transaction active on a given channel at any given time—but there can be multiple channels.
[5.3_s0071] Or said another way, the channel abstraction makes it possible to multiplex multiple RPC request/reply transactions between a client/server pair.
[5.3_s0072] Each message includes a channel ID field to indicate which channel the message belongs to.
[5.3_s0073] A request message in a given channel would implicitly acknowledge the previous reply in that channel, if it hadn’t already been acknowledged.
[5.3_s0074] An application program can open multiple channels to a server if it wants to have more than one request/reply transaction between them at the same time (the application would need multiple threads).
[5.3_s0075] As illustrated in Figure, the reply message serves to acknowledge the request message, and a subsequent request acknowledges the preceding reply.
[5.3_s0076] Note that we saw a very similar approach—called concurrent logical channels—in an earlier section as a way to improve on the performance of a stop-and-wait reliability mechanism.
[5.3_s0077] Another complication that RPC must address is that the server may take an arbitrarily long time to produce the result, and, worse yet, it may crash before generating the reply.
[5.3_s0078] Keep in mind that we are talking about the period of time after the server has acknowledged the request but before it has sent the reply.
[5.3_s0079] To help the client distinguish between a slow server and a dead server, the RPC’s client side can periodically send an “Are you alive?” message to the server, and the server side responds with an ACK.
[5.3_s0080] Alternatively, the server could send “I am still alive” messages to the client without the client having first solicited them.
[5.3_s0081] The approach is more scalable because it puts more of the per-client burden (managing the timeout timer) on the clients.
[5.3_s0082] RPC reliability may include the property known as at-most-once semantics.
[5.3_s0083] This means that for every request message that the client sends, at most one copy of that message is delivered to the server.
[5.3_s0084] Each time the client calls a remote procedure, that procedure is invoked at most one time on the server machine.
[5.3_s0085] We say “at most once” rather than “exactly once” because it is always possible that either the network or the server machine has failed, making it impossible to deliver even one copy of the request message.
[5.3_s0086] To implement at-most-once semantics, RPC on the server side must recognize duplicate requests (and ignore them), even if it has already successfully replied to the original request.
[5.3_s0087] Hence, it must maintain some state information that identifies past requests.
[5.3_s0088] One approach is to identify requests using sequence numbers, so a server need only remember the most recent sequence number.
[5.3_s0089] Unfortunately, this would limit an RPC to one outstanding request (to a given server) at a time, since one request must be completed before the request with the next sequence number can be transmitted.
[5.3_s0090] Once again, channels provide a solution.
[5.3_s0091] The server could recognize duplicate requests by remembering the current sequence number for each channel, without limiting the client to one request at a time.
[5.3_s0092] As obvious as at-most-once sounds, not all RPC protocols support this behavior.
[5.3_s0093] Some support a semantics that is facetiously called zero-or-more semantics; that is, each invocation on a client results in the remote procedure being invoked zero or more times.
[5.3_s0094] It is not difficult to understand how this would cause problems for a remote procedure that changed some local state variable (e.g., incremented a counter) or that had some externally visible side effect (e.g., launched a missile) each time it was invoked.
[5.3_s0095] On the other hand, if the remote procedure being invoked is idempotent—multiple invocations have the same effect as just one—then the RPC mechanism need not support at-most-once semantics; a simpler (possibly faster) implementation will suffice.
[5.3_s0096] As was the case with reliability, the two reasons why an RPC protocol might implement message fragmentation and reassembly are that it is not provided by the underlying protocol stack or that it can be implemented more efficiently by the RPC protocol.
[5.3_s0097] Consider the case where RPC is implemented on top of UDP/IP and relies on IP for fragmentation and reassembly.
[5.3_s0098] If even one fragment of a message fails to arrive within a certain amount of time, IP discards the fragments that did arrive and the message is effectively lost.
[5.3_s0099] Eventually, the RPC protocol (assuming it implements reliability) would time out and retransmit the message.
[5.3_s0100] In contrast, consider an RPC protocol that implements its own fragmentation and reassembly and aggressively ACKs or NACKs (negatively acknowledges) individual fragments.
[5.3_s0101] Lost fragments would be more quickly detected and retransmitted, and only the lost fragments would be retransmitted, not the whole message.
[5.3_s0102] Synchronous versus Asynchronous Protocols  One way to characterize a protocol is by whether it is synchronous or asynchronous.
[5.3_s0103] The precise meaning of these terms depends on where in the protocol hierarchy you use them.
[5.3_s0104] At the transport layer, it is most accurate to think of them as defining the extremes of a spectrum rather than as two mutually exclusive alternatives.
[5.3_s0105] The key attribute of any point along the spectrum is how much the sending process knows after the operation to send a message returns.
[5.3_s0106] In other words, if we assume that an application program invokes a send operation on a transport protocol, then exactly what does the application know about the success of the operation when the send operation returns?
[5.3_s0107] At the asynchronous end of the spectrum, the application knows absolutely nothing when send returns.
[5.3_s0108] Not only does it not know if the message was received by its peer, but it doesn’t even know for sure that the message has successfully left the local machine.
[5.3_s0109] At the synchronous end of the spectrum, the send operation typically returns a reply message.
[5.3_s0110] That is, the application not only knows that the message it sent was received by its peer, but it also knows that the peer has returned an answer.
[5.3_s0111] Thus, synchronous protocols implement the request/reply abstraction, while asynchronous protocols are used if the sender wants to be able to transmit many messages without having to wait for a response.
[5.3_s0112] Using this definition, RPC protocols are usually synchronous protocols.
[5.3_s0113] Although we have not discussed them in this chapter, there are interesting points between these two extremes.
[5.3_s0114] For example, the transport protocol might implement send so that it blocks (does not return) until the message has been successfully received at the remote machine, but returns before the sender’s peer on that machine has actually processed and responded to it.
[5.3_s0115] This is sometimes called a reliable datagram protocol.
[5.3_s0116] 5.3.2 RPC Implementations (SunRPC, DCE, gRPC)
[5.3_s0117] We now turn our discussion to some example implementations of RPC protocols.
[5.3_s0118] These will serve to highlight some of the different design decisions that protocol designers have made.
[5.3_s0119] Our first example is SunRPC, a widely used RPC protocol also known as Open Network Computing RPC (ONC RPC).
[5.3_s0120] Our second example, which we will refer to as DCE-RPC, is part of the Distributed Computing Environment (DCE).
[5.3_s0121] DCE is a set of standards and software for building distributed systems that was defined by the Open Software Foundation (OSF), a consortium of computer companies that originally included IBM, Digital Equipment Corporation, and Hewlett-Packard; today, OSF goes by the name The Open Group.
[5.3_s0122] Our third example is gRPC, a popular RPC mechanism that Google has open sourced, based on an RPC mechanism that they have been using internally to implement cloud services in their datacenters.
[5.3_s0123] These three examples represent interesting alternative design choices in the RPC solution space, but lest you think they are the only options, we describe three other RPC-like mechanisms (WSDL, SOAP, and REST) in the context of web services in Chapter 9.
[5.3_s0124] SunRPC  SunRPC became a de facto standard thanks to its wide distribution with Sun workstations and the central role it plays in Sun’s popular Network File System (NFS).
[5.3_s0125] The IETF subsequently adopted it as a standard Internet protocol under the name ONC RPC.
[5.3_s0126] SunRPC can be implemented over several different transport protocols.
[5.3_s0127] Figure illustrates the protocol graph when SunRPC is implemented on UDP.
[5.3_s0128] As we noted earlier in this section, a strict layerist might frown on the idea of running a transport protocol over a transport protocol, or argue that RPC must be something other than a transport protocol since it appears “above” the transport layer.
[5.3_s0129] Pragmatically, the design decision to run RPC over an existing transport layer makes quite a lot of sense, as will be apparent in the following discussion.
[5.3_s0130] SunRPC uses two-tier identifiers to identify remote procedures: a 32-bit program number and a 32-bit procedure number.
[5.3_s0131] (There is also a 32-bit version number, but we ignore that in the following discussion.)
[5.3_s0132] For example, the NFS server has been assigned program number x00100003, and within this program getattr is procedure 1, setattr is procedure 2, read is procedure 6, write is procedure 8, and so on.
[5.3_s0133] The program number and procedure number are transmitted in the SunRPC request message’s header, whose fields are shown in Figure.
[5.3_s0134] The server—which may support several program numbers—is responsible for calling the specified procedure of the specified program.
[5.3_s0135] A SunRPC request really represents a request to call the specified program and procedure on the particular machine to which the request was sent, even though the same program number may be implemented on other machines in the same network.
[5.3_s0136] Thus, the address of the server’s machine (e.g., an IP address) is an implicit third tier of the RPC address.
[5.3_s0137] Different program numbers may belong to different servers on the same machine.
[5.3_s0138] These different servers have different transport layer demux keys (e.g., UDP ports), most of which are not well-known numbers but instead are assigned dynamically.
[5.3_s0139] These demux keys are called transport selectors.
[5.3_s0140] How can a SunRPC client that wants to talk to a particular program determine which transport selector to use to reach the corresponding server?
[5.3_s0141] The solution is to assign a well-known address to just one program on the remote machine and let that program handle the task of telling clients which transport selector to use to reach any other program on the machine.
[5.3_s0142] The original version of this SunRPC program is called the Port Mapper, and it supports only UDP and TCP as underlying protocols.
[5.3_s0143] Its program number is x00100000, and its well-known port is 111.
[5.3_s0144] RPCBIND, which evolved from the Port Mapper, supports arbitrary underlying transport protocols.
[5.3_s0145] As each SunRPC server starts, it calls an RPCBIND registration procedure, on the server’s own home machine, to register its transport selector and the program numbers that it supports.
[5.3_s0146] A remote client can then call an RPCBIND lookup procedure to look up the transport selector for a particular program number.
[5.3_s0147] To make this more concrete, consider an example using the Port Mapper with UDP.
[5.3_s0148] To send a request message to NFS’s read procedure, a client first sends a request message to the Port Mapper at well-known UDP port \ 111, asking that procedure 3 be invoked to map program number x00100003 to the UDP port where the NFS program currently resides.
[5.3_s0149] The client then sends a SunRPC request message with program number x00100003 and procedure number 6 to this UDP port, and the SunRPC module listening at that port calls the NFS read procedure.
[5.3_s0150] The client also caches the program-to-port number mapping so that it need not go back to the Port Mapper each time it wants to talk to the NFS program.\
[5.3_s0151] [#]_  To match up a reply message with the corresponding request, so that the result of the RPC can be returned to the correct caller, both request and reply message headers include a XID (transaction ID) field, as in Figure.
[5.3_s0152] A XID is a unique transaction ID used only by one request and the corresponding reply.
[5.3_s0153] After the server has successfully replied to a given request, it does not remember the XID.
[5.3_s0154] Because of this, SunRPC cannot guarantee at-most-once semantics.
[5.3_s0155] The details of SunRPC’s semantics depend on the underlying transport protocol.
[5.3_s0156] It does not implement its own reliability, so it is only reliable if the underlying transport is reliable.
[5.3_s0157] (Of course, any application that runs over SunRPC may also choose to implement its own reliability mechanisms above the level of SunRPC.)
[5.3_s0158] The ability to send request and reply messages that are larger than the network MTU is also dependent on the underlying transport.
[5.3_s0159] In other words, SunRPC does not make any attempt to improve on the underlying transport when it comes to reliability and message size.
[5.3_s0160] Since SunRPC can run over many different transport protocols, this gives it considerable flexibility without complicating the design of the RPC protocol itself.
[5.3_s0161] Returning to the SunRPC header format of Figure, the request message contains variable-length Credentials and Verifier fields, both of which are used by the client to authenticate itself to the server—that is, to give evidence that the client has the right to invoke the server.
[5.3_s0162] How a client authenticates itself to a server is a general issue that must be addressed by any protocol that wants to provide a reasonable level of security.
[5.3_s0163] This topic is discussed in more detail in another chapter.
[5.3_s0164] DCE-RPC  DCE-RPC is the RPC protocol at the core of the DCE system and was the basis of the RPC mechanism underlying Microsoft’s DCOM and ActiveX.
[5.3_s0165] It can be used with the Network Data Representation (NDR) stub compiler described in another chapter, but it also serves as the underlying RPC protocol for the Common Object Request Broker Architecture (CORBA), which is an industry-wide standard for building distributed, object-oriented systems.
[5.3_s0166] DCE-RPC, like SunRPC, can be implemented on top of several transport protocols including UDP and TCP.
[5.3_s0167] It is also similar to SunRPC in that it defines a two-level addressing scheme: the transport protocol demultiplexes to the correct server, DCE-RPC dispatches to a particular procedure exported by that server, and clients consult an “endpoint mapping service” (similar to SunRPC’s Port Mapper) to learn how to reach a particular server.
[5.3_s0168] Unlike SunRPC, however, DCE-RPC implements at-most-once call semantics.
[5.3_s0169] (In truth, DCE-RPC supports multiple call semantics, including an idempotent semantics similar to SunRPC’s, but at-most-once is the default behavior.)
[5.3_s0170] There are some other differences between the two approaches, which we will highlight in the following paragraphs.
[5.3_s0171] Figure gives a timeline for the typical exchange of messages, where each message is labeled by its DCE-RPC type.
[5.3_s0172] The client sends a Request message, the server eventually replies with a Response message, and the client acknowledges (Ack) the response.
[5.3_s0173] Instead of the server acknowledging the request messages, however, the client periodically sends a Ping message to the server, which responds with a Working message to indicate that the remote procedure is still in progress.
[5.3_s0174] If the server’s reply is received reasonably quickly, no Ping\ s are sent.
[5.3_s0175] Although not shown in the figure, other message types are also supported.
[5.3_s0176] For example, the client can send a Quit message to the server, asking it to abort an earlier call that is still in progress; the server responds with a Quack (quit acknowledgment) message.
[5.3_s0177] Also, the server can respond to a Request message with a Reject message (indicating that a call has been rejected), and it can respond to a Ping message with a Nocall message (indicating that the server has never heard of the caller).
[5.3_s0178] Each request/reply transaction in DCE-RPC takes place in the context of an activity.
[5.3_s0179] An activity is a logical request/reply channel between a pair of participants.
[5.3_s0180] At any given time, there can be only one message transaction active on a given channel.
[5.3_s0181] Like the concurrent logical channel approach described above, the application programs have to open multiple channels if they want to have more than one request/reply transaction between them at the same time.
[5.3_s0182] The activity to which a message belongs is identified by the message’s ActivityId field.
[5.3_s0183] A SequenceNum field then distinguishes between calls made as part of the same activity; it serves the same purpose as SunRPC’s XID (transaction id) field.
[5.3_s0184] Unlike SunRPC, DCE-RPC keeps track of the last sequence number used as part of a particular activity, so as to ensure at-most-once semantics.
[5.3_s0185] To distinguish between replies sent before and after a server machine reboots, DCE-RPC uses a ServerBoot field to hold the machine’s boot ID.
[5.3_s0186] Another design choice made in DCE-RPC that differs from SunRPC is the support of fragmentation and reassembly in the RPC protocol.
[5.3_s0187] As noted above, even if an underlying protocol such as IP provides fragmentation/reassembly, a more sophisticated algorithm implemented as part of RPC can result in quicker recovery and reduced bandwidth consumption when fragments are lost.
[5.3_s0188] The FragmentNum field uniquely identifies each fragment that makes up a given request or reply message.
[5.3_s0189] Each DCE-RPC fragment is assigned a unique fragment number (0, 1, 2, 3, and so on).
[5.3_s0190] Both the client and server implement a selective acknowledgment mechanism, which works as follows.
[5.3_s0191] (We describe the mechanism in terms of a client sending a fragmented request message to the server; the same mechanism applies when a server sends a fragment response to the client.)
[5.3_s0192] First, each fragment that makes up the request message contains both a unique FragmentNum and a flag indicating whether this packet is a fragment of a call (frag) or the last fragment of a call (); request messages that fit in a single packet carry a flag.
[5.3_s0193] The server knows it has received the complete request message when it has the packet and there are no gaps in the fragment numbers.
[5.3_s0194] Second, in response to each arriving fragment, the server sends a Fack (fragment acknowledgment) message to the client.
[5.3_s0195] This acknowledgment identifies the highest fragment number that the server has successfully received.
[5.3_s0196] In other words, the acknowledgment is cumulative, much like in TCP.
[5.3_s0197] In addition, however, the server selectively acknowledges any higher fragment numbers it has received out of order.
[5.3_s0198] It does so with a bit vector that identifies these out-of-order fragments relative to the highest in-order fragment it has received.
[5.3_s0199] Finally, the client responds by retransmitting the missing fragments.
[5.3_s0200] Figure illustrates how this all works.
[5.3_s0201] Suppose the server has successfully received fragments up through number 20, plus fragments 23, 25, and 26.
[5.3_s0202] The server responds with a Fack that identifies fragment 20 as the highest in-order fragment, plus a bit-vector (SelAck) with the third (23=20+3), fifth (25=20+5), and sixth (26=20+6) bits turned on.
[5.3_s0203] So as to support an (almost) arbitrarily long bit vector, the size of the vector (measured in 32-bit words) is given in the SelAckLen field.
[5.3_s0204] Given DCE-RPC’s support for very large messages—the FragmentNum field is 16 bits long, meaning it can support 64K fragments—it is not appropriate for the protocol to blast all the fragments that make up a message as fast as it can since doing so might overrun the receiver.
[5.3_s0205] Instead, DCE-RPC implements a flow-control algorithm that is very similar to TCP’s.
[5.3_s0206] Specifically, each Fack message not only acknowledges received fragments but also informs the sender of how many fragments it may now send.
[5.3_s0207] This is the purpose of the WindowSize field in Figure, which serves exactly the same purpose as TCP’s AdvertisedWindow field except it counts fragments rather than bytes.
[5.3_s0208] DCE-RPC also implements a congestion-control mechanism that is similar to TCP’s.
[5.3_s0209] Given the complexity of congestion control, it is perhaps not surprising that some RPC protocols avoid it by avoiding fragmentation.
[5.3_s0210] In summary, designers have quite a range of options open to them when designing an RPC protocol.
[5.3_s0211] SunRPC takes the more minimalist approach and adds relatively little to the underlying transport beyond the essentials of locating the right procedure and identifying messages.
[5.3_s0212] DCE-RPC adds more functionality, with the possibility of improved performance in some environments at the cost of greater complexity.
[5.3_s0213] gRPC  Despite its origins in Google, gRPC does not stand for Google RPC.
[5.3_s0214] The “g” stands for something different in each release.
[5.3_s0215] For version 1.10 it stood for “glamorous” and for 1.18 it stood for “goose”.
[5.3_s0216] According to the official gRPC
[5.3_s0217] FAQ, it is now a recursive acronym: gRPC means  “gRPC Remote Procedure Call”.
[5.3_s0218] Googlers are wild and crazy people.
[5.3_s0219] Nonetheless, gRPC is popular because it makes available to everyone—as open source—a decade’s worth of experience within Google using RPC to build scalable cloud services.
[5.3_s0220] Before getting into the details, there are some major differences between gRPC and the other two examples we’ve just covered.
[5.3_s0221] The biggest is that gRPC is designed for cloud services rather than the simpler client/server paradigm that preceded it.
[5.3_s0222] The difference is essentially an extra level of indirection.
[5.3_s0223] In the client/server world, the client invokes a method on a specific server process running on a specific server machine.
[5.3_s0224] One server process is presumed to be enough to serve calls from all the client processes that might call it.
[5.3_s0225] With cloud services, the client invokes a method on a service, which in order to support calls from arbitrarily many clients at the same time, is implemented by a scalable number of server processes, each potentially running on a different server machine.
[5.3_s0226] This is where the cloud comes into play: datacenters make a seemingly infinite number of server machines available to scale up cloud services.
[5.3_s0227] When we use the term “scalable” we mean that the number of identical server processes you elect to create depends on the workload (i.e., the number of clients that want service at any given time) and that number can be adjusted dynamically over time.
[5.3_s0228] One other detail is that cloud services don’t typically create a new process, per se, but rather, they launch a new container, which is essentially a process encapsulated inside an isolated environment that includes all the software packages the process needs to run.
[5.3_s0229] Docker is today’s canonical example of a container platform.
[5.3_s0230] Back to the claim that a service is essentially an extra level of indirection layered on top of a server, all this means is that the caller identifies the service it wants to invoke, and a load balancer directs that invocation to one of the many available server processes (containers) that implement that service, as shown in Figure.
[5.3_s0231] The load balancer can be implemented in different ways, including a hardware device, but it is typically implemented by a proxy process that runs in a virtual machine (also hosted in the cloud) rather than as a physical appliance.
[5.3_s0232] There is a set of best practices for implementing the actual server code that eventually responds to that request, and some additional cloud machinery to create/destroy containers and load balance requests across those containers.
[5.3_s0233] Kubernetes is today’s canonical example of such a container management system, and the micro-services architecture is what we call the best practices in building services in this cloud native manner.
[5.3_s0234] Both are interesting topics, but beyond the scope of this book.
[5.3_s0235] What we are interested in here is transport protocol at the core of gRPC.
[5.3_s0236] Here again, there is a major departure from the two previous example protocols, not in terms of fundamental problems that need to be addressed, but in terms of gRPC’s approach to addressing them.
[5.3_s0237] In short, gRPC “outsources” many of the problems to other protocols, leaving gRPC to essentially package those capabilities in an easy-to-use form.
[5.3_s0238] Let’s look at the details.
[5.3_s0239] First, gRPC runs on top of TCP instead of UDP, which means it outsources the problems of connection management and reliably transmitting request and reply messages of arbitrary size.
[5.3_s0240] Second, gRPC actually runs on top of a secured version of TCP called Transport Layer Security (TLS)—a thin layer that sits above TCP in the protocol stack—which means it outsources responsibility for securing the communication channel so adversaries can’t eavesdrop or hijack the message exchange.
[5.3_s0241] Third, gRPC actually, actually runs on top of HTTP/2 (which is itself layered on top of TCP and TLS), meaning gRPC outsources yet two other problems: (1) efficiently encoding/compressing binary data into a message, (2) multiplexing multiple remote procedure calls onto a single TCP connection.
[5.3_s0242] In other words, gRPC encodes the identifier for the remote method as a URI, the request parameters to the remote method as content in the HTTP message, and the return value from the remote method in the HTTP response.
[5.3_s0243] The full gRPC stack is depicted in Figure, which also includes the language-specific elements.
[5.3_s0244] (One strength of gRPC is the wide set of programming languages it supports, with only a small subset shown in Figure.)
[5.3_s0245] We discuss TLS in Chapter 8 (in the context of a broad range of security topics) and HTTP in Chapter 9 (in the context of what are traditionally viewed as application level protocols).
[5.3_s0246] But we find ourselves in an interesting dependency loop: RPC is a flavor of transport protocol used to implement distributed applications, HTTP is an example of an application-level protocol, and yet gRPC
[5.3_s0247] runs on top of HTTP rather than the other way around.
[5.3_s0248] The short explanation is that layering provides a convenient way for humans to wrap their heads around complex systems, but what we’re really trying to do is solve a set of problem (e.g., reliably transfer messages of arbitrary size, identify senders and recipients, match requests messages with reply messages, and so on) and the way these solutions get bundled into protocols, and those protocols then layered on top of each other, is the consequence of incremental changes over time.
[5.3_s0249] You could argue it’s an historical accident.
[5.3_s0250] Had the Internet started with an RPC mechanism as ubiquitous as TCP, HTTP might have been implemented on top of it (as might have almost all of the other application-level protocols described in Chapter 9) and Google would have spent their time improving that protocol rather than inventing one of their own (as they and others have been doing with TCP).
[5.3_s0251] What happened instead is that the web became the Internet’s killer app, which meant that its application protocol (HTTP) became universally supported by the rest of the Internet’s infrastructure: Firewalls, Load Balancers, Encryption, Authentication, Compression, and so on.
[5.3_s0252] Because all of these network elements have been designed to work well with HTTP, HTTP has effectively become the Internet’s universal request/reply transport protocol.
[5.3_s0253] Returning to the unique characteristics of gRPC, the biggest value it brings to the table is to incorporate streaming into the RPC mechanism, which is to say, gRPC supports four different request/reply patterns:  1.
[5.3_s0254] Simple RPC:
[5.3_s0255] The client sends a single request message and the server responds with a single reply message.
[5.3_s0256] 2.
[5.3_s0257] Server Streaming RPC:
[5.3_s0258] The client sends a single request message and the server responds with a stream of reply messages.
[5.3_s0259] The client completes once it has all the server’s responses.
[5.3_s0260] 3.
[5.3_s0261] Client Streaming RPC:
[5.3_s0262] The client sends a stream of requests to the server, and the server sends back a single response, typically (but not necessarily) after it has received all the client’s requests.
[5.3_s0263] 4.
[5.3_s0264] Bidirectional Streaming RPC:
[5.3_s0265] The call is initiated by the client, but after that, the client and server can read and write requests and responses in any order; the streams are completely independent.
[5.3_s0266] This extra freedom in how the client and server interact means the gRPC transport protocol needs to send additional metadata and control messages—in addition to the actual request and reply messages—between the two peers.
[5.3_s0267] Examples include Error and Status codes (to indicate success or why something failed), Timeouts (to indicate how long a client is willing to wait for a response), PING (a keep-alive notice to indicate that one side or the other is still running), EOS (end-of-stream notice to indicate that there are no more requests or responses), and GOAWAY (a notice from servers to clients to indicate that they will no longer accept any new streams).
[5.3_s0268] Unlike many other protocols in this book, where we show the protocol’s header format, the way this control information gets passed between the two sides is largely dictated by the underlying transport protocol, in this case HTTP/2.
[5.3_s0269] For example, as we’ll see in Chapter 9, HTTP already includes a set of header fields and reply codes that gRPC takes advantage of.

=== SECTION 6.1: Congestion Control > Issues in Resource Allocation ===
[6.1_s0000] Resource allocation and congestion control are complex issues that have been the subject of much study ever since the first network was designed.
[6.1_s0001] They are still active areas of research.
[6.1_s0002] One factor that makes these issues complex is that they are not isolated to one single level of a protocol hierarchy.
[6.1_s0003] Resource allocation is partially implemented in the routers, switches, and links inside the network and partially in the transport protocol running on the end hosts.
[6.1_s0004] End systems may use signalling protocols to convey their resource requirements to network nodes, which respond with information about resource availability.
[6.1_s0005] One of the main goals of this chapter is to define a framework in which these mechanisms can be understood, as well as to give the relevant details about a representative sample of mechanisms.
[6.1_s0006] We should clarify our terminology before going any further.
[6.1_s0007] By resource allocation, we mean the process by which network elements try to meet the competing demands that applications have for network resources—primarily link bandwidth and buffer space in routers or switches.
[6.1_s0008] Of course, it will often not be possible to meet all the demands, meaning that some users or applications may receive fewer network resources than they want.
[6.1_s0009] Part of the resource allocation problem is deciding when to say no and to whom.
[6.1_s0010] We use the term congestion control to describe the efforts made by network nodes to prevent or respond to overload conditions.
[6.1_s0011] Since congestion is generally bad for everyone, the first order of business is making congestion subside, or preventing it in the first place.
[6.1_s0012] This might be achieved simply by persuading a few hosts to stop sending, thus improving the situation for everyone else.
[6.1_s0013] However, it is more common for congestion-control mechanisms to have some aspect of fairness—that is, they try to share the pain among all users, rather than causing great pain to a few.
[6.1_s0014] Thus, we see that many congestion-control mechanisms have some sort of resource allocation built into them.
[6.1_s0015] It is also important to understand the difference between flow control and congestion control.
[6.1_s0016] Flow control involves keeping a fast sender from overrunning a slow receiver.
[6.1_s0017] Congestion control, by contrast, is intended to keep a set of senders from sending too much data into the network because of lack of resources at some point.
[6.1_s0018] These two concepts are often confused; as we will see, they also share some mechanisms.
[6.1_s0019] 6.1.1 Network Model  We begin by defining three salient features of the network architecture.
[6.1_s0020] For the most part, this is a summary of material presented in the previous chapters that is relevant to the problem of resource allocation.
[6.1_s0021] Packet-Switched Network
[6.1_s0022] We consider resource allocation in a packet-switched network (or internet) consisting of multiple links and switches (or routers).
[6.1_s0023] Since most of the mechanisms described in this chapter were designed for use on the Internet, and therefore were originally defined in terms of routers rather than switches, we use the term router throughout our discussion.
[6.1_s0024] The problem is essentially the same, whether on a network or an internetwork.
[6.1_s0025] In such an environment, a given source may have more than enough capacity on the immediate outgoing link to send a packet, but somewhere in the middle of a network its packets encounter a link that is being used by many different traffic sources.
[6.1_s0026] Figure illustrates this situation—two high-speed links are feeding a low-speed link.
[6.1_s0027] This is in contrast to shared-access networks like Ethernet and wireless networks, where the source can directly observe the traffic on the network and decide accordingly whether or not to send a packet.
[6.1_s0028] We have already seen the algorithms used to allocate bandwidth on shared-access networks (e.g., Ethernet and Wi-Fi).
[6.1_s0029] These access-control algorithms are, in some sense, analogous to congestion-control algorithms in a switched network.
[6.1_s0030] Connectionless Flows  For much of our discussion, we assume that the network is essentially connectionless, with any connection-oriented service implemented in the transport protocol that is running on the end hosts.
[6.1_s0031] (We explain the qualification “essentially” in a moment.)
[6.1_s0032] This is precisely the model of the Internet, where IP provides a connectionless datagram delivery service and TCP implements an end-to-end connection abstraction.
[6.1_s0033] Note that this assumption does not hold in virtual circuit networks such as ATM and X.25.
[6.1_s0034] In such networks, a connection setup message traverses the network when a circuit is established.
[6.1_s0035] This setup message reserves a set of buffers for the connection at each router, thereby providing a form of congestion control—a connection is established only if enough buffers can be allocated to it at each router.
[6.1_s0036] The major shortcoming of this approach is that it leads to an underutilization of resources—buffers reserved for a particular circuit are not available for use by other traffic even if they were not currently being used by that circuit.
[6.1_s0037] The focus of this chapter is on resource allocation approaches that apply in an internetwork, and thus we focus mainly on connectionless networks.
[6.1_s0038] We need to qualify the term connectionless because our classification of networks as being either connectionless or connection oriented is a bit too restrictive; there is a gray area in between.
[6.1_s0039] In particular, the assumption that all datagrams are completely independent in a connectionless network is too strong.
[6.1_s0040] The datagrams are certainly switched independently, but it is usually the case that a stream of datagrams between a particular pair of hosts flows through a particular set of routers.
[6.1_s0041] This idea of a flow—a sequence of packets sent between a source/destination pair and following the same route through the network—is an important abstraction in the context of resource allocation; it is one that we will use in this chapter.
[6.1_s0042] One of the powers of the flow abstraction is that flows can be defined at different granularities.
[6.1_s0043] For example, a flow can be host-to-host (i.e., have the same source/destination host addresses) or process-to-process (i.e., have the same source/destination host/port pairs).
[6.1_s0044] In the latter case, a flow is essentially the same as a channel, as we have been using that term throughout this book.
[6.1_s0045] The reason we introduce a new term is that a flow is visible to the routers inside the network, whereas a channel is an end-to-end abstraction.
[6.1_s0046] Figure illustrates several flows passing through a series of routers.
[6.1_s0047] Because multiple related packets flow through each router, it sometimes makes sense to maintain some state information for each flow, information that can be used to make resource allocation decisions about the packets that belong to the flow.
[6.1_s0048] This state is sometimes called soft state.
[6.1_s0049] The main difference between soft state and hard state is that soft state need not always be explicitly created and removed by signalling.
[6.1_s0050] Soft state represents a middle ground between a purely connectionless network that maintains no state at the routers and a purely connection-oriented network that maintains hard state at the routers.
[6.1_s0051] In general, the correct operation of the network does not depend on soft state being present (each packet is still routed correctly without regard to this state), but when a packet happens to belong to a flow for which the router is currently maintaining soft state, then the router is better able to handle the packet.
[6.1_s0052] Note that a flow can be either implicitly defined or explicitly established.
[6.1_s0053] In the former case, each router watches for packets that happen to be traveling between the same source/destination pair—the router does this by inspecting the addresses in the header—and treats these packets as belonging to the same flow for the purpose of congestion control.
[6.1_s0054] In the latter case, the source sends a flow setup message across the network, declaring that a flow of packets is about to start.
[6.1_s0055] While explicit flows are arguably no different than a connection across a connection-oriented network, we call attention to this case because, even when explicitly established, a flow does not imply any end-to-end semantics and, in particular, does not imply the reliable and ordered delivery of a virtual circuit.
[6.1_s0056] It simply exists for the purpose of resource allocation.
[6.1_s0057] We will see examples of both implicit and explicit flows in this chapter.
[6.1_s0058] Service Model
[6.1_s0059] In the early part of this chapter, we will focus on mechanisms that assume the best-effort service model of the Internet.
[6.1_s0060] With best-effort service, all packets are given essentially equal treatment, with end hosts given no opportunity to ask the network that some packets or flows be given certain guarantees or preferential service.
[6.1_s0061] Defining a service model that supports some kind of preferred service or guarantee—for example, guaranteeing the bandwidth needed for a video stream—is the subject of a later section.
[6.1_s0062] Such a service model is said to provide multiple qualities of service (QoS).
[6.1_s0063] As we will see, there is actually a spectrum of possibilities, ranging from a purely best-effort service model to one in which individual flows receive quantitative guarantees of QoS. One of the greatest challenges is to define a service model that meets the needs of a wide range of applications and even allows for the applications that will be invented in the future.
[6.1_s0064] 6.1.2
[6.1_s0065] Taxonomy  There are countless ways in which resource allocation mechanisms differ, so creating a thorough taxonomy is a difficult proposition.
[6.1_s0066] For now, we describe three dimensions along which resource allocation mechanisms can be characterized; more subtle distinctions will be called out during the course of this chapter.
[6.1_s0067] Router-Centric versus Host-Centric  Resource allocation mechanisms can be classified into two broad groups: those that address the problem from inside the network (i.e., at the routers or switches) and those that address it from the edges of the network (i.e., in the hosts, perhaps inside the transport protocol).
[6.1_s0068] Since it is the case that both the routers inside the network and the hosts at the edges of the network participate in resource allocation, the real issue is where the majority of the burden falls.
[6.1_s0069] In a router-centric design, each router takes responsibility for deciding when packets are forwarded and selecting which packets are to be dropped, as well as for informing the hosts that are generating the network traffic how many packets they are allowed to send.
[6.1_s0070] In a host-centric design, the end hosts observe the network conditions (e.g., how many packets they are successfully getting through the network) and adjust their behavior accordingly.
[6.1_s0071] Note that these two groups are not mutually exclusive.
[6.1_s0072] For example, a network that places the primary burden for managing congestion on routers still expects the end hosts to adhere to any advisory messages the routers send, while the routers in networks that use end-to-end congestion control still have some policy, no matter how simple, for deciding which packets to drop when their queues do overflow.
[6.1_s0073] Reservation-Based versus Feedback-Based  A second way that resource allocation mechanisms are sometimes classified is according to whether they use reservations or feedback.
[6.1_s0074] In a reservation-based system, some entity (e.g., the end host) asks the network for a certain amount of capacity to be allocated for a flow.
[6.1_s0075] Each router then allocates enough resources (buffers and/or percentage of the link’s bandwidth) to satisfy this request.
[6.1_s0076] If the request cannot be satisfied at some router, because doing so would overcommit its resources, then the router rejects the reservation.
[6.1_s0077] This is analogous to getting a busy signal when trying to make a phone call.
[6.1_s0078] In a feedback-based approach, the end hosts begin sending data without first reserving any capacity and then adjust their sending rate according to the feedback they receive.
[6.1_s0079] This feedback can be either explicit (i.e., a congested router sends a “please slow down” message to the host) or implicit (i.e., the end host adjusts its sending rate according to the externally observable behavior of the network, such as packet losses).
[6.1_s0080] Note that a reservation-based system always implies a router-centric resource allocation mechanism.
[6.1_s0081] This is because each router is responsible for keeping track of how much of its capacity is currently available and deciding whether new reservations can be admitted.
[6.1_s0082] Routers may also have to make sure each host lives within the reservation it made.
[6.1_s0083] If a host sends data faster than it claimed it would when it made the reservation, then that host’s packets are good candidates for discarding, should the router become congested.
[6.1_s0084] On the other hand, a feedback-based system can imply either a router- or host-centric mechanism.
[6.1_s0085] Typically, if the feedback is explicit, then the router is involved, to at least some degree, in the resource allocation scheme.
[6.1_s0086] If the feedback is implicit, then almost all of the burden falls to the end host; the routers silently drop packets when they become congested.
[6.1_s0087] Reservations do not have to be made by end hosts.
[6.1_s0088] It is possible for a network administrator to allocate resources to flows or to larger aggregates of traffic, as we will see in a later section.
[6.1_s0089] Window Based versus Rate Based  A third way to characterize resource allocation mechanisms is according to whether they are window based or rate based.
[6.1_s0090] This is one of the areas, noted above, where similar mechanisms and terminology are used for both flow control and congestion control.
[6.1_s0091] Both flow-control and resource allocation mechanisms need a way to express, to the sender, how much data it is allowed to transmit.
[6.1_s0092] There are two general ways of doing this: with a window or with a rate.
[6.1_s0093] We have already seen window-based transport protocols, such as TCP, in which the receiver advertises a window to the sender.
[6.1_s0094] This window corresponds to how much buffer space the receiver has, and it limits how much data the sender can transmit; that is, it supports flow control.
[6.1_s0095] A similar mechanism—window advertisement—can be used within the network to reserve buffer space (i.e., to support resource allocation).
[6.1_s0096] TCP’s congestion-control mechanisms are window based.
[6.1_s0097] It is also possible to control a sender’s behavior using a rate—that is, how many bits per second the receiver or network is able to absorb.
[6.1_s0098] Rate-based control makes sense for many multimedia applications, which tend to generate data at some average rate and which need at least some minimum throughput to be useful.
[6.1_s0099] For example, a video codec might generate video at an average rate of 1 Mbps with a peak rate of 2 Mbps.
[6.1_s0100] As we will see later in this chapter, rate-based characterization of flows is a logical choice in a reservation-based system that supports different qualities of service—the sender makes a reservation for so many bits per second, and each router along the path determines if it can support that rate, given the other flows it has made commitments to.
[6.1_s0101] Summary of Resource Allocation Taxonomy  Classifying resource allocation approaches at two different points along each of three dimensions, as we have just done, would seem to suggest up to eight unique strategies.
[6.1_s0102] While eight different approaches are certainly possible, we note that in practice two general strategies seem to be most prevalent; these two strategies are tied to the underlying service model of the network.
[6.1_s0103] On the one hand, a best-effort service model usually implies that feedback is being used, since such a model does not allow users to reserve network capacity.
[6.1_s0104] This, in turn, means that most of the responsibility for congestion control falls to the end hosts, perhaps with some assistance from the routers.
[6.1_s0105] In practice, such networks use window-based information.
[6.1_s0106] This is the general strategy adopted in the Internet.
[6.1_s0107] On the other hand, a QoS-based service model probably implies some form of reservation.
[6.1_s0108] Support for these reservations is likely to require significant router involvement, such as queuing packets differently depending on the level of reserved resources they require.
[6.1_s0109] Moreover, it is natural to express such reservations in terms of rate, since windows are only indirectly related to how much bandwidth a user needs from the network.
[6.1_s0110] We discuss this topic in a later section.
[6.1_s0111] 6.1.3 Evaluation Criteria  The final issue is one of knowing whether a resource allocation mechanism is good or not.
[6.1_s0112] Recall that in the problem statement at the start of this chapter we posed the question of how a network effectively and fairly allocates its resources.
[6.1_s0113] This suggests at least two broad measures by which a resource allocation scheme can be evaluated.
[6.1_s0114] We consider each in turn.
[6.1_s0115] Effective Resource Allocation  A good starting point for evaluating the effectiveness of a resource allocation scheme is to consider the two principal metrics of networking: throughput and delay.
[6.1_s0116] Clearly, we want as much throughput and as little delay as possible.
[6.1_s0117] Unfortunately, these goals are often somewhat at odds with each other.
[6.1_s0118] One sure way for a resource allocation algorithm to increase throughput is to allow as many packets into the network as possible, so as to drive the utilization of all the links up to 100%.
[6.1_s0119] We would do this to avoid the possibility of a link becoming idle because an idle link necessarily hurts throughput.
[6.1_s0120] The problem with this strategy is that increasing the number of packets in the network also increases the length of the queues at each router.
[6.1_s0121] Longer queues, in turn, mean packets are delayed longer in the network.
[6.1_s0122] To describe this relationship, some network designers have proposed using the ratio of throughput to delay as a metric for evaluating the effectiveness of a resource allocation scheme.
[6.1_s0123] This ratio is sometimes referred to as the power of the network:
[6.1_s0124] Note that it is not obvious that power is the right metric for judging resource allocation effectiveness.
[6.1_s0125] For one thing, the theory behind power is based on an M/M/1 queuing network that assumes infinite queues;\ [#]_ real networks have finite buffers and sometimes have to drop packets.
[6.1_s0126] For another, power is typically defined relative to a single connection (flow); it is not clear how it extends to multiple, competing connections.
[6.1_s0127] Despite these rather severe limitations, however, no alternatives have gained wide acceptance, and so power continues to be used.
[6.1_s0128] The objective is to maximize this ratio, which is a function of how much load you place on the network.
[6.1_s0129] The load, in turn, is set by the resource allocation mechanism.
[6.1_s0130] Figure gives a representative power curve, where, ideally, the resource allocation mechanism would operate at the peak of this curve.
[6.1_s0131] To the left of the peak, the mechanism is being too conservative; that is, it is not allowing enough packets to be sent to keep the links busy.
[6.1_s0132] To the right of the peak, so many packets are being allowed into the network that increases in delay due to queuing are starting to dominate any small gains in throughput.
[6.1_s0133] Interestingly, this power curve looks very much like the system throughput curve in a timesharing computer system.
[6.1_s0134] System throughput improves as more jobs are admitted into the system, until it reaches a point when there are so many jobs running that the system begins to thrash (spends all of its time swapping memory pages) and the throughput begins to drop.
[6.1_s0135] As we will see in later sections of this chapter, many congestion-control schemes are able to control load in only very crude ways; that is, it is simply not possible to turn the “knob” a little and allow only a small number of additional packets into the network.
[6.1_s0136] As a consequence, network designers need to be concerned about what happens even when the system is operating under extremely heavy load—that is, at the rightmost end of the curve in Figure.
[6.1_s0137] Ideally, we would like to avoid the situation in which the system throughput goes to zero because the system is thrashing.
[6.1_s0138] In networking terminology, we want a system that is stable—where packets continue to get through the network even when the network is operating under heavy load.
[6.1_s0139] If a mechanism is not stable, the network may experience congestion collapse.
[6.1_s0140] Fair Resource Allocation  The effective utilization of network resources is not the only criterion for judging a resource allocation scheme.
[6.1_s0141] We must also consider the issue of fairness.
[6.1_s0142] However, we quickly get into murky waters when we try to define what exactly constitutes fair resource allocation.
[6.1_s0143] For example, a reservation-based resource allocation scheme provides an explicit way to create controlled unfairness.
[6.1_s0144] With such a scheme, we might use reservations to enable a video stream to receive 1 Mbps across some link while a file transfer receives only 10 kbps over the same link.
[6.1_s0145] In the absence of explicit information to the contrary, when several flows share a particular link, we would like for each flow to receive an equal share of the bandwidth.
[6.1_s0146] This definition presumes that a fair share of bandwidth means an equal share of bandwidth.
[6.1_s0147] But, even in the absence of reservations, equal shares may not equate to fair shares.
[6.1_s0148] Should we also consider the length of the paths being compared?
[6.1_s0149] For example, as illustrated in Figure, what is fair when one four-hop flow is competing with three one-hop flows?

=== SECTION 6.4: Congestion Control > Advanced Congestion Control ===
[6.4_s0000] This section explores congestion control more deeply.
[6.4_s0001] In doing so, it is important to understand that the standard TCP’s strategy is to control congestion once it happens, as opposed to trying to avoid congestion in the first place.
[6.4_s0002] In fact, TCP repeatedly increases the load it imposes on the network in an effort to find the point at which congestion occurs, and then it backs off from this point.
[6.4_s0003] Said another way, TCP needs to create losses to find the available bandwidth of the connection.
[6.4_s0004] An appealing alternative is to predict when congestion is about to happen and then to reduce the rate at which hosts send data just before packets start being discarded.
[6.4_s0005] We call such a strategy congestion avoidance to distinguish it from congestion control, but it’s probably most accurate to think of “avoidance” as a subset of “control.”
[6.4_s0006] We describe two different approaches to congestion-avoidance.
[6.4_s0007] The first puts a small amount of additional functionality into the router to assist the end node in the anticipation of congestion.
[6.4_s0008] This approach is often referred to as Active Queue Management (AQM).
[6.4_s0009] The second approach attempts to avoid congestion purely from the end hosts.
[6.4_s0010] This approach is implemented in TCP, making it variant of the congestion control mechanisms described in the previous section.
[6.4_s0011] 6.4.1 Active Queue Management (DECbit, RED, ECN)
[6.4_s0012] The first approach requires changes to routers, which has never been the Internet’s preferred way of introducing new features, but nonetheless, has been a constant source of consternation over the last 20 years.
[6.4_s0013] The problem is that while it’s generally agreed that routers are in an ideal position to detect the onset of congestion—i.e., their queues start to fill up—there has not been a consensus on exactly what the best algorithm is.
[6.4_s0014] The following describes two of the classic mechanisms, and concludes with a brief discussion of where things stand today.
[6.4_s0015] DECbit  The first mechanism was developed for use on the Digital Network Architecture (DNA), a connectionless network with a connection-oriented transport protocol.
[6.4_s0016] This mechanism could, therefore, also be applied to TCP and IP.
[6.4_s0017] As noted above, the idea here is to more evenly split the responsibility for congestion control between the routers and the end nodes.
[6.4_s0018] Each router monitors the load it is experiencing and explicitly notifies the end nodes when congestion is about to occur.
[6.4_s0019] This notification is implemented by setting a binary congestion bit in the packets that flow through the router, hence the name DECbit.
[6.4_s0020] The destination host then copies this congestion bit into the ACK it sends back to the source.
[6.4_s0021] Finally, the source adjusts its sending rate so as to avoid congestion.
[6.4_s0022] The following discussion describes the algorithm in more detail, starting with what happens in the router.
[6.4_s0023] A single congestion bit is added to the packet header.
[6.4_s0024] A router sets this bit in a packet if its average queue length is greater than or equal to 1 at the time the packet arrives.
[6.4_s0025] This average queue length is measured over a time interval that spans the last busy+idle cycle, plus the current busy cycle.
[6.4_s0026] (The router is busy when it is transmitting and idle when it is not.)
[6.4_s0027] Figure shows the queue length at a router as a function of time.
[6.4_s0028] Essentially, the router calculates the area under the curve and divides this value by the time interval to compute the average queue length.
[6.4_s0029] Using a queue length of 1 as the trigger for setting the congestion bit is a trade-off between significant queuing (and hence higher throughput) and increased idle time (and hence lower delay).
[6.4_s0030] In other words, a queue length of 1 seems to optimize the power function.
[6.4_s0031] Now turning our attention to the host half of the mechanism, the source records how many of its packets resulted in some router setting the congestion bit.
[6.4_s0032] In particular, the source maintains a congestion window, just as in TCP, and watches to see what fraction of the last window’s worth of packets resulted in the bit being set.
[6.4_s0033] If less than 50% of the packets had the bit set, then the source increases its congestion window by one packet.
[6.4_s0034] If 50% or more of the last window’s worth of packets had the congestion bit set, then the source decreases its congestion window to 0.875 times the previous value.
[6.4_s0035] The value 50% was chosen as the threshold based on analysis that showed it to correspond to the peak of the power curve.
[6.4_s0036] The “increase by 1, decrease by 0.875” rule was selected because additive increase/multiplicative decrease makes the mechanism stable.
[6.4_s0037] Random Early Detection  A second mechanism, called random early detection (RED), is similar to the DECbit scheme in that each router is programmed to monitor its own queue length and, when it detects that congestion is imminent, to notify the source to adjust its congestion window.
[6.4_s0038] RED, invented by Sally Floyd and Van Jacobson in the early 1990s, differs from the DECbit scheme in two major ways.
[6.4_s0039] The first is that rather than explicitly sending a congestion notification message to the source, RED is most commonly implemented such that it implicitly notifies the source of congestion by dropping one of its packets.
[6.4_s0040] The source is, therefore, effectively notified by the subsequent timeout or duplicate ACK.
[6.4_s0041] In case you haven’t already guessed, RED is designed to be used in conjunction with TCP, which currently detects congestion by means of timeouts (or some other means of detecting packet loss such as duplicate ACKs).
[6.4_s0042] As the “early” part of the RED acronym suggests, the gateway drops the packet earlier than it would have to, so as to notify the source that it should decrease its congestion window sooner than it would normally have.
[6.4_s0043] In other words, the router drops a few packets before it has exhausted its buffer space completely, so as to cause the source to slow down, with the hope that this will mean it does not have to drop lots of packets later on.
[6.4_s0044] The second difference between RED and DECbit is in the details of how RED decides when to drop a packet and what packet it decides to drop.
[6.4_s0045] To understand the basic idea, consider a simple FIFO queue.
[6.4_s0046] Rather than wait for the queue to become completely full and then be forced to drop each arriving packet (the tail drop policy of the previous section), we could decide to drop each arriving packet with some drop probability whenever the queue length exceeds some drop level.
[6.4_s0047] This idea is called early random drop.
[6.4_s0048] The RED algorithm defines the details of how to monitor the queue length and when to drop a packet.
[6.4_s0049] In the following paragraphs, we describe the RED algorithm as originally proposed by Floyd and Jacobson.
[6.4_s0050] We note that several modifications have since been proposed both by the inventors and by other researchers.
[6.4_s0051] However, the key ideas are the same as those presented below, and most current implementations are close to the algorithm that follows.
[6.4_s0052] First, RED computes an average queue length using a weighted running average similar to the one used in the original TCP timeout computation.
[6.4_s0053] That is, AvgLen is computed as  where 0 <
[6.4_s0054] Weight < 1 and SampleLen is the length of the queue when a sample measurement is made.
[6.4_s0055] In most software implementations, the queue length is measured every time a new packet arrives at the gateway.
[6.4_s0056] In hardware, it might be calculated at some fixed sampling interval.
[6.4_s0057] The reason for using an average queue length rather than an instantaneous one is that it more accurately captures the notion of congestion.
[6.4_s0058] Because of the bursty nature of Internet traffic, queues can become full very quickly and then become empty again.
[6.4_s0059] If a queue is spending most of its time empty, then it’s probably not appropriate to conclude that the router is congested and to tell the hosts to slow down.
[6.4_s0060] Thus, the weighted running average calculation tries to detect long-lived congestion, as indicated in the right-hand portion of Figure, by filtering out short-term changes in the queue length.

[6.4_s0062] The question of how we pick this time constant is discussed below.
[6.4_s0063] Second, RED has two queue length thresholds that trigger certain activity: MinThreshold and MaxThreshold.
[6.4_s0064] When a packet arrives at the gateway, RED compares the current AvgLen with these two thresholds, according to the following rules:  If the average queue length is smaller than the lower threshold, no action is taken, and if the average queue length is larger than the upper threshold, then the packet is always dropped.
[6.4_s0065] If the average queue length is between the two thresholds, then the newly arriving packet is dropped with some probability P.
[6.4_s0066] This situation is depicted in Figure.
[6.4_s0067] The approximate relationship between P and AvgLen is shown in Figure.
[6.4_s0068] Note that the probability of drop increases slowly when AvgLen is between the two thresholds, reaching MaxP at the upper threshold, at which point it jumps to unity.
[6.4_s0069] The rationale behind this is that, if AvgLen reaches the upper threshold, then the gentle approach (dropping a few packets) is not working and drastic measures are called for: dropping all arriving packets.
[6.4_s0070] Some research has suggested that a smoother transition from random dropping to complete dropping, rather than the discontinuous approach shown here, may be appropriate.
[6.4_s0071] Although Figure shows the probability of drop as a function only of AvgLen, the situation is actually a little more complicated.
[6.4_s0072] In fact, P is a function of both AvgLen and how long it has been since the last packet was dropped.
[6.4_s0073] Specifically, it is computed as follows:
[6.4_s0074] TempP is the variable that is plotted on the y-axis in Figure, count keeps track of how many newly arriving packets have been queued (not dropped), and AvgLen has been between the two thresholds.
[6.4_s0075] P increases slowly as count increases, thereby making a drop increasingly likely as the time since the last drop increases.
[6.4_s0076] This makes closely spaced drops relatively less likely than widely spaced drops.
[6.4_s0077] This extra step in calculating P was introduced by the inventors of RED when they observed that, without it, the packet drops were not well distributed in time but instead tended to occur in clusters.
[6.4_s0078] Because packet arrivals from a certain connection are likely to arrive in bursts, this clustering of drops is likely to cause multiple drops in a single connection.
[6.4_s0079] This is not desirable, since only one drop per round-trip time is enough to cause a connection to reduce its window size, whereas multiple drops might send it back into slow start.
[6.4_s0080] As an example, suppose that we set MaxP to 0.02 and count is initialized to zero.
[6.4_s0081] If the average queue length were halfway between the two thresholds, then TempP, and the initial value of P, would be half of MaxP, or 0.01.
[6.4_s0082] An arriving packet, of course, has a 99 in 100 chance of getting into the queue at this point.
[6.4_s0083] With each successive packet that is not dropped, P slowly increases, and by the time 50 packets have arrived without a drop, P would have doubled to 0.02.
[6.4_s0084] In the unlikely event that 99 packets arrived without loss, P reaches 1, guaranteeing that the next packet is dropped.
[6.4_s0085] The important thing about this part of the algorithm is that it ensures a roughly even distribution of drops over time.
[6.4_s0086] The intent is that, if RED drops a small percentage of packets when AvgLen exceeds MinThreshold, this will cause a few TCP connections to reduce their window sizes, which in turn will reduce the rate at which packets arrive at the router.
[6.4_s0087] All going well, AvgLen will then decrease and congestion is avoided.
[6.4_s0088] The queue length can be kept short, while throughput remains high since few packets are dropped.
[6.4_s0089] Note that, because RED is operating on a queue length averaged over time, it is possible for the instantaneous queue length to be much longer than AvgLen.
[6.4_s0090] In this case, if a packet arrives and there is nowhere to put it, then it will have to be dropped.
[6.4_s0091] When this happens, RED is operating in tail drop mode.
[6.4_s0092] One of the goals of RED is to prevent tail drop behavior if possible.
[6.4_s0093] The random nature of RED confers an interesting property on the algorithm.
[6.4_s0094] Because RED drops packets randomly, the probability that RED decides to drop a particular flow’s packet(s) is roughly proportional to the share of the bandwidth that flow is currently getting at that router.
[6.4_s0095] This is because a flow that is sending a relatively large number of packets is providing more candidates for random dropping.
[6.4_s0096] Thus, there is some sense of fair resource allocation built into RED, although it is by no means precise.
[6.4_s0097] While arguably fair, because RED punishes high-bandwidth flows more than low-bandwidth flows, it increases the probability of a TCP restart, which is doubly painful for those high-bandwidth flows.
[6.4_s0098] Consider the setting of the two thresholds, MinThreshold and MaxThreshold.
[6.4_s0099] If the traffic is fairly bursty, then MinThreshold should be sufficiently large to allow the link utilization to be maintained at an acceptably high level.
[6.4_s0100] Also, the difference between the two thresholds should be larger than the typical increase in the calculated average queue length in one RTT.
[6.4_s0101] Setting MaxThreshold to twice MinThreshold seems to be a reasonable rule of thumb given the traffic mix on today’s Internet.
[6.4_s0102] In addition, since we expect the average queue length to hover between the two thresholds during periods of high load, there should be enough free buffer space above MaxThreshold to absorb the natural bursts that occur in Internet traffic without forcing the router to enter tail drop mode.
[6.4_s0103] We noted above that Weight determines the time constant for the running average low-pass filter, and this gives us a clue as to how we might pick a suitable value for it.
[6.4_s0104] Recall that RED is trying to send signals to TCP flows by dropping packets during times of congestion.
[6.4_s0105] Suppose that a router drops a packet from some TCP connection and then immediately forwards some more packets from the same connection.
[6.4_s0106] When those packets arrive at the receiver, it starts sending duplicate ACKs to the sender.
[6.4_s0107] When the sender sees enough duplicate ACKs, it will reduce its window size.
[6.4_s0108] So, from the time the router drops a packet until the time when the same router starts to see some relief from the affected connection in terms of a reduced window size, at least one round-trip time must elapse for that connection.
[6.4_s0109] There is probably not much point in having the router respond to congestion on time scales much less than the round-trip time of the connections passing through it.
[6.4_s0110] As noted previously, 100 ms is not a bad estimate of average round-trip times in the Internet.
[6.4_s0111] Thus, Weight should be chosen such that changes in queue length over time scales much less than 100 ms are filtered out.
[6.4_s0112] Since RED works by sending signals to TCP flows to tell them to slow down, you might wonder what would happen if those signals are ignored.
[6.4_s0113] This is often called the unresponsive flow problem.
[6.4_s0114] Unresponsive flows use more than their fair share of network resources and could cause congestive collapse if there were enough of them, just as in the days before TCP congestion control.
[6.4_s0115] Some of the techniques described in the next section can help with this problem by isolating certain classes of traffic from others.
[6.4_s0116] There is also the possibility that a variant of RED could drop more heavily from flows that are unresponsive to the initial hints that it sends.
[6.4_s0117] Explicit Congestion Notification  RED is the most extensively studied AQM mechanism, but it has not been widely deployed, due in part to the fact that it does not result in ideal behavior in all circumstances.
[6.4_s0118] It is, however, the benchmark for understanding AQM behavior.
[6.4_s0119] The other thing that came out of RED is the recognition that TCP could do a better job if routers were to send a more explicit congestion signal.
[6.4_s0120] That is, instead of dropping a packet and assuming TCP will eventually notice (e.g., due to the arrival of a duplicate ACK), RED (or any AQM algorithm for that matter) can do a better job if it instead marks the packet and continues to send it along its way to the destination.
[6.4_s0121] This idea was codified in changes to the IP and TCP headers known as Explicit Congestion Notification (ECN).
[6.4_s0122] Specifically, this feedback is implemented by treating two bits in the IP TOS field as ECN bits.
[6.4_s0123] One bit is set by the source to indicate that it is ECN-capable, that is, able to react to a congestion notification.
[6.4_s0124] This is called the ECT bit (ECN-Capable Transport).
[6.4_s0125] The other bit is set by routers along the end-to-end path when congestion is encountered, as computed by whatever AQM algorithm it is running.
[6.4_s0126] This is called the CE bit (Congestion Encountered).
[6.4_s0127] In addition to these two bits in the IP header (which are transport-agnostic), ECN also includes the addition of two optional flags to the TCP header.
[6.4_s0128] The first, ECE (ECN-Echo), communicates from the receiver to the sender that it has received a packet with the CE bit set.
[6.4_s0129] The second, CWR (Congestion Window Reduced) communicates from the sender to the receiver that it has reduced the congestion window.
[6.4_s0130] While ECN is now the standard interpretation of two of the eight bits in the TOS field of the IP header and support for ECN is highly recommended, it is not required.
[6.4_s0131] Moreover, there is no single recommended AQM algorithm, but instead, there is a list of requirements a good AQM algorithm should meet.
[6.4_s0132] Like TCP congestion control algorithms, every AQM algorithm has its advantages and disadvantages, and so we need a lot of them.
[6.4_s0133] There is one particular scenario, however, where the TCP congestion control algorithm and AQM algorithm are designed to work in concert: the datacenter.
[6.4_s0134] We return to this use case at the end of this section.

[6.4_s0136] Source-Based Approaches (Vegas, BBR, DCTCP)  Unlike the previous congestion-avoidance schemes, which depended on cooperation from routers, we now describe a strategy for detecting the incipient stages of congestion—before losses occur—from the end hosts.
[6.4_s0137] We first give a brief overview of a collection of related mechanisms that use different information to detect the early stages of congestion, and then we describe two specific mechanisms in more detail.
[6.4_s0138] The general idea of these techniques is to watch for a sign from the network that some router’s queue is building up and that congestion will happen soon if nothing is done about it.
[6.4_s0139] For example, the source might notice that as packet queues build up in the network’s routers, there is a measurable increase in the RTT for each successive packet it sends.
[6.4_s0140] One particular algorithm exploits this observation as follows: The congestion window normally increases as in TCP, but every two round-trip delays the algorithm checks to see if the current RTT is greater than the average of the minimum and maximum RTTs seen so far.
[6.4_s0141] If it is, then the algorithm decreases the congestion window by one-eighth.
[6.4_s0142] A second algorithm does something similar.
[6.4_s0143] The decision as to whether or not to change the current window size is based on changes to both the RTT and the window size.
[6.4_s0144] The window is adjusted once every two round-trip delays based on the product  If the result is positive, the source decreases the window size by one-eighth; if the result is negative or 0, the source increases the window by one maximum packet size.
[6.4_s0145] Note that the window changes during every adjustment; that is, it oscillates around its optimal point.
[6.4_s0146] Another change seen as the network approaches congestion is the flattening of the sending rate.
[6.4_s0147] A third scheme takes advantage of this fact.
[6.4_s0148] Every RTT, it increases the window size by one packet and compares the throughput achieved to the throughput when the window was one packet smaller.
[6.4_s0149] If the difference is less than one-half the throughput achieved when only one packet was in transit—as was the case at the beginning of the connection—the algorithm decreases the window by one packet.
[6.4_s0150] This scheme calculates the throughput by dividing the number of bytes outstanding in the network by the RTT.
[6.4_s0151] TCP Vegas  The mechanism we are going to describe in more detail is similar to the last algorithm in that it looks at changes in the throughput rate or, more specifically, changes in the sending rate.
[6.4_s0152] However, it differs from the previous algorithm in the way it calculates throughput, and instead of looking for a change in the slope of the throughput it compares the measured throughput rate with an expected throughput rate.
[6.4_s0153] The algorithm, TCP Vegas, is not widely deployed in the Internet today, but the strategy it uses has been adopted by other implementations that are now being deployed.
[6.4_s0154] The intuition behind the Vegas algorithm can be seen in the trace of standard TCP given in Figure.
[6.4_s0155] The top graph shown in Figure traces the connection’s congestion window; it shows the same information as the traces given earlier in this section.
[6.4_s0156] The middle and bottom graphs depict new information: The middle graph shows the average sending rate as measured at the source, and the bottom graph shows the average queue length as measured at the bottleneck router.
[6.4_s0157] All three graphs are synchronized in time.
[6.4_s0158] In the period between 4.5 and 6.0 seconds (shaded region), the congestion window increases (top graph).
[6.4_s0159] We expect the observed throughput to also increase, but instead it stays flat (middle graph).
[6.4_s0160] This is because the throughput cannot increase beyond the available bandwidth.
[6.4_s0161] Beyond this point, any increase in the window size only results in packets taking up buffer space at the bottleneck router (bottom graph).
[6.4_s0162] A useful metaphor that describes the phenomenon illustrated in Figure is driving on ice.
[6.4_s0163] The speedometer (congestion window) may say that you are going 30 miles an hour, but by looking out the car window and seeing people pass you on foot (measured sending rate)
[6.4_s0164] you know that you are going no more than 5 miles an hour.
[6.4_s0165] The extra energy is being absorbed by the car’s tires (router buffers).
[6.4_s0166] TCP Vegas uses this idea to measure and control the amount of extra data this connection has in transit, where by “extra data” we mean data that the source would not have transmitted had it been trying to match exactly the available bandwidth of the network.
[6.4_s0167] The goal of TCP Vegas is to maintain the “right” amount of extra data in the network.
[6.4_s0168] Obviously, if a source is sending too much extra data, it will cause long delays and possibly lead to congestion.
[6.4_s0169] Less obviously, if a connection is sending too little extra data, it cannot respond rapidly enough to transient increases in the available network bandwidth.
[6.4_s0170] TCP Vegas’s congestion-avoidance actions are based on changes in the estimated amount of extra data in the network, not only on dropped packets.
[6.4_s0171] We now describe the algorithm in detail.
[6.4_s0172] First, define a given flow’s BaseRTT to be the RTT of a packet when the flow is not congested.
[6.4_s0173] In practice, TCP Vegas sets BaseRTT to the minimum of all measured round-trip times; it is commonly the RTT of the first packet sent by the connection, before the router queues increase due to traffic generated by this flow.
[6.4_s0174] If we assume that we are not overflowing the connection, then the expected throughput is given by  where CongestionWindow is the TCP congestion window, which we assume (for the purpose of this discussion) to be equal to the number of bytes in transit.
[6.4_s0175] Second, TCP Vegas calculates the current sending rate, ActualRate.
[6.4_s0176] This is done by recording the sending time for a distinguished packet, recording how many bytes are transmitted between the time that packet is sent and when its acknowledgment is received, computing the sample RTT for the distinguished packet when its acknowledgment arrives, and dividing the number of bytes transmitted by the sample RTT.
[6.4_s0177] This calculation is done once per round-trip time.
[6.4_s0178] Third, TCP Vegas compares ActualRate to ExpectedRate and adjusts the window accordingly.
[6.4_s0179] We let Diff = ExpectedRate - ActualRate.
[6.4_s0180] Note that Diff is positive or 0 by definition, since ActualRate >ExpectedRate implies that we need to change BaseRTT to the latest sampled RTT.
[6.4_s0181] We also define two thresholds, α < β, roughly corresponding to having too little and too much extra data in the network, respectively.
[6.4_s0182] When Diff < α, TCP Vegas increases the congestion window linearly during the next RTT, and when Diff > β, TCP Vegas decreases the congestion window linearly during the next RTT.
[6.4_s0183] TCP Vegas leaves the congestion window unchanged
[6.4_s0184] when α < Diff < β.  Intuitively, we can see that the farther away the actual throughput gets from the expected throughput, the more congestion there is in the network, which implies that the sending rate should be reduced.
[6.4_s0185] The β threshold triggers this decrease.
[6.4_s0186] On the other hand, when the actual throughput rate gets too close to the expected throughput, the connection is in danger of not utilizing the available bandwidth.
[6.4_s0187] The α threshold triggers this increase.
[6.4_s0188] The overall goal is to keep between α and β extra bytes in the network.

[6.4_s0190] The top graph traces the congestion window, showing the same information as the other traces given throughout this chapter.
[6.4_s0191] The bottom graph traces the expected and actual throughput rates that govern how the congestion window is set.

[6.4_s0193] The colored line tracks the ExpectedRate, while the black line tracks the ActualRate.
[6.4_s0194] The wide shaded strip gives the region between the α and β thresholds; the top of the shaded strip is α KBps away from ExpectedRate, and the bottom of the shaded strip is β KBps away from ExpectedRate.
[6.4_s0195] The goal is to keep the ActualRate between these two thresholds, within the shaded region.
[6.4_s0196] Whenever ActualRate falls below the shaded region (i.e., gets too far from ExpectedRate), TCP Vegas decreases the congestion window because it fears that too many packets are being buffered in the network.
[6.4_s0197] Likewise, whenever ActualRate goes above the shaded region (i.e., gets too close to the ExpectedRate), TCP Vegas increases the congestion window because it fears that it is underutilizing the network.
[6.4_s0198] Because the algorithm, as just presented, compares the difference between the actual and expected throughput rates to the α and β thresholds, these two thresholds are defined in terms of KBps.
[6.4_s0199] However, it is perhaps more accurate to think in terms of how many extra buffers the connection is occupying in the network.
[6.4_s0200] For example, on a connection with a BaseRTT of 100 ms and a packet size of 1 KB, if α = 30 KBps and β = 60 KBps, then we can think of α as specifying that the connection needs to be occupying at least 3 extra buffers in the network and β as specifying that the connection should occupy no more than 6 extra buffers in the network.
[6.4_s0201] In practice, a setting of α to 1 buffer and β to 3 buffers works well.
[6.4_s0202] Finally, you will notice that TCP Vegas decreases the congestion window linearly, seemingly in conflict with the rule that multiplicative decrease is needed to ensure stability.
[6.4_s0203] The explanation is that TCP Vegas does use multiplicative decrease when a timeout occurs; the linear decrease just described is an early decrease in the congestion window that should happen before congestion occurs and packets start being dropped.
[6.4_s0204] TCP BBR  BBR (Bottleneck Bandwidth and RTT) is a new TCP congestion control algorithm developed by researchers at Google.
[6.4_s0205] Like Vegas, BBR is delay based, which means it tries to detect buffer growth so as to avoid congestion and packet loss.
[6.4_s0206] Both BBR and Vegas use the minimum RTT and maximum RTT, as calculated over some time interval, as their main control signals.
[6.4_s0207] BBR also introduces new mechanisms to improve performance, including packet pacing, bandwidth probing, and RTT probing.
[6.4_s0208] Packet pacing spaces the packets based on the estimate of the available bandwidth.
[6.4_s0209] This eliminates bursts and unnecessary queuing, which results in a better feedback signal.
[6.4_s0210] BBR also periodically increases its rate, thereby probing the available bandwidth.
[6.4_s0211] Similarly, BBR periodically decreases its rate, thereby probing for a new minimum RTT.
[6.4_s0212] The RTT probing mechanism attempts to be self-synchronizing, which is to say, when there are multiple BBR flows, their respective RTT probes happen at the same time.
[6.4_s0213] This gives a more accurate view of the actual uncongested path RTT, which solves one of the major issues with delay-based congestion control mechanisms: having accurate knowledge of the uncongested path RTT.
[6.4_s0214] BBR is actively being worked on and rapidly evolving.
[6.4_s0215] One major focus is fairness.
[6.4_s0216] For example, some experiments show CUBIC flows get 100× less bandwidth when competing with BBR flows, and other experiments show that unfairness among BBR flows is even possible.
[6.4_s0217] Another major focus is avoiding high retransmission rates, where in some cases as many as 10% of packets are retransmitted.  DCTCP  We conclude with an example of a situation where a variant of the TCP congestion control algorithm has been designed to work in concert with ECN: in cloud datacenters.
[6.4_s0218] The combination is called DCTCP, which stands for Data Center TCP.
[6.4_s0219] The situation is unique in that a datacenter is self-contained, and so it is possible to deploy a tailor-made version of TCP that does not need to worry about treating other TCP flows fairly.
[6.4_s0220] Datacenters are also unique in that they are built using commodity switches, and because there is no need to worry about long-fat pipes spanning a continent, the switches are typically provisioned without an excess of buffers.
[6.4_s0221] The idea is straightforward.
[6.4_s0222] DCTCP adapts ECN by estimating the fraction of bytes that encounter congestion rather than simply detecting that some congestion is about to occur.
[6.4_s0223] At the end hosts, DCTCP then scales the congestion window based on this estimate.
[6.4_s0224] The standard TCP algorithm still kicks in should a packet actually be lost.
[6.4_s0225] The approach is designed to achieve high-burst tolerance, low latency, and high throughput with shallow-buffered switches.
[6.4_s0226] The key challenge DCTCP faces is to estimate the fraction of bytes encountering congestion.
[6.4_s0227] Each switch is simple.
[6.4_s0228] If a packet arrives and the switch sees the queue length (K) is above some threshold; e.g.,  where C is the link rate in packets per second, then the switch sets the CE bit in the IP header.
[6.4_s0229] The complexity of RED is not required.
[6.4_s0230] The receiver then maintains a boolean variable for every flow, which we’ll denote SeenCE, and implements the following state machine in response to every received packet:  -  If the CE bit is set and SeenCE=False, set SeenCE to True and send an immediate ACK.  -  If the CE bit is not set and SeenCE=True, set SeenCE to False and send an immediate ACK.  -
[6.4_s0231] Otherwise, ignore the CE bit.
[6.4_s0232] The non-obvious consequence of the “otherwise” case is that the receiver continues to send delayed ACKs once every n packets, whether or not the CE bit is set.
[6.4_s0233] This has proven important to maintaining high performance.
[6.4_s0234] Finally, the sender computes the fraction of bytes that encountered congestion during the previous observation window (usually chosen to be approximately the RTT), as the ratio of the total bytes transmitted and the bytes acknowledged with the ECE flag set.
[6.4_s0235] DCTCP grows the congestion window in exactly the same way as the standard algorithm, but it reduces the window in proportion to how many bytes encountered congestion during the last observation window.
=== SECTION 7.2: End-to-End Data > Multimedia Data ===
[7.2_s0000] Multimedia data, comprised of audio, video, and still images, now makes up the majority of traffic on the Internet.
[7.2_s0001] Part of what has made the widespread transmission of multimedia across networks possible is advances in compression technology.
[7.2_s0002] Because multimedia data is consumed mostly by humans using their senses—vision and hearing—and processed by the human brain, there are unique challenges to compressing it.
[7.2_s0003] You want to try to keep the information that is most important to a human, while getting rid of anything that doesn’t improve the human’s perception of the visual or auditory experience.
[7.2_s0004] Hence, both computer science and the study of human perception come into play.
[7.2_s0005] In this section, we’ll look at some of the major efforts in representing and compressing multimedia data.
[7.2_s0006] The uses of compression are not limited to multimedia data of course—for example, you may well have used a utility like zip or compress to compress files before sending them over a network, or to uncompress a data file after downloading.
[7.2_s0007] It turns out that the techniques used for compressing data—which are typically lossless, because most people don’t like to lose data from a file—also show up as part of the solution for multimedia compression.
[7.2_s0008] In contrast, lossy compression, commonly used for multimedia data, does not promise that the data received is exactly the same as the data sent.
[7.2_s0009] As noted above, this is because multimedia data often contains information that is of little utility to the human who receives it.
[7.2_s0010] Our senses and brains can only perceive so much detail.
[7.2_s0011] They are also very good at filling in missing pieces and even correcting some errors in what we see or hear.
[7.2_s0012] And, lossy algorithms typically achieve much better compression ratios than do their lossless counterparts; they can be an order of magnitude better or more.
[7.2_s0013] To get a sense of how important compression has been to the spread of networked multimedia, consider the following example.
[7.2_s0014] A high-definition TV screen has something like 1080 × 1920 pixels, each of which has 24 bits of color information, so each frame is  so if you want to send 24 frames per second, that would be over 1 Gbps.
[7.2_s0015] That’s more than most Internet users have access to.
[7.2_s0016] By contrast, modern compression techniques can get a reasonably high-quality HDTV signal down to the range of 10 Mbps, a two order of magnitude reduction and well within the reach of most broadband users.
[7.2_s0017] Similar compression gains apply to lower quality video such as YouTube clips—Web video could never have reached its current popularity without compression to make all those entertaining videos fit within the bandwidth of today’s networks.
[7.2_s0018] Compression techniques as applied to multimedia have been an area of great innovation, particularly lossy compression.
[7.2_s0019] Lossless techniques also have an important role to play, however.
[7.2_s0020] Indeed, most of the lossy techniques include some steps that are lossless, so we begin our discussion with an overview of lossless compression.
[7.2_s0021] 7.2.1 Lossless Compression Techniques  In many ways, compression is inseparable from data encoding.
[7.2_s0022] When thinking about how to encode a piece of data in a set of bits, we might just as well think about how to encode the data in the smallest set of bits possible.
[7.2_s0023] For example, if you have a block of data that is made up of the 26 symbols A through Z, and if all of these symbols have an equal chance of occurring in the data block you are encoding, then encoding each symbol in 5 bits is the best you can do (since 2\ 5 = 32 is the lowest power of 2 above 26).
[7.2_s0024] If, however, the symbol R occurs 50% of the time, then it would be a good idea to use fewer bits to encode the R than any of the other symbols.
[7.2_s0025] In general, if you know the relative probability that each symbol will occur in the data, then you can assign a different number of bits to each possible symbol in a way that minimizes the number of bits it takes to encode a given block of data.
[7.2_s0026] This is the essential idea of Huffman codes, one of the important early developments in data compression.
[7.2_s0027] Run Length Encoding  Run length encoding (RLE) is a compression technique with a brute-force simplicity.
[7.2_s0028] The idea is to replace consecutive occurrences of a given symbol with only one copy of the symbol, plus a count of how many times that symbol occurs—hence, the name run length.
[7.2_s0029] For example, the string AAABBCDDDD would be encoded as 3A2B1C4D.  RLE turns out to be useful for compressing some classes of images.
[7.2_s0030] It can be used in this context by comparing adjacent pixel values and then encoding only the changes.
[7.2_s0031] For images that have large homogeneous regions, this technique is quite effective.
[7.2_s0032] For example, it is not uncommon that RLE can achieve compression ratios on the order of 8-to-1 for scanned text images.
[7.2_s0033] RLE works well on such files because they often contain a large amount of white space that can be removed.
[7.2_s0034] For those old enough to remember the technology, RLE was the key compression algorithm used to transmit faxes.
[7.2_s0035] However, for images with even a small degree of local variation, it is not uncommon for compression to actually increase the image byte size, since it takes 2 bytes to represent a single symbol when that symbol is not repeated.
[7.2_s0036] Differential Pulse Code Modulation  Another simple lossless compression algorithm is Differential Pulse Code Modulation (DPCM).
[7.2_s0037] The idea here is to first output a reference symbol and then, for each symbol in the data, to output the difference between that symbol and the reference symbol.
[7.2_s0038] For example, using symbol A as the reference symbol, the string AAABBCDDDD would be encoded as A0001123333 because A is the same as the reference symbol, B has a difference of 1 from the reference symbol, and so on.
[7.2_s0039] Note that this simple example does not illustrate the real benefit of DPCM, which is that when the differences are small they can be encoded with fewer bits than the symbol itself.
[7.2_s0040] In this example, the range of differences, 0-3, can be represented with 2 bits each, rather than the 7 or 8 bits required by the full character.
[7.2_s0041] As soon as the difference becomes too large, a new reference symbol is selected.
[7.2_s0042] DPCM works better than RLE for most digital imagery, since it takes advantage of the fact that adjacent pixels are usually similar.
[7.2_s0043] Due to this correlation, the dynamic range of the differences between the adjacent pixel values can be significantly less than the dynamic range of the original image, and this range can therefore be represented using fewer bits.
[7.2_s0044] Using DPCM, we have measured compression ratios of 1.5-to-1 on digital images.
[7.2_s0045] DPCM also works on audio, because adjacent samples of an audio waveform are likely to be close in value.
[7.2_s0046] A slightly different approach, called delta encoding, simply encodes a symbol as the difference from the previous one.
[7.2_s0047] Thus, for example, AAABBCDDDD would be represented as A001011000.
[7.2_s0048] Note that delta encoding is likely to work well for encoding images where adjacent pixels are similar.
[7.2_s0049] It is also possible to perform RLE after delta encoding, since we might find long strings of 0s if there are many similar symbols next to each other.
[7.2_s0050] Dictionary-Based Methods  The final lossless compression method we consider is the dictionary-based approach, of which the Lempel-Ziv (LZ) compression algorithm is the best known.
[7.2_s0051] The Unix compress and gzip commands use variants of the LZ algorithm.
[7.2_s0052] The idea of a dictionary-based compression algorithm is to build a dictionary (table) of variable-length strings (think of them as common phrases) that you expect to find in the data and then to replace each of these strings when it appears in the data with the corresponding index to the dictionary.
[7.2_s0053] For example, instead of working with individual characters in text data, you could treat each word as a string and output the index in the dictionary for that word.
[7.2_s0054] To further elaborate on this example, the word compression has the index 4978 in one particular dictionary; it is the 4978th word in /usr/share/dict/words.
[7.2_s0055] To compress a body of text, each time the string “compression” appears, it would be replaced by 4978.
[7.2_s0056] Since this particular dictionary has just over 25,000 words in it, it would take 15 bits to encode the index, meaning that the string “compression” could be represented in 15 bits rather than the 77 bits required by 7-bit ASCII.
[7.2_s0057] This is a compression ratio of 5-to-1!
[7.2_s0058] At another data point, we were able to get a 2-to-1 compression ratio when we applied the compress command to the source code for the protocols described in this book.
[7.2_s0059] Of course, this leaves the question of where the dictionary comes from.
[7.2_s0060] One option is to define a static dictionary, preferably one that is tailored for the data being compressed.
[7.2_s0061] A more general solution, and the one used by LZ compression, is to adaptively define the dictionary based on the contents of the data being compressed.
[7.2_s0062] In this case, however, the dictionary constructed during compression has to be sent along with the data so that the decompression half of the algorithm can do its job.
[7.2_s0063] Exactly how you build an adaptive dictionary has been a subject of extensive research.
[7.2_s0064] 7.2.2 Image Representation and Compression (GIF, JPEG)  Given the ubiquitous use of digital imagery—this use was spawned by the invention of graphical displays, not high-speed networks—the need for standard representation formats and compression algorithms for digital imagery data has become essential.
[7.2_s0065] In response to this need, the ISO defined a digital image format known as JPEG, named after the Joint Photographic Experts Group that designed it.
[7.2_s0066] (The “Joint” in JPEG stands for a joint ISO/ITU effort.)
[7.2_s0067] JPEG is the most widely used format for still images in use today.
[7.2_s0068] At the heart of the definition of the format is a compression algorithm, which we describe below.
[7.2_s0069] Many techniques used in JPEG also appear in MPEG, the set of standards for video compression and transmission created by the Moving Picture Experts Group.
[7.2_s0070] Before delving into the details of JPEG, we observe that there are quite a few steps to get from a digital image to a compressed representation of that image that can be transmitted, decompressed, and displayed correctly by a receiver.
[7.2_s0071] You probably know that digital images are made up of pixels (hence, the megapixels quoted in smartphone camera advertisements).
[7.2_s0072] Each pixel represents one location in the two-dimensional grid that makes up the image, and for color images each pixel has some numerical value representing a color.
[7.2_s0073] There are lots of ways to represent colors, referred to as color spaces; the one most people are familiar with is RGB (red, green, blue).
[7.2_s0074] You can think of color as being a three dimensional quantity—you can make any color out of red, green, and blue light in different amounts.
[7.2_s0075] In a three-dimensional space, there are lots of different, valid ways to describe a given point (consider Cartesian and polar coordinates, for example).
[7.2_s0076] Similarly, there are various ways to describe a color using three quantities, and the most common alternative to RGB is YUV.
[7.2_s0077] The Y is luminance, roughly the overall brightness of the pixel, and U and V contain chrominance, or color information.
[7.2_s0078] Confoundingly, there are a few different variants of the YUV color space as well.
[7.2_s0079] More on this in a moment.
[7.2_s0080] The significance of this discussion is that the encoding and transmission of color images (either still or moving) requires agreement between the two ends on the color space.
[7.2_s0081] Otherwise, of course, you’d end up with different colors being displayed by the receiver than were captured by the sender.
[7.2_s0082] Hence, agreeing on a color space definition (and perhaps a way to communicate which particular space is in use) is part of the definition of any image or video format.
[7.2_s0083] Let’s look at the example of the Graphical Interchange Format (GIF).
[7.2_s0084] GIF uses the RGB color space and starts out with 8 bits to represent each of the three dimensions of color for a total of 24 bits.
[7.2_s0085] Rather than sending those 24 bits per pixel, however, GIF first reduces 24-bit color images to 8-bit color images.
[7.2_s0086] This is done by identifying the colors used in the picture, of which there will typically be considerably fewer than 2\ 24, and then picking the 256 colors that most closely approximate the colors used in the picture.
[7.2_s0087] There might be more than 256 colors, however, so the trick is to try not to distort the color too much by picking 256 colors such that no pixel has its color changed too much.
[7.2_s0088] The 256 colors are stored in a table, which can be indexed with an 8-bit number, and the value for each pixel is replaced by the appropriate index.
[7.2_s0089] Note that this is an example of lossy compression for any picture with more than 256 colors.
[7.2_s0090] GIF then runs an LZ variant over the result, treating common sequences of pixels as the strings that make up the dictionary—a lossless operation.
[7.2_s0091] Using this approach, GIF is sometimes able to achieve compression ratios on the order of 10:1, but only when the image consists of a relatively small number of discrete colors.
[7.2_s0092] Graphical logos, for example, are handled well by GIF.
[7.2_s0093] Images of natural scenes, which often include a more continuous spectrum of colors, cannot be compressed at this ratio using GIF.
[7.2_s0094] It is also not too hard for a human eye to detect the distortion caused by the lossy color reduction of GIF in some cases.
[7.2_s0095] The JPEG format is considerably more well suited to photographic images, as you would hope given the name of the group that created it.
[7.2_s0096] JPEG does not reduce the number of colors like GIF.
[7.2_s0097] Instead, JPEG starts off by transforming the RGB colors (which are what you usually get out of a digital camera) to the YUV space.
[7.2_s0098] The reason for this has to do with the way the eye perceives images.
[7.2_s0099] There are receptors in the eye for brightness, and separate receptors for color.
[7.2_s0100] Because we’re very good at perceiving variations in brightness, it makes sense to spend more bits on transmitting brightness information.
[7.2_s0101] Since the Y component of YUV is, roughly, the brightness of the pixel, we can compress that component separately, and less aggressively, from the other two (chrominance) components.
[7.2_s0102] As noted above, YUV and RGB are alternative ways to describe a point in a 3-dimensional space, and it’s possible to convert from one color space to another using linear equations.
[7.2_s0103] For one YUV space that is commonly used to represent digital images, the equations are:  The exact values of the constants here are not important, as long as the encoder and decoder agree on what they are.
[7.2_s0104] (The decoder will have to apply the inverse transformations to recover the RGB components needed to drive a display.)
[7.2_s0105] The constants are, however, carefully chosen based on the human perception of color.
[7.2_s0106] You can see that Y, the luminance, is a sum of the red, green, and blue components, while U and V are color difference components.
[7.2_s0107] U represents the difference between the luminance and blue, and V the difference between luminance and red.
[7.2_s0108] You may notice that setting R, G, and B to their maximum values (which would be 255 for 8-bit representations) will also produce a value of Y=255 while U and V in this case would be zero.
[7.2_s0109] That is, a fully white pixel is (255,255,255) in RGB space and (255,0,0) in YUV space.
[7.2_s0110] Once the image has been transformed into YUV space, we can now think about compressing each of the three components separately.
[7.2_s0111] We want to be more aggressive in compressing the U and V components, to which human eyes are less sensitive.
[7.2_s0112] One way to compress the U and V components is to subsample them.
[7.2_s0113] The basic idea of subsampling is to take a number of adjacent pixels, calculate the average U or V value for that group of pixels, and transmit that, rather than sending the value for every pixel.
[7.2_s0114] Figure illustrates the point.
[7.2_s0115] The luminance (Y) component is not subsampled, so the Y value of all the pixels will be transmitted, as indicated by the 16 × 16 grid of pixels on the left.
[7.2_s0116] In the case of U and V, we treat each group of four adjacent pixels as a group, calculate the average of the U or V value for that group, and transmit that.
[7.2_s0117] Hence, we end up with an 8 × 8 grid of U and V values to transmit.
[7.2_s0118] Thus, in this example, for every four pixels, we transmit six values (four Y and one each of U and V) rather than the original 12 values (four each for all three components), for a 50% reduction in information.
[7.2_s0119] It’s worth noting that you could be either more or less aggressive in the subsampling, with corresponding increases in compression and decreases in quality.
[7.2_s0120] The subsampling approach shown here, in which chrominance is subsampled by a factor of two in both horizontal and vertical directions (and which goes by the identification 4:2:0), happens to match the most common approach used for both JPEG and MPEG.
[7.2_s0121] Once subsampling is done, we now have three grids of pixels to deal with, and each one is dealt with separately.
[7.2_s0122] JPEG compression of each component takes place in three phases, as illustrated in Figure.
[7.2_s0123] On the compression side, the image is fed through these three phases one 8 × 8 block at a time.
[7.2_s0124] The first phase applies the discrete cosine transform (DCT) to the block.
[7.2_s0125] If you think of the image as a signal in the spatial domain, then DCT transforms this signal into an equivalent signal in the spatial frequency domain.
[7.2_s0126] This is a lossless operation but a necessary precursor to the next, lossy step.
[7.2_s0127] After the DCT, the second phase applies a quantization to the resulting signal and, in so doing, loses the least significant information contained in that signal.
[7.2_s0128] The third phase encodes the final result, but in so doing also adds an element of lossless compression to the lossy compression achieved by the first two phases.
[7.2_s0129] Decompression follows these same three phases, but in reverse order.
[7.2_s0130] DCT Phase  DCT is a transformation closely related to the fast Fourier transform (FFT).
[7.2_s0131] It takes an 8 × 8 matrix of pixel values as input and outputs an 8 × 8 matrix of frequency coefficients.
[7.2_s0132] You can think of the input matrix as a 64-point signal that is defined in two spatial dimensions (x and y); DCT breaks this signal into 64 spatial frequencies.
[7.2_s0133] To get an intuitive feel for spatial frequency, imagine yourself moving across a picture in, say, the x direction.
[7.2_s0134] You would see the value of each pixel varying as some function of x. If this value changes slowly with increasing x, then it has a low spatial frequency; if it changes rapidly, it has a high spatial frequency.
[7.2_s0135] So the low frequencies correspond to the gross features of the picture, while the high frequencies correspond to fine detail.
[7.2_s0136] The idea behind the DCT is to separate the gross features, which are essential to viewing the image, from the fine detail, which is less essential and, in some cases, might be barely perceived by the eye.
[7.2_s0137] DCT, along with its inverse, which recovers the original pixels and during decompression, are defined by the following formulas:  where C(x) = 1/\sqrt{2} when x=0 and 1 when x>0, and pixel(x,y) is the grayscale value of the pixel at position (x,y) in the 8 × 8 block being compressed; N = 8 in this case.
[7.2_s0138] The first frequency coefficient, at location (0,0) in the output matrix, is called the DC coefficient.
[7.2_s0139] Intuitively, we can see that the DC coefficient is a measure of the average value of the 64 input pixels.
[7.2_s0140] The other 63 elements of the output matrix are called the AC coefficients.
[7.2_s0141] They add the higher-spatial-frequency information to this average value.
[7.2_s0142] Thus, as you go from the first frequency coefficient toward the 64th frequency coefficient, you are moving from low-frequency information to high-frequency information, from the broad strokes of the image to finer and finer detail.
[7.2_s0143] These higher-frequency coefficients are increasingly unimportant to the perceived quality of the image.
[7.2_s0144] It is the second phase of JPEG that decides which portion of which coefficients to throw away.
[7.2_s0145] Quantization Phase  The second phase of JPEG is where the compression becomes lossy.
[7.2_s0146] DCT does not itself lose information; it just transforms the image into a form that makes it easier to know what information to remove.
[7.2_s0147] (Although not lossy, per se, there is of course some loss of precision during the DCT phase because of the use of fixed-point arithmetic.)
[7.2_s0148] Quantization is easy to understand—it’s simply a matter of dropping the insignificant bits of the frequency coefficients.
[7.2_s0149] To see how the quantization phase works, imagine that you want to compress some whole numbers less than 100, such as 45, 98, 23, 66, and 7.
[7.2_s0150] If you decided that knowing these numbers truncated to the nearest multiple of 10 is sufficient for your purposes, then you could divide each number by the quantum 10 using integer arithmetic, yielding 4, 9, 2, 6, and 0.
[7.2_s0151] These numbers can each be encoded in 4 bits rather than the 7 bits needed to encode the original numbers.

[7.2_s0158] Encoding Phase  The final phase of JPEG encodes the quantized frequency coefficients in a compact form.
[7.2_s0159] This results in additional compression, but this compression is lossless.
[7.2_s0160] Starting with the DC coefficient in position (0,0), the coefficients are processed in the zigzag sequence shown in Figure.
[7.2_s0161] Along this zigzag, a form of run length encoding is used—RLE is applied to only the 0 coefficients, which is significant because many of the later coefficients are 0.

[7.2_s0163] (The JPEG standard allows the implementer to use an arithmetic coding instead of the Huffman code.)
[7.2_s0164] In addition, because the DC coefficient contains a large percentage of the information about the 8 × 8 block from the source image, and images typically change slowly from block to block, each DC coefficient is encoded as the difference from the previous DC coefficient.
[7.2_s0165] This is the delta encoding approach described in a later section.
[7.2_s0166] JPEG includes a number of variations that control how much compression you achieve versus the fidelity of the image.
[7.2_s0167] This can be done, for example, by using different quantization tables.
[7.2_s0168] These variations, plus the fact that different images have different characteristics, make it impossible to say with any precision the compression ratios that can be achieved with JPEG.
[7.2_s0169] Ratios of 30:1 are common, and higher ratios are certainly possible, but artifacts (noticeable distortion due to compression) become more severe at higher ratios.
[7.2_s0170] 7.2.3 Video Compression (MPEG)
[7.2_s0171] We now turn our attention to the MPEG format, named after the Moving Picture Experts Group that defined it.
[7.2_s0172] To a first approximation, a moving picture (i.e., video) is simply a succession of still images—also called frames or pictures—displayed at some video rate.
[7.2_s0173] Each of these frames can be compressed using the same DCT-based technique used in JPEG.
[7.2_s0174] Stopping at this point would be a mistake, however, because it fails to remove the interframe redundancy present in a video sequence.
[7.2_s0175] For example, two successive frames of video will contain almost identical information if there is not much motion in the scene, so it would be unnecessary to send the same information twice.
[7.2_s0176] Even when there is motion, there may be plenty of redundancy since a moving object may not change from one frame to the next; in some cases, only its position changes.
[7.2_s0177] MPEG takes this interframe redundancy into consideration.
[7.2_s0178] MPEG also defines a mechanism for encoding an audio signal with the video, but we consider only the video aspect of MPEG in this section.
[7.2_s0179] Frame Types  MPEG takes a sequence of video frames as input and compresses them into three types of frames, called I frames (intrapicture), P frames (predicted picture), and B frames (bidirectional predicted picture).
[7.2_s0180] Each frame of input is compressed into one of these three frame types.
[7.2_s0181] I frames can be thought of as reference frames; they are self-contained, depending on neither earlier frames nor later frames.
[7.2_s0182] To a first approximation, an I frame is simply the JPEG compressed version of the corresponding frame in the video source.
[7.2_s0183] P and B frames are not self-contained; they specify relative differences from some reference frame.
[7.2_s0184] More specifically, a P frame specifies the differences from the previous I frame, while a B frame gives an interpolation between the previous and subsequent I or P frames.
[7.2_s0185] Figure illustrates a sequence of seven video frames that, after being compressed by MPEG, result in a sequence of I, P, and B frames.
[7.2_s0186] The two I frames stand alone; each can be decompressed at the receiver independently of any other frames.
[7.2_s0187] The P frame depends on the preceding I frame; it can be decompressed at the receiver only if the preceding I frame also arrives.
[7.2_s0188] Each of the B frames depends on both the preceding I or P frame and the subsequent I or P frame.
[7.2_s0189] Both of these reference frames must arrive at the receiver before MPEG can decompress the B frame to reproduce the original video frame.
[7.2_s0190] Note that, because each B frame depends on a later frame in the sequence, the compressed frames are not transmitted in sequential order.
[7.2_s0191] Instead, the sequence I B B P B B I shown in Figure is transmitted as I P B B I B B. Also, MPEG does not define the ratio of I frames to P and B frames; this ratio may vary depending on the required compression and picture quality.
[7.2_s0192] For example, it is permissible to transmit only I frames.
[7.2_s0193] This would be similar to using JPEG to compress the video.
[7.2_s0194] In contrast to the preceding discussion of JPEG, the following focuses on the decoding of an MPEG stream.
[7.2_s0195] It is a little easier to describe, and it is the operation that is more often implemented in networking systems today, since MPEG coding is so expensive that it is frequently done offline (i.e., not in real time).
[7.2_s0196] For example, in a video-on-demand system, the video would be encoded and stored on disk ahead of time.
[7.2_s0197] When a viewer wanted to watch the video, the MPEG stream would then be transmitted to the viewer’s machine, which would decode and display the stream in real time.
[7.2_s0198] Let’s look more closely at the three frame types.
[7.2_s0199] As mentioned above, I frames are approximately equal to the JPEG compressed version of the source frame.
[7.2_s0200] The main difference is that MPEG works in units of 16 × 16 macroblocks.
[7.2_s0201] For a color video represented in YUV, the U and V components in each macroblock are subsampled into an 8 × 8 block, as we discussed above in the context of JPEG.
[7.2_s0202] Each 2 × 2 subblock in the macroblock is given by one U value and one V value—the average of the four pixel values.
[7.2_s0203] The subblock still has four Y values.
[7.2_s0204] The relationship between a frame and the corresponding macroblocks is given in Figure.
[7.2_s0205] The P and B frames are also processed in units of macroblocks.
[7.2_s0206] Intuitively, we can see that the information they carry for each macroblock captures the motion in the video; that is, it shows in what direction and how far the macroblock moved relative to the reference frame(s).
[7.2_s0207] The following describes how a B frame is used to reconstruct a frame during decompression; P frames are handled in a similar manner, except that they depend on only one reference frame instead of two.
[7.2_s0208] Before getting to the details of how a B frame is decompressed, we first note that each macroblock in a B frame is not necessarily defined relative to both an earlier and a later frame, as suggested above, but may instead simply be specified relative to just one or the other.
[7.2_s0209] In fact, a given macroblock in a B frame can use the same intracoding as is used in an I frame.
[7.2_s0210] This flexibility exists because if the motion picture is changing too rapidly then it sometimes makes sense to give the intrapicture encoding rather than a forward- or backward-predicted encoding.
[7.2_s0211] Thus, each macroblock in a B frame includes a type field that indicates which encoding is used for that macroblock.
[7.2_s0212] In the following discussion, however, we consider only the general case in which the macroblock uses bidirectional predictive encoding.
[7.2_s0213] In such a case, each macroblock in a B frame is represented with a 4-tuple: (1) a coordinate for the macroblock in the frame, (2) a motion vector relative to the previous reference frame, (3) a motion vector relative to the subsequent reference frame, and (4) a delta (\delta) for each pixel in the macroblock (i.e., how much each pixel has changed relative to the two reference pixels).
[7.2_s0214] For each pixel in the macroblock, the first task is to find the corresponding reference pixel in the past and future reference frames.
[7.2_s0215] This is done using the two motion vectors associated with the macroblock.
[7.2_s0216] Then, the delta for the pixel is added to the average of these two reference pixels.
[7.2_s0217] Stated more precisely, if we let F\ p and F\ f denote the past and future reference frames, respectively, and the past/future motion vectors are given by (x\ p, y\ p) and (x\ f, y\ f), then the pixel at coordinate (x,y) in the current frame (denoted F\ c) is computed as  where \delta is the delta for the pixel as specified in the B frame.
[7.2_s0218] These deltas are encoded in the same way as pixels in I frames; that is, they are run through DCT and then quantized.
[7.2_s0219] Since the deltas are typically small, most of the DCT coefficients are 0 after quantization; hence, they can be effectively compressed.
[7.2_s0220] It should be fairly clear from the preceding discussion how encoding would be performed, with one exception.
[7.2_s0221] When generating a B or P frame during compression, MPEG must decide where to place the macroblocks.
[7.2_s0222] Recall that each macroblock in a P frame, for example, is defined relative to a macroblock in an I frame, but that the macroblock in the P frame need not be in the same part of the frame as the corresponding macroblock in the I frame—the difference in position is given by the motion vector.
[7.2_s0223] You would like to pick a motion vector that makes the macroblock in the P frame as similar as possible to the corresponding macroblock in the I frame, so that the deltas for that macroblock can be as small as possible.
[7.2_s0224] This means that you need to figure out where objects in the picture moved from one frame to the next.
[7.2_s0225] This is the problem of motion estimation, and several techniques (heuristics) for solving this problem are known.
[7.2_s0226] (We discuss papers that consider this problem at the end of this chapter.)
[7.2_s0227] The difficulty of this problem is one of the reasons why MPEG encoding takes longer than decoding on equivalent hardware.
[7.2_s0228] MPEG does not specify any particular technique; it only defines the format for encoding this information in B and P frames and the algorithm for reconstructing the pixel during decompression, as given above.
[7.2_s0229] Effectiveness and Performance  MPEG typically achieves a compression ratio of 90:1, although ratios as high as 150:1 are not unheard of.
[7.2_s0230] In terms of the individual frame types, we can expect a compression ratio of approximately 30:1 for the I frames (this is consistent with the ratios achieved using JPEG when 24-bit color is first reduced to 8-bit color), while P and B frame compression ratios are typically three to five times smaller than the rates for the I frame.
[7.2_s0231] Without first reducing the 24 bits of color to 8 bits, the achievable compression with MPEG is typically between 30:1 and 50:1.
[7.2_s0232] MPEG involves an expensive computation.
[7.2_s0233] On the compression side, it is typically done offline, which is not a problem for preparing movies for a video-on-demand service.
[7.2_s0234] Video can be compressed in real time using hardware today, but software implementations are quickly closing the gap.
[7.2_s0235] On the decompression side, low-cost MPEG video boards are available, but they do little more than YUV color lookup, which fortunately is the most expensive step.
[7.2_s0236] Most of the actual MPEG decoding is done in software.
[7.2_s0237] In recent years, processors have become fast enough to keep pace with 30-frames-per-second video rates when decoding MPEG streams purely in software—modern processors can even decode MPEG streams of high definition video (HDTV).
[7.2_s0238] Video Encoding Standards
[7.2_s0239] We conclude by noting that MPEG is an evolving standard of significant complexity.
[7.2_s0240] This complexity comes from a desire to give the encoding algorithm every possible degree of freedom in how it encodes a given video stream, resulting in different video transmission rates.
[7.2_s0241] It also comes from the evolution of the standard over time, with the Moving Picture Experts Group working hard to retain backwards compatibility (e.g., MPEG-1, MPEG-2, MPEG-4).
[7.2_s0242] What we describe in this book is the essential ideas underlying MPEG-based compression, but certainly not all the intricacies involved in an international standard.
[7.2_s0243] What’s more, MPEG is not the only standard available for encoding video.
[7.2_s0244] For example, the ITU-T has also defined the H series for encoding real-time multimedia data.
[7.2_s0245] Generally, the H series includes standards for video, audio, control, and multiplexing (e.g., mixing audio, video, and data onto a single bit stream).
[7.2_s0246] Within the series, H.261 and H.263 were the first- and second-generation video encoding standards.
[7.2_s0247] In principle, both H.261 and H.263 look a lot like MPEG: They use DCT, quantization, and interframe compression.
[7.2_s0248] The differences between H.261/H.263 and MPEG are in the details.
[7.2_s0249] Today, a partnership between the ITU-T and the MPEG group has lead to the joint H.264/MPEG-4 standard, which is used for both Blu-ray Discs and by many popular streaming sources (e.g., YouTube, Vimeo).
[7.2_s0250] 7.2.4 Transmitting MPEG over a Network  As we’ve noted, MPEG and JPEG are not just compression standards but also definitions of the format of video and images, respectively.
[7.2_s0251] Focusing on MPEG, the first thing to keep in mind is that it defines the format of a video stream; it does not specify how this stream is broken into network packets.
[7.2_s0252] Thus, MPEG can be used for videos stored on disk, as well as videos transmitted over a stream-oriented network connection, like that provided by TCP.
[7.2_s0253] What we describe below is called the main profile of an MPEG video stream that is being sent over a network.
[7.2_s0254] You can think of an MPEG profile as being analogous to a “version,” except the profile is not explicitly specified in an MPEG header; the receiver has to deduce the profile from the combination of header fields it sees.
[7.2_s0255] A main profile MPEG stream has a nested structure, as illustrated in Figure.
[7.2_s0256] (Keep in mind that this figure hides a lot of messy details.)
[7.2_s0257] At the outermost level, the video contains a sequence of groups of pictures (GOP) separated by a SeqHdr.
[7.2_s0258] The sequence is terminated by a SeqEndCode (0xb7).
[7.2_s0259] The SeqHdr that precedes every GOP specifies—among other things—the size of each picture (frame) in the GOP (measured in both pixels and macroblocks), the interpicture period (measured in μs), and two quantization matrices for the macroblocks within this GOP: one for intracoded macroblocks (I blocks) and one for intercoded macroblocks (B and P blocks).
[7.2_s0260] Since this information is given for each GOP—rather than once for the entire video stream, as you might expect—it is possible to change the quantization table and frame rate at GOP boundaries throughout the video.
[7.2_s0261] This makes it possible to adapt the video stream over time, as we discuss below.
[7.2_s0262] Each GOP is given by a GOPHdr, followed by the set of pictures that make up the GOP.
[7.2_s0263] The GOPHdr specifies the number of pictures in the GOP, as well as synchronization information for the GOP (i.e., when the GOP should play, relative to the beginning of the video).
[7.2_s0264] Each picture, in turn, is given by a PictureHdr and a set of slices that make up the picture.
[7.2_s0265] (A slice is a region of the picture, such as one horizontal line.)
[7.2_s0266] The PictureHdr identifies the type of the picture (I, B, or P) and defines a picture-specific quantization table.
[7.2_s0267] The SliceHdr gives the vertical position of the slice, plus another opportunity to change the quantization table—this time by a constant scaling factor rather than by giving a whole new table.
[7.2_s0268] Next, the SliceHdr is followed by a sequence of macroblocks.
[7.2_s0269] Finally, each macroblock includes a header that specifies the block address within the picture, along with data for the six blocks within the macroblock: one for the U component, one for the V component, and four for the Y component.
[7.2_s0270] (Recall that the Y component is 16 × 16, while the U and V components are 8 × 8.)
[7.2_s0271] It should be clear that one of the powers of the MPEG format is that it gives the encoder an opportunity to change the encoding over time.
[7.2_s0272] It can change the frame rate, the resolution, the mix of frame types that define a GOP, the quantization table, and the encoding used for individual macroblocks.
[7.2_s0273] As a consequence, it is possible to adapt the rate at which a video is transmitted over a network by trading picture quality for network bandwidth.
[7.2_s0274] Exactly how a network protocol might exploit this adaptability is currently a subject of research (see sidebar).
[7.2_s0275] Another interesting aspect of sending an MPEG stream over the network is exactly how the stream is broken into packets.
[7.2_s0276] If sent over a TCP connection, packetization is not an issue; TCP decides when it has enough bytes to send the next IP datagram.
[7.2_s0277] When using video interactively, however, it is rare to transmit it over TCP, since TCP has several features that are ill suited to highly latency-sensitive applications (such as abrupt rate changes after a packet loss and retransmission of lost packets).
[7.2_s0278] If we are transmitting video using UDP, say, then it makes sense to break the stream at carefully selected points, such as at macroblock boundaries.
[7.2_s0279] This is because we would like to confine the effects of a lost packet to a single macroblock, rather than damaging several macroblocks with a single loss.
[7.2_s0280] This is an example of Application Level Framing, which was discussed in an earlier chapter.
[7.2_s0281] Packetizing the stream is only the first problem in sending MPEG-compressed video over a network.
[7.2_s0282] The next complication is dealing with packet loss.
[7.2_s0283] On the one hand, if a B frame is dropped by the network, then it is possible to simply replay the previous frame without seriously compromising the video; 1 frame out of 30 is no big deal.
[7.2_s0284] On the other hand, a lost I frame has serious consequences—none of the subsequent B and P frames can be processed without it.
[7.2_s0285] Thus, losing an I frame would result in losing multiple frames of the video.
[7.2_s0286] While you could retransmit the missing I frame, the resulting delay would probably not be acceptable in a real-time videoconference.
[7.2_s0287] One solution to this problem would be to use the Differentiated Services techniques described in the previous chapter to mark the packets containing I frames with a lower drop probability than other packets.
[7.2_s0288] One final observation is that how you choose to encode video depends on more than just the available network bandwidth.
[7.2_s0289] It also depends on the application’s latency constraints.
[7.2_s0290] Once again, an interactive application like videoconferencing needs small latencies.
[7.2_s0291] The critical factor is the combination of I, P, and B frames in the GOP.
[7.2_s0292] Consider the following GOP:
[7.2_s0293] The problem this GOP causes a videoconferencing application is that the sender has to delay the transmission of the four B frames until the P or I that follows them is available.
[7.2_s0294] This is because each B frame depends on the subsequent P or I frame.
[7.2_s0295] If the video is playing at 15 frames per second (i.e., one frame every 67 ms), this means the first B frame is delayed 4 × 67 ms, which is more than a quarter of a second.
[7.2_s0296] This delay is in addition to any propagation delay imposed by the network.
[7.2_s0297] A quarter of a second is far greater than the 100-ms threshold that humans are able to perceive.
[7.2_s0298] It is for this reason that many videoconference applications encode video using JPEG, which is often called motion-JPEG.
[7.2_s0299] (Motion-JPEG also addresses the problem of dropping a reference frame since all frames are able to stand alone.)
[7.2_s0300] Notice, however, that an interframe encoding that depends upon only prior frames rather than later frames is not a problem.
[7.2_s0301] Thus, a GOP of  would work just fine for interactive videoconferencing.
[7.2_s0302] Adaptive Streaming
[7.2_s0303] Because encoding schemes like MPEG allow for a trade-off between the bandwidth consumed and the quality of the image, there is an opportunity to adapt a video stream to match the available network bandwidth.
[7.2_s0304] This is effectively what video streaming services like Netflix do today.
[7.2_s0305] For starters, let’s assume that we have some way to measure the amount of free capacity and level of congestion along a path, for example, by observing the rate at which packets are successfully arriving at the destination.
[7.2_s0306] As the available bandwidth fluctuates, we can feed that information back to the codec so that it adjusts its coding parameters to back off during congestion and to send more aggressively (with a higher picture quality) when the network is idle.
[7.2_s0307] This is analogous to the behavior of TCP, except in the video case we are actually modifying the total amount of data sent rather than how long we take to send a fixed amount of data, since we don’t want to introduce delay into a video application.
[7.2_s0308] In the case of video-on-demand services like Netflix, we don’t adapt the encoding on the fly, but instead we encode a handful of video quality levels ahead of time, and save them to files named accordingly.
[7.2_s0309] The receiver simply changes the file name it requests to match the quality its measurements indicate the network will be able to deliver.
[7.2_s0310] The receiver watches its playback queue, and asks for a higher quality encoding when the queue becomes too full and a lower quality encoding when the queue becomes too empty.
[7.2_s0311] How does this approach know where in the movie to jump to should the requested quality change?
[7.2_s0312] In effect, the receiver never asks the sender to stream the whole movie, but instead it requests a sequence of short movie segments, typically a few seconds long (and always on GOP boundary).
[7.2_s0313] Each segment is an opportunity to change the quality level to match what the network is able to deliver.
[7.2_s0314] (It turns out that requesting movie chunks also makes it easier to implement trick play, jumping around from one place to another in the movie.)
[7.2_s0315] In other words, a movie is typically stored as a set of N × M chunks (files): N quality levels for each of M segments.
[7.2_s0316] There’s one last detail.
[7.2_s0317] Since the receiver is effectively requesting a sequence of discrete video chunks by name, the most common approach for issuing these requests is to use HTTP.
[7.2_s0318] Each chuck is a separate HTTP GET request with the URL identifying the specific chunk the receiver wants next.
[7.2_s0319] When you start downloading a movie, your video player first downloads a manifest file that contains nothing more than the URLs for the N × M chunks in the movie, and then it issues a sequence of HTTP requests using the appropriate URL for the situation.
[7.2_s0320] This general approach is called HTTP adaptive streaming, although it has been standardized in slightly different ways by various organizations, most notably MPEG’s DASH (Dynamic Adaptive Streaming over HTTP) and Apple’s HLS (HTTP Live Streaming).
[7.2_s0321] 7.2.5 Audio Compression (MP3)  Not only does MPEG define how video is compressed, but it also defines a standard for compressing audio.
[7.2_s0322] This standard can be used to compress the audio portion of a movie (in which case the MPEG standard defines how the compressed audio is interleaved with the compressed video in a single MPEG stream) or it can be used to compress stand-alone audio (for example, an audio CD).
[7.2_s0323] The MPEG audio compression standard is just one of many for audio compression, but the pivotal role it played means that MP3 (which stands for MPEG Layer III—see below) has become almost synonymous with audio compression.
[7.2_s0324] To understand audio compression, we need to begin with the data.
[7.2_s0325] CD-quality audio, which is the de facto digital representation for high-quality audio, is sampled at a rate of 44.1 KHz (i.e., a sample is collected approximately once every 23 μs).
[7.2_s0326] Each sample is 16 bits, which means that a stereo (2-channel) audio stream results in a bit rate of  By comparison, traditional telephone-quality voice is sampled at a rate of 8 KHz, with 8-bit samples, resulting in a bit rate of 64 kbps.
[7.2_s0327] Clearly, some amount of compression is going to be required to transmit CD-quality audio over a network of limited bandwidth.
[7.2_s0328] (Consider the fact that MP3 audio streaming became popular in an era when 1.5Mbps home Internet connections were a novelty).
[7.2_s0329] To make matters worse, synchronization and error correction overheads inflated the number of bits stored on a CD by a factor of three, so if you just read the data from the CD and sent it over the network, you would need 4.32 Mbps.
[7.2_s0330] Just like video, there is lots of redundancy in audio, and compression takes advantage of this.
[7.2_s0331] The MPEG standards define three levels of compression, as enumerated in Table.
[7.2_s0332] Of these, Layer III, which is more widely known as MP3, was for many years the most commonly used.
[7.2_s0333] In recent years, higher bandwidth codecs have proliferated as streaming audio has become the dominant way many people consume music.
[7.2_s0334] To achieve these compression ratios, MP3 uses techniques that are similar to those used by MPEG to compress video.
[7.2_s0335] First, it splits the audio stream into some number of frequency subbands, loosely analogous to the way MPEG processes the Y, U, and V components of a video stream separately.
[7.2_s0336] Second, each subband is broken into a sequence of blocks, which are similar to MPEG’s macroblocks except they can vary in length from 64 to 1024 samples.
[7.2_s0337] (The encoding algorithm can vary the block size depending on certain distortion effects that are beyond our discussion.)
[7.2_s0338] Finally, each block is transformed using a modified DCT algorithm, quantized, and Huffman encoded, just as for MPEG video.
[7.2_s0339] The trick to MP3 is how many subbands it elects to use and how many bits it allocates to each subband, keeping in mind that it is trying to produce the highest-quality audio possible for the target bit rate.
[7.2_s0340] Exactly how this allocation is made is governed by psychoacoustic models that are beyond the scope of this book, but to illustrate the idea consider that it makes sense to allocate more bits to low-frequency subbands when compressing a male voice and more bits to high-frequency subbands when compressing a female voice.
[7.2_s0341] Operationally, MP3 dynamically changes the quantization tables used for each subband to achieve the desired effect.
[7.2_s0342] Once compressed, the subbands are packaged into fixed-size frames, and a header is attached.
[7.2_s0343] This header includes synchronization information, as well as the bit allocation information needed by the decoder to determine how many bits are used to encode each subband.
[7.2_s0344] As mentioned above, these audio frames can then be interleaved with video frames to form a complete MPEG stream.
[7.2_s0345] One interesting side note is that, while it might work to drop B frames in the network should congestion occur, experience teaches us that it is not a good idea to drop audio frames since users are better able to tolerate bad video than bad audio.
=== SECTION 8.3: Network Security > Key Predistribution ===
[8.3_s0000] To use ciphers and authenticators, the communicating participants need to know what keys to use.
[8.3_s0001] In the case of a secret-key cipher, how does a pair of participants obtain the key they share?
[8.3_s0002] In the case of a public-key cipher, how do participants know what public key belongs to a certain participant?
[8.3_s0003] The answer differs depending on whether the keys are short-lived session keys or longer-lived predistributed keys.
[8.3_s0004] A session key is a key used to secure a single, relatively short episode of communication: a session.
[8.3_s0005] Each distinct session between a pair of participants uses a new session key, which is always a secret key for speed.
[8.3_s0006] The participants determine what session key to use by means of a protocol—a session key establishment protocol.
[8.3_s0007] A session key establishment protocol needs its own security (so that, for example, an adversary cannot learn the new session key); that security is based on the longer-lived predistributed keys.
[8.3_s0008] There are two primary motivations for this division of labor between session keys and predistributed keys:  -  Limiting the amount of time a key is used results in less time for computationally intensive attacks, less ciphertext for cryptanalysis, and less information exposed should the key be broken.  -  Public key ciphers are generally superior for authentication and session key establishment but too slow to use for encrypting entire messages for confidentiality.
[8.3_s0009] This section explains how predistributed keys are distributed, and the next section will explain how session keys are then established.
[8.3_s0010] We henceforth use “Alice” and “Bob” to designate participants, as is common in the cryptography literature.
[8.3_s0011] Bear in mind that although we tend to refer to participants in anthropomorphic terms, we are more frequently concerned with the communication between software or hardware entities such as clients and servers that often have no direct relationship with any particular person.
[8.3_s0012] 8.3.1 Predistribution of Public Keys  The algorithms to generate a matched pair of public and private keys are publicly known, and software that does it is widely available.
[8.3_s0013] So, if Alice wanted to use a public-key cipher, she could generate her own pair of public and private keys, keep the private key hidden, and publicize the public key.
[8.3_s0014] But, how can she publicize her public key—assert that it belongs to her—in such a way that other participants can be sure it really belongs to her?
[8.3_s0015] Not via email or Web, because an adversary could forge an equally plausible claim that key x belongs to Alice when x really belongs to the adversary.
[8.3_s0016] A complete scheme for certifying bindings between public keys and identities—what key belongs to whom—is called a Public Key Infrastructure (PKI).
[8.3_s0017] A PKI starts with the ability to verify identities and bind them to keys out of band.
[8.3_s0018] By “out of band,” we mean something outside the network and the computers that comprise it, such as in the following If Alice and Bob are individuals who know each other, then they could get together in the same room and Alice could give her public key to Bob directly, perhaps on a business card.
[8.3_s0019] If Bob is an organization, Alice the individual could present conventional identification, perhaps involving a photograph or fingerprints.
[8.3_s0020] If Alice and Bob are computers owned by the same company, then a system administrator could configure Bob with Alice’s public key.
[8.3_s0021] Establishing keys out of band doesn’t sound like it would scale well, but it suffices to bootstrap a PKI.
[8.3_s0022] Bob’s knowledge that Alice’s key is x can be widely, scalably disseminated using a combination of digital signatures and a concept of trust.
[8.3_s0023] For example, suppose that you have received Bob’s public key out of band and that you know enough about Bob to trust him on matters of keys and identities.
[8.3_s0024] Then Bob could send you a message asserting that Alice’s key is x and—since you already know Bob’s public key—you could authenticate the message as having come from Bob.
[8.3_s0025] (Remember that to digitally sign the statement Bob would append a cryptographic hash of it that has been encrypted using his private key.)
[8.3_s0026] Since you trust Bob to tell the truth, you would now know that Alice’s key is x, even though you had never met her or exchanged a single message with her.
[8.3_s0027] Using digital signatures, Bob wouldn’t even have to send you a message; he could simply create and publish a digitally signed statement that Alice’s key is x.
[8.3_s0028] Such a digitally signed statement of a public key binding is called a public key certificate, or simply a certificate.
[8.3_s0029] Bob could send Alice a copy of the certificate, or post it on a website.
[8.3_s0030] If and when someone needs to verify Alice’s public key, they could do so by getting a copy of the certificate, perhaps directly from Alice—as long as they trust Bob and know his public key.
[8.3_s0031] You can see how starting from a very small number of keys (in this case, just Bob’s) you could build up a large set of trusted keys over time.
[8.3_s0032] Bob in this case is playing the role often referred to as a certification authority (CA), and much of today’s Internet security depends on CAs.
[8.3_s0033] VeriSign is one well-known commercial CA.
[8.3_s0034] We return to this topic below.
[8.3_s0035] One of the major standards for certificates is known as X.509.
[8.3_s0036] This standard leaves a lot of details open, but specifies a basic structure.
[8.3_s0037] A certificate clearly must include:  -  The identity of the entity being certified  -  The public key of the entity being certified  -  The identity of the signer  -  The digital signature  -  A digital signature algorithm identifier (which cryptographic hash and which cipher)
[8.3_s0038] An optional component is an expiration time for the certificate.
[8.3_s0039] We will see a particular use of this feature below.
[8.3_s0040] Since a certificate creates a binding between an identity and a public key, we should look more closely at what we mean by “identity.”
[8.3_s0041] For example, a certificate that says, “This public key belongs to John Smith,” may not be terribly useful if you can’t tell which of the thousands of John Smiths is being identified.
[8.3_s0042] Thus, certificates must use a well-defined name space for the identities being certified; for example, certificates are often issued for email addresses and DNS domains.
[8.3_s0043] There are different ways a PKI could formalize the notion of trust.
[8.3_s0044] We discuss the two main approaches.
[8.3_s0045] Certification Authorities  In this model of trust, trust is binary; you either trust someone completely or not at all.
[8.3_s0046] Together with certificates, this allows the building of chains of trust.
[8.3_s0047] If X certifies that a certain public key belongs to Y, and then Y goes on to certify that another public key belongs to Z, then there exists a chain of certificates from X to Z, even though X and Z may have never met.
[8.3_s0048] If you know X’s key—and you trust X and Y—then you can believe the certificate that gives Z’s key.
[8.3_s0049] In other words, all you need is a chain of certificates, all signed by entities you trust, as long as it leads back to an entity whose key you already know.
[8.3_s0050] A certification authority or certificate authority (CA) is an entity claimed (by someone) to be trustworthy for verifying identities and issuing public key certificates.
[8.3_s0051] There are commercial CAs, governmental CAs, and even free CAs.
[8.3_s0052] To use a CA, you must know its own key.
[8.3_s0053] You can learn that CA’s key, however, if you can obtain a chain of CA-signed certificates that starts with a CA whose key you already know.
[8.3_s0054] Then you can believe any certificate signed by that new CA.
[8.3_s0055] A common way to build such chains is to arrange them in a tree-structured hierarchy, as shown in Figure.
[8.3_s0056] If everyone has the public key of the root CA, then any participant can provide a chain of certificates to another participant and know that it will be sufficient to build a chain of trust for that participant.
[8.3_s0057] There are some significant issues with building chains of trust.
[8.3_s0058] Most importantly, even if you are certain that you have the public key of the root CA, you need to be sure that every CA from the root on down is doing its job properly.
[8.3_s0059] If just one CA in the chain is willing to issue certificates to entities without verifying their identities, then what looks like a valid chain of certificates becomes meaningless.
[8.3_s0060] For example, a root CA might issue a certificate to a second-tier CA and thoroughly verify that the name on the certificate matches the business name of the CA, but that second-tier CA might be willing to sell certificates to anyone who asks, without verifying their identity.
[8.3_s0061] This problem gets worse the longer the chain of trust.
[8.3_s0062] X.509 certificates provide the option of restricting the set of entities that the subject of a certificate is, in turn, trusted to certify.
[8.3_s0063] There can be more than one root to a certification tree, and this is common in securing Web transactions today, for example.
[8.3_s0064] Web browsers such as Firefox and Internet Explorer come pre-equipped with certificates for a set of CAs; in effect, the browser’s producer has decided these CAs and their keys can be trusted.
[8.3_s0065] A user can also add CAs to those that their browser recognizes as trusted.
[8.3_s0066] These certificates are accepted by Secure Socket Layer (SSL)/Transport Layer Security (TLS), the protocol most often used to secure Web transactions, which we discuss in a later section.
[8.3_s0067] (If you are curious, you can poke around in the preferences settings for your browser and find the “view certificates” option to see how many CAs your browser is configured to trust.)
[8.3_s0068] Web of Trust  An alternative model of trust is the web of trust exemplified by Pretty Good Privacy (PGP), which is further discussed in a later section.
[8.3_s0069] PGP is a security system for email, so email addresses are the identities to which keys are bound and by which certificates are signed.
[8.3_s0070] In keeping with PGP’s roots as protection against government intrusion, there are no CAs.
[8.3_s0071] Instead, every individual decides whom they trust and how much they trust them—in this model, trust is a matter of degree.
[8.3_s0072] In addition, a public key certificate can include a confidence level indicating how confident the signer is of the key binding claimed in the certificate, so a given user may have to have several certificates attesting to the same key binding before he is willing to trust it.
[8.3_s0073] For example, suppose you have a certificate for Bob provided by Alice; you can assign a moderate level of trust to that certificate.
[8.3_s0074] However, if you have additional certificates for Bob that were provided by C and D, each of whom is also moderately trustworthy, that might considerably increase your level of confidence that the public key you have for Bob is valid.
[8.3_s0075] In short, PGP recognizes that the problem of establishing trust is quite a personal matter and gives users the raw material to make their own decisions, rather than assuming that they are all willing to trust in a single hierarchical structure of CAs.
[8.3_s0076] To quote Phil Zimmerman, the developer of PGP, “PGP is for people who prefer to pack their own parachutes.”
[8.3_s0077] PGP has become quite popular in the networking community, and PGP key-signing parties are a regular feature of various networking events, such as IETF meetings.
[8.3_s0078] At these gatherings, an individual can  -  Collect public keys from others whose identity he knows.
[8.3_s0079] -  Provide his public key to others.
[8.3_s0080] -  Get his public key signed by others, thus collecting certificates that will be persuasive to an increasingly large set of people.
[8.3_s0081] -  Sign the public key of other individuals, thus helping them build up their set of certificates that they can use to distribute their public keys.
[8.3_s0082] -  Collect certificates from other individuals whom he trusts enough to sign keys.
[8.3_s0083] Thus, over time, a user will collect a set of certificates with varying degrees of trust.
[8.3_s0084] Certificate Revocation  One issue that arises with certificates is how to revoke, or undo, a certificate.
[8.3_s0085] Why is this important?
[8.3_s0086] Suppose that you suspect that someone has discovered your private key.
[8.3_s0087] There may be any number of certificates in the universe that assert that you are the owner of the public key corresponding to that private key.
[8.3_s0088] The person who discovered your private key thus has everything he needs to impersonate you: valid certificates and your private key.
[8.3_s0089] To solve this problem, it would be nice to be able to revoke the certificates that bind your old, compromised key to your identity, so that the impersonator will no longer be able to persuade other people that he is you.
[8.3_s0090] The basic solution to the problem is simple enough.
[8.3_s0091] Each CA can issue a certificate revocation list (CRL), which is a digitally signed list of certificates that have been revoked.
[8.3_s0092] The CRL is periodically updated and made publicly available.
[8.3_s0093] Because it is digitally signed, it can just be posted on a website.
[8.3_s0094] Now, when Alice receives a certificate for Bob that she wants to verify, she will first consult the latest CRL issued by the CA.
[8.3_s0095] As long as the certificate has not been revoked, it is valid.
[8.3_s0096] Note that, if all certificates have unlimited life spans, the CRL would always be getting longer, since you could never take a certificate off the CRL for fear that some copy of the revoked certificate might be used.
[8.3_s0097] For this reason, it is common to attach an expiration date to a certificate when it is issued.
[8.3_s0098] Thus, we can limit the length of time that a revoked certificate needs to stay on a CRL.
[8.3_s0099] As soon as its original expiration date is passed, it can be removed from the CRL.
[8.3_s0100] 8.3.2 Predistribution of Secret Keys  If Alice wants to use a secret-key cipher to communicate with Bob, she can’t just pick a key and send it to him because, without already having a key, they can’t encrypt this key to keep it confidential and they can’t authenticate each other.
[8.3_s0101] As with public keys, some predistribution scheme is needed.
[8.3_s0102] Predistribution is harder for secret keys than for public keys for two obvious reasons:  -  While only one public key per entity is sufficient for authentication and confidentiality, there must be a secret key for each pair of entities who wish to communicate.
[8.3_s0103] If there are N entities, that means N(N-1)/2 keys.  -  Unlike public keys, secret keys must be kept secret.
[8.3_s0104] In summary, there are a lot more keys to distribute, and you can’t use certificates that everyone can read.
[8.3_s0105] The most common solution is to use a Key Distribution Center (KDC).
[8.3_s0106] A KDC is a trusted entity that shares a secret key with each other entity.
[8.3_s0107] This brings the number of keys down to a more manageable N-1, few enough to establish out of band for some applications.
[8.3_s0108] When Alice wishes to communicate with Bob, that communication does not travel via the KDC.
[8.3_s0109] Rather, the KDC participates in a protocol that authenticates Alice and Bob—using the keys that the KDC already shares with each of them—and generates a new session key for them to use.
[8.3_s0110] Then Alice and Bob communicate directly using their session key.
[8.3_s0111] Kerberos is a widely used system based on this approach.
[8.3_s0112] We describe Kerberos (which also provides authentication) in the next section.
[8.3_s0113] The following subsection describes a powerful alternative.
[8.3_s0114] 8.3.3 Diffie-Hellman Key Exchange  Another approach to establishing a shared secret key is to use the Diffie-Hellman key exchange protocol, which works without using any predistributed keys.
[8.3_s0115] The messages exchanged between Alice and Bob can be read by anyone able to eavesdrop, and yet the eavesdropper won’t know the secret key that Alice and Bob end up with.
[8.3_s0116] Diffie-Hellman doesn’t authenticate the participants.
[8.3_s0117] Since it is rarely useful to communicate securely without being sure whom you’re communicating with, Diffie-Hellman is usually augmented in some way to provide authentication.
[8.3_s0118] One of the main uses of Diffie-Hellman is in the Internet Key Exchange (IKE) protocol, a central part of the IP Security (IPsec) architecture.

=== SECTION 8.4: Network Security > Authentication Protocols ===
[8.4_s0000] So far we described how to encrypt messages, build authenticators, predistribute the necessary keys.
[8.4_s0001] It might seem as if all we have to do to make a protocol secure is append an authenticator to every message and, if we want confidentiality, encrypt the message.
[8.4_s0002] There are two main reasons why it’s not that simple.
[8.4_s0003] First, there is the problem of a replay attack: an adversary retransmitting a copy of a message that was previously sent.
[8.4_s0004] If the message was an order you had placed on a website, for example, then the replayed message would appear to the website as though you had ordered more of the same.
[8.4_s0005] Even though it wasn’t the original incarnation of the message, its authenticator would still be valid; after all, the message was created by you, and it wasn’t modified.
[8.4_s0006] Clearly, we need a solution that ensures originality.
[8.4_s0007] In a variation of this attack called a suppress-replay attack, an adversary might merely delay your message (by intercepting and later replaying it), so that it is received at a time when it is no longer appropriate.
[8.4_s0008] For example, an adversary could delay your order to buy stock from an auspicious time to a time when you would not have wanted to buy.
[8.4_s0009] Although this message would in a sense be the original, it wouldn’t be timely.
[8.4_s0010] So we also need to ensure timeliness.
[8.4_s0011] Originality and timeliness may be considered aspects of integrity.
[8.4_s0012] Ensuring them will in most cases require a nontrivial, back-and-forth protocol.
[8.4_s0013] The second problem we have not yet solved is how to establish a session key.
[8.4_s0014] A session key is a secret-key cipher key generated on the fly and used for just one session.
[8.4_s0015] This too involves a nontrivial protocol.
[8.4_s0016] What these two issues have in common is authentication.
[8.4_s0017] If a message is not original and timely, then from a practical standpoint we want to consider it as not being authentic, not being from whom it claims to be.
[8.4_s0018] And, obviously, when you are arranging to share a new session key with someone, you want to know you are sharing it with the right person.
[8.4_s0019] Usually, authentication protocols establish a session key at the same time, so that at the end of the protocol Alice and Bob have authenticated each other and they have a new secret key to use.
[8.4_s0020] Without a new session key, the protocol would just authenticate Alice and Bob at one point in time; a session key allows them to efficiently authenticate subsequent messages.
[8.4_s0021] Generally, session key establishment protocols perform authentication.
[8.4_s0022] A notable exception is Diffie-Hellman, as described below, so the terms authentication protocol and session key establishment protocol are almost synonymous.
[8.4_s0023] There is a core set of techniques used to ensure originality and timeliness in authentication protocols.
[8.4_s0024] We describe those techniques before moving on to particular protocols.
[8.4_s0025] 8.4.1 Originality and Timeliness Techniques  We have seen that authenticators alone do not enable us to detect messages that are not original or timely.
[8.4_s0026] One approach is to include a timestamp in the message.
[8.4_s0027] Obviously the timestamp itself must be tamperproof, so it must be covered by the authenticator.
[8.4_s0028] The primary drawback to timestamps is that they require distributed clock synchronization.
[8.4_s0029] Since our system would then depend on synchronization, the clock synchronization itself would need to be defended against security threats, in addition to the usual challenges of clock synchronization.
[8.4_s0030] Another issue is that distributed clocks are synchronized to only a certain degree—a certain margin of error.
[8.4_s0031] Thus, the timing integrity provided by timestamps is only as good as the degree of synchronization.
[8.4_s0032] Another approach is to include a nonce—a random number used only once—in the message.
[8.4_s0033] Participants can then detect replay attacks by checking whether a nonce has been used previously.
[8.4_s0034] Unfortunately, this requires keeping track of past nonces, of which a great many could accumulate.
[8.4_s0035] One solution is to combine the use of timestamps and nonces, so that nonces are required to be unique only within a certain span of time.
[8.4_s0036] That makes ensuring uniqueness of nonces manageable while requiring only loose synchronization of clocks.
[8.4_s0037] Another solution to the shortcomings of timestamps and nonces is to use one or both of them in a challenge-response protocol.
[8.4_s0038] Suppose we use a timestamp.
[8.4_s0039] In a challenge-response protocol, Alice sends Bob a timestamp, challenging Bob to encrypt it in a response message (if they share a secret key) or digitally sign it in a response message (if Bob has a public key, as in Figure).
[8.4_s0040] The encrypted timestamp is like an authenticator that additionally proves timeliness.
[8.4_s0041] Alice can easily check the timeliness of the timestamp in a response from Bob since that timestamp comes from Alice’s own clock—no distributed clock synchronization needed.
[8.4_s0042] Suppose instead that the protocol uses nonces.
[8.4_s0043] Then Alice need only keep track of those nonces for which responses are currently outstanding and haven’t been outstanding too long; any purported response with an unrecognized nonce must be bogus.
[8.4_s0044] The beauty of challenge-response, which might otherwise seem excessively complex, is that it combines timeliness and authentication; after all, only Bob (and possibly Alice, if it’s a secret-key cipher) knows the key necessary to encrypt the never before seen timestamp or nonce.
[8.4_s0045] Timestamps or nonces are used in most of the authentication protocols that follow.
[8.4_s0046] 8.4.2 Public-Key Authentication Protocols
[8.4_s0047] In the following discussion, we assume that Alice and Bob’s public keys have been predistributed to each other via some means such as a PKI.
[8.4_s0048] We mean this to include the case where Alice includes her certificate in her first message to Bob, and the case where Bob searches for a certificate about Alice when he receives her first message.
[8.4_s0049] This first protocol (Figure) relies on Alice and Bob’s clocks being synchronized.
[8.4_s0050] Alice sends Bob a message with a timestamp and her identity in plaintext plus her digital signature.
[8.4_s0051] Bob uses the digital signature to authenticate the message and the timestamp to verify its freshness.
[8.4_s0052] Bob sends back a message with a timestamp and his identity in plaintext, as well as a new session key encrypted (for confidentiality) using Alice’s public key, all digitally signed.
[8.4_s0053] Alice can verify the authenticity and freshness of the message, so she knows she can trust the new session key.
[8.4_s0054] To deal with imperfect clock synchronization, the timestamps could be augmented with nonces.
[8.4_s0055] The second protocol (Figure) is similar but does not rely on clock synchronization.
[8.4_s0056] In this protocol, Alice again sends Bob a digitally signed message with a timestamp and her identity.
[8.4_s0057] Because their clocks aren’t synchronized, Bob cannot be sure that the message is fresh.
[8.4_s0058] Bob sends back a digitally signed message with Alice’s original timestamp, his own new timestamp, and his identity.
[8.4_s0059] Alice can verify the freshness of Bob’s reply by comparing her current time against the timestamp that originated with her.
[8.4_s0060] She then sends Bob a digitally signed message with his original timestamp and a new session key encrypted using Bob’s public key.
[8.4_s0061] Bob can verify the freshness of the message because the timestamp came from his clock, so he knows he can trust the new session key.
[8.4_s0062] The timestamps essentially serve as convenient nonces, and indeed this protocol could use nonces instead.
[8.4_s0063] 8.4.3 Secret-Key Authentication Protocols  Only in fairly small systems is it practical to predistribute secret keys to every pair of entities.
[8.4_s0064] We focus here on larger systems, where each entity would have its own master key shared only with a Key Distribution Center (KDC).
[8.4_s0065] In this case, secret-key-based authentication protocols involve three parties: Alice, Bob, and a KDC.
[8.4_s0066] The end product of the authentication protocol is a session key shared between Alice and Bob that they will use to communicate directly, without involving the KDC.
[8.4_s0067] The Needham-Schroeder authentication protocol is illustrated in Figure.
[8.4_s0068] Note that the KDC doesn’t actually authenticate Alice’s initial message and doesn’t communicate with Bob at all.
[8.4_s0069] Instead, the KDC uses its knowledge of Alice’s and Bob’s master keys to construct a reply that would be useless to anyone other than Alice (because only Alice can decrypt it) and contains the necessary ingredients for Alice and Bob to perform the rest of the authentication protocol themselves.
[8.4_s0070] The nonce in the first two messages is to assure Alice that the KDC’s reply is fresh.
[8.4_s0071] The second and third messages include the new session key and Alice’s identifier, encrypted together using Bob’s master key.
[8.4_s0072] It is a sort of secret-key version of a public-key certificate; it is in effect a signed statement by the KDC (because the KDC is the only entity besides Bob who knows Bob’s master key) that the enclosed session key is owned by Alice and Bob.
[8.4_s0073] Although the nonce in the last two messages is intended to assure Bob that the third message was fresh, there is a flaw in this reasoning.
[8.4_s0074] Kerberos  Kerberos is an authentication system based on the Needham-Schroeder protocol and specialized for client/server environments.
[8.4_s0075] Originally developed at MIT, it has been standardized by the IETF and is available as both open source and commercial products.
[8.4_s0076] We will focus here on some of Kerberos’s interesting innovations.
[8.4_s0077] Kerberos clients are generally human users, and users authenticate themselves using passwords.
[8.4_s0078] Alice’s master key, shared with the KDC, is derived from her password—if you know the password, you can compute the key.
[8.4_s0079] Kerberos assumes anyone can physically access any client machine; therefore, it is important to minimize the exposure of Alice’s password or master key not just in the network but also on any machine where she logs in.
[8.4_s0080] Kerberos takes advantage of Needham-Schroeder to accomplish this.
[8.4_s0081] In Needham-Schroeder, the only time Alice needs to use her password is when decrypting the reply from the KDC.
[8.4_s0082] Kerberos client-side software waits until the KDC’s reply arrives, prompts Alice to enter her password, computes the master key and decrypts the KDC’s reply, and then erases all information about the password and master key to minimize its exposure.
[8.4_s0083] Also note that the only sign a user sees of Kerberos is when the user is prompted for a password.
[8.4_s0084] In Needham-Schroeder, the KDC’s reply to Alice plays two roles: It gives her the means to prove her identity (only Alice can decrypt the reply), and it gives her a sort of secret-key certificate or “ticket” to present to Bob—the session key and Alice’s identifier, encrypted with Bob’s master key.
[8.4_s0085] In Kerberos, those two functions—and the KDC itself, in effect—are split up (Figure).
[8.4_s0086] A trusted server called an Authentication Server (AS) plays the first KDC role of providing Alice with something she can use to prove her identity—not to Bob this time, but to a second trusted server called a Ticket Granting Server (TGS).
[8.4_s0087] The TGS plays the second KDC role, replying to Alice with a ticket she can present to Bob.
[8.4_s0088] The attraction of this scheme is that if Alice needs to communicate with several servers, not just Bob, then she can get tickets for each of them from the TGS without going back to the AS.
[8.4_s0089] In the client/server application domain for which Kerberos is intended, it is reasonable to assume a degree of clock synchronization.
[8.4_s0090] This allows Kerberos to use timestamps and lifespans instead of Needham-Shroeder’s nonces, and thereby eliminate the Needham-Schroeder security weakness.
[8.4_s0091] Kerberos supports a choice of hash functions and secret-key ciphers, allowing it to keep pace with the state-of-the-art in cryptographic algorithms.
=== SECTION 8.5: Network Security > Example Systems ===
[8.5_s0000] We have now seen many of the components required to provide one or two aspects of security.
[8.5_s0001] These components include cryptographic algorithms, key predistribution mechanisms, and authentication protocols.
[8.5_s0002] In this section, we examine some complete systems that use these components.
[8.5_s0003] These systems can be roughly categorized by the protocol layer at which they operate.
[8.5_s0004] Systems that operate at the application layer include Pretty Good Privacy (PGP), which provides electronic mail security, and Secure Shell (SSH), a secure remote login facility.
[8.5_s0005] At the transport layer, there is the IETF’s Transport Layer Security (TLS) standard and the older protocol from which it derives, Secure Socket Layer (SSL).
[8.5_s0006] The IPsec (IP Security) protocols, as their name implies, operate at the IP (network) layer.
[8.5_s0007] 802.11i provides security at the link layer of wireless networks.
[8.5_s0008] This section describes the salient features of each of these approaches.
[8.5_s0009] You might reasonably wonder why security has to be provided at so many different layers.
[8.5_s0010] One reason is that different threats require different defensive measures, and this often translates into securing a different protocol layer.
[8.5_s0011] For example, if your main concern is with a person in the building next door snooping on your traffic as it flows between your laptop and your 802.11 access point, then you probably want security at the link layer.
[8.5_s0012] However, if you want to be really sure you are connected to your bank’s website and preventing all the data that you send to the bank from being read by curious employees of some Internet service provider, then something that extends all the way from your machine to the bank’s server—like the transport layer—may be the right place to secure the traffic.
[8.5_s0013] As is often the case, there is no one-size-fits-all solution.
[8.5_s0014] The security systems described below have the ability to vary which cryptographic algorithms they use.
[8.5_s0015] The idea of making a security system algorithm independent is a very good one, because you never know when your favorite cryptographic algorithm might be proved to be insufficiently strong for your purposes.
[8.5_s0016] It would be nice if you could quickly change to a new algorithm without having to change the protocol specification or implementation.
[8.5_s0017] Note the analogy to being able to change keys without changing the algorithm; if one of your cryptographic algorithms turns out to be flawed, it would be great if your entire security architecture didn’t need an immediate redesign.
[8.5_s0018] 8.5.1
[8.5_s0019] Pretty Good Privacy (PGP)
[8.5_s0020] Pretty Good Privacy (PGP) is a widely used approach to providing security for electronic mail.
[8.5_s0021] It provides authentication, confidentiality, data integrity, and nonrepudiation.
[8.5_s0022] Originally devised by Phil Zimmerman, it has evolved into an IETF standard known as OpenPGP.
[8.5_s0023] As we saw in a previous section, PGP is notable for using a “web of trust” model for distribution of keys rather than a tree-like hierarchy.
[8.5_s0024] PGP’s confidentiality and receiver authentication depend on the receiver of an email message having a public key that is known to the sender.
[8.5_s0025] To provide sender authentication and nonrepudiation, the sender must have a public key that is known by the receiver.
[8.5_s0026] These public keys are predistributed using certificates and a web-of-trust PKI.
[8.5_s0027] PGP supports RSA and DSS for public key certificates.
[8.5_s0028] These certificates may additionally specify which cryptographic algorithms are supported or preferred by the key’s owner.
[8.5_s0029] The certificates provide bindings between email addresses and public keys.
[8.5_s0030] Consider the following example of PGP being used to provide both sender authentication and confidentiality.
[8.5_s0031] Suppose Alice has a message to email to Bob.
[8.5_s0032] Alice’s PGP application goes through the steps illustrated in Figure.
[8.5_s0033] First, the message is digitally signed by Alice; MD5, SHA-1, and the SHA-2 family are among the hashes that may be used in the digital signature.
[8.5_s0034] Her PGP application then generates a new session key for just this one message; AES and 3DES are among the supported secret-key ciphers.
[8.5_s0035] The digitally signed message is encrypted using the session key, then the session key itself is encrypted using Bob’s public key and appended to the message.
[8.5_s0036] Alice’s PGP application reminds her of the level of trust she had previously assigned to Bob’s public key, based on the number of certificates she has for Bob and the trustworthiness of the individuals who signed the certificates.
[8.5_s0037] Finally, not for security but because email messages have to be sent in ASCII, a base64 encoding is applied to the message to convert it to an ASCII-compatible representation.
[8.5_s0038] Upon receiving the PGP message in an email, Bob’s PGP application reverses this process step-by-step to obtain the original plaintext message and confirm Alice’s digital signature—and reminds Bob of the level of trust he has in Alice’s public key.
[8.5_s0039] Email has particular characteristics that allow PGP to embed an adequate authentication protocol in this one-message data transmission protocol, avoiding the need for any prior message exchange (and sidestepping some of the complexities described in the previous section).
[8.5_s0040] Alice’s digital signature suffices to authenticate her.
[8.5_s0041] Although there is no proof that the message is timely, legitimate email isn’t guaranteed to be timely either.
[8.5_s0042] There is also no proof that the message is original, but Bob is an email user and probably a fault-tolerant human who can recover from duplicate emails (which, again, are not out of the question under normal operation anyway).
[8.5_s0043] Alice can be sure that only Bob could read the message because the session key was encrypted with his public key.
[8.5_s0044] Although this protocol doesn’t prove to Alice that Bob is actually there and received the email, an authenticated email from Bob back to Alice could do this.
[8.5_s0045] The preceding discussion gives a good example of why application-layer security mechanisms can be helpful.
[8.5_s0046] Only with a full knowledge of how the application works can you make the right choices about which attacks to defend against (like forged email) versus which to ignore (like delayed or replayed email).
[8.5_s0047] 8.5.2 Secure Shell (SSH)  The Secure Shell (SSH) protocol is used to provide a remote login service, replacing the less secure Telnet used in the early days of the Internet.
[8.5_s0048] (SSH can also be used to remotely execute commands and transfer files, but we will focus first on how SSH supports remote login.)
[8.5_s0049] SSH is most often used to provide strong client/server authentication/message integrity—where the SSH client runs on the user’s desktop machine and the SSH server runs on some remote machine that the user wants to log into—but it also supports confidentiality.
[8.5_s0050] Telnet provides none of these capabilities.
[8.5_s0051] Note that “SSH” is often used to refer to both the SSH protocol and applications that use it; you need to figure out which from the context.
[8.5_s0052] To better appreciate the importance of SSH on today’s Internet, consider a couple of the scenarios where it is used.
[8.5_s0053] Telecommuters, for example, often subscribe to ISPs that offer high-speed fiber-to-the-home, and they use these ISPs (plus some chain of other ISPs) to reach machines operated by their employer.
[8.5_s0054] This means that when a telecommuter logs into a machine inside his employer’s data center, both the passwords and all the data sent or received potentially passes through any number of untrusted networks.
[8.5_s0055] SSH provides a way to encrypt the data sent over these connections and to improve the strength of the authentication mechanism used to log in.
[8.5_s0056] (A similar situation occurs when said employee connects to work using the public Wi-Fi at Starbucks.)
[8.5_s0057] Another usage of SSH is remote login to a router, perhaps to change its configuration or read its log files; clearly, a network administrator wants to be sure that he can log into a router securely and that unauthorized parties can neither log in nor intercept the commands sent to the router or output sent back to the administrator.
[8.5_s0058] The latest version of SSH, version 2, consists of three protocols:  -  SSH-TRANS, a transport layer protocol  -  SSH-AUTH, an authentication protocol  -  SSH-CONN, a connection protocol  We focus on the first two, which are involved in remote login.
[8.5_s0059] We briefly discuss the purpose of SSH-CONN at the end of the section.
[8.5_s0060] SSH-TRANS provides an encrypted channel between the client and server machines.
[8.5_s0061] It runs on top of a TCP connection.
[8.5_s0062] Any time a user uses an SSH application to log into a remote machine, the first step is to set up an SSH-TRANS channel between those two machines.
[8.5_s0063] The two machines establish this secure channel by first having the client authenticate the server using RSA.
[8.5_s0064] Once authenticated, the client and server establish a session key that they will use to encrypt any data sent over the channel.
[8.5_s0065] This high-level description skims over several details, including the fact that the SSH-TRANS protocol includes a negotiation of the encryption algorithm the two sides are going to use.
[8.5_s0066] For example, AES is commonly selected.
[8.5_s0067] Also, SSH-TRANS includes a message integrity check of all data exchanged over the channel.
[8.5_s0068] The one issue we can’t skim over is how the client came to possess the server’s public key that it needs to authenticate the server.
[8.5_s0069] Strange as it may sound, the server tells the client its public key at connection time.
[8.5_s0070] The first time a client connects to a particular server, the SSH application warns the user that it has never talked to this machine before and asks if the user wants to continue.
[8.5_s0071] Although it is a risky thing to do, because SSH is effectively not able to authenticate the server, users often say “yes” to this question.
[8.5_s0072] The SSH application then remembers the server’s public key, and the next time the user connects to that same machine it compares this saved key with the one the server responds with.
[8.5_s0073] If they are the same, SSH authenticates the server.
[8.5_s0074] If they are different, however, the SSH application again warns the user that something is amiss, and the user is then given an opportunity to abort the connection.
[8.5_s0075] Alternatively, the prudent user can learn the server’s public key through some out-of-band mechanism, save it on the client machine, and thus never take the “first time” risk.
[8.5_s0076] Once the SSH-TRANS channel exists, the next step is for the user to actually log into the machine, or more specifically, authenticate himself or herself to the server.
[8.5_s0077] SSH allows three different mechanisms for doing this.
[8.5_s0078] First, since the two machines are communicating over a secure channel, it is OK for the user to simply send his or her password to the server.
[8.5_s0079] This is not a safe thing to do when using Telnet since the password would be sent in the clear, but in the case of SSH the password is encrypted in the SSH-TRANS channel.
[8.5_s0080] The second mechanism uses public-key encryption.
[8.5_s0081] This requires that the user has already placed his or her public key on the server.
[8.5_s0082] The third mechanism, called host-based authentication, basically says that any user claiming to be so-and-so from a certain set of trusted hosts is automatically believed to be that same user on the server.
[8.5_s0083] Host-based authentication requires that the client host authenticate itself to the server when they first connect; standard SSH-TRANS only authenticates the server by default.
[8.5_s0084] The main thing you should take away from this discussion is that SSH is a fairly straightforward application of the protocols and algorithms we have seen throughout this chapter.
[8.5_s0085] However, what sometimes makes SSH a challenge to understand is all the keys a user has to create and manage, where the exact interface is operating system dependent.
[8.5_s0086] For example, the OpenSSH package that runs on most Unix machines supports a command that can be used to create public/private key pairs.
[8.5_s0087] These keys are then stored in various files in directory in the user’s home directory.
[8.5_s0088] For example, file ~/.ssh/known_hosts records the keys for all the hosts the user has logged into, file ~/.ssh/authorized_keys contains the public keys needed to authenticate the user when he or she logs into this machine (i.e., they are used on the server side), and file ~/.ssh/id_rsa contains the private keys needed to authenticate the user on remote machines (i.e., they are used on the client side).
[8.5_s0089] Finally, SSH has proven so useful as a system for securing remote login, it has been extended to also support other applications, such as sending and receiving email.
[8.5_s0090] The idea is to run these applications over a secure “SSH tunnel.”
[8.5_s0091] This capability is called port forwarding, and it uses the SSH-CONN protocol.
[8.5_s0092] The idea is illustrated in Figure, where we see a client on host A indirectly communicating with a server on host B by forwarding its traffic through an SSH connection.
[8.5_s0093] The mechanism is called port forwarding because when messages arrive at the well-known SSH port on the server, SSH first decrypts the contents and then “forwards” the data to the actual port at which the server is listening.
[8.5_s0094] This is just another sort of tunnel, which in this case happens to provide confidentiality and authentication.
[8.5_s0095] It’s possible to provide a form of virtual private network (VPN) using SSH tunnels in this way.
[8.5_s0096] 8.5.3 Transport Layer Security (TLS, SSL, HTTPS)  To understand the design goals and requirements for the Transport Layer Security (TLS) standard and the Secure Socket Layer (SSL) on which TLS is based, it is helpful to consider one of the main problems that they are intended to solve.
[8.5_s0097] As the World Wide Web became popular and commercial enterprises began to take an interest in it, it became clear that some level of security would be necessary for transactions on the Web.
[8.5_s0098] The canonical example of this is making purchases by credit card.
[8.5_s0099] There are several issues of concern when sending your credit card information to a computer on the Web.
[8.5_s0100] First, you might worry that the information would be intercepted in transit and subsequently used to make unauthorized purchases.
[8.5_s0101] You might also worry about the details of a transaction being modified, such as changing the purchase amount.
[8.5_s0102] And you would certainly like to know that the computer to which you are sending your credit card information is in fact one belonging to the vendor in question and not some other party.
[8.5_s0103] Thus, we immediately see a need for confidentiality, integrity, and authentication in Web transactions.
[8.5_s0104] The first widely used solution to this problem was SSL, originally developed by Netscape and subsequently the basis for the IETF’s TLS standard.
[8.5_s0105] The designers of SSL and TLS recognized that these problems were not specific to Web transactions (i.e., those using HTTP) and instead built a general-purpose protocol that sits between an application protocol such as HTTP and a transport protocol such as TCP.
[8.5_s0106] The reason for calling this “transport layer security” is that, from the application’s perspective, this protocol layer looks just like a normal transport protocol except for the fact that it is secure.
[8.5_s0107] That is, the sender can open connections and deliver bytes for transmission, and the secure transport layer will get them to the receiver with the necessary confidentiality, integrity, and authentication.
[8.5_s0108] By running the secure transport layer on top of TCP, all of the normal features of TCP (reliability, flow control, congestion control, etc.) are also provided to the application.
[8.5_s0109] This arrangement of protocol layers is depicted in Figure.
[8.5_s0110] When HTTP is used in this way, it is known as HTTPS (Secure HTTP).
[8.5_s0111] In fact, HTTP itself is unchanged.
[8.5_s0112] It simply delivers data to and accepts data from the SSL/TLS layer rather than TCP.
[8.5_s0113] For convenience, a default TCP port has been assigned to HTTPS (443).
[8.5_s0114] That is, if you try to connect to a server on TCP port 443, you will likely find yourself talking to the SSL/TLS protocol, which will pass your data through to HTTP provided all goes well with authentication and decryption.
[8.5_s0115] Although standalone implementations of SSL/TLS are available, it is more common for an implementation to be bundled with applications that need it, primarily web browsers.
[8.5_s0116] In the remainder of our discussion of transport layer security, we focus on TLS.
[8.5_s0117] Although SSL and TLS are unfortunately not interoperable, they differ in only minor ways, so nearly all of this description of TLS applies to SSL.
[8.5_s0118] Handshake Protocol  A pair of TLS participants negotiate at runtime which cryptography to use.
[8.5_s0119] The participants negotiate a choice of:  -  Data integrity hash (MD5, SHA-1, etc.), used to implement HMACs  -  secret-key cipher for confidentiality (among the possibilities are DES, 3DES, and AES)  -  Session key establishment approach (among the possibilities are Diffie-Hellman, and public-key authentication protocols using DSS)
[8.5_s0120] Interestingly, the participants may also negotiate the use of a compression algorithm, not because this offers any security benefits, but because it’s easy to do when you’re negotiating all this other stuff and you’ve already decided to do some expensive per-byte operations on the data.
[8.5_s0121] In TLS, the confidentiality cipher uses two keys, one for each direction, and similarly two initialization vectors.
[8.5_s0122] The HMACs are likewise keyed with different keys for the two participants.
[8.5_s0123] Thus, regardless of the choice of cipher and hash, a TLS session requires effectively six keys.
[8.5_s0124] TLS derives all of them from a single shared master secret.
[8.5_s0125] The master secret is a 384-bit (48-byte) value that in turn is derived in part from the “session key” that results from TLS’s session key establishment protocol.
[8.5_s0126] The part of TLS that negotiates the choices and establishes the shared master secret is called the handshake protocol.
[8.5_s0127] (Actual data transfer is performed by TLS’s record protocol.)
[8.5_s0128] The handshake protocol is at heart a session key establishment protocol, with a master secret instead of a session key.
[8.5_s0129] Since TLS supports a choice of approaches to session key establishment, these call for correspondingly different protocol variants.
[8.5_s0130] Furthermore, the handshake protocol supports a choice between mutual authentication of both participants, authentication of just one participant (this is the most common case, such as authenticating a website but not a user), or no authentication at all (anonymous Diffie-Hellman).
[8.5_s0131] Thus, the handshake protocol knits together several session key establishment protocols into a single protocol.
[8.5_s0132] Figure shows the handshake protocol at a high level.
[8.5_s0133] The client initially sends a list of the combinations of cryptographic algorithms that it supports, in decreasing order of preference.
[8.5_s0134] The server responds, giving the single combination of cryptographic algorithms it selected from those listed by the client.
[8.5_s0135] These messages also contain a client nonce and a server nonce, respectively, that will be incorporated in generating the master secret later.
[8.5_s0136] At this point, the negotiation phase is complete.
[8.5_s0137] The server now sends additional messages based on the negotiated session key establishment protocol.
[8.5_s0138] That could involve sending a public-key certificate or a set of Diffie-Hellman parameters.
[8.5_s0139] If the server requires authentication of the client, it sends a separate message indicating that.
[8.5_s0140] The client then responds with its part of the negotiated key exchange protocol.
[8.5_s0141] Now the client and server each have the information necessary to generate the master secret.
[8.5_s0142] The “session key” that they exchanged is not in fact a key, but instead what TLS calls a pre-master secret.
[8.5_s0143] The master secret is computed (using a published algorithm) from this pre-master secret, the client nonce, and the server nonce.
[8.5_s0144] Using the keys derived from the master secret, the client then sends a message that includes a hash of all the preceding handshake messages, to which the server responds with a similar message.
[8.5_s0145] This enables them to detect any discrepancies between the handshake messages they sent and received, such as would result, for example, if a man in the middle modified the initial unencrypted client message to weaken its choices of cryptographic algorithms.
[8.5_s0146] Record Protocol  Within a session established by the handshake protocol, TLS’s record protocol adds confidentiality and integrity to the underlying transport service.
[8.5_s0147] Messages handed down from the application layer are:  1.
[8.5_s0148] Fragmented or coalesced into blocks of a convenient size for the following steps  2.
[8.5_s0149] Optionally compressed  3.
[8.5_s0150] Integrity-protected using an HMAC  4.
[8.5_s0151] Encrypted using a secret-key cipher  5.
[8.5_s0152] Passed to the transport layer (normally TCP) for transmission  The record protocol uses an HMAC as an authenticator.
[8.5_s0153] The HMAC uses whichever hash algorithm (MD5, SHA-1, etc.) was negotiated by the participants.
[8.5_s0154] The client and server have different keys to use when computing HMACs, making them even harder to break.
[8.5_s0155] Furthermore, each record protocol message is assigned a sequence number, which is included when the HMAC is computed—even though the sequence number is never explicit in the message.
[8.5_s0156] This implicit sequence number prevents replays or reorderings of messages.
[8.5_s0157] This is needed because, although TCP can deliver sequential, unduplicated messages to the layer above it under normal assumptions, those assumptions do not include an adversary that can intercept TCP messages, modify messages, or send bogus ones.
[8.5_s0158] On the other hand, it is TCP’s delivery guarantees that make it possible for TLS to rely on a legitimate TLS message having the next implicit sequence number in order.
[8.5_s0159] Another interesting feature of the TLS protocol is the ability to resume a session.
[8.5_s0160] To understand the original motivation for this, it is helpful to understand how HTTP originally made use of TCP connections.
[8.5_s0161] (The details of HTTP are presented in the next chapter.)
[8.5_s0162] Each HTTP operation, such as getting a page from a server, required a new TCP connection to be opened.
[8.5_s0163] Retrieving a single page with a number of embedded graphical objects might take many TCP connections.
[8.5_s0164] Opening a TCP connection requires a three-way handshake before data transmission can start.
[8.5_s0165] Once the TCP connection is ready to accept data, the client would then need to start the TLS handshake protocol, taking at least another two round-trip times (and consuming some amount of processing resources and network bandwidth) before actual application data could be sent.
[8.5_s0166] The resumption capability of TLS was designed to alleviate this problem.
[8.5_s0167] The idea of session resumption is to optimize away the handshake in those cases where the client and the server have already established some shared state in the past.
[8.5_s0168] The client simply includes the session ID from a previously established session in its initial handshake message.
[8.5_s0169] If the server finds that it still has state for that session, and the resumption option was negotiated when that session was originally created, then the server can reply to the client with an indication of success, and data transmission can begin using the algorithms and parameters previously negotiated.
[8.5_s0170] If the session ID does not match any session state cached at the server, or if resumption was not allowed for the session, then the server will fall back to the normal handshake process.
[8.5_s0171] The reason the preceding discussion emphasized the original motivation is that having to do a TCP handshake for every embedded object in a web page led to so much overhead, independent of TLS, that HTTP was eventually optimized to support persistent connections (also discussed in the next chapter).
[8.5_s0172] Because optimizing HTTP mitigated the value of session resumption in TLS (plus the realization that reusing the same session IDs and master secret key in a series of resumed sessions is a security risk), TLS changed its approach to resumption in the latest version (1.3).
[8.5_s0173] In TLS 1.3, the client sends an opaque, server-encrypted session ticket to the server upon resumption.
[8.5_s0174] This ticket contains all the information required to resume the session.
[8.5_s0175] The same master secret is used across handshakes, but the default behavior is to perform a session key exchange upon resumption.
[8.5_s0176] 8.5.4 IP Security (IPsec)  Probably the most ambitious of all the efforts to integrate security into the Internet happens at the IP layer.
[8.5_s0177] Support for IPsec, as the architecture is called, is optional in IPv4 but mandatory in IPv6.
[8.5_s0178] IPsec is really a framework (as opposed to a single protocol or system) for providing all the security services discussed throughout this chapter.
[8.5_s0179] IPsec provides three degrees of freedom.
[8.5_s0180] First, it is highly modular, allowing users (or more likely, system administrators) to select from a variety of cryptographic algorithms and specialized security protocols.
[8.5_s0181] Second, IPsec allows users to select from a large menu of security properties, including access control, integrity, authentication, originality, and confidentiality.
[8.5_s0182] Third, IPsec can be used to protect narrow streams (e.g., packets belonging to a particular TCP connection being sent between a pair of hosts) or wide streams (e.g., all packets flowing between a pair of routers).
[8.5_s0183] When viewed from a high level, IPsec consists of two parts.
[8.5_s0184] The first part is a pair of protocols that implement the available security services.
[8.5_s0185] They are the Authentication Header (AH), which provides access control, connectionless message integrity, authentication, and antireplay protection, and the Encapsulating Security Payload (ESP), which supports these same services, plus confidentiality.
[8.5_s0186] AH is rarely used so we focus on ESP here.
[8.5_s0187] The second part is support for key management, which fits under an umbrella protocol known as the Internet Security Association and Key Management Protocol (ISAKMP).
[8.5_s0188] The abstraction that binds these two pieces together is the security association (SA).
[8.5_s0189] An SA is a simplex (one-way) connection with one or more of the available security properties.
[8.5_s0190] Securing a bidirectional communication between a pair of hosts—corresponding to a TCP connection, for example—requires two SAs, one in each direction.
[8.5_s0191] Although IP is a connectionless protocol, security depends on connection state information such as keys and sequence numbers.
[8.5_s0192] When created, an SA is assigned an ID number called a security parameters index (SPI) by the receiving machine.
[8.5_s0193] A combination of this SPI and the destination IP addresses uniquely identifies an SA.
[8.5_s0194] An ESP header includes the SPI so the receiving host can determine which SA an incoming packet belongs to and, hence, what algorithms and keys to apply to the packet.
[8.5_s0195] SAs are established, negotiated, modified, and deleted using ISAKMP.
[8.5_s0196] It defines packet formats for exchanging key generation and authentication data.
[8.5_s0197] These formats aren’t terribly interesting because they provide a framework only—the exact form of the keys and authentication data depends on the key generation technique, the cipher, and the authentication mechanism that is used.
[8.5_s0198] Moreover, ISAKMP does not specify a particular key exchange protocol, although it does suggest the Internet Key Exchange (IKE) as one possibility, and IKE v2 is what is used in practice.
[8.5_s0199] ESP is the protocol used to securely transport data over an established SA.
[8.5_s0200] In IPv4, the ESP header follows the IP header; in IPv6, it is an extension header.
[8.5_s0201] Its format uses both a header and a trailer, as shown in Figure.
[8.5_s0202] The SPI field lets the receiving host identify the security association to which the packet belongs.
[8.5_s0203] The SeqNum field protects against replay attacks.
[8.5_s0204] The packet’s PayloadData contains the data described by the NextHdr field.
[8.5_s0205] If confidentiality is selected, then the data is encrypted using whatever cipher was associated with the SA.
[8.5_s0206] The PadLength field records how much padding was added to the data; padding is sometimes necessary because, for example, the cipher requires the plaintext to be a multiple of a certain number of bytes or to ensure that the resulting ciphertext terminates on a 4-byte boundary.
[8.5_s0207] Finally, the AuthenticationData carries the authenticator.
[8.5_s0208] IPsec supports a tunnel mode as well as the more straightforward transport mode.
[8.5_s0209] Each SA operates in one or the other mode.
[8.5_s0210] In a transport mode SA, ESP’s payload data is simply a message for a higher layer such as UDP or TCP.
[8.5_s0211] In this mode, IPsec acts as an intermediate protocol layer, much like SSL/TLS does between TCP and a higher layer.
[8.5_s0212] When an ESP message is received, its payload is passed to the higher level protocol.
[8.5_s0213] In a tunnel mode SA, however, ESP’s payload data is itself an IP packet, as in Figure.
[8.5_s0214] The source and destination of this inner IP packet may be different from those of the outer IP packet.
[8.5_s0215] When an ESP message is received, its payload is forwarded on as a normal IP packet.
[8.5_s0216] The most common way to use the ESP is to build an “IPsec tunnel” between two routers, typically firewalls.
[8.5_s0217] For example, a corporation wanting to link two sites using the Internet could open a pair of tunnel-mode SAs between a router at one site and a router at the other site.
[8.5_s0218] An IP packet outgoing from one site would, at the outgoing router, become the payload of an ESP message sent to the other site’s router.
[8.5_s0219] The receiving router would unwrap the payload IP packet and forward it on to its true destination.
[8.5_s0220] These tunnels may also be configured to use ESP with confidentiality and authentication, thus preventing unauthorized access to the data that traverses this virtual link and ensuring that no spurious data is received at the far end of the tunnel.
[8.5_s0221] Furthermore, tunnels can provide traffic confidentiality, since multiplexing multiple flows through a single tunnel obscures information about how much traffic is flowing between particular endpoints.
[8.5_s0222] A network of such tunnels can be used to implement an entire virtual private network.
[8.5_s0223] Hosts communicating over a VPN need not even be aware that it exists.
[8.5_s0224] 8.5.5 Wireless Security (802.11i)  Wireless links are particularly exposed to security threats due to the lack of any physical security on the medium.
[8.5_s0225] While the convenience of 802.11 has prompted widespread acceptance of the technology, lack of security has been a recurring problem.
[8.5_s0226] For example, it is all too easy for an employee of a corporation to connect an 802.11 access point to the corporate network.
[8.5_s0227] Since radio waves pass through most walls, if the access point lacks the correct security measures, an attacker can now gain access to the corporate network from outside the building.
[8.5_s0228] Similarly, a computer with a wireless network adaptor inside the building could connect to an access point outside the building, potentially exposing it to attack, not to mention the rest of the corporate network if that same computer has, say, an Ethernet connection as well.
[8.5_s0229] Consequently, there has been considerable work on securing Wi-Fi links.
[8.5_s0230] Somewhat surprisingly, one of the early security techniques developed for 802.11, known as Wired Equivalent Privacy (WEP), turned out to be seriously flawed and quite easily breakable.
[8.5_s0231] The IEEE 802.11i standard provides authentication, message integrity, and confidentiality to 802.11 (Wi-Fi) at the link layer.
[8.5_s0232] WPA3 (Wi-Fi Protected Access 3) is often used as a synonym for 802.11i, although it is technically a trademark of the Wi-Fi Alliance that certifies product compliance with 802.11i.
[8.5_s0233] For backward compatibility, 802.11i includes definitions of first-generation security algorithms—including WEP—that are now known to have major security flaws.
[8.5_s0234] We will focus here on 802.11i’s newer, stronger algorithms.
[8.5_s0235] 802.11i authentication supports two modes.
[8.5_s0236] In either mode, the end result of successful authentication is a shared Pairwise Master Key.
[8.5_s0237] Personal mode, also known as Pre-Shared Key (PSK) mode, provides weaker security but is more convenient and economical for situations like a home 802.11 network.
[8.5_s0238] The wireless device and the Access Point (AP) are preconfigured with a shared passphrase—essentially a very long password—from which the Pairwise Master Key is cryptographically derived.
[8.5_s0239] 802.11i’s stronger authentication mode is based on the IEEE 802.1X framework for controlling access to a LAN, which uses an Authentication Server (AS) as in Figure.
[8.5_s0240] The AS and AP must be connected by a secure channel and could even be implemented as a single box, but they are logically separate.
[8.5_s0241] The AP forwards authentication messages between the wireless device and the AS.
[8.5_s0242] The protocol used for authentication is called the Extensible Authentication Protocol (EAP).
[8.5_s0243] EAP is designed to support multiple authentication methods—smart cards, Kerberos, one-time passwords, public key authentication, and so on—as well as both one-sided and mutual authentication.
[8.5_s0244] So EAP is better thought of as an authentication framework than a protocol.
[8.5_s0245] Specific EAP-compliant protocols, of which there are many, are called EAP methods.
[8.5_s0246] For example, EAP-TLS is an EAP method based on TLS authentication.
[8.5_s0247] 802.11i does not place any restrictions on what the EAP method can use as a basis for authentication.
[8.5_s0248] It does, however, require an EAP method that performs mutual authentication, because not only do we want to prevent an adversary from accessing the network via our AP, we also want to prevent an adversary from fooling our wireless devices with a bogus, malicious AP.
[8.5_s0249] The end result of a successful authentication is a Pairwise Master Key shared between the wireless device and the AS, which the AS then conveys to the AP.
[8.5_s0250] One of the main differences between the stronger AS-based mode and the weaker personal mode is that the former readily supports a unique key per client.
[8.5_s0251] This in turn makes it easier to change the set of clients that can authenticate themselves (e.g., to revoke access to one client) without needing to change the secret stored in every client.
[8.5_s0252] With a Pairwise Master Key in hand, the wireless device and the AP execute a session key establishment protocol called the 4-way handshake to establish a Pairwise Transient Key.
[8.5_s0253] This Pairwise Transient Key is really a collection of keys that includes a session key called a Temporal Key.
[8.5_s0254] This session key is used by the protocol, called CCMP, that provides 802.11i’s data confidentiality and integrity.
[8.5_s0255] CCMP stands for CTR (Counter Mode) with CBC-MAC (Cipher-Block Chaining with Message Authentication Code) Protocol.
[8.5_s0256] CCMP uses AES in counter mode to encrypt for confidentiality.
[8.5_s0257] Recall that in counter mode encryption successive values of a counter are incorporated into the encryption of successive blocks of plaintext.
[8.5_s0258] CCMP uses a Message Authentication Code (MAC) as an authenticator.
[8.5_s0259] The MAC algorithm is based on CBC, even though CCMP doesn’t use CBC in the confidentiality encryption.
[8.5_s0260] In effect, CBC is performed without transmitting any of the CBC-encrypted blocks, solely so that the last CBC-encrypted block can be used as a MAC (only its first 8 bytes are actually used).
[8.5_s0261] The role of initialization vector is played by a specially constructed first block that includes a 48-bit packet number—a sequence number.
[8.5_s0262] (The packet number is also incorporated in the confidentiality encryption and serves to expose replay attacks.)
[8.5_s0263] The MAC is subsequently encrypted along with the plaintext in order to prevent birthday attacks, which depend on finding different messages with the same authenticator.
[8.5_s0264] 8.5.6 Firewalls  Whereas much of this chapter has focused on the uses of cryptography to provide such security features as authentication and confidentiality, there is a whole set of security issues that are not readily addressed by cryptographic means.
[8.5_s0265] For example, worms and viruses spread by exploiting bugs in operating systems and application programs (and sometimes human gullibility as well), and no amount of cryptography can help you if your machine has unpatched vulnerabilities.
[8.5_s0266] So other approaches are often used to keep out various forms of potentially harmful traffic.
[8.5_s0267] Firewalls are one of the most common ways to do this.
[8.5_s0268] A firewall is a system that typically sits at some point of connectivity between a site it protects and the rest of the network, as illustrated in Figure.
[8.5_s0269] It is usually implemented as an “appliance” or part of a router, although a “personal firewall” may be implemented on an end-user machine.
[8.5_s0270] Firewall-based security depends on the firewall being the only connectivity to the site from outside; there should be no way to bypass the firewall via other gateways, wireless connections, or dial-up connections.
[8.5_s0271] The wall metaphor is somewhat misleading in the context of networks since a great deal of traffic passes through a firewall.
[8.5_s0272] One way to think of a firewall is that by default it blocks traffic unless that traffic is specifically allowed to pass through.
[8.5_s0273] For example, it might filter out all incoming messages except those addresses to a particular set of IP addresses or to particular TCP port numbers.
[8.5_s0274] In effect, a firewall divides a network into a more-trusted zone internal to the firewall and a less-trusted zone external to the firewall.
[8.5_s0275] This is useful if you do not want external users to access a particular host or service within your site.
[8.5_s0276] Much of the complexity comes from the fact that you want to allow different kinds of access to different external users, ranging from the general public, to business partners, to remotely located members of your organization.
[8.5_s0277] A firewall may also impose restrictions on outgoing traffic to prevent certain attacks and to limit losses if an adversary succeeds in getting access inside the firewall.
[8.5_s0278] The location of a firewall also often happens to be the dividing line between globally addressable regions and those that use local addresses.
[8.5_s0279] Hence, Network Address Translation (NAT) functionality and firewall functionality often are found in the same device, even though they are logically separate.
[8.5_s0280] Firewalls may be used to create multiple zones of trust, such as a hierarchy of increasingly trusted zones.
[8.5_s0281] A common arrangement involves three zones of trust: the internal network, the DMZ (“demilitarized zone”); and the rest of the Internet.
[8.5_s0282] The DMZ is used to hold services such as DNS and email servers that need to be accessible to the outside.
[8.5_s0283] Both the internal network and the outside world can access the DMZ, but hosts in the DMZ cannot access the internal network; therefore, an adversary who succeeds in compromising a host in the exposed DMZ still cannot access the internal network.
[8.5_s0284] The DMZ can be periodically restored to a clean state.
[8.5_s0285] Firewalls filter based on IP, TCP, and UDP information, among other things.
[8.5_s0286] They are configured with a table of addresses that characterize the packets they will, and will not, forward.
[8.5_s0287] By addresses, we mean more than just the destination’s IP address, although that is one possibility.
[8.5_s0288] Generally, each entry in the table is a 4-tuple: It gives the IP address and TCP (or UDP) port number for both the source and destination.
[8.5_s0289] For example, a firewall might be configured to filter out (not forward) all packets that match the following description:  This pattern says to discard all packets from port 1234 on host 192.12.13.14 addressed to port 80 on host 128.7.6.5.
[8.5_s0290] (Port 80 is the well-known TCP port for HTTP.)
[8.5_s0291] Of course, it’s often not practical to name every source host whose packets you want to filter, so the patterns can include wildcards.
[8.5_s0292] For example,  says to filter out all packets addressed to port 80 on 128.7.6.5, regardless of what source host or port sent the packet.
[8.5_s0293] Notice that address patterns like these require the firewall to make forwarding/filtering decisions based on level 4 port numbers, in addition to level 3 host addresses.
[8.5_s0294] It is for this reason that network layer firewalls are sometimes called level 4 switches.
[8.5_s0295] In the preceding discussion, the firewall forwards everything except where specifically instructed to filter out certain kinds of packets.
[8.5_s0296] A firewall could also filter out everything unless explicitly instructed to forward it, or use a mix of the two strategies.
[8.5_s0297] For example, instead of blocking access to port 80 on host 128.7.6.5, the firewall might be instructed to only allow access to port 25 (the SMTP mail port) on a particular mail server, such as  but to block all other traffic.
[8.5_s0298] Experience has shown that firewalls are very frequently configured incorrectly, allowing unsafe access.
[8.5_s0299] Part of the problem is that filtering rules can overlap in complex ways, making it hard for a system administrator to correctly express the intended filtering.
[8.5_s0300] A design principle that maximizes security is to configure a firewall to discard all packets other than those that are explicitly allowed.
[8.5_s0301] Of course, this means that some valid applications might be accidentally disabled; presumably users of those applications eventually notice and ask the system administrator to make the appropriate change.
[8.5_s0302] Many client/server applications dynamically assign a port to the client.
[8.5_s0303] If a client inside a firewall initiates access to an external server, the server’s response would be addressed to the dynamically assigned port.
[8.5_s0304] This poses a problem: How can a firewall be configured to allow an arbitrary server’s response packet but disallow a similar packet for which there was no client request?
[8.5_s0305] This is not possible with a stateless firewall, which evaluates each packet in isolation.
[8.5_s0306] It requires a stateful firewall, which keeps track of the state of each connection.
[8.5_s0307] An incoming packet addressed to a dynamically assigned port would then be allowed only if it is a valid response in the current state of a connection on that port.
[8.5_s0308] Modern firewalls also understand and filter based on many specific application-level protocols such as HTTP, Telnet, or FTP.
[8.5_s0309] They use information specific to that protocol, such as URLs in the case of HTTP, to decide whether to discard a message.
[8.5_s0310] Strengths and Weaknesses of Firewalls  At best, a firewall protects a network from undesired access from the rest of the Internet; it cannot provide security to legitimate communication between the inside and the outside of the firewall.
[8.5_s0311] In contrast, the cryptography-based security mechanisms described in this chapter are capable of providing secure communication between any participants anywhere.
[8.5_s0312] This being the case, why are firewalls so common?
[8.5_s0313] One reason is that firewalls can be deployed unilaterally, using mature commercial products, while cryptography-based security requires support at both endpoints of the communication.
[8.5_s0314] A more fundamental reason for the dominance of firewalls is that they encapsulate security in a centralized place, in effect factoring security out of the rest of the network.
[8.5_s0315] A system administrator can manage the firewall to provide security, freeing the users and applications inside the firewall from security concerns—at least some kinds of security concerns.
[8.5_s0316] Unfortunately, firewalls have serious limitations.
[8.5_s0317] Since a firewall does not restrict communication between hosts that are inside the firewall, the adversary who does manage to run code internal to a site can access all local hosts.
[8.5_s0318] How might an adversary get inside the firewall?
[8.5_s0319] The adversary could be a disgruntled employee with legitimate access, or the adversary’s software could be hidden in some software installed from a CD or downloaded from the Web.
[8.5_s0320] It might be possible to bypass the firewall by using wireless communication or dial-up connections.
[8.5_s0321] Another problem is that any parties granted access through your firewall, such as business partners or externally located employees, become a security vulnerability.
[8.5_s0322] If their security is not as good as yours, then an adversary could penetrate your security by penetrating their security.
[8.5_s0323] One of the most serious problems for firewalls is their vulnerability to the exploitation of bugs in machines inside the firewall.
[8.5_s0324] Such bugs are discovered regularly, so a system administrator has to constantly monitor announcements of them.
[8.5_s0325] Administrators frequently fail to do so, since firewall security breaches routinely exploit security flaws that have been known for some time and have straightforward solutions.
[8.5_s0326] Malware (for “malicious software”) is the term for software that is designed to act on a computer in ways concealed from and unwanted by the computer’s user.
[8.5_s0327] Viruses, worms, and spyware are common types of malware.
[8.5_s0328] (Virus is sometimes used synonymously with malware, but we will use it in the narrower sense in which it refers to only a particular kind of malware.)
[8.5_s0329] Malware code need not be natively executable object code; it could as well be interpreted code such as a script or an executable macro such as those used by Microsoft Word.
[8.5_s0330] Viruses and worms are characterized by the ability to make and spread copies of themselves; the difference between them is that a worm is a complete program that replicates itself, while a virus is a bit of code that is inserted (and inserts copies of itself) into another piece of software or a file, so that it is executed as part of the execution of that piece of software or as a result of opening the file.
[8.5_s0331] Viruses and worms typically cause problems such as consuming network bandwidth as mere side effects of attempting to spread copies of themselves.
[8.5_s0332] Even worse, they can also deliberately damage a system or undermine its security in various ways.
[8.5_s0333] They could, for example, install a backdoor—software that allows remote access to the system without the normal authentication.
[8.5_s0334] This could lead to a firewall exposing a service that should be providing its own authentication procedures but has been undermined by a backdoor.
[8.5_s0335] Spyware is software that, without authorization, collects and transmits private information about a computer system or its users.
[8.5_s0336] Usually spyware is secretly embedded in an otherwise useful program and is spread by users deliberately installing copies.
[8.5_s0337] The problem for firewalls is that the transmission of the private information looks like legitimate communication.
[8.5_s0338] A natural question to ask is whether firewalls (or cryptographic security) could keep malware out of a system in the first place.
[8.5_s0339] Most malware is indeed transmitted via networks, although it may also be transmitted via portable storage devices such as CDs and memory sticks.
[8.5_s0340] Certainly this is one argument in favor of the “block everything not explicitly allowed” approach taken by many administrators in their firewall configurations.
[8.5_s0341] One approach that is used to detect malware is to search for segments of code from known malware, sometimes called a signature.
[8.5_s0342] This approach has its own challenges, as cleverly designed malware can tweak its representation in various ways.
[8.5_s0343] There is also a potential impact on network performance to perform such detailed inspection of data entering a network.
[8.5_s0344] Cryptographic security cannot eliminate the problem either, although it does provide a means to authenticate the originator of a piece of software and detect any tampering, such as when a virus inserts a copy of itself.
[8.5_s0345] Related to firewalls are systems known as intrusion detection systems (IDS) and intrusion prevention systems (IPS).
[8.5_s0346] These systems try to look for anomalous activity, such as an unusually large amount of traffic targeting a given host or port number, for example, and generate alarms for network managers or perhaps even take direct action to limit a possible attack.
[8.5_s0347] While there are commercial products in this space today, it is still a developing field.
